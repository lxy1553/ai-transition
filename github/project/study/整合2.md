## 一、run_query 核心（text2sql.py 逐段）

### ① 缓存判断（多轮跳过）

```python
async def run_query(req):
    # 缓存仅用于"无历史"请求。多轮答案依赖上下文，不能按 (db, 问题) 做键
    use_cache = not req.history   # ★ 有历史就不缓存（防串答案）
```

**大白话**：单轮可缓存（同问同答）；多轮跳过（答案依赖上下文，缓存会错）。

### ② 两级缓存短路

```python
    if use_cache:
        # 精确缓存（Redis：同问题命中）
        cached = await get_cached(req.db_id, req.question)
        if cached:
            return QueryResponse(**cached, from_cache=True)   # ★ 命中直接返回，不调 LLM

        # 语义近似缓存（pgvector：同义问题命中）
        sem = await get_semantic_cached(req.db_id, req.question)
        if sem:
            await set_cached(req.db_id, req.question, sem)   # 回填精确缓存
            return QueryResponse(**sem, from_cache=True)
```

**大白话**：先精确缓存（同问题）→ 再语义缓存（同义问题）→ 命中就返回，**跳过整条 LLM 链路**。

### ③ 调 LangGraph

```python
    graph = await get_graph()
    init_state = {
        "question": req.question, "db_id": req.db_id,
        "attempt": 0, "history": history,   # 多轮上下文
    }
    thread_id = req.thread_id or f"oneshot-{uuid.uuid4().hex}"   # 单轮用临时 id
    config = {"recursion_limit": 25, "configurable": {"thread_id": thread_id}}
    final = await graph.ainvoke(init_state, config=config)   # 走完整链路
```

### ④ 错误处理（两类失败区分）

```python
    except Exception as e:
        # 图抛异常（限流/超时/熔断/未知bug）→ 分类映射 429/503/500
        err = classify(e)   # ★ 错误分类
        raise err from e
    # 注意区分：
    #   - 图抛异常 = 系统错误（429/503/500）
    #   - 图正常返回但 success=false = SQL 多次自纠错仍失败（返回 QueryResponse）
```

**大白话**：两类失败分开——系统挂了（限流/超时）报 429/503；SQL 没生成对返回 success=false。**正是之前学的"系统错误vs 安全阻断"**。

### ⑤ 组装响应 + 写缓存

```python
    resp = QueryResponse(
        question=req.question, db_id=req.db_id,
        sql=final.get("sql", ""), success=bool(final.get("success")),
        answer=final.get("answer", ""), language=final.get("language", "zh"),
        columns=result.get("columns", []), rows=result.get("rows", []),
        row_count=result.get("row_count", 0),
        attempts=final.get("attempt", 0), error=final.get("error"),
    )

    # 只缓存成功结果 + 单轮
    if resp.success and use_cache:
        await set_cached(req.db_id, req.question, payload)          # 精确缓存
        await set_semantic_cached(req.db_id, req.question, payload) # 语义缓存
    return resp
```

**大白话**：把图的 final 状态组装成 QueryResponse（含 sql/success/answer/rows），成功结果写缓存。

# RAGFlow DeepDoc 文档解析 —— 完整总结

> **一句话定位**：DeepDoc 是 RAGFlow 的**生产级文档解析引擎**，把 PDF/扫描件变成"带版面结构的文本块 + 表格 HTML + 图片资产"，是 RAG 知识入库的第一道门。


## 一、核心思路：先"看"版面，再"理解"结构

普通 RAG 解析 PDF = 抽文本。DeepDoc 解析 PDF = **先版面、后内容**——版面模型先把页面切成 title/table/figure/header/footer 区域，再针对不同区域做精细化处理。

```
PDF 每一页
  │
  ├─ 版面分析 (layout_recognizer)     → 识别标题/正文/表格/图片/页眉页脚
  ├─ 文本检测+OCR (ocr.py)           → 扫描件/图片里的文字
  ├─ 表格结构识别 (table_structure)   → 表格的"行×列"结构 → 转 HTML
  ├─ 阅读顺序合并 (_text_merge)       → 双栏/多栏按"人类阅读顺序"拼接
  └─ 图表分离 (_extract_table_figure) → 表格/图片单独拎出来，附上说明
```

**产出**：`sections`（带位置信息的文本块）+ `tables`（结构化表格）。


## 二、关键设计：插件化识别底座

layout / table / OCR 三个识别器**复用同一个 `Recognizer` 的 ONNX 批处理底座**，统一输出 `{type, bbox, score}` 的 **bxs 结构**。
{
  "type": "元素类型，如 title / table / figure / text / header / footer",
  "bbox": [x0, y0, x1, y1],   // 边界框坐标，四个整数
  "score": 0.95               // 模型置信度，0~1 之间的浮点数
}
> 意义：换模型不用改管线，真正实现插件化热插拔。


## 三、7 步流水线

### 🔬 第一阶段：视觉感知（步骤 1-3）

| 步骤 | 方法 | 功能 |
| :--- | :--- | :--- |
| 1 | `__images__` | PDF 每一页渲染成高分辨率图片 |
| 2 | `_layouts_rec` | ONNX 模型做版面识别（DLR），切出 title/table/figure/header/footer 等 10 种区域 |
| 3 | `_table_transformer_job` | 标记为"表格"的区域单独走 TSR，还原行列 + `colspan`/`rowspan`，输出 HTML |

**关键规则**：
- `find_overlapped_with_threshold(thr=0.4)`：OCR 框与版面区域重叠 > 40% 才认归属，否则标"无版面"
- 高窄 OCR 框做 **0°/90°/270° 旋转择优**（抗扫描歪斜）
- 页眉页脚靠**位置规则二次过滤**：顶部 10% 以内才留页眉，底部 10% 以内才留页脚

### 🧩 第二阶段：内容重组（步骤 4-5）

| 步骤 | 方法 | 功能 |
| :--- | :--- | :--- |
| 4 | `_text_merge` | 同一行内、同一布局区域（`layoutno`相同）、间距达标 → 合并为文本块 |
| 5 | `_concat_downward` | XGBoost 模型判断上下相邻块是否同一段落（垂直间距 + 水平重叠度 + 标点符号） |

### ✨ 第三阶段：精炼输出（步骤 6-7）

| 步骤 | 方法 | 功能 |
| :--- | :--- | :--- |
| 6 | `_filter_forpages` | 过滤目录页、页眉页脚等重复导航信息，只留核心正文 |
| 7 | `_extract_table_figure` | 表格以 HTML 格式提取（带 `colspan`/`rowspan`），图片裁剪为独立资产，关联标题（caption），跨页表格自动合并 |


## 四、三类物料的存储

| 物料 | 存储位置 | 存储形式 |
| :--- | :--- | :--- |
| **文本块** | 检索引擎（ES / Infinity） | 原始文本 + 向量 + 全文索引 |
| **表格** | 检索引擎（ES / Infinity） | **HTML 格式**（保留 `colspan`/`rowspan`） |
| **图片** | 对象存储（MinIO / S3 / GCS） | 独立图片文件，文本块中存引用路径；OCR 文字/描述作为文本被索引 |


## 五、为什么"HTML 结构本身就是强特征"

表格不只是一串文字，而是一个**二维结构化对象**。用纯文本表示会丢失行列关系：

| 方式 | 表示 | 问题 |
| :--- | :--- | :--- |
| 纯文本 | `季度汇总 Q1 Q2 Q3 100 120 110` | 不知道"季度汇总"覆盖了哪几列 |
| HTML | `<th colspan="3">季度汇总</th>` | 明确知道跨 3 列，检索时"行头+列头"交叉定位 |

**三层含义**：
1. **行头+列头交叉定位**：问"Q3 利润"→ 查 "Q3" 列 ∩ "利润" 行
2. **colspan/rowspan 语义**：合并单元格表达"这个标题覆盖了多列/多行"
3. **结构相似度匹配**：结构相似的表格可做类比检索

离线阶段 ⑤：索引写入与文档库

> 这是离线链路的**收尾**——把「chunk + 向量 + 关键词 + 元数据」批量写入文档库（ES ）。
>**核心代码**：
```python
# rag/nlp/__init__.py:365 —— 两级 token：粗 ltks（主召回）+ 细 sm_ltks（精确匹配）
def tokenize(d, txt, eng, language="English"):
    rag_tokenizer.tokenizer.set_language(language)
    d["content_with_weight"] = txt
    # 先剥表格 HTML 标签（<table>/<td>/<caption>...），别让标签字符串进分词
    t = re.sub(r"</?(table|td|caption|tr|th)( [^<>]{0,12})?>", " ", txt)
    d["content_ltks"] = rag_tokenizer.tokenize(t)                                    # 粗粒度：主索引
    d["content_sm_ltks"] = rag_tokenizer.fine_grained_tokenize(d["content_ltks"])    # 细粒度：精确匹配
```
**代码注释**：分词前 `re.sub` 剥掉 <table>/<td>/<tr> 等 HTML 标签，防止标签字符串污染 token；
`content_ltks` 是粗粒度 token 串（主索引召回）、`content_sm_ltks` 是细粒度（精确匹配兜底）——两级让"术语完整"
与"召回兜底"兼得；索引和查询必须用同一套 tokenizer*索引/查询分词一致**（这是 BM25 能命中的前提）。
ltks 是 Lexical Tokens（词汇标记）的缩写，sm=small

## 一、一个 chunk 存什么（写入文档库的字段结构）

从 `search.py` 的 `src` 字段列表（检索时取回的字段）+ `insert_chunks` 可以还原 chunk 结构：

```python
# 写入文档库的一条 chunk（ES/Infinity 的一条 document）
{
    "id": "xxhash64(内容)",            # ★ 稳定 ID（内容哈希，幂等/去重）
    "text": "上文+正文+下文",           # chunk 最终文本（含表格/图片上下文）
    "q_1024_vec": [0.12, -0.03, ...], # ★ 向量（维度写在字段名里）
    "content_ltks": "词 词 词",         # 正文分词（粗粒度，BM25 用）
    "content_sm_ltks": "...",          # 正文分词（细粒度）
    "title_tks": "文档名分词",          # 标题分词
    "important_kwd": ["关键词1", ...],  # 重要词
    "question_tks": "...",             # 问题分词（预生成的 Q&A）
    "doc_id": "...",                   # 来源文档 ID
    "docnm_kwd": "季度报告.pdf",        # 文档名（前端显示 + 聚合）
    "kb_id": "...",                    # 知识库 ID（租户隔离过滤）
    "page_num_int": 3,                 # ★ 页码（引用定位/高亮）
    "position_int": 12,                # ★ 位置（引用定位/高亮）
    "chunk_order_int": 5,              # 块序号（还原文档顺序）
    "create_timestamp_flt": 1723456789,# 时间戳
    "mom_id": "...",                   # 父级大块 ID（父子文档结构）
}
```

**作用（关键）**：
- **向量列 + 分词列并存** → 同一份 chunk 既支持向量检索又支持 BM25 全文检索（混合检索的基础）。
- **`page_num_int` / `position_int` / `docnm_kwd`** → 支撑前端「引用定位 + 原文高亮」（README 的 Grounded citations）。
- **`q_{dim}_vec` 维度写进字段名** → 换 embedding 模型维度变了，字段名也变，新旧向量不冲突。
- **`mom_id`** → 父子文档结构（小 chunk 检索、大 chunk 喂 LLM）的落库形态。

- 
- 
- 父块 (Parent Chunk)：作为独立的文档块（Chunk）存入数据库，拥有自己的唯一 ID（如 mom_id）。它包含了完整的上下文信息，用于最终提供给 LLM 生成答案。
子块 (Child Chunk)：作为更细粒度的文档块存入数据库，每个子块会记录它所属父块的 ID，即 mom_id。这些小块专门用于向量检索，以提高召回精度。
 # CORE：子块打分（检索阶段）
操作：系统将用户的问题向量化，并在向量数据库中对所有的子块进行相似度检索。
结果：每个子块会得到一个与问题的相关性分数（如余弦相似度）。
目的：这一步的目标是“精确命中”。通过小粒度切分，确保能精准定位到文档中最匹配用户问题的那段具体文字。
2. Top-M：筛选出最相关的子块
操作：根据第一步的分数，对所有子块进行排序，并选出分数最高的 M 个子块（比如 Top-3 或 Top-5）。
目的：这一步是“降噪”。只保留最相关的少量子块，剔除大量无关信息，为下一步的上下文扩展做准备。
3. 映射回父块（关键环节）
操作：每一个子块在入库时，都会保存一个指向其父块（大块）的ID或引用。这一步就是根据Top-M子块的这个引用，去数据库中完整地取出它们各自所属的大块。
目的：这是“恢复上下文”的关键一步。它实现了“检索时看细节，理解时看全局”的转变。
父子两层分块：子块（256 token）做精确检索，父块（1024 token）喂 LLM 完整上下文，解决"块小检索准但上下文碎"与"块大上下文全但检索噪声大"的矛盾。

🔧 核心机制
机制	说明
边界感知分块	块绝不跨 ##/### 章节边界，语义完整不切断
子块滑窗切分	父块内部按 child_size - overlap 步进滑动，生成子块
双代 Schema	子块带 parent_id（映射回父块），父块带 child_ids（展开子块）

## §8 编排 —— 最强：queryforge（LangGraph + 自纠错环 + HIL）

**能力**：12 节点 + 条件路由的 LangGraph 图：`detect_language → rewrite → expand → retrieve → schema_linking → generate_sql → validate_sql → execute_sql → format_answer`，含 **自纠错环**（validate/execute 失败绕回 generate_sql 重生成，最多 `SQL_MAX_RETRY` 次）和 **HIL 人审断点**（human_review_sql + checkpointer 断点续跑）。

**解释**：编排层写的是**控制流**——哪些节点跑、失败怎么回退。选 LangGraph 是因为这里有两处**非线性流**：自纠错环（回边）和 HIL 中断（interrupt/断点续跑），手写状态机难维护。`_route_*` 函数是链路的大脑，`GraphState(total=False)` 让节点只返回增量字段，改链路只动 graph.py。

**代码位置**：`queryforge-test2sql/app/core/langgraph/graph.py:25-47`（路由）、`:56-99`（建图）；`state.py:13-43`（状态）

**代码注释**：`_route_after_validate` 和 `_route_after_execute` 是自纠错的两处触发器——失败且
`attempt < SQL_MAX_RETRY` 回 `self_correct` → `generate_sql` 携带上次 error 重生成；`GraphState` 
是节点间的**数据契约**，改链路只动 `graph.py` 的 `_route_*` 与 `add_*edge`。

**面试怎么说**：> "当链路出现自纠错回边和人工审批断点这类非线性流时，我上 LangGraph：节点只返回状态增量、条件路由函数决定分支回退，
改链路只动图定义不动节点。设计上我用 total=False 的 TypedDict 做状态协议，让每个节点独立可测——编排和业务彻底解耦。"
**大白话**：路由函数 = 判断"下一步去哪"，像 Vanna 的 `is_tool_call()`。自纠错 = 失败回 generate 带错误重来。
**大白话**：checkpointer = 存图执行到哪了，断了能恢复（人机确认时暂停等审批）。
**这是 Vanna 手写版没有的**——正是之前学的"框架补上手写版缺的能力"。

## 一、条件路由函数（graph.py:25-47）

```python
# ============================================================
# 条件路由 = 链路的分支/回退决策
# 每个函数看 state 里的状态，决定"下一步去哪"
# ============================================================

def _route_after_retrieve(state: GraphState) -> str:
    """
    retrieve（检索）节点之后的路由
    判断依据：有没有检索到 schema（数据库表结构文档）
    """
    # 如果 state 里有 schema_docs → 走 schema_linking 节点
    # 否则 → 走 error_node（报错结束）
    return "schema_linking" if state.get("schema_docs") else "error_node"


def _route_after_validate(state: GraphState) -> str:
    """
    validate_sql（验证SQL）节点之后的路由
    判断依据：SQL有没有语法/逻辑错误 + 重试次数有没有超限
    """
    # 如果没有错误 → 去执行 SQL
    if not state.get("error"):
        return "execute_sql"
    
    # 如果有错误：
    #   - 重试次数 < 最大限制 → 走 self_correct 自纠错环，回去重生成
    #   - 重试次数 >= 最大限制 → 直接 format_answer 返回失败信息
    return "self_correct" if state.get("attempt", 0) < settings.SQL_MAX_RETRY else "format_answer"


def _route_after_execute(state: GraphState) -> str:
    """
    execute_sql（执行SQL）节点之后的路由
    判断依据：SQL执行结果是否成功 + 重试次数有没有超限
    """
    result = state.get("sql_result", {})
    
    # 如果执行成功（ok=True）→ 去 format_answer 生成最终答案
    if result.get("ok"):
        return "format_answer"
    
    # 如果执行失败：
    #   - 重试次数 < 最大限制 → 走 self_correct 自纠错环
    #   - 重试次数 >= 最大限制 → 直接 format_answer 返回失败信息
    return "self_correct" if state.get("attempt", 0) < settings.SQL_MAX_RETRY else "format_answer"
```


## 二、图构建（graph.py:56-99）

```python
# ============================================================
# 建图：节点注册 + 固定边 + 条件边
# ============================================================

def build_graph(checkpointer=None, enable_hil=None):
    """
    构建整个 LangGraph 执行图
    checkpointer: 断点续跑器（用于 HIL 人工审批中断恢复）
    enable_hil:   是否启用人工审批（Human-in-the-Loop）
    """
    
    # ① 创建图，传入共享状态 GraphState
    #    GraphState 是所有节点之间传递的数据结构
    g = StateGraph(GraphState)
    
    # ② 注册所有节点
    #    add_node("节点名", 对应的处理函数)
    #    每个节点函数签名：def func(state: GraphState) -> dict
    #    返回的 dict 会合并到 state 中（增量更新）
    
    g.add_node("detect_language", nodes.detect_language)   # 检测查询语言（中文/英文）
    g.add_node("rewrite", nodes.rewrite)                   # 查询改写（术语对齐）
    g.add_node("expand", nodes.expand)                     # 多查询扩展
    g.add_node("retrieve", nodes.retrieve)                 # 混合检索（BM25 + 向量）
    g.add_node("schema_linking", nodes.schema_linking)     # 找相关表结构
    g.add_node("generate_sql", nodes.generate_sql)         # 生成 SQL
    g.add_node("human_review_sql", nodes.human_review_sql) # 人工审批断点（HIL）
    g.add_node("validate_sql", nodes.validate_sql)         # 验证 SQL（语法/逻辑）
    g.add_node("execute_sql", nodes.execute_sql)           # 执行 SQL
    g.add_node("self_correct", nodes.self_correct)         # 自纠错（带错误信息回传）
    g.add_node("format_answer", nodes.format_answer)       # 格式化最终答案
    g.add_node("error_node", nodes.error_node)             # 错误出口
    
    # ③ 固定边（顺序执行，无分支）
    #    add_edge(from, to)：从 A 走到 B，无条件的确定性流转
    
    g.add_edge(START, "detect_language")    # 起点 → 检测语言
    g.add_edge("detect_language", "rewrite")  # 检测 → 改写
    g.add_edge("rewrite", "expand")           # 改写 → 扩展
    g.add_edge("expand", "retrieve")          # 扩展 → 检索
    
    # ④ 条件边（分支决策）
    #    add_conditional_edges(from, route_func, mapping)
    #    route_func 返回的字符串决定跳到哪个节点
    
    # retrieve 之后：
    #   - 有 schema_docs → schema_linking
    #   - 无 schema_docs → error_node
    g.add_conditional_edges(
        "retrieve", 
        _route_after_retrieve,
        {
            "schema_linking": "schema_linking",  # route_func 返回 "schema_linking" 时走这里
            "error_node": "error_node",          # route_func 返回 "error_node" 时走这里
        }
    )
    
    # validate_sql 之后：
    #   - 无错误 → execute_sql
    #   - 有错误且可重试 → self_correct（进自纠错环）
    #   - 有错误且不可重试 → format_answer
    g.add_conditional_edges(
        "validate_sql", 
        _route_after_validate,
        {
            "execute_sql": "execute_sql",
            "self_correct": "self_correct",
            "format_answer": "format_answer",
        }
    )
    
    # ⑤ 自纠错环的回边
    #    self_correct 节点完成后，回到 generate_sql 重新生成
    #    注意：这次 generate_sql 会收到上一次的错误信息（通过 state 传递）
    g.add_edge("self_correct", "generate_sql")
    
    # ⑥ 终点边
    g.add_edge("format_answer", END)   # 正常结束
    g.add_edge("error_node", END)      # 异常结束
    
    # ⑦ 编译成可执行图
    #    传入 checkpointer：如果挂载了，就支持 HIL 中断/断点续跑
    return g.compile(checkpointer=checkpointer)
```

## §9 Agent 能力 核心总结

### 🎯 一句话定位

> **while 循环 + Tool 抽象 + Registry 分派 + 钩子**：把 Agent 收敛成一个带迭代上限的单分支循环，
> LLM 返回 `tool_calls` 就执行工具回喂，返回 `stop` 就输出答案。**工具抽象五件套 + 六步安全分派 + 三种扩展钩子**
> ——通用引擎不动、业务规则可插拔。


### 🔧 核心机制拆解

#### 1. 核心循环（唯一的 Agent 大脑）

**关键点**：
- `is_tool_call()` 是循环**唯一分支**（按 `finish_reason` 判断）
- `max_tool_iterations` 防止死循环（安全网）
- `assistant` 消息必须带 `tool_calls`、工具结果必须 `role="tool"`——这是 OpenAI API 硬性要求

#### 2. Tool 抽象五件套（最小可注册单元）

| 组件 | 作用 | LLM 能看到？ |
| :--- | :--- | :--- |
| `name` | 工具名称 | ✅ LLM 靠它调用 |
| `description` | 工具描述 | ✅ LLM 靠它判断"什么时候用" |
| `access_groups` | 权限组 | ❌ 系统内部鉴权用 |
| `args_schema` | Pydantic 参数模型 | ✅ 转成 JSON Schema 给 LLM |
| `execute` | 真正干活的函数 | ❌ |

```python
class Tool(ABC, Generic[T]):
    @property @abstractmethod def name(self) -> str: ...
    @property @abstractmethod def description(self) -> str: ...
    @property def access_groups(self) -> List[str]: return []
    @abstractmethod def get_args_schema(self) -> Type[T]: ...
    @abstractmethod async def execute(self, context, args) -> ToolResult: ...
    
    def get_schema(self) -> ToolSchema:
        # Pydantic → 给 LLM 看的 JSON Schema
        return ToolSchema(
            name=self.name,
            description=self.description,
            parameters=self.get_args_schema().model_json_schema()
        )
```


**意义**：权限、校验、审计在 Registry 层统一处理，工具本身只关心业务逻辑。

## §10 评估体系 核心总结

### 🎯 一句话定位

> **三层漏斗 + 六类坏例决策树 + 收敛判据**：把"改进"从拍脑袋变成数学——检索与生成**不可互减**地分开打分、坏例分六类定位根因、收敛判据告诉你"什么时候该停"。


### 🔧 核心机制拆解

#### 1. 三层评估漏斗

```
┌─────────────────────────────────────────────────────────────┐
│                    三层评估漏斗                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  Level 1: 离线管线层（parse + chunk）                       │
│    检查：文档解析有没有报错？文本块切分有没有异常？        │
│    ↓                                                       │
│  Level 2: 检索层（Q-DOC）                                  │
│    检查：GT 文档被召回了吗？（recall@K）                   │
│    指标：文档级 recall，不管精确排名（那是 reranker 的事）  │
│    ↓                                                       │
│  Level 3: 生成层（Q-DOC-A）                                │
│    检查：答案对不对？（6 维 LLM Judge + 人工对齐）        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**关键设计**：检索和生成**不可互减**地分开打分。
- 检索 recall 低 → 生成再好也没用（上下文里没答案）
- 生成质量差 → 检索 recall 再高也没用（LLM 没用好上下文）

#### 2. 检索层指标：为什么是文档级 recall 而非 chunk 级 MRR？

```python
def compute_chunk_recall_at_k(retrieved_ids, gt_ids, k):
    """
    为什么用文档级 recall（而不是 chunk-level MRR）：
    检索阶段只看 GT 文档能不能"活到 reranker"。
    精确排名是 reranker 的活，不是检索的活。
    """
    top_k = retrieved_ids[:k]
    hit = len(set(top_k) & set(gt_ids))
    return hit / len(gt_ids) if gt_ids else 0.0
```

| 指标 | 含义 | 谁的责任 |
| :--- | :--- | :--- |
| 文档级 recall@K | GT 文档是否在 Top-K 中被召回 | 检索器（BM25 + 向量） |
| 精确排名（MRR） | GT 文档排第几 | Reranker |

**分层清晰**：检索只负责"捞回来"，精排负责"排准"。

#### 3. 生成层指标：6 维 LLM Judge

用 LLM 当裁判，对生成答案打 6 个维度的分（每个维度 1-5 分），再映射成 3 级（好/中/差），最后用 **Cohen's Kappa** 校准与人工打分的一致性。

| 维度 | 检查什么 |
| :--- | :--- |
| 正确性 | 答案事实对不对？ |
| 完整性 | 有没有漏掉关键信息？ |
| 引用性 | 有没有引用来源？引用对不对？ |
| 一致性 | 答案内部有没有矛盾？ |
| 简洁性 | 有没有废话？ |
| 安全性 | 有没有有害内容？ |

#### 4. 六类坏例决策树

```

```

**核心原则**：**工程问题永远排在第一位**——解析失败产生的错误答案看起来像质量问题，但修 prompt 是修不好的，必须先修解析器。

#### 5. 收敛判据：什么时候停？

```python
def check_loop1_convergence(history, config):
    """
    连续 2 轮 Recall@5 增益 < loop1_convergence_pp 就停
    """
    threshold = config["eval"]["loop1_convergence_pp"] / 100.0  # 默认 5pp = 0.05
    window = 2
    
    if len(history) < window + 1:
        return False
    
    recent = history[-(window + 1):]
    gains = [recent[i]["recall_at_5"] - recent[i-1]["recall_at_5"] 
             for i in range(1, len(recent))]
    
    return all(g < threshold for g in gains)
```

**不同 Loop 不同收敛阈值**：

| 阶段 | 优化手段 | 收敛判据 | 说明 |
| :--- | :--- | :--- | :--- |
| Loop 1 | 微调 embedding / 改词典 | 连续 2 轮增益 < 5pp | 微调收益递减快 |
| Loop 2 | 改 prompt / 加 few-shot | 连续 2 轮增益 < 0.5pp | prompt 优化收益更细 |
| Loop 3 | 改融合策略 / 调权重 | 看曲线拐点 | 不设硬阈值 |

**核心思想**：优化不是"做越多越好"，而是**知道什么时候该停、转方向**。

> ## TOKENIZER_ISSUE 是什么？

**一句话**：`TOKENIZER_ISSUE` 是坏例决策树中的一类根因，表示**"检索失败是因为分词没切对"**——用户写的词和文档里的词，在 token 层面没对上。


### 🎯 为什么会出 TOKENIZER_ISSUE？

BM25 关键词检索依赖 **token 精确匹配**。如果用户查询和文档的 token 对不上，就搜不到。

```
用户查询： "SSO 怎么配置"
     ↓ 分词器切
token: ["SSO", "怎么", "配置"]

文档原文： "单点登录（SSO）配置指南"
     ↓ 分词器切
token: ["单点登录", "SSO", "配置", "指南"]

BM25 匹配：["SSO"] ✅ + ["配置"] ✅
→ 能命中，没问题
```

但如果分词器不认识"单点登录"，把它切碎了：

```
文档原文： "单点登录（SSO）配置指南"
     ↓ 坏分词器切
token: ["单点", "登录", "SSO", "配置", "指南"]
         ↑     ↑
       "单点"和"登录"分开了

用户搜 "单点登录"
     ↓ 切
token: ["单点", "登录"]

BM25 匹配：文档里有 "单点" 和 "登录" → 能匹配上，但 "单点登录" 作为一个完整术语的语义丢了
```

**更严重的**：用户搜缩写变体

```
用户查询： "Single Sign-On 怎么配"
     ↓ 切
token: ["Single", "Sign-On", "怎么", "配"]

文档原文： "SSO 配置"
     ↓ 切
token: ["SSO", "配置"]

BM25 匹配：一个 token 都对不上 ❌
→ 明明说的是同一件事，但召回率为 0
```


### 🔍 决策树中如何判断 TOKENIZER_ISSUE？

```python
# bad_case_analyzer.py:183
# Stage 1: retrieval recall
if record["recall_at_k"] < LOW_RECALL_THRESHOLD:
    # 如果 BM25 召回率低 → 分词没切对
    if record.get("bm25_recall", 1.0) < LOW_RECALL_THRESHOLD:
        return TOKENIZER_ISSUE   # ← 这里
    # 如果向量召回率低 → embedding 不行
    if record.get("dense_recall", 1.0) < LOW_RECALL_THRESHOLD:
        return TOKENIZER_ISSUE
    return FUSION_ISSUE
```

**判断逻辑**：

| 情况 | 分类 | 根因 |
| :--- | :--- | :--- |
| BM25 recall 低 | `TOKENIZER_ISSUE` | 分词词典缺词/切错 |
| 向量 recall 低 | `TOKENIZER_ISSUE` | Embedding 模型对领域词理解弱 |
| 两者都低 | `FUSION_ISSUE` | 融合策略有问题 |


### 🛠️ 怎么修 TOKENIZER_ISSUE？

| 子类型 | 修复动作 |
| :--- | :--- |
| **BM25 分词缺词** | 把领域词加入 jieba 自定义词典（`领域词典 §4`） |
| **BM25 切错词** | 调整词典词频/词性，确保长词优先（如"单点登录">"单点"） |
| **向量 embedding 弱** | 领域语料微调 embedding 模型（Loop 1） |
| **术语变体匹配不上** | 查询改写补全缩写/全称（`缩写补全 §7`） |


### 💡 面试总结

> "TOKENIZER_ISSUE 是坏例分类的一种，指的是**检索失败的本质原因是分词没切对**——要么 BM25 词典里缺了领域词导致 token 对不上，要么 embedding 模型对领域术语理解不够。
>
> 判断方式是看召回率：**BM25 召回低 → 改分词词典；向量召回低 → 微调 embedding；都低 → 看融合策略。**
>
> 修分词词典是最快的——把领域词加进 jieba 自定义词典，新词立竿见影。"
> ## 分词词典 vs 领域词典：两本不同的"词典"

**一句话区分**：
- **分词词典**：告诉系统"**怎么切**"（"单点登录"是一个词，不能切成"单点"+"登录"）
- **领域词典**：告诉系统"**什么意思**"（"SSO" = "单点登录"，"登不上" = "单点登录"）


## 📖 详细拆解

### 1. 分词词典（Tokenizer Dictionary）

**定义**：决定**文本切分边界**的规则集合。它告诉分词器"哪些字符组合应该被当做一个完整的词"。

| 属性 | 说明 |
| :--- | :--- |
| **作用** | 切词（把句子切成 token） |
| **消费者** | jieba / rag_tokenizer（分词器） |
| **输入** | 文档内容 + 用户查询 |
| **产出** | token 列表（`content_ltks`） |
| **核心问题** | "单点登录" 被切成 ["单点登录"] 还是 ["单点", "登录"]？ |

**例子**：

```python
# 没有分词词典
"单点登录配置指南" → ["单点", "登录", "配置", "指南"]

# 有分词词典（词条："单点登录"）
"单点登录配置指南" → ["单点登录", "配置", "指南"]
                      ↑ 被识别为一个完整术语
```

**存储位置**：`rag/res/huqie.txt`（格式：`词 频率 词性`）

**怎么维护**：
- TF-IDF 从领域文档自动抽候选词（`max_df/min_df` 过滤）
- 人工审核后加入词典
- 或从领域词典的 `standard_term` 字段同步


### 2. 领域词典（Domain Dictionary）

**定义**：**同义/变体映射表**。它告诉系统"用户的说法对应文档里的哪个标准术语"。

| 属性 | 说明 |
| :--- | :--- |
| **作用** | 映射（口语/缩写 → 标准术语） |
| **消费者** | 查询改写器 + 路由过滤器 + 分词器（供词） |
| **输入** | 用户查询 |
| **产出** | 改写后的查询（术语对齐后的文本） |
| **核心问题** | 用户说"SSO登不上" → 映射到文档里的"单点登录配置"？ |

**例子**：

```json
{
  "standard_term": "单点登录",
  "abbreviation": "SSO",
  "full_form": "Single Sign-On",
  "colloquial": ["登不上", "进不去", "咋登录"],
  "tag": "auth"
}
```

当用户搜 `"SSO 登不上"`：
1. 查领域词典 → `SSO` → `单点登录`，`登不上` → `单点登录`
2. 查询改写器把查询改成 `"单点登录 配置"`（对齐文档用词）
3. 分词器（已经加载了"单点登录"）切出 `["单点登录", "配置"]`
4. BM25 命中文档 ✅


## 📊 对比总结

| 维度 | 分词词典 | 领域词典 |
| :--- | :--- | :--- |
| **核心问题** | 怎么切？ | 什么意思？ |
| **输入** | 任意中文文本 | 用户查询 |
| **产出** | token 列表 | 改写后的查询 |
| **数据结构** | 词列表（词+频率+词性） | 五字段 Schema（std/abbr/full/colloq/tag） |
| **消费者** | jieba / rag_tokenizer | 查询改写器 + 路由 + jieba |
| **存储位置** | `huqie.txt` | 数据库/配置文件 |
| **更新频率** | 低频（稳定后少动） | 中频（随业务词典迭代） |
| **错了会怎样** | 术语被切碎，BM25 漏召回 | 用户说法映射不到，改写出错 |


## 🔗 两者关系：领域词典 → 分词词典

**领域词典是上游，分词词典是下游**。

```
领域词典（五字段）
    │
    │ 抽取 standard_term
    ▼
分词词典（词列表）
    │
    │ 加载到 jieba
    ▼
分词器切出完整术语
    │
    ▼
BM25 索引中有完整的 token
    │
    ▼
查询改写后对齐到同一个 token → 命中 ✅
```


## 💡 面试金句

> "**分词词典**解决的是'**怎么切**'——让 jieba 把'单点登录'切成一个词而不是两个。**领域词典**解决的是'**什么意思**'——把用户的'SSO'/'登不上'映射到文档里的'单点登录'。
>
> 两者配合：领域词典的五字段 `standard_term` 喂给分词词典，分词器切出完整术语；查询时领域词典把用户口语改写成标准术语，两边的 token 对上，BM25 才能命中。
>
> 领域词典是'**术语对齐**'的源头，分词词典是'**切词执行**'的保障——缺一不可。"
>

> ## §11 增量知识管理 —— 最强：RAG-BUILD-SKILLS（三类分诊 + 双层元数据）

**能力**：上线后文档持续变更的管理方法论——**文档级三类分诊**（替换 / 并行 / legacy）+ **双层元数据**（文档级关系库 + chunk 级标量字段）+ **append-only 词典**。

**解释**：RAG 上线后最大的杀手不是检索，是**文档版本混乱**——旧版失效内容还在被召回。三类分诊是一次摄入一个决策：同型号升级→**替换**（删旧写新）、不同型号→**并行**（只写新不动旧）、同型号但旧版有参考价值→**legacy**（标记退役、默认过滤、要历史才放宽 + prompt 加版本警告）。双层元数据让"文档版本链"和"chunk 检索过滤"各归其位。

**核心决策逻辑（伪代码，纯方法论无现成代码）**：
```
对每份新文档 D（型号 m，版本 v）：
  if 已有 m 且 v 更新     → 替换：删旧版 chunk，写新版，标记 supersedes
  if m 是新型号          → 并行：只写新，旧不动
  if 同型号但旧版有参考价值 → legacy：旧块 status=legacy，检索默认过滤，
                                放宽过滤才召回 + prompt 加 ⚠️ 旧版警告
删文档 D 时：删除 D 的 chunks，但不删词典词条（query 可能还在用）
```

**面试怎么说**：> "RAG 上线后的长期胜负手是增量知识管理。我的原则是文档级三类分诊：升级就替换、新型号就并行、旧版有价值就标 legacy 默认过滤。元数据分两层——文档版本链放关系库，chunk 过滤标签放向量库标量字段。关键词词典 append-only，删文档不删词条，因为用户查询可能还在用。"
