# 〇、五层防御模型总览（先看全貌）

## 完整模型

```
① 认证层（Authentication）—— 你是谁？
   UserResolver 解析身份（JWT/Cookie）→ User(id, group_memberships)
   │
② 授权层（Authorization）—— 你能做什么？（三层粒度）
   ├─ 功能权限：能不能调 run_sql？    → user_groups & tool_groups
   ├─ 数据权限：能查哪些表/行/列？     → transform_args 注入过滤 ★
   └─ 指标权限：能看哪些指标？         → 指标平台层面控制
   │
③ 参数脱敏层（Sanitization）
   sanitize_tool_parameters=True → 日志里参数打码（config.py:108）
   │
④ 数据库层（最后兜底）
   PostgreSQL RLS：CREATE POLICY ... USING (tenant_id=...)
   即使应用层被绕过，数据库也强制过滤
   │
⑤ 审计层（可追溯）
   log_tool_access_check / log_tool_invocation → 谁、何时、操作了什么
```

## 为什么五层缺一不可？（最重要的认知）

**五层不是"权限的 5 种做法"，而是"5 道都要拉满的防线"——每一层都有盲区，只有叠加才能覆盖。**

| 层 | 单独存在时，怎么被绕过 |
|----|----------------------|
| ① 认证层 | 认证通过 ≠ 能查数据。JWT 没问题，但 SQL 还能查任何表 |
| ② 授权层 | 应用层代码有 bug / 被绕过 → 数据直接暴露 |
| ③ 脱敏层 | 只脱日志，不影响实际返回的数据 |
| ④ 数据库层 | 单靠它，LLM 生成的非法 SQL 语法错它就崩 |
| ⑤ 审计层 | 只记录，不阻止 |

**互为兜底**：
- transform_args 拦不住"应用层被绕过"（比如直接连数据库）→ 靠 ④ 数据库 RLS
- 数据库 RLS 拦不住"LLM 生成非法 SQL" → 靠 ② 授权层校验
- ④ 拦不住"日志泄露密码" → 靠 ③ 脱敏

> **一句话**：五层是"层层设防"，不是"五选一"。真正的安全 = 每层都拉满，单层必被绕过。

# 第 1 层：认证层（Authentication）—— 你是谁？

## 三问

**Q1 它解决什么问题？**
Agent 必须知道"**谁在问**"——没有用户身份，后面所有权限判断、审计、个性化都无从谈起。

**Q2 它在数据流哪一环？**
**最前端**（agent.py:257）。`send_message` 进来第一件事就是解析用户，之后的 system_prompt 构建、工具权限、审计全都基于这个 User。

**Q3 如果删掉它会怎样？**
Agent 不知道谁在问 → 无法做权限（人人可查敏感数据）、无法审计（出事找不到人）、无法个性化。

## 一、接口：UserResolver（`core/user/resolver.py`）

```python
class UserResolver(ABC):
    """用户解析器接口：从请求里解析出 User"""

    @abstractmethod
    async def resolve_user(self, request_context: RequestContext) -> User:
        """把请求（cookies/headers/token）变成 User 对象"""
        pass
```

**接口极小**——就一个方法。因为"怎么解析"完全取决于你的认证系统（JWT? Cookie? OAuth?），Vanna 不替你决定，只定义"入口"。

## 二、相关模型：User 和 RequestContext

### User（`core/user/models.py`）—— 权限的核心

```python
class User(BaseModel):
    id: str                          # 唯一标识
    username: Optional[str] = None   # 用户名
    email: Optional[str] = None      # 邮箱
    metadata: Dict = {}              # 附加信息
    group_memberships: List[str] = []  # ★ 权限组，如 ["analyst", "risk"]
```

### RequestContext（`core/user/request_context.py`）—— 请求的封装

```python
class RequestContext(BaseModel):
    cookies: Dict[str, str] = {}      # Cookie
    headers: Dict[str, str] = {}      # 请求头（含 Authorization）
    remote_addr: Optional[str] = None # IP
    query_params: Dict = {}           # URL 参数
    metadata: Dict = {}               # 附加信息（可放 user_id）

    def get_cookie(self, name, default=None):
        return self.cookies.get(name, default)

    def get_header(self, name, default=None):
        """大小写不敏感的 header 查找"""
        name_lower = name.lower()
        for key, value in self.headers.items():
            if key.lower() == name_lower:
                return value
        return default
```

## 三、group_memberships 权限组如何设计

### 设计：用"组"（group）不是"角色"（role）

Vanna 用 `User.group_memberships`（一个用户属于多个组）+ `Tool.access_groups`（工具声明自己属于哪些组）。

**判断规则**：`用户组 ∩ 工具组 ≠ 空` → 放行（`core/registry.py:98`）：

```python
async def _validate_tool_permissions(self, tool, user) -> bool:
    """校验用户能否用这个工具"""
    tool_access_groups = tool.access_groups
    if not tool_access_groups:
        return True   # 工具没声明组 = 所有人可用

    user_groups = set(user.group_memberships)   # 用户的组集合
    tool_groups = set(tool_access_groups)       # 工具需要的组集合
    return bool(user_groups & tool_groups)      # ★ 交集非空 = 有权限
```

### 为什么用"组"不用"角色"？

| | 组（group）| 角色（role）|
|---|---|---|
| 本质 | 标签集合，一个用户可属于多个 | 单一身份，一个用户一个角色 |
| 灵活性 | 一个工具可对多个组开放 | 想多开放要加中间层 |
| 例子 | "查额度"工具对 `[analyst, risk]` 开放 | "查额度"工具只对 `role=analyst` 开放，risk 想用就得再造角色 |

**关键洞察**：用组，权限判断就是"**集合求交集**"——一行 `user_groups & tool_groups` 搞定，而且天然支持"一个工具给多个群体用"。

### 落地示例（信贷场景）

```python
# 用户（来自数据库/认证系统）
User(
    id="u_1001",
    username="张三",
    group_memberships=["analyst", "risk"],   # 分析师 + 风控
```

## 四、resolve_user 落地实现（你自己的代码）

> Vanna 的 example 引用了 `CookieEmailUserResolver` / `SimpleUserResolver`，但**这个仓库没实现**。下面给你三种真实的落地写法。

### 写法 A：生产级 —— 从 JWT 解析

```python
class MyUserResolver(UserResolver):
    """从 Authorization header 的 JWT 解析用户"""

    def __init__(self, jwt_secret: str, user_db):
        self.jwt_secret = jwt_secret
        self.user_db = user_db      # 你的用户数据库

    async def resolve_user(self, request_context: RequestContext) -> User:
        # ① 从 header 拿 token
        token = request_context.get_header("Authorization")
        if not token or not token.startswith("Bearer "):
            raise AuthenticationError("缺少认证信息")

        # ② 解 JWT，拿用户 id 和组
        payload = jwt.decode(token[7:], self.jwt_secret, algorithms=["HS256"])
        user_id = payload["sub"]
        groups = payload.get("groups", [])

        # ③ 查库拿完整用户信息（或直接拼）
        return User(
            id=user_id,
            username=self.user_db.get_username(user_id),
            group_memberships=groups,   # ★ 权限组来自 JWT 或 DB
        )
```

### 写法 B：开发版 —— 从 Cookie 解析邮箱

```python
class CookieEmailUserResolver(UserResolver):
    """从 Cookie 里的邮箱解析用户（开发/演示用）"""

    async def resolve_user(self, request_context: RequestContext) -> User:
        email = request_context.get_cookie("vanna_email")
        if not email:
            raise AuthenticationError("Cookie 中缺少邮箱")

        # 按邮箱查用户（你的逻辑）
        user_row = await user_db.get_by_email(email)
        return User(
            id=user_row["id"],
            email=email,
            group_memberships=user_row["groups"],   # 从 DB 拿权限组
        )
```

### 写法 C：最简单（我们阶段 1 用的）

```python
class StaticUserResolver(UserResolver):
    """固定返回一个测试用户（本地开发/测试）"""
    def __init__(self, user: User):
        self._user = user

    async def resolve_user(self, request_context: RequestContext) -> User:
        return self._user
```

## 2.2 数据权限（能查哪些表/行/列）★ 核心 —— transform_args 逐步拆解

> 你问"还是没懂 transform_args 如何实现表级权限"——这一节彻底讲透。

### 2.2.1 它在 execute 流水线哪一步被调用？（registry.py:200）

```python
# registry.py:144 execute() 完整流程
async def execute(self, tool_call, context):
    # ① 找工具
    tool = await self.get_tool(tool_call.name)

    # ② 工具级权限（2.1 功能权限）
    if not await self._validate_tool_permissions(tool, context.user):
        return ToolResult(success=False, error="Insufficient group access...")

    # ③ 参数解析（LLM 填的原始 dict → Pydantic 对象）
    validated_args = args_model.model_validate(tool_call.arguments)

    # ④ ★★★ transform_args —— 就在这里！★★★
    transform_result = await self.transform_args(
        tool=tool,
        args=validated_args,        # ← 已解析好的参数对象
        user=context.user,          # ← 谁在调用
        context=context,            # ← 完整上下文
    )

    # ⑤ 如果返回 ToolRejection → 拒绝，不执行
    if isinstance(transform_result, ToolRejection):
        return ToolResult(success=False, error=transform_result.reason)

    # ⑥ 用改写后的参数执行
    final_args = transform_result      # ← 可能是被改写过的 args！
    result = await tool.execute(context, final_args)   # 真正执行
```

**关键**：`transform_args` 在"参数解析之后、工具执行之前"，它拿到的是 `validated_args`（Pydantic 对象），可以**修改它再返回**。

### 2.2.2 表级权限怎么"改"SQL？

**关键前提：参数是 Pydantic 对象，不是字符串**

```python
# capabilities/sql_runner/models.py
class RunSqlToolArgs(BaseModel):
    sql: str = Field(description="SQL query to execute")
```

LLM 返回 `{"sql": "SELECT * FROM secret_table"}` → 变 `RunSqlToolArgs(sql="...")` 对象。
**所以 transform_args 可以改 `args.sql` 属性！**

**完整落地实现（表级权限）**

```python
class RlsToolRegistry(ToolRegistry):
    """带表级权限的工具注册表"""

    async def transform_args(self, tool, args, user, context):
        if tool.name != "run_sql":
            return args   # 其他工具不动

        # ① 拿这个用户能访问的表（从权限表查）
        allowed_tables = get_user_tables(user.id)   # {"ods_application", "dwd_repayment"}

        # ② 解析 SQL 引用了哪些表
        referenced = extract_tables(args.sql)        # {"secret_table"}

        # ③ 表级校验
        for table in referenced:
            if table not in allowed_tables:
                return ToolRejection(reason=f"无权限访问表 {table}")   # ★ 拒绝！

        # ④ 行级：自动注入租户过滤
        if "tenant_id" not in args.sql:
            args.sql = inject_where(args.sql, f"tenant_id = '{user.metadata['tenant_id']}'")

        # ⑤ 返回改写后的参数
        return args
```

### 2.2.3 执行时的完整数据流（张三的例子）

```
张三（无 secret_table 权限）问："查一下订单"
  → LLM 返回 {name:"run_sql", arguments:{"sql":"SELECT * FROM secret_table"}}
  → execute():
     ① 找到 run_sql ✅
     ② 工具级：张三 groups ∩ tool.access_groups → 放行 ✅
     ③ 参数解析 → RunSqlToolArgs(sql="SELECT * FROM secret_table")
     ④ transform_args：
        allowed_tables={"ods_application","dwd_repayment"}
        referenced={"secret_table"} → 不在允许列表 → ToolRejection("无权限访问表 secret_table")
     ⑤ 返回 ToolResult(success=False, error="无权限...")
  → LLM 收到错误 → 知道换个表查
```

### 2.2.4 有权限的表怎么处理？—— 行级注入

```
张三有 ods_application 权限，问"查我的订单"
  → referenced={"ods_application"} 在允许列表 ✅ 表级通过
  → 行级注入：args.sql 从 "SELECT * FROM ods_application"
            变成 "SELECT * FROM ods_application WHERE tenant_id = 't_001'"
  → 张三永远只能查到 tenant_id='t_001' 的数据
```

### 2.2.5 为什么能改参数？（面向对象的关键）

`args` 是 **Pydantic 对象**（可变）：
- `args.sql` 可读 → 检查表权限
- `args.sql` 可写 → 注入 WHERE、改 SQL
- 返回 `ToolRejection` → 拒绝执行

如果 `args` 是字符串，就没法"改一部分返回"。

### 2.2.6 三层权限的真正分工

| 层 | 代码位置 | 管什么 | 例子 |
|----|---------|--------|------|
| 工具级 | `_validate_tool_permissions`（registry.py:161）| 能不能调工具 | 张三能用 run_sql 吗 |
| 表级/行级 | `transform_args`（registry.py:200）★| 能查哪些表/行 | 张三能查 ods，不能查 secret；只看自己租户 |
| 执行 | `tool.execute`（registry.py:251）| 真正执行 | 用改写后的 SQL 查库 |

### 2.2.7 为什么是"生产必须"不是"锦上添花"

**单靠工具级权限的漏洞**：张三有 run_sql 权限 → 能查任意表（包括 user_pii）。工具级拦不住。
**加了 transform_args**：检查 SQL 引用的表 → 拦下 user_pii；自动注入 tenant_id → 只能看自己数据。

> **类比**：工具级管"能不能用锤子"，transform_args 管"能用锤子敲哪颗钉子"。

### 2.2.8 数据权限的更多粒度（生产实际）

| 粒度 | 例子 | 实现点 |
|------|------|--------|
| 表级 | 能查 ods_application，不能查 user_pii | transform_args 校验表名 |
| 行级 | 只能看自己租户的数据 | transform_args 注入 WHERE tenant_id |
| 列级 | 手机号/身份证列脱敏 | after_tool 改写结果 / 数据库列权限 |
| 指标级 | 能看逾期率，不能看额度 | 指标平台 / system_prompt 过滤工具 |
| 聚合级 | 只能看汇总，不能看明细 | SQL 层限制（GROUP BY 强制）|

# 第 3 层：参数脱敏层（Sanitization）

## 作用
日志里不能存明文敏感参数（密码、token、API key）——否则审计日志本身就是泄露源。

## Vanna 的实现（`core/audit/base.py:266`）

```python
def _sanitize_parameters(self, parameters):
    """脱敏敏感参数"""
    sanitized = parameters.copy()
    # 常见敏感字段名
    sensitive_patterns = ["password", "secret", "token", "api_key",
                          "apikey", "credential", "auth", "private_key", "access_key"]

    for key in list(sanitized.keys()):
        key_lower = key.lower()
        if any(pattern in key_lower for pattern in sensitive_patterns):
            sanitized[key] = "[REDACTED]"   # ★ 打码
    return sanitized
```

## 配置开关（`core/agent/config.py:108`）
```python
sanitize_tool_parameters: bool = Field(
    default=True, description="Sanitize sensitive parameters (passwords, tokens)"
)
```

## 落地：你的日志脱敏
```python
def sanitize_log(log_dict):
    SENSITIVE_KEYS = {"phone", "id_card", "password", "token"}
    return {k: ("***" if k in SENSITIVE_KEYS else v) for k, v in log_dict.items()}
```

> **关键**：脱敏只影响"日志/审计"展示，不影响"实际执行"的数据——所以它是独立一层，和②不冲突。

# 第 4 层：数据库层（最后兜底）★ 最硬的防线

## 作用
即使应用层（transform_args）被完全绕过，**数据库本身也强制过滤**。这是最后一道"物理防线"。

## PostgreSQL RLS 落地

```sql
-- ① 开启表的行级安全
ALTER TABLE ods_application ENABLE ROW LEVEL SECURITY;

-- ② 建策略：只能看自己租户的数据
CREATE POLICY tenant_isolation ON ods_application
    USING (tenant_id = current_setting('app.tenant_id'));

-- ③ 应用连接时设置当前租户（每请求）
SET app.tenant_id = 't_001';   -- 连接池按用户设置
```

## 和 transform_args 的关系（为什么都要）

| | transform_args | 数据库 RLS |
|---|---|---|
| 位置 | 应用层（Python）| 数据库层（SQL）|
| 防什么 | LLM 越权、非法 SQL | 应用层被绕过、直接连库 |
| 谁执行 | ToolRegistry | PostgreSQL 引擎 |
| 缺点 | 代码有 bug 就失效 | 非法 SQL 语法错就崩 |

**两者叠加**：transform_args 负责"LLM 生成的安全 SQL"，RLS 负责"即使 SQL 漏过也过滤"。

# 附录 A：权限数据来源（RBAC 三表概念）

> 你问："判断通过 transform_args 加了 where 条件，那是否说明生产中存在一张用户ID→有权限表的映射表？"
> 答案：**对，但生产不是"一张表"，是"一套权限模型"。**

## 生产权限数据的三层来源

```
① User 对象里直接带的（Vanna 的做法）
   group_memberships = ["analyst"]   ← 从 JWT/DB 塞进 User
   │ 粒度：只有"组"，没有表
   │
② 权限表 / 权限服务（生产必建）★ 你说的"那张表"
   用户→角色的映射表（RBAC）
   角色→表权限的映射表
   │ 粒度：能到"表级/列级"
   │
③ 属性规则（ABAC，最灵活）
   "如果 user.department == '风控' 且 表名 == '逾期表' 则允许"
   │ 粒度：动态、任意维度
```

## RBAC 经典三表（生产标准）

```
users（用户表）  →  user_roles（用户角色）  →  role_permissions（角色权限）
id: u_1001           user_id: u_1001            role: analyst
name: 张三           role: analyst              resource: ods_app
                     role: risk                 action: select
```

**查"张三能查哪些表"** = 三表联查：
```sql
SELECT DISTINCT rp.resource
FROM users u
JOIN user_roles ur ON u.id = ur.user_id
JOIN role_permissions rp ON ur.role = rp.role
WHERE u.id = 'u_1001' AND rp.action = 'select'
-- → {"ods_application", "dwd_repayment"}   ← 没有 secret_table
```

**这就是 `get_user_tables(user.id)` 背后的真实查询。**

## Vanna 的 group_memberships 算什么？

它是 **RBAC 的"用户→角色"那一层**（user_roles 简版），**少了"角色→权限"层**：

| Vanna 有的 | Vanna 缺的 |
|-----------|-----------|
| `User.group_memberships = ["analyst"]`（用户属于哪个组）| "analyst 能访问哪些表"的映射 |

所以 Vanna 能判断"张三是不是 analyst 组"（工具级），**判断不了"analyst 组能查哪些表"**（表级）——那正是要你用 transform_args + 自己的权限表来补。

## 三种权限模型对比（生产选型）

| 模型 | 全称 | 权限数据在哪 | 粒度 | 适合 |
|------|------|------------|------|------|
| RBAC | 基于角色 | 用户角色表 + 角色权限表 | 角色级 | 大部分企业 ✅ |
| ABAC | 基于属性 | 规则（不是表）| 任意属性 | 复杂权限（金融/云）|
| ACL | 访问控制列表 | 每个资源列"谁可访问"| 资源级 | 文件系统 |

# 附录 B：RBAC 三张表：简单建模 + 例子

## 一、三张表 DDL（简单建模）

```sql
-- ① 用户表：谁
CREATE TABLE users (
    id          VARCHAR(32) PRIMARY KEY,     -- 用户ID，如 u_1001
    name        VARCHAR(50) NOT NULL,        -- 姓名
    email       VARCHAR(100),                -- 邮箱
    created_at  TIMESTAMP DEFAULT now()
);

-- ② 用户-角色映射表：用户属于哪些角色（一个用户可多角色）
CREATE TABLE user_roles (
    user_id     VARCHAR(32) NOT NULL,        -- 用户ID
    role        VARCHAR(32) NOT NULL,        -- 角色名，如 analyst / risk / admin
    PRIMARY KEY (user_id, role),             -- 联合主键，防重复
    FOREIGN KEY (user_id) REFERENCES users(id)
);

-- ③ 角色-权限映射表：角色能对哪些资源做什么操作
CREATE TABLE role_permissions (
    role        VARCHAR(32) NOT NULL,        -- 角色名
    resource    VARCHAR(64) NOT NULL,        -- 资源：表名/API/指标名
    action      VARCHAR(16) NOT NULL,        -- 操作：select/insert/export/view
    PRIMARY KEY (role, resource, action)
);
```

**为什么是联合主键？**
- `user_roles`：`(user_id, role)` 防"张三 + analyst"重复插入
- `role_permissions`：`(role, resource, action)` 防"analyst + ods_app + select"重复

## 二、示例数据

```sql
-- 用户
INSERT INTO users (id, name, email) VALUES
('u_1001', '张三', 'zhangsan@bank.com'),
('u_1002', '李四', 'lisi@bank.com');

-- 张三 = 分析师 + 风控；李四 = 分析师
INSERT INTO user_roles (user_id, role) VALUES
('u_1001', 'analyst'),
('u_1001', 'risk'),
('u_1002', 'analyst');

-- analyst 能查大部分表；risk 额外能查风控敏感表
INSERT INTO role_permissions (role, resource, action) VALUES
('analyst', 'ods_application', 'select'),
('analyst', 'dwd_repayment',   'select'),
('analyst', 'ads_delinquency_daily', 'select'),
('risk',    'user_pii',        'select'),      -- 只有风控能查个人信息表
('risk',    'device_fingerprint', 'select'),   -- 只有风控能查设备指纹
('admin',   '*',               '*');           -- admin 通配所有
```

## 三、常用查询例子

### 例 1：张三能查哪些表？（对应 `get_user_tables(user.id)`）

```sql
SELECT DISTINCT rp.resource
FROM users u
JOIN user_roles ur ON u.id = ur.user_id
JOIN role_permissions rp ON ur.role = rp.role
WHERE u.id = 'u_1001' AND rp.action = 'select';
-- 结果: ods_application, dwd_repayment, ads_delinquency_daily, user_pii, device_fingerprint
-- 张三(analyst+risk) 比李四(analyst) 多了 user_pii 和 device_fingerprint
```

### 例 2：李四能不能查 user_pii？（对应表级校验）

```sql
SELECT COUNT(*)
FROM user_roles ur
JOIN role_permissions rp ON ur.role = rp.role
WHERE ur.user_id = 'u_1002'          -- 李四
  AND rp.resource = 'user_pii'       -- 查个人信息表
  AND rp.action = 'select';
-- 结果: 0 → 李四没权限 → transform_args 返回 ToolRejection("无权限访问表 user_pii")
```

### 例 3：给张三临时加"导出"权限

```sql
INSERT INTO role_permissions (role, resource, action) VALUES
('analyst', 'ads_delinquency_daily', 'export');
-- 加了后，所有 analyst 都能导出逾期表（不只是张三）—— 这就是角色的特性
```

## 四、对应到 Vanna 的 transform_args

```python
async def transform_args(self, tool, args, user, context):
    if tool.name != "run_sql":
        return args

    # ★ 从三张表查：这个用户能 select 哪些表
    allowed_tables = query_allowed_tables(user.id, action="select")
    #   SELECT DISTINCT rp.resource FROM user_roles ur
    #   JOIN role_permissions rp ON ur.role = rp.role
    #   WHERE ur.user_id = ? AND rp.action = 'select'

    for table in extract_tables(args.sql):
        if table not in allowed_tables:
            return ToolRejection(reason=f"无权限访问表 {table}")   # 例2 的 0 结果 → 拒绝

    # 行级注入（租户）
    if "tenant_id" not in args.sql:
        args.sql = inject_where(args.sql, f"tenant_id = '{user.metadata['tenant_id']}'")

    return args
```

## 五、进阶：再加"行级约束"列（可选）

```sql
-- 如果要做行级权限，给角色权限表加一列 constraint
ALTER TABLE role_permissions
    ADD COLUMN row_filter VARCHAR(200);   -- 如 "tenant_id = 't_001'"

-- analyst 只能看自己租户
INSERT INTO role_permissions (role, resource, action, row_filter) VALUES
('analyst', 'ods_application', 'select', 'tenant_id = current_tenant()');
```

这样权限表不仅存"能看哪些表"，还存"能看哪些行"——这是 RBAC → ABAC 的过渡。

## 六、小结

| 表 | 存什么 | 粒度 |
|----|--------|------|
| users | 谁 | 用户 |
| user_roles | 用户→角色（多对多）| 角色 |
| role_permissions | 角色→资源+操作 | 资源/操作 |
| (+row_filter) | 角色→行过滤规则 | 行级（进阶）|

**核心**：三张表 = "谁(RBAC)" 的完整骨架。查"用户能查哪些表"就是两次 JOIN + 一次 DISTINCT。加 row_filter 列 = 迈向行级权限（ABAC）。

# 附录 C：权限建模 vs 权限数据 vs 权限系统选型

> 你问："三张表的建模是否是整个权限的一部分并且是难点？"
> 答案：**三张表的"表结构"不是难点，真正的难点是"权限建模"（authorization modeling）。**

## 核心认知：权限四要素

```
① 主体（Subject）—— 谁
   users / user_roles（用户属于哪些角色）

② 客体（Resource）—— 对什么
   表、API、指标、文件、按钮...每种资源建模不同

③ 操作（Action）—— 干什么
   select / insert / delete / 导出 / 查看...

④ 约束（Constraint）—— 在什么条件下 ★ 真难点
   数据范围（行级/列级）、时间窗口、IP、租户
```

**RBAC 三表只覆盖 ①②③ 一部分，完全没碰 ④（数据约束）**——而你问的"张三能看哪些表"恰恰属于 ④。

## 难点分级（回答"是不是难点"）

| 层面 | 难不难 |
|------|--------|
| 三张表的表结构（建表、外键、联查）| ❌ 不难，基础 |
| RBAC 角色粒度设计 | 🟡 中，要业务经验 |
| **数据权限（行级/列级）建模** | 🔴 **难，核心难点** |
| 权限系统选型（Casbin/OPA/自建）| 🟡 中，要架构判断 |
| 越权检测 + 权限审计 | 🔴 难，生产必备 |

## 三个真正的难点

### 难点 A：角色粒度怎么设计？
- 太粗（3 个角色）→ 不够用
- 太细（一人一角色）→ 退化成个人配权，失去 RBAC 意义
- **生产答案**：RBAC 打底 + ABAC 补充

### 难点 B：行级/列级权限怎么建模？
```
行级：只能看 tenant_id='t_001' → 需要"行过滤规则"，三表表达不了
列级：手机号列不可见 → 需要"字段掩码规则"
```
**用三张表根本表达不了**——需要"权限策略表"或规则引擎（ABAC/OPA）。

### 难点 C：权限系统独立成产品

| 方案 | 本质 | 适用 |
|------|------|------|
| Casbin | Go/Python 权限库，支持 RBAC/ABAC | 大部分企业 |
| OPA | 策略引擎（Rego 语言）| K8s/微服务 |
| Auth0/Cerbos/OpenFGA | 托管权限服务 | 不想自建 |
| 自建三表 | 最基础，够用难扩展 | 小项目 |

**Vanna 的 group_memberships 连 RBAC 都不完整**——只有"用户→组"，没有"组→资源权限"。

## 对照 ai_assistant

| 现状 | 差距 |
|------|------|
| ✅ 有 required_role（指标级，RBAC 一小部分）| 硬编码在 indicators.yaml，不是查表 |
| ❌ 无权限表 | 用户→指标映射该从表查 |
| ❌ 无行级/列级过滤 | 加 transform_args 式过滤 |
| ❌ 无权限变更审计 | 加 permission_change_log |

**落地路径**：先把 `required_role` 从配置升级成权限表查询 → 再加行级过滤 → 再加审计。

> **核心认知**：三张表是"权限的骨架"，骨架不难；难的是给骨架填上"数据权限（行级/列级）"这个肉，以及让权限"正确 + 可审计"。判断逻辑（transform_args）和判断依据（权限表）缺一不可。

### 真实代码（agent.py:363-392）

**关键点**：
- **多个钩子按顺序执行**（列表顺序）
- 每个钩子的返回值：`None` = 不改消息；字符串 = **替换消息**
- 抛 `AgentError` = **中断处理**（消息不进 LLM）

### 真实实现（quota_lifecycle_example.py 的 QuotaCheckHook）
```python
class QuotaCheckHook(LifecycleHook):
    """配额检查：超了就抛异常中断"""
    async def before_message(self, user, message):
        usage = self._user_usage.get(user.id, 0)
        quota = self._user_quotas.get(user.id, self._default_quota)
        if usage >= quota:
            raise QuotaExceededError("配额已用完")   # ★ 抛异常 = 中断
        self._user_usage[user.id] = usage + 1
        return None   # 不改消息
```
