## ⓐ WorkflowHandler —— 命令拦截器 / 确定性流程

### 三问

**Q1 它解决什么问题？**
有些消息**不该进 LLM 循环**——`/help`、`/status`、`/reset`。让 LLM 答既浪费 token 又不可靠（可能瞎编）。WorkflowHandler 用**确定性代码**拦截，`should_skip_llm` 决定进不进 LLM。

**Q2 它在数据流哪一环？**
进循环**之前**。`_send_message`：解析完用户 → `try_handle(message)` → 返回 `WorkflowResult`。

**Q3 如果删掉它会怎样？**
斜杠命令进 LLM 循环 → 浪费 token、回答不可靠、无法做确定性的"清空会话"操作。

### 真实接口（`core/workflow/base.py`）

```python
@dataclass
class WorkflowResult:
    should_skip_llm: bool            # True=我处理了别进LLM；False=放行进LLM
    components: list = None          # 返回给用户的 UI（帮助文本/状态卡片）
    conversation_mutation = None     # 可选的：改会话状态（如 /reset 清空历史）

class WorkflowHandler(ABC):
    async def try_handle(self, agent, user, conversation, message) -> WorkflowResult:
        """你实现：判断 message 是不是你认识的命令"""
        # if message == "/help": return WorkflowResult(should_skip_llm=True, ...)
        # return WorkflowResult(should_skip_llm=False)  # 不归我管，放行
        pass
```

### 默认实现（`core/workflow/default.py`）—— 命令分发器

```python
class DefaultWorkflowHandler(WorkflowHandler):
    """默认工作流处理器：把斜杠命令拦截在 LLM 之外"""

    async def try_handle(self, agent, user, conversation, message) -> WorkflowResult:

        # ── /help：返回帮助文本 ──
        if message.strip().lower() in ["/help", "help", "/h"]:
            is_admin = "admin" in user.group_memberships   # 管理员看更多命令
            help_content = "## 🤖 Vanna AI Assistant\n..."
            if is_admin:
                help_content += "\n- `/status` - Check setup status\n..."
            return WorkflowResult(
                should_skip_llm=True,                    # ★ 不进 LLM！
                components=[UiComponent(...)],           # 直接返回帮助文本
            )

        # ── /status：检查系统配置状态（仅管理员）──
        if message.strip().lower() in ["/status", "status"]:
            if "admin" not in user.group_memberships:    # 权限检查
                return WorkflowResult(should_skip_llm=True, components=[拒绝组件])
            return await self._generate_status_check(agent, user)
            # 内部检查：SQL 工具在不在 / 记忆在不在 / 可视化在不在

        # ── /memories：查看最近记忆（仅管理员）──
        if message.strip().lower() in ["/memories", ...]:
            ...同样权限检查 + 返回记忆列表...

        # ── /delete id：删记忆（仅管理员）──
        if message.strip().lower().startswith("/delete "):
            ...同样权限检查 + 删记忆...

        # ── 兜底：不认识的命令 → 放行进 LLM ──
        return WorkflowResult(should_skip_llm=False)   # ★ 放行
```

### 关键设计

| 字段 | 作用 |
|------|------|
| `should_skip_llm=True` | 我处理了，别浪费 token 调 LLM |
| `should_skip_llm=False` | 不归我管，放行进 LLM 循环 |
| `conversation_mutation` | 可改会话状态（比如 `/reset` 清空历史）|

### 真实用法（`examples/default_workflow_handler_example.py`）

```python
from vanna import Agent, DefaultWorkflowHandler

agent = Agent(
    llm_service=llm_service,
    tool_registry=tool_registry,
    workflow_handler=DefaultWorkflowHandler(),   # 传自定义 handler
)
# 空消息时，agent 调 get_starter_ui() 返回欢迎卡片，不调 LLM
```

> **类比**：客服 IVR 语音菜单——按 1/2/3 走固定流程，按错才转人工（LLM）。

## ⓑ LifecycleHook —— 消息全生命周期钩子

### 三问

**Q1 它解决什么问题？**
在消息处理的**关键节点**插入自定义逻辑：配额、日志、内容过滤、改写工具结果。

**Q2 它在数据流哪一环？**
4 个钩子点分布在消息完整生命周期（agent.py 行号）：
```
before_message（365行，消息进来时）
    ↓
before_tool（787行，每个工具执行前）
    ↓
after_tool（848行，每个工具执行后）
    ↓
after_message（1111行，整条消息处理完）
```

**Q3 如果删掉它会怎样？**
无法做配额/日志/过滤这些横切关注点——只能写死在核心代码里，核心循环就会膨胀。

### 真实接口（`core/lifecycle/base.py`）

```python
class LifecycleHook(ABC):
    async def before_message(self, user, message) -> Optional[str]:
        # 返回改写后的消息，或 None 保持原样
        # 抛 AgentError 可中断处理（如配额超了）
        return None

    async def after_message(self, result) -> None:
        """整条消息处理完后的回调"""
        pass

    async def before_tool(self, tool, context) -> None:
        # 抛 AgentError 可阻止工具执行（如权限）
        pass

    async def after_tool(self, result) -> Optional[ToolResult]:
        # 返回改写后的 ToolResult（如给结果加脱敏）
        return None
```

### 真实实现（`examples/quota_lifecycle_example.py`）—— 配额检查

```python
class QuotaExceededError(AgentError):
    """用户超配时抛的异常"""
    pass

class QuotaCheckHook(LifecycleHook):
    """生命周期钩子：强制每个用户的消息配额"""

    def __init__(self, default_quota: int = 10):
        self._user_quotas = {}    # {用户id: 配额}
        self._user_usage = {}     # {用户id: 已用次数}
        self._default_quota = default_quota

    def set_user_quota(self, user_id, quota):
        """给特定用户设置配额"""
        self._user_quotas[user_id] = quota

    def get_user_remaining(self, user_id):
        """查剩余配额"""
        return self.get_user_quota(user_id) - self.get_user_usage(user_id)

    async def before_message(self, user, message):
        """消息进 LLM 前检查配额"""
        usage = self.get_user_usage(user.id)
        quota = self.get_user_quota(user.id)

        if usage >= quota:
            # ★ 抛异常 = 中断处理，消息根本不进 LLM 循环
            raise QuotaExceededError(
                f"User {user.username} has exceeded their quota of {quota} messages."
            )

        # 计数 +1
        current = self._user_usage.get(user.id, 0)
        self._user_usage[user.id] = current + 1
        return None   # 不修改消息，正常放行
```

```python
class LoggingHook(LifecycleHook):
    """日志钩子：记录消息进出的日志"""
    async def before_message(self, user, message):
        print(f"[LOG] User {user.username} sent: {message[:50]}...")
        return None

    async def after_message(self, result):
        print("[LOG] Message processing completed")
```

### 怎么挂上去（真实用法）

```python
agent = Agent(
    llm_service=...,
    lifecycle_hooks=[
        logging_hook,   # 先记日志
        quota_hook,     # 再查配额
    ],
)
```
**多个钩子按顺序执行**——日志先跑，配额后跑。

> **类比**：安检口——登机前、过安检、取行李，每个关键节点都有人查。

## ⓒ LlmMiddleware —— LLM 调用的外层包装

### 三问

**Q1 它解决什么问题？**
所有 LLM 调用（循环里每次 `send_request`）都经过它——缓存、成本追踪、请求改写、响应过滤。

**Q2 它在数据流哪一环？**
包在 LLM 调用**外**（agent.py 行号）：
```
request → before_llm_request（1244行，非流式 / 1317行，流式）
        → LLM
        → after_llm_response（1290行，非流式 / 1379行，流式）
        → 循环
```

**Q3 如果删掉它会怎样？**
每次 LLM 调用都重新计算/花钱/过滤——无法缓存、无法控成本。

### 真实接口（`core/middleware/base.py`）

```python
class LlmMiddleware(ABC):
    async def before_llm_request(self, request) -> LlmRequest:
        # 发 LLM 前：查缓存、加 prompt 工程、记日志
        return request

    async def after_llm_response(self, request, response) -> LlmResponse:
        # 拿到响应后：写缓存、过滤内容、记成本
        return response
```

### 真实实现（`examples/extensibility_example.py`）—— 缓存

```python
class CachingMiddleware(LlmMiddleware):
    """LLM 中间件：缓存响应，省钱省延迟"""

    def __init__(self):
        self.cache = {}    # {缓存key: LlmResponse}
        self.hits = 0
        self.misses = 0

    def _compute_cache_key(self, request):
        """用消息内容 + 温度 生成缓存 key"""
        messages_str = str([(m.role, m.content) for m in request.messages])
        return f"{messages_str}:{request.temperature}"

    async def before_llm_request(self, request):
        """发 LLM 前：检查缓存是否命中"""
        key = self._compute_cache_key(request)
        if key in self.cache:
            self.hits += 1
            print(f"[CACHE HIT] {self.hits} hits")
        return request    # ★ 注意：这个示例只检查，没有真正短路返回

    async def after_llm_response(self, request, response):
        """拿到响应后：写缓存"""
        key = self._compute_cache_key(request)
        if key not in self.cache:
            self.cache[key] = response   # 存起来
            self.misses += 1
            print("[CACHE MISS] Caching response")
        return response   # ★ 关键：必须返回 response，不能吞掉
```

> **⚠️ 真实中间件的坑**：`before_llm_request` 只返回 request，无法直接"短路返回缓存命中"。
> 生产级缓存中间件要在 `before_llm_request` 抛一个特殊异常/标记，让框架跳过真实 LLM 调用。
> Vanna 这个示例其实没完全实现"命中直接返回"——这是个可深挖的生产级点。

### 怎么挂上去（真实用法）

```python
agent = Agent(
    llm_service=...,
    llm_middlewares=[caching_middleware],   # 传中间件列表
)
```

> **类比**：CDN——每次访问先过缓存层，命中直接返回，不穿透到源站（LLM）。

## 三个扩展点对比

| | WorkflowHandler | LifecycleHook | LlmMiddleware |
|---|---|---|---|
| **位置** | 进循环前 | 消息全生命周期 | LLM 调用外层 |
| **核心问题** | 这条消息要进 LLM 吗？ | 关键节点插什么逻辑？ | 每次 LLM 调用包什么？|
| **典型用途** | 斜杠命令、确定性流程 | 配额、日志、内容过滤 | 缓存、成本、请求改写 |
| **能否中断** | 返回 should_skip_llm=True | 抛 AgentError | 改 request/response |
| **接口位置** | `core/workflow/base.py` | `core/lifecycle/base.py` | `core/middleware/base.py` |
| **调用点** | agent.py:274 | agent.py:365/787/848/1111 | agent.py:1244/1290/1317/1379 |

**为什么三个而不是一个？**
关注点、粒度、插入点都不同：
- WorkflowHandler：**要不要进 LLM**（大颗粒，消息级）
- LifecycleHook：**消息生命周期里做什么**（中颗粒，事件级）
- LlmMiddleware：**每次 LLM 调用包什么**（小颗粒，调用级）

这就是"**面向扩展设计**"——核心循环保持收敛，灵活性通过扩展点注入。

# 第二部分：Vanna 不具备的响应分类（is_refusal / is_empty）

## 核实结论（来自 04 主干①的表格）

| 方法 | Vanna 有没有 | 证据 |
|------|-------------|------|
| `is_tool_call()` | ✅ | `core/llm/models.py:50` |
| `is_refusal()` | ❌ 没有 | `LlmResponse` 只有 `is_tool_call` |
| `is_empty()` | ❌ 没有 | 同上 |
| 空响应处理 | ❌ 没有 | `else` 分支只 `if response.content:` yield，空就 yield 空 |

**为什么 Vanna 没有？**
Vanna 假设 LLM 总是返回**有效的 content 或 tool_calls**（乐观假设），把边界处理留给使用者。

**为什么生产级必须补？**
真实 LLM 会：
- 因内容安全过滤器触发 **refusal**（OpenAI 返回 `finish_reason="content_filter"`，Anthropic 返回 `stop_reason="refusal"`）
- 因临时故障返回**空响应**（content 和 tool_calls 都 None）

不处理 = 用户看到"无响应"或系统误判。

## 补全代码：加到 `core/llm/models.py` 的 LlmResponse 上

```python
class LlmResponse(BaseModel):
    """LLM 的响应。★ 生产级补全版（加 is_refusal / is_empty）"""

    content: Optional[str] = None              # LLM 生成的自然语言文本
    tool_calls: Optional[List[ToolCall]] = None  # LLM 想调的工具列表
    finish_reason: Optional[str] = None        # LLM 为什么结束：
                                               #   "stop"=正常答完
                                               #   "tool_calls"=还要调工具
                                               #   "content_filter"=被安全过滤器拦截（OpenAI）
                                               #   "length"=超长截断
    usage: Optional[Dict[str, int]] = None     # token 用量 {prompt, completion, total}
    metadata: Dict[str, Any] = Field(default_factory=dict)

    # ── Vanna 原有的 ──
    def is_tool_call(self) -> bool:
        """LLM 是否要调工具"""
        return self.tool_calls is not None and len(self.tool_calls) > 0

    # ── ★ 生产级补全 1：安全拒绝 ──
    def is_refusal(self) -> bool:
        """LLM 是否拒绝回答（内容安全过滤器触发）"""
        # OpenAI: finish_reason == "content_filter"
        # Anthropic: stop_reason == "refusal"
        return self.finish_reason in ("content_filter", "refusal")

    # ── ★ 生产级补全 2：空响应 ──
    def is_empty(self) -> bool:
        """LLM 是否什么都没返回（content 和 tool_calls 都空）"""
        return not self.content and not self.tool_calls
```

## 补全代码：加到循环里（接在主干①修正版最前面）

```python
tool_iterations = 0
retry_count = 0

while tool_iterations < max_tool_iterations:
    response = llm_service.send_request(request)

    # ── ① 安全检查（最先，安全红线）──
    if response.is_refusal():
        # LLM 拒绝回答（内容违规），明确告知用户，不进任何后续
        yield "抱歉，我无法回答这个问题"
        break

    # ── ② 空响应（先重试一次，别直接放弃）──
    if response.is_empty():
        # 可能是 LLM 服务临时抖动，重试一次
        if retry_count < 1:
            retry_count += 1
            continue                      # 重新发请求
        yield "系统暂时无响应，请重试"
        break

    # ── ③ 混合响应（思考 + 调工具）──
    if response.content and response.tool_calls:
        yield f"[思考] {response.content}"   # 先让用户看到思考
        # 不 break，继续走 ④ 执行工具

    # ── ④ 工具调用（含失败处理，核心）──
    if response.tool_calls:
        tool_iterations += 1
        conversation.add_message(assistant_message)

        tool_results = []
        for tool_call in response.tool_calls:
            try:                                 # ★ 关键：包异常
                result = tool_registry.execute(tool_call, context)
            except Exception as e:
                result = ToolResult(success=False, error=f"执行失败: {e}")
            tool_results.append(result)
            conversation.add_message(tool_response_message)   # ★ 错误也回喂

        request = _build_llm_request(conversation, context)
        continue                                 # 显式进入下一轮

    # ── ⑤ 纯文本回答（最终答案）──
    if response.content:
        yield response.content
        break

    # ── ⑥ 理论到不了的兜底（防御 + 日志）──
    logger.error(f"无法解析的响应: {response}")
    yield "系统遇到异常，请重试"
    break

# ── ⑦ 循环外：撞上限兜底 ──
if tool_iterations >= max_tool_iterations:
    logger.warning(f"达到工具迭代上限: {tool_iterations}")
    yield "任务太复杂没做完，请简化问题或重试"
```

## 这三条补全用在你的 ai_assistant 哪里？

| 补全 | 用在 ai_assistant 哪 |
|------|---------------------|
| `is_refusal()` | 你的 `LLMClient.chat_json()` 返回前先判断——LLM 拒绝（如违规问题）就拦截 |
| `is_empty()` | 你的 `intent_classifier` / `sql_generator` 返回空时——重试一次 |
| 工具失败回喂 | 你的 `pipeline` 里 SQL 执行失败 → 回喂给 LLM 让它改 SQL |

## 总结

**第一部分（三个扩展点）** = Vanna 把灵活性放循环外，核心保持收敛
- WorkflowHandler：命令拦截（要不要进 LLM）
- LifecycleHook：全生命周期钩子（配额/日志/过滤）
- LlmMiddleware：LLM 调用外层（缓存/成本）

**第二部分（补全）** = 生产级该有、Vanna 没有的响应分类
- `is_refusal()`：处理内容安全拒绝
- `is_empty()`：处理空响应 + 重试

> **核心心法**：框架的"收敛"是设计不是缺陷。而"生产级该补的边界"（refusal/空响应）正是你和框架的差距——补上它，你的 ai_assistant 就比 Vanna 默认更健壮。
