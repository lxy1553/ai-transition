# 主干 ②：Tool 抽象（完整版）

> 7 个主干的第 2 个。Tool 是 Agent 的"手和脚"——LLM 靠工具 schema 知道能做什么、怎么做。
> 这是 function calling 的本质，也是你 ai_assistant 从"写死查数"到"多工具自主"的关键。
>
> 代码位置：
> - 接口：`src/vanna/core/tool/base.py`（70 行）
> - 真实实例：`src/vanna/tools/run_sql.py`（RunSqlTool，166 行）
> - 数据模型：`src/vanna/core/tool/models.py`（ToolCall/ToolResult/ToolContext）

---

## 三问（先想清楚再读代码）
### Q1：它解决什么问题？

把"一个能力"（查库、发邮件、画图）统一封装成一个**标准接口**，让 LLM 能：
- **知道有这个能力**（通过 description）
- **知道何时用它**（通过 description 语义）
- **知道怎么调它**（通过 args schema）

没有 Tool 抽象，每个能力各写一套，LLM 无法动态选择 → 无法成为 Agent。

### Q2：它在数据流哪一环？

工具是 Agent 的"手和脚"。LLM 说"调 run_sql"，Agent 找到这个 Tool 执行：

```
LLM 返回 ToolCall(name="run_sql", args={sql: "..."})
  → registry.get_tool("run_sql")   → 找到 RunSqlTool
  → registry.execute(...)            → 调 RunSqlTool.execute()
  → 返回 ToolResult
```

### Q3：如果删掉它会怎样？

没有统一抽象，每个能力都写死一套调用，LLM 无法动态选择工具 → 系统退化成"脚本"，不是 Agent。

## 一、接口：Tool（`core/tool/base.py`，全文解读）

```python
class Tool(ABC, Generic[T]):        # 所有工具必须继承
    """工具抽象基类"""

    # ── ① 工具名：LLM 靠它调用 ──
    @property
    @abstractmethod
    def name(self) -> str: ...
    #   例：run_sql / query_credit_report / visualize_data

    # ── ② 工具描述：LLM 靠它判断"何时用" ──
    @property
    @abstractmethod
    def description(self) -> str: ...
    #   例："Execute SQL queries against the configured database"
    #   LLM 看到描述，才知道"用户想查数据时调这个"

    # ── ③ 权限组：谁能用这个工具 ──
    @property
    def access_groups(self) -> List[str]:
        return []                    # 空 = 所有人可用

    # ── ④ 参数 schema：LLM 靠它填参数 ──
    @abstractmethod
    def get_args_schema(self) -> Type[T]: ...
    #   返回一个 Pydantic 模型，定义参数结构
    #   例：RunSqlToolArgs(sql: str) → LLM 知道要传 {"sql": "..."}

    # ── ⑤ 执行函数：真正干活的地方 ──
    @abstractmethod
    async def execute(self, context: ToolContext, args: T) -> ToolResult:
        ...
    #   context：谁在调用（用户/会话/追踪）
    #   args：Pydantic 校验后的参数
    #   返回：ToolResult（给 LLM 看的结果 + 给用户看的 UI）

    # ── 生成给 LLM 看的 schema（框架自动调）──
    def get_schema(self) -> ToolSchema:
        args_model = self.get_args_schema()
        schema = args_model.model_json_schema()   # Pydantic → JSON Schema
        return ToolSchema(
            name=self.name,
            description=self.description,
            parameters=schema,
            access_groups=self.access_groups,
        )
```

### 一个工具 = 5 个部分

| 部分 | 作用 | LLM 怎么用它 |
|------|------|-------------|
| name | 调用标识 | 返回 ToolCall(name=...) |
| description | 何时用 | 判断"这个能力适不适合当前问题" |
| access_groups | 谁能用 | 权限判断（registry 校验）|
| get_args_schema | 参数怎么填 | 看 JSON Schema 生成参数 |
| execute | 真正执行 | （不直接，registry 调）|

**核心洞察**：LLM 看到的是 `get_schema()` 生成的 JSON Schema（name + description + parameters），它靠这个"理解"工具。**描述写得越清楚，LLM 调用越准。**

## 二、真实实例：RunSqlTool（`tools/run_sql.py`，逐段解读）

> 这是 Vanna 最核心的工具——用户问数，它执行 SQL。看它怎么实现 Tool 接口。

```python
class RunSqlTool(Tool[RunSqlToolArgs]):
    """执行 SQL 查询的工具（注入 SqlRunner 实现）"""

    def __init__(self, sql_runner, file_system=None, custom_name=None, custom_desc=None):
        # ★ 依赖注入：不写死连哪个库，由外部传入
        self.sql_runner = sql_runner            # 真正执行 SQL 的（SqliteRunner/PostgresRunner...）
        self.file_system = file_system or LocalFileSystem()   # 保存结果用
        self._custom_name = custom_name
        self._custom_description = custom_desc

    # ── ① name ──
    @property
    def name(self):
        return self._custom_name if self._custom_name else "run_sql"

    # ── ② description ──
    @property
    def description(self):
        return self._custom_description if self._custom_description \
            else "Execute SQL queries against the configured database"

    # ── ④ args schema ──
    def get_args_schema(self):
        return RunSqlToolArgs   # {sql: str}

    # ── ⑤ execute（核心）──
    async def execute(self, context, args):
        try:
            # (a) 用注入的 sql_runner 执行
            df = await self.sql_runner.run_sql(args, context)
            query_type = args.sql.strip().upper().split()[0]   # SELECT/INSERT...

            if query_type == "SELECT":
                if df.empty:
                    # 无结果
                    result = "Query executed successfully. No rows returned."
                else:
                    # 有结果：存 CSV 供可视化工具用
                    filename = f"query_results_{uuid4()[:8]}.csv"
                    csv_content = df.to_csv(index=False)
                    await self.file_system.write_file(filename, csv_content, context)

                    # ★ 关键：给 LLM 看的结果（截断到 1000 字符）
                    results_preview = csv_content[:1000]
                    result = f"{results_preview}\n\nResults saved to: {filename}"
            else:
                # 非 SELECT（INSERT 等）
                result = f"Query executed successfully. {rows_affected} row(s) affected."

            # ★ 返回 ToolResult：给 LLM + 给用户
            return ToolResult(
                success=True,
                result_for_llm=result,      # 回喂给 LLM 的文本
                ui_component=ui_component,  # 给前端渲染的表格/通知
                metadata={...},             # 额外信息
            )
        except Exception as e:
            # ★ 错误也返回 ToolResult（success=False），不抛异常
            return ToolResult(
                success=False,
                result_for_llm=f"Error executing query: {str(e)}",
                ui_component=error_component,
                error=str(e),
            )
```

### RunSqlTool 揭示的 4 个设计要点

1. **依赖注入**：`sql_runner` 由外部传，工具本身不写死连哪个库 → 可复用
2. **结果分两个**：`result_for_llm`（给 LLM）+ `ui_component`（给用户）
3. **错误也返回 ToolResult**（success=False），不抛异常 → 错误回喂给 LLM 让它修正
4. **结果存文件**：SQL 结果存 CSV，供下游 visualize_data 工具用 → 工具链协作

## 二点五、第二个实例：SaveQuestionToolArgsTool（记忆工具）

> RunSqlTool 是"执行型"工具（查数）。SaveQuestionToolArgsTool 是"记忆型"工具——不查数据，而是**把成功的查询模式存进记忆**。展示另一类工具怎么写。

```python
class SaveQuestionToolArgsTool(Tool[SaveQuestionToolArgsParams]):
    """保存成功的"问题+工具+参数"组合，供未来参考"""

    # ── ① name ──
    @property
    def name(self):
        return "save_question_tool_args"

    # ── ② description ──
    @property
    def description(self):
        return "Save a successful question-tool-argument combination for future reference"
        #   LLM 靠这个判断："这个查询成功了，值得记住"

    # ── ④ args schema ──
    def get_args_schema(self):
        return SaveQuestionToolArgsParams
        #   Pydantic 模型：{question, tool_name, args}

    # ── ⑤ execute（核心）──
    async def execute(self, context, args):
        try:
            # ★ 关键：用 context.agent_memory 存记忆（不是查数据！）
            await context.agent_memory.save_tool_usage(
                question=args.question,    # 用户问什么
                tool_name=args.tool_name,  # 用了哪个工具
                args=args.args,            # 传了什么参数
                context=context,
                success=True,
            )
            return ToolResult(
                success=True,
                result_for_llm=f"Successfully saved usage pattern for '{args.tool_name}' tool",
                ui_component=...,
            )
        except Exception as e:
            return ToolResult(
                success=False,
                result_for_llm=f"Failed to save memory: {str(e)}",
                error=str(e),
            )
```

### 参数模型（Pydantic）
```python
class SaveQuestionToolArgsParams(BaseModel):
    question: str = Field(description="The original question that was asked")
    tool_name: str = Field(description="The name of the tool that was used successfully")
    args: Dict[str, Any] = Field(description="The arguments that were passed to the tool")
```

### 与 RunSqlTool 的对比（两类工具）

| | RunSqlTool（执行型）| SaveQuestionToolArgsTool（记忆型）|
|---|---|---|
| 做什么 | 查数据 | 存记忆 |
| 依赖 | sql_runner（执行 SQL）| **context.agent_memory**（记忆）|
| 结果 | result_for_llm = 查询结果 | result_for_llm = 确认消息 |
| 副作用 | 查库 | **写记忆** |
| 用途 | 用户问数 | 记住成功模式（训练式RAG）|

**关键洞察**：工具不只是"执行"，还能"记忆"——`context.agent_memory` 让工具能读写记忆。这展示了 Tool 的灵活性：**任何能力（查数/记忆/画图/发邮件）都能包装成 Tool**。

**对照 ai_assistant**：你可以加 `SaveUsageTool`（记住哪些查询成功）——用户问过且查对的 SQL 存下来，下次类似问题先搜记忆复用。

## 三、配套数据模型（`core/tool/models.py`）

```python
# LLM 说"我要调这个工具"
class ToolCall(BaseModel):
    id: str                      # 唯一 ID
    name: str                    # 工具名（registry 靠它找）
    arguments: Dict               # 参数（LLM 填的原始 JSON）

# 每次工具调用带着的上下文
class ToolContext(BaseModel):
    user: User                   # ★ 谁在调用（权限）
    conversation_id: str         # 哪个会话
    request_id: str              # 哪个请求（追踪）
    agent_memory: AgentMemory    # 记忆
    metadata: Dict

# 工具执行结果
class ToolResult(BaseModel):
    success: bool                # 成功/失败
    result_for_llm: str          # ★ 给 LLM 看的结果（回喂循环）
    ui_component: Optional       # 给用户看的 UI
    error: Optional[str]         # 失败原因

# 给 LLM 看的工具描述
class ToolSchema(BaseModel):
    name: str
    description: str
    parameters: Dict              # JSON Schema
    access_groups: List[str]
```

## 四、对照 ai_assistant 的改造动作

你的 ai_assistant 现在"查数/解释/血缘"都写死在 pipeline。Tool 式改造 = 拆成 3 个 Tool：

```python
# ① 查指标工具（复用你的 sql_generator + executor）
class QueryIndicatorTool(Tool[QueryIndicatorArgs]):
    name = "query_indicator"
    description = "查询信贷指标（逾期率/通过率/额度），输入指标名和时间"
    access_groups = ["analyst"]

    def get_args_schema(self):
        return QueryIndicatorArgs   # {indicator, time_range}

    async def execute(self, context, args):
        indicator = catalog.get_indicator(args.indicator)   # 复用 schema_catalog
        sql = sql_generator.generate(indicator, args.time_range)  # 复用
        result = executor.execute(sql)                       # 复用
        return ToolResult(success=result.success,
                          result_for_llm=str(result.data))

# ② 解释口径工具（复用你的 retriever）
class ExplainDefinitionTool(Tool[ExplainArgs]):
    name = "explain_definition"
    description = "解释信贷指标的口径和定义"
    ...

# ③ 血缘追溯工具（复用你的 catalog.get_lineage）
class TraceLineageTool(Tool[LineageArgs]):
    name = "trace_lineage"
    description = "追溯信贷指标的来源和计算链路"
    ...
```

**改造要点**：
1. 你的 `sql_generator`/`executor`/`retriever`/`catalog` → 成为 Tool 内部的依赖
2. 每个 Tool 的 `description` 要写清楚（LLM 靠它判断何时调）
3. 每个 Tool 的 `args` 用 Pydantic 定义（LLM 靠它填参数）
4. 结果返回 `ToolResult(result_for_llm=...)`（给 LLM 回喂）

**改造后的效果**：pipeline 不再写死 8 步，而是"LLM 看到 3 个工具 schema，自己决定调哪个"——这就是 Agent 编排（主干①）。

## 五、小结

| 学到 | 一句话 |
|------|--------|
| Tool 抽象 | 一个工具 = name + description + args + execute + 权限 |
| description 的重要性 | LLM 靠它判断"何时用"，写得越清调用越准 |
| 依赖注入 | sql_runner 外部传，工具可复用 |
| 结果分两个 | result_for_llm（给LLM）+ ui_component（给用户）|
| 错误也返回 | success=False 的 ToolResult，不抛异常，回喂让 LLM 修正 |
| 工具链协作 | run_sql 存 CSV → visualize_data 读 CSV |

> **核心心法**：Tool 是 Agent 的"手和脚"，LLM 通过 schema 理解它。你的 ai_assistant 从"写死 8 步"到"多工具自主"，第一步就是**把能力拆成 Tool**。
