# 数仓 + AI 应用：多版本进化路径（数据仓库为 1.0）

> 基于数仓背景，重新设计一个干净的项目，逐步加入 AI 应用能力。
> 定位：AI 应用开发工程师（数仓背景差异化）。
> 设计原则：数仓是地基（1.0），AI 是上层（2.0+），工程化越到后面越重。

---

## 版本总览

```
1.x 数仓地基        2.x 单点AI          3.x Agent化          4.x 生产工程化       5.x ML增强
1.0 分层 ────── 2.0 NL2SQL ────── 3.0 工具化 ────── 4.0 评测 ────── 5.0 异常检测
1.1 治理 ────── 2.1 RAG    ────── 3.1 循环   ────── 4.1 权限 ────── 5.1 智能报表
1.2 服务 ────── 2.2 血缘   ────── 3.2 记忆   ────── 4.2 降级
                                                 └── 4.3 可观测
```

**共 14 个版本**，从纯数仓到 AI Agent 到 ML，每个都能跑、能演示、能面试讲。

---

# 阶段 1.x：数仓地基（你的专业，打牢）

> 定位：先做一个"能查、能追溯、能治理"的数仓。这是你的差异化地基，AI 应用都建在它上面。

## v1.0 数仓分层

**目标**：四层架构（ODS/DWD/DWS/ADS）落地，数据能跑通。

**核心产出**：
- ODS/DWD/DWS/ADS 四层建表 + ETL
- 指标字典（口径定义、计算公式）
- 数据血缘（每列来源）

**验证**：SQL 能查出指标（如逾期率）。

**对应三支柱**：② 知识接入的"数据底座"。

---

## v1.1 数据治理

**目标**：元数据 + 数据质量体系。

**核心产出**：
- Schema Registry（表结构元数据管理）
- 数据质量分（扣分制，dq_score）
- 分区策略（按 dt 分区）

**验证**：能追溯指标来源 + 能看质量分。

---

## v1.2 数据服务化

**目标**：数仓对外可用，成为"数据产品"。

**核心产出**：
- 指标 API（查询接口）
- ADS 数据产品（预聚合、即查即用）
- 血缘可查询服务

**验证**：接口能查数，BI/业务方可用。

> 阶段 1 产出：一个"能查、能追溯、能治理、能服务"的数仓。AI 应用都在这上面长出来。

# 阶段 2.x：单点 AI 接入（三支柱②：知识接入）

> 定位：把 AI 能力一个个接进数仓，先单点、后整合。

## v2.0 NL2SQL —— 自然语言问数

**目标**：用户用自然语言查数仓。

**核心产出**：
- 意图识别 → NL2SQL 生成 → SQL 校验 → 执行 → 回答
- Schema 注入（防 LLM 瞎编字段）
- SQL 安全校验（禁 DROP/分区/行数）

**验证**：问"上个月逾期率" → 得 3.2%。

**对应 Vanna 学到的**：run_sql 工具思想（你已更完整）。

---

## v2.1 RAG 口径解释

**目标**：用户问"指标什么意思"，能解释。

**核心产出**：
- 指标文档切分、向量化、检索
- RAG 检索 → LLM 解释口径
- 多路召回 + 重排（检索质量）

**验证**：问"逾期率是啥" → 返回准确定义。

**对应 Vanna 学到的**：context_enricher 思想（文档 RAG 你已超过 Vanna）。

---

## v2.2 AI 血缘追溯

**目标**：用户问"指标怎么来的"，能讲清链路。

**核心产出**：
- 血缘数据 → LLM 生成来源解释
- 正向/反向追溯

**验证**：问"逾期率怎么算" → 讲清 ODS→DWD→DWS→ADS 链路。

> 阶段 2 产出：三个单点 AI 能力（NL2SQL/RAG/血缘），各是各的，还没整合。

---

# 阶段 3.x：Agent 化（三支柱①：编排）★ 质变

> 定位：把单点能力整合成 Agent——LLM 自主决定调哪个工具。这是"脚本→Agent"的分水岭。

## v3.0 工具化

**目标**：把单点能力拆成可注册的工具。

**核心产出**：
- 3 个 Tool：QueryIndicator / ExplainDefinition / TraceLineage
- ToolRegistry（注册、查找、执行）

**验证**：LLM 能"看到"3 个工具及其 schema。

**对应 Vanna 学到的**：Tool 抽象 + ToolRegistry（阶段2·主干②③）。

---

## v3.1 Agent 循环

**目标**：LLM 在循环里自主决定下一步。

**核心产出**：
- while 循环 + is_tool_call() 判断
- 工具结果回喂（role="tool"）
- 多步推理（查数→看结果→再决定）

**验证**：问复杂问题 → LLM 自己拆解调工具。

**对应 Vanna 学到的**：主干① Agent 循环（★★★ 最重要）。

---

## v3.2 记忆 + 多轮

**目标**：上下文衔接 + 指代消解。

**核心产出**：
- 会话记忆（短期/长期）
- "这个指标"→ 上一轮指标（指代消解）
- 训练式 RAG（记住成功查询）

**验证**：连续追问能衔接。

**对应 Vanna 学到的**：主干⑦ 记忆（阶段4）。

> 阶段 3 产出：从"脚本"变"Agent"——用户一句话，LLM 自主编排完成。

## v3.3 框架化重构（可选，非必须）

**目标**：把手写 while 循环用框架（LangGraph）重构——**仅在需要复杂编排时**做。

**为什么可选**：Vanna 证明 Agent 编排可手写（无 LangChain/LangGraph）。简单编排（数据问答）手写就够，框架是"补上手写版缺的能力"。

**框架补什么**（手写版没有的）：
- 断点/恢复（checkpoint 持久化）
- 中断续跑（长任务）
- 并行/分支（多 Agent）
- 可视化调试（LangSmith）

**何时才需要**：
```
简单编排（单Agent顺序执行）→ 手写够了，不用框架
复杂编排（长任务恢复/多Agent/并行分支）→ 才上 LangGraph
```

**核心产出**：手写 while → LangGraph 图（State + 节点 + 边）。

**验证**：能断点恢复 + 能可视化追踪每步。

> 学习顺序：先手写 while（v3.1）→ 懂了原理 → 需要复杂编排再上框架（v3.3）。**别一上来用框架，会丢失底层理解。**

# 阶段 4.x：生产工程化（三支柱③：能上线）

> 定位：把 Agent 变成能上线的产品——可靠、安全、可观测、可控成本。

## v4.0 评测体系

**目标**：效果可量化。

**核心产出**：
- 评测集（按维度设计，正例反例）
- 准确率（意图/指标/行为）
- bad case 归因

**验证**：能报出"意图 98%、指标 100%"。

**对应 Vanna 学到的**：阶段6 评测体系（你已有 eval_qa.py + 55 条）。

---

## v4.1 权限安全

**目标**：数据隔离，防止越权。

**核心产出**：
- 用户系统（User + 权限组）
- 表级权限（transform_args 注入过滤）
- 审计日志（谁、何时、查了什么）

**验证**：无权限表查不到，且有审计。

**对应 Vanna 学到的**：05 权限五层（已学，落地）。

---

## v4.2 降级容错

**目标**：系统可靠，不因单点故障崩。

**核心产出**：
- 超时控制 + 重试
- 熔断（LLM 挂了→降级回答）
- 撞上限兜底

**验证**：模拟 LLM 超时 → 系统降级不崩。

**对应 Vanna 学到的**：降级（Vanna 有接口未接线，你要自己落地）。

---

## v4.3 可观测 + 成本

**目标**：可控可追踪。

**核心产出**：
- 日志 + 指标 + 链路追踪
- 缓存（省钱省延迟）
- 成本记录（每次调用 token）

**验证**：能看每次调用成本、出错能追踪。

> 阶段 4 产出：能上线的产品——面试"工程化落地"的核心。

---

# 阶段 5.x：ML 增强（三支柱④：贯穿）

> 定位：ML 融入，不只是"问数"，还能"预测"。这是数仓+AI 的终局。

## v5.0 指标异常检测

**目标**：数仓 + ML 主动告警。

**核心产出**：
- 用历史指标训练异常检测模型
- 指标突变 → 系统主动提醒

**验证**：模拟指标突变 → 系统告警。

**对应你的优势**：信贷 XGBoost 项目（ML 应用决策已会）。

---

## v5.1 智能报表

**目标**：ML 增强问答。

**核心产出**：
- 指标趋势预测
- AI 生成报表（"下季度逾期率会怎样"）

**验证**：问"下季度逾期率" → 得到预测 + 报表。

> 阶段 5 产出：数仓 + AI + ML 的完整闭环——能问、能答、能预测。
