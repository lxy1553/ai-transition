







# AI 工程新范式：从 Prompt 到 Graph，AI 系统的四次演进与工程落地

> 导读：过去两年，AI 工程领域经历了四次重心迁移——从 Prompt Engineering 到 Context Engineering，再到 Harness Engineering、Loop Engineering，最后到 Graph Engineering。它们不是谁取代谁，而是任务复杂度变高后，工程重心自然外扩。本文系统性地拆解这四次演进的内在逻辑、核心概念，以及如何在一套统一的工程框架中落地。


## 开篇：AI 工程的四次演进

过去两年，AI 工程领域经历了四次重心迁移：

```
2023 年       Prompt Engineering     —— 怎么"说"
2024 年       Context Engineering    —— 喂什么"材料"
2026 年 2 月  Harness Engineering    —— 干活的"驾驶舱"
2026 年 6 月  Loop Engineering       —— 不按回车"松手"
2026 年 6 月  Graph Engineering      —— 多 agent 并行编排
```

**核心规律**：每个新词的出现，都是上一瓶颈被解决、新瓶颈暴露。模型每变强一截，瓶颈就往外移一层：

- 从你说的那句话（Prompt）
- → 到你给的那堆材料（Context）
- → 到它干活的环境（Harness）
- → 落到你本人身上（Loop）
- → 再到多任务协作（Graph）

**核心公式**：
> **Agent = Model + Harness**
>
> 模型提供智能，Harness 让智能变成生产力。同一个模型，驾驶舱不一样，能力可以差出几倍。

**四次演进的关系**：
> **Prompt ⊂ Context ⊂ Harness ⊂ Loop ⊂ Graph**
>
> 后者天然包含前者，边界一层比一层大。不是谁取代谁，而是当任务越来越复杂时，工程重心自然外扩。


## 第一部分：三次演进（Prompt → Context → Harness）

### 1.1 第一次：Prompt Engineering（"怎么说"）

大模型刚爆发时，同一个模型换一种说法，结果天差地别。核心思想很朴素：**模型不是不会，而是你没有把问题讲清楚**。

**典型方法**：角色设定、风格约束、Few-shot 示例、分步引导、格式约束、拒答边界。

**本质**：不是"下命令"，而是"塑造局部概率空间"。谁更懂模型的脾气，谁就更容易做出看起来更聪明的效果。

**天花板**：Prompt 解决的是"表达问题"，不是"信息问题"。当任务需要真实知识、动态信息、长链条执行时，提示词再漂亮也没用。

### 1.2 第二次：Context Engineering（"给什么"）

默认假设变了：**模型未必知道，所以系统必须在调用时把正确的信息送进去**。

**Context 是什么**？所有会影响模型当前决策的信息总和：用户输入、历史对话、知识检索、工具返回、任务状态、工作记忆、系统规则、其他 Agent 的结构化结果。

**典型实践**：
- **RAG**：从外部知识库检索相关内容，注入上下文
- **Agent Skills（渐进式披露）**：

| 层级 | Token 消耗 | 内容 | 加载时机 |
|------|-----------|------|----------|
| 元数据层 | ~50 Token | 名称、触发条件、概述 | 启动时全局加载 |
| 指令层 | ~500 Token | SOP、输入输出规范 | 任务触发时加载 |
| 资源层 | 按需加载 | 脚本、模板、API 文档 | 执行具体步骤时动态调用 |

**天花板**：即便信息是对的，模型也未必会稳定执行对——计划偏了、误解工具结果、出错后一路错下去。

### 1.3 第三次：Harness Engineering（"怎么驾驭"）

前两代都作用在"输入侧"：Prompt 优化意图表达，Context 优化信息供给。但当模型开始连续行动时，还需要解决更难的问题：**谁来持续监督它、约束它、纠正它？**

Harness 这个词来自马术，是"缰绳、马具"的意思。一匹没驯服的马力量很大，但你没法让它耕地、运货、上战场。AI 也一样——模型提供智能，**Harness 让智能变成生产力**。

> **AI 落地的核心挑战，正在从"让模型显得聪明"，转向"让模型在真实世界里稳定工作"。**

#### Harness 的六大核心构成

| 核心层 | 核心问题 | 关键实践 |
|--------|----------|----------|
| **1. 上下文管理** | AI 看到什么信息？ | 渐进式披露（AGENTS.md ~100 行）、知识库挂载、结构化分层 |
| **2. 工具系统** | AI 能触达什么？ | MCP（数据通道）+ Skills（专家经验）+ 知识库（业务上下文） |
| **3. 执行编排** | AI 按什么顺序做？ | 3+1 Phase：Planner → Generator → Evaluator → Archiver |
| **4. 状态与记忆** | AI 怎么持续记住？ | Git + Memories + Spec Deltas，区分临时/会话/长期 |
| **5. 评估与观测** | AI 做得对不对？ | 四层验收：语法→逻辑→规范→架构 |
| **6. 约束与恢复** | AI 不能做什么？出错了怎么办？ | 硬性红线 + 软性约束 + 安全策略 + 自动回滚 |

#### 工具系统的三大组成部分

**① MCP（Model Context Protocol）—— 连接外部数据源**
- DB MCP：自动读取实时数据库 Schema
- Knowledge Base MCP：挂载团队内部文档
- API MCP：实时查询其他服务接口定义
- 运维 MCP：接入 CI/CD、监控系统

**② Skills（Agent Skills）—— 封装专家经验**
- 工具接入类：封装内部工具链接入规范
- 代码生成类：固化特定模式的代码生成逻辑
- 元技能类：让 AI 能自我扩展（skill-creator）
- 搜索发现类：从 80,000+ 技能库搜索安装

**③ 知识库（Knowledge Base）—— 注入业务上下文**
- iWiki 文档库、工蜂代码库、AI Wiki、自定义文件

> **核心比喻**：MCP 是开门的钥匙，Skills 是开门后做的事情，知识库是进门前读的说明书。三者缺一不可。

#### 约束分三级

```
┌──────────────────────────────────────────────────────────┐
│  硬性红线（Rules - 不可违反）                              │
│  "所有 API 必须包含 Swagger 注解"                         │
│  "禁止在 Controller 层编写业务逻辑"                       │
├──────────────────────────────────────────────────────────┤
│  软性约束（Skills - 推荐遵循）                             │
│  "优先使用项目已有的工具类"                                │
├──────────────────────────────────────────────────────────┤
│  安全策略（Safety - 兜底保护）                             │
│  "涉及数据库变更，优先生成 SQL 脚本"                       │
└──────────────────────────────────────────────────────────┘
```


## 第二部分：Loop Engineering（"不按回车"）

### 2.1 起因

2026 年 6 月，三位行业关键人物在同一周说了同一件事：

- **Peter Steinberger**（OpenClaw 作者）：「每月例行提醒：你不该再给 coding agent 打 prompt 了。你该去设计那个给 agent 打 prompt 的 loop。」
- **Addy Osmani**（Google Cloud AI 总监）给出定义并写长文
- **Boris Cherny**（Claude Code 创始人）：「我已经不 prompt Claude 了。是 loop 在运行着 prompt Claude、决定做什么。我的工作是写 loop。」

### 2.2 什么是 Loop Engineering？

> **定义**：Loop engineering 就是把"亲自给 agent 写 prompt 的那个你"替换掉，转而设计那个代替你做这件事的系统。

- **过去**：回合制协作。你写一条 prompt → 读输出 → 再写一条。agent 是工具，你全程握着它。
- **现在**：把"发现任务、布置任务、检查结果、决定下一步"设计成一个能自己运转的循环，让循环去握着 agent。

**打个比方**：以前你是客服热线的接线员，每个电话亲自接；现在你升级成设计工单系统的人——电话怎么分流、哪类问题转给谁、办结标准是什么、办不了的怎么升级。

> 你不再是 prompt 的作者，你是 **prompt 生产系统的设计师**。
>
> 以前写一条好 prompt，收益是"这一次回答变好"；现在设计一个好 loop，收益是"之后每一次循环都变好"。投入从消耗品变成了资产。

### 2.3 一个 Loop 的六大部件

| 部件 | 职责 | 在 Codex 中 | 在 Claude Code 中 |
|------|------|-------------|-------------------|
| **自动化** | loop 的心跳——定时或事件触发 | Automations 面板 + 分诊收件箱 | 计划任务、/loop、hooks |
| **worktree** | 让并行不变成打架——给每个 agent 独立工作目录和分支 | 每个线程内置 worktree | git worktree、隔离配置 |
| **skill** | 治好 agent 的"金鱼记忆"——项目知识复利 | Agent Skills | Agent Skills |
| **connector** | 让 loop 摸到真实世界——基于 MCP 协议 | 基于 MCP 的 Connectors | MCP servers |
| **sub-agent** | 写查分离——让 A 出方案，让 B 来挑刺 | 配置文件定义子 agent | 子 agent、agent teams |
| **记忆** | loop 的命根子——放在磁盘上而不是上下文里 | markdown 或接工单系统 | markdown 或接工单系统 |

**两个关键点**：
- 两家都有 `/goal` 类能力——跑到你写的条件为真才停（"所有测试通过且 lint 干净"），每轮结束由独立模型判断条件
- **loop 的设计正在变得工具无关**——部件是同样的部件，差的只是商标。值得积累的是图纸，不是对某家工具的肌肉记忆

### 2.4 一个真实的 Loop 长什么样？

> 任务：每天早上自动把项目里值得修的问题找出来、修好、提交审核。

1. 每天早晨，自动化准时触发，调用负责**分诊**的 skill
2. skill 读昨天的 CI 失败记录、未关闭的 issue、最近提交，把"哪些问题值得处理"写进状态文件
3. 对每个值得处理的问题，开隔离的 worktree，派 sub-agent 起草修复
4. 第二个 sub-agent 对照项目 skill 规范和现有测试，审草稿
5. 审过了，connector 自动开 PR、更新工单
6. loop 搞不定的问题不硬来，丢进待办收件箱，等真人来看
7. 所有经过写回状态文件，明天从今天停下的地方继续

> 整个过程你只设计了一次，中间任何一步都没写 prompt。你的活从"每一步都出现"变成"只在两个地方出现"：**设计循环的时候** + **收件箱里有东西的时候**。

### 2.5 实操：30 秒搭出第一个 Loop

```bash
/loop 10m 检查当前分支 PR 的 CI 状态：
  有失败的检查就读日志、修复、推送；
  全部变绿后停下来，给我一句话总结改了什么
```

- `10m` 是心跳：每 10 分钟自动醒来跑一轮
- 中间是任务：每一轮干什么
- 最后是停止条件加汇报

### 2.6 Addy Osmani 指出的三个风险

**第一盆：验证仍然归你（Validation）**
- 无人值守运行的 loop，也是无人值守犯错的 loop
- 它说没问题，和真的没问题，中间还隔着你的眼睛

**第二盆：理解债（Comprehension Debt）越顺滑涨得越快**
- loop 交付你没写过的代码越快，"仓库里实际存在的东西"和"你脑子里真正理解的东西"之间的鸿沟就越大
- 技术债是代码烂；理解债是代码可能不烂，但你不知道它为什么是对的

**第三盆：认知投降（Cognitive Surrender）**
- 不再对产出有自己的观点，它给什么就收什么
- > "带着判断力去设计 loop，它是解药；为了逃避思考去设计 loop，它是助燃剂。同一个动作，相反的结果。"

**还有一笔现实的账**：token 成本。loop 按循环烧 token，sub-agent 每多一个就多一份开销。


## 第三部分：Graph Engineering（"多 Agent 并行"）

### 3.1 起因

距 loop engineering 才 40 天，OpenClaw 创始人说："我们还在聊 loop，还是已经切到 graph 了？"
大佬跟帖："loop engineering 已死，graph engineering 永生！"

### 3.2 什么是 Graph Engineering？

graph = 数据结构里的"节点加连线"。节点叫 **Node**，连线叫**边（Edge）**。

**它干什么**：按照任务之间的依赖关系，用 graph 编排整个流程——该串行的串行，该并行的并行，每一块交给职责明确的节点完成。

**和 loop 的关系**：不冲突。
- **loop engineering** 解决单个 agent 如何反复思考、调用工具、修正结果（管**节点内部**）
- **graph engineering** 解决多个执行单元如何拆分、并行、汇合、返工（管**节点之间**）

> 一个 loop 就是一张最小的 graph：只有一个节点、一条边，且这条边指回自己。

**为什么不能一个 agent 串行走到底？**

1. **慢** — 后端、前端、测试能三路一起跑，串行只能排着队
2. **中断灾难** — 执行到第 40 步突然中断，要么从头重跑，要么钻进上下文翻
3. **暂停麻烦** — 很难中途停下来等人工审批，隔天再从断点接着干
4. **无法表达复杂分工** — 想要"一个规划的、三个干活的、一个挑刺的"，串行流程开始吃力

### 3.3 工作原理：节点 + 边 + 状态

**第一样：节点（Node）—— 干活的那个**
- 可以是完整思考循环的 agent、固定规则的普通代码、数据库查询、甚至**人**（审批节点）
- 好节点的标准：只干一件事，单独就能测，想换掉它别的节点不受牵连

**第二样：边（Edge）—— 决定下一步执行哪个节点**

1. 下一个节点由什么决定？
   - **确定性边**：固定规则，如"测试全过就部署"，不用模型掺和
   - **模型决策边**：交给模型判断，如"工单派给退款还是投诉节点"

2. 流程是否固定？
   - **条件边**：根据上一步结果分叉，"测试通过进下一节点，失败返回返工"

> 设计的功夫就在分清哪条边该写死、哪条该交给模型。能写死的尽量写死，把模型的判断留给少数需要理解语义的分支。

**第三样：状态（State）—— 字段结构固定的对象**

```json
{
  "backend": {"status": "done", "artifact": "api/export.js"},
  "frontend": {"status": "running"},
  "tests": {"status": "pending"},
  "tokens_used": 12000
}
```

- 执行到哪、每步产出什么、消耗多少 token，都存这里
- 每个节点完成后保存状态 = 存一次档。中断不再是"白跑了"，而是"读档，重试那一个节点"

### 3.4 适合用 Graph 的特征

**先泼冷水**：大部分任务按顺序执行就够了，犯不着专门用 graph 编排。

**适合用 graph 的特征：**
- 任务能拆成互相独立的子任务，需要缩短总耗时
- 不同环节需要不同模型、工具、权限（干活的节点可写、审查的节点只读）
- 流程中间有必须人工确认的环节
- 任务执行时间长、分支多，需要随时查看每个分支的进度

### 3.5 用 LangGraph 怎么写？

```python
from langgraph.graph import StateGraph, START, END

g = StateGraph(DevState)

# 注册节点
g.add_node("plan", plan_task)
g.add_node("backend", backend_dev)
g.add_node("frontend", frontend_dev)
g.add_node("tests", test_dev)
g.add_node("integrate", integrate_code)
g.add_node("rework", rework_code)
g.add_node("approval", human_approval)

# 从规划节点开始
g.add_edge(START, "plan")

# 规划完成后，三个节点并行执行
g.add_edge("plan", "backend")
g.add_edge("plan", "frontend")
g.add_edge("plan", "tests")

# 三个节点都完成后，再进入集成节点
g.add_edge(["backend", "frontend", "tests"], "integrate")

# 根据测试结果决定下一步
g.add_conditional_edges(
    "integrate",
    check_tests,
    {"pass": "approval", "fail": "rework"}
)

# 返工完成后重新集成
g.add_edge("rework", "integrate")

# 人工确认后结束
g.add_edge("approval", END)

app = g.compile()
```

**关键解读**：
- `add_edge(["backend","frontend","tests"], "integrate")`：必须等三个节点都完成才进集成
- `add_conditional_edges`：读测试结果，通过进人工确认，失败进返工

### 3.6 Graph Engineering 和 LangGraph 的区别

- **graph engineering 是一种设计方法**：关注任务怎么拆、哪些并行、下一步由什么决定、状态怎么记录
- **LangGraph 是实现这套方法的框架**：提供现成的节点、边、状态、流程控制
- 做 graph engineering 不一定要 LangGraph：AutoGen、Google ADK、Claude Code 的 workflow，甚至自己写调度代码都行

> 这套技术并不新，新的是这个名字，以及大家把注意力从"单个 agent 怎么完成一步"转向"多个 agent 怎么共同完成一条复杂流程"。


## 第四部分：Harness 落地实操（怎么做）

### 4.1 三阶段实施路线图

| 阶段 | 目标 | 周期 | 核心产出 |
|------|------|------|----------|
| **第一阶段：基础建设** | 人人能用上 AI Coding | 1-2 周 | CodeBuddy 安装 + team-harness 仓库 + 基础 Rules + 知识库 |
| **第二阶段：工具接入** | 深度集成 | 2-4 周 | MCP 配置 + Skills 沉淀 + Plan 模式 SDD |
| **第三阶段：持续优化** | 知识飞轮 | 持续 | 度量看板 + 规范迭代 + harness-audit 自检 |

### 4.2 核心配置产物

**1. team-harness 仓库结构**

```
team-harness/
├── rules/                      # 团队 Rules 集合
│   ├── global/base.md          # 基础规范（所有项目必须加载）
│   ├── golang/go-backend.md    # Go 语言专用
│   └── frontend/               # 前端专用
├── skills/                     # 团队 Skills 集合
│   ├── common/                 # skill-creator、find-skills
│   └── business/               # rainbow-config 等业务 Skill
├── templates/                  # AGENTS.md、project.md 模板
└── docs/onboarding.md          # 新人上手指南
```

**2. Rules 分层体系**

| 层级 | 作用域 | 配置方式 | 加载方式 |
|------|--------|----------|----------|
| User Rules | 所有项目（个人） | CodeBuddy 设置页面 | 每次对话自动带入 |
| Team Rules | 团队所有成员 | Knot 平台管理下发 | `always` 或 `manual` |
| Project Rules | 单个项目 | `.codebuddy/rules/` 下的 `.md` | 总是生效 或 `@` 引用 |

**3. AGENTS.md（约 100 行，充当"目录页"）**

```

ARCHITECTURE.md        ← 架构总览
docs/
├── design-docs/       ← 设计文档（带验证状态）
├── exec-plans/        ← 执行计划（活跃/已完成/技术债务）
├── product-specs/     ← 产品规格
├── references/        ← 第三方参考
└── SECURITY.md
```

**4. MCP 配置（mcp.json）**

{

### 4.3 Plan 模式（规范驱动开发）

**4 Stage 流程**：

| 阶段 | 操作 | 模式 | 产出 |
|------|------|------|------|
| Stage 1 | 描述需求，AI 生成需求文档 | Plan 模式 | `requirements.md` |

### 4.4 日常开发 SOP

**SOP-A：新需求开发**
- 半天以上的需求走 Plan 模式

- 必须编写能复现该 Bug 的测试用例

### 4.7 合规性自检：harness-audit Skill

把整套规范的检查项固化成一个可执行的合规性审计工具。

**七个审计维度**：

| 维度 | 权重 | 检查内容 |
|------|------|----------|
| AGENTS.md | 15% | 是否存在、是否精简（~100行） |
| Rules | 20% | `.codebuddy/rules/` 目录、约束完整性 |
| Skills | 15% | `.codebuddy/skills/` 目录、Skill 规范性 |
| MCP | 10% | `mcp.json` 是否存在、配置规范 |
| Plan 模式 | 15% | `.codebuddy/plan/` 目录、文档完整性 |
| 工程规范 | 15% | 目录结构、分层架构 |
| Commit 规范 | 10% | Commit 格式、变更粒度 |

**使用方式**：

```bash
# 审计当前本地项目
请用 harness-audit Skill 对当前项目做一次合规性审计。

# 只关注某几个维度
请用 harness-audit Skill 审计当前项目，重点检查 Rules 和 Skills 维度。
```

**输出**：总分 + 等级（S/A/B/C/D）+ 各维度得分 + 亮点 + 问题 + P0/P1/P2/P3 优先级改进建议。


## 第五部分：行业头部实践

### OpenAI：5 个月 100 万行代码，3 人团队

**铁律**：人类不写代码，只设计环境。

**工程师三件事**：
1. **拆解意图**：把产品目标拆成 Agent 能理解的小块任务
2. **补全能力**：Agent 失败时，问"环境里缺了什么"，把缺的东西补上
3. **建立反馈回路**：让 Agent 能看到自己工作的结果

**关键做法**：
- **渐进式披露**：AGENTS.md 仅 ~100 行作为目录，CI 自动校验文档新鲜度
- **Agent 自验**：给 Agent 浏览器、日志、指标、隔离验收环境
- **架构规则自动化**：把资深程序员的经验写成机器可执行的检查规则

**成果**：单次 Codex 运行经常连续工作 6 小时以上，效率约为人工开发的 1/10。

### Anthropic：Context Reset + 独立 Evaluator

**两个典型问题**：
1. **上下文焦虑**：任务一长，模型丢细节、丢重点
2. **自评失真**：模型自己做完再自己评判，往往偏乐观

**解法一：Context Reset**
- 不是压缩（Compaction），而是直接换一个干净上下文的 Agent，交接清楚工作
- 给模型"清空包袱、重新出发"的效果

**解法二：Generator + Evaluator 分离**
- **Planner**：把短需求扩展成完整产品规格
- **Generator**：逐步实现
- **Evaluator**：像 QA 一样，用浏览器和工具真实操作应用

**核心原则**：生产与验收必须分离。Evaluator 是"带环境的验证"。

### LangChain：不改模型，分数从 52.8 到 66.5

仅通过改造和迭代 Harness，底层模型完全不变，在 Terminal Bench 2.0 上的得分从 52.8 提升到 66.5，直接从 Top 30 开外杀入 Top 5。

### 共同本质

OpenAI、Anthropic、LangChain 看起来路径不同，但本质上都在补同一套东西：

| Harness 核心层 | 要解决的问题 |
|----------------|--------------|
| 上下文管理 | 模型到底应该看到什么 |
| 工具系统 | 模型到底能做什么 |
| 执行编排 | 模型下一步该做什么 |
| 状态与记忆 | 系统如何保持连续工作 |
| 评估与观测 | 系统怎么知道自己做得对不对 |
| 约束与恢复 | 系统出错后怎么拉回来 |


## 第六部分：总结

### 三句话带走

1. **Agent = Model + Harness** —— 模型决定上限，Harness 决定能不能稳定落地。同一个模型在不同 Harness 里表现天差地别。

2. **四次演进不是谁取代谁**：Prompt ⊂ Context ⊂ Harness ⊂ Loop ⊂ Graph。从"怎么说"→"给什么"→"怎么驾驭"→"不按回车"→"多 Agent 并行"，是任务变复杂后，工程重心自然外扩。

3. **Harness 的六大核心是上下文管理、工具系统、执行编排、状态与记忆、评估与观测、约束与恢复**——真正决定 AI 产品能否稳定交付的，往往是这六层有没有搭好，而不是模型强不强。

### 核心原则

- **成本降低了，标准不能降低。工具变强了，人的判断力要跟着变强。**
- **让各类工具适配规范，而不是靠个人去适配各类工具。** 这就是从"人驱动 AI"到"AI 自驱动"的转变。
- **流水的工具，铁打的规范。**
- **真正决定 AI 产品上限的，也许是模型；但真正决定 AI 产品能否落地、能否稳定交付的，往往是 Harness。**

### 推荐阅读顺序

1. 先理解"四次演进"的内在逻辑和"六大构成"（是什么、为什么）
2. 再按"三阶段路线图"动手落地（怎么做）
3. 最后用 harness-audit 自检（做对了没）

> **AI 落地的核心挑战，正在从"让模型显得聪明"，转向"让模型在真实世界里稳定工作"。**
