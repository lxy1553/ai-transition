## §1 文档解析 —— 最强：RAGFlow（DeepDoc）

**能力**：把 PDF/扫描件变成"带版面结构的 Markdown + 图片资产 + 表格 HTML"，是 RAG 知识入库的第一道门。

**解释**：DeepDoc 是一套**版面识别驱动**的解析管线。`RAGFlowPdfParser.__call__` 按固定顺序跑 7 步：
渲染页面图 → 版面识别贴标签 → 表格裁剪/TSR/重 OCR → 文本合并 → 抽表格与图片。
关键设计是"**先版面、后内容**"——版面模型先把页面切成 title/table/figure/header/footer 区域，
表格区才单独裁剪走 TableStructureRecognizer 生成 HTML、高窄 OCR 框会做 0°/90°/270° 旋转择优。
layout/table/OCR 三个识别器复用同一个 `Recognizer` 的 ONNX 批处理底座，统一输出 `{type, bbox, score}` 
的 bxs 结构——这是插件化的关键。

**代码位置**：RAGFlow `deepdoc/parser/pdf_parser.py:1744-1769`（7 步编排）、`deepdoc/vision/layout_recognizer.py:102-136`
（打标+垃圾框剔除）、`deepdoc/vision/table_structure_recognizer.py:355-397`（表格 HTML）、`deepdoc/vision/ocr.py:660-703`（OCR 三段流水线）

**核心代码**：

## §2 分块策略 —— 最强：RAG-BUILD-SKILLS（父子分块）

**能力**：**父子两层分块**——子块（256 token）做精确检索，父块（1024 token）做完整上下文喂 LLM；块**绝不跨 `##`/`###` 章节边界**。

**解释**：单层分块有两个互相矛盾的需求：块小了检索准但上下文碎，块大了上下文全但检索噪声大。父子分块把两者分开：**检索命中子块 → 重排子块 → 映射回父块喂 LLM**（`reranker._map_to_parent`），这就是"子块精确、父块完整"。`boundary_aware` 保证块不跨章节，语义才完整。

**代码位置**：`RAG-BUILD-SKILLS/scripts/offline/parse_and_chunk.py:132-157`（边界感知）、`:215-225`（子块滑窗）、`:282-314`（双代 schema）

**核心代码**：

```python
# parse_and_chunk.py:215-225 —— 子块滑窗切分（overlap 步进）
def split_parent_into_children(parent_text, child_size, overlap, count_tokens):
    words = parent_text.split()
    children = []
    step = max(1, child_size - overlap)  # avoid zero / negative step
    i = 0
    while i < len(words):
        chunk_words = words[i:i + child_size]
        children.append(" ".join(chunk_words))
        if i + child_size >= len(words):
            break
        i += step
    return children
```

**检索侧闭环 —— 子块命中后映射回父块**（这就是"子块精确、父块完整"的下半段）：
```python
# RAG-BUILD-SKILLS/scripts/online/reranker.py:154-200 —— _map_to_parent
def _map_to_parent(top_m_children: list[dict], parent_map: dict) -> list[dict]:
    # CORE: 重排选出的 Top-M 子块 → 映射回父块 → 喂 LLM。父子分块的核心价值：
    #       在子块上精确检索，从父块拿完整上下文（子块被切断的上下文正是 LLM 需要的）。
    _PARENT_META_FIELDS = ["doc_id", "doc_version", "product_model", "status",
                           "page", "section", "chapter", "tag"]   # 给 LLM 引用溯源
    seen_parents = {}
    for child in top_m_children:
        pid = child["parent_id"]
        if pid not in seen_parents:                     # 同一父块多个子块命中 → 只保留一个
            parent_chunk = parent_map.get(pid, {})
            entry = {"parent_id": pid,
                     "content": parent_chunk.get("content", child["content"]),  # 父块完整内容
                     "child_hits": [child["chunk_id"]]}
            for field in _PARENT_META_FIELDS:           # 溯源元数据从父块复制
                if field in parent_chunk:
                    entry[field] = parent_chunk[field]
            seen_parents[pid] = entry
        else:
            seen_parents[pid]["child_hits"].append(child["chunk_id"])
    return list(seen_parents.values())                  # 按首现顺序（最高分子块在前）
```

**代码注释**：`_map_to_parent` 的 `seen_parents` 按 `parent_id` 去重——同父块的多个子块命中只喂一次父块，省上下文窗口，同时用 `child_hits` 记录命中来源做引用溯源；`_PARENT_META_FIELDS` 从父块复制 doc_id/page/section/status 给 LLM 生成引用；`parent_map` 来自 offline 入库时建立的 `child_id → parent_id` 查找表（reranker.py:74-109）。

**面试怎么说**：> "分块我不用单层固定 size。我采用父子两层分块——子块做精确检索、父块喂 LLM 完整上下文，重排命中子块后按 parent_id 映射回父块、同父多子去重只喂一次。关键细节是块不能跨章节边界，否则语义被切断，召回率看着高、生成质量上不去。"

## §3 分词/索引 —— 最强：RAGFlow（rag_tokenizer）

**能力**：**两级中文分词**——粗粒度 token（`content_ltks`）建主索引、细粒度 token（`content_sm_ltks`）做精确匹配兜底；
分词前先用正则剥掉表格 HTML 标签，索引/查询用同一套 tokenizer。

**解释**：RAGFlow 的索引不是"一次分词定终身"，而是粗/细两级：`tokenize()` 生成粗 token 做**主召回**，再对粗 token 
做 `fine_grained_tokenize` 生成细 token 做**精确匹配兜底**——术语完整和召回兜底兼得。分词核心以 C++/Cython 编译扩展下沉（
infinity-sdk），Python 侧只留薄封装 + `DOC_ENGINE_INFINITY` 短路开关。注意：当前仓库版本分词核心在编译扩展里、源码不可见；
经典 datrie 前缀树 + huqite 领域词典那套在旧版 RAGFlow（本仓库无源码），实现时按新版接口即可。

**代码位置**：RAGFlow `rag/nlp/__init__.py:365-372`（两级 token 生成）、`rag/nlp/rag_tokenizer.py:20-61`（薄封装 + 短路开关）

## §4 领域词典 —— 最强：RAG-BUILD-SKILLS（TF-IDF + 专家审核）

**能力**：TF-IDF 从领域文档自动抽取候选词 + query 日志合并真实用词 → 统一 **5 字段 schema**（standard_term / abbreviation / full_form / colloquial / tag）→ 专家审核定稿。被 tag 标注、查询改写、jieba 自定义词典三方消费。

**解释**：领域词典解决 RAG 最痛的"**用户的话 ≠ 文档的词**"。TF-IDF 天然抽高频特异词（max_df 滤掉通用词、min_df 滤掉一次噪声），schema 里 abbreviation/full_form 支撑"缩写→全称"改写，colloquial 支撑"口语→标准术语"回退。词典是**全局共享资源**，删文档不删词条（用户查询可能还在用）。

**代码位置**：`RAG-BUILD-SKILLS/scripts/offline/build_keyword_dict.py:51-78`（TF-IDF）、`:118-134`（5 字段 schema）

**核心代码**：
```python
# build_keyword_dict.py:51-78 —— TF-IDF 抽取领域候选词
def extract_tfidf_candidates(documents, top_k_per_doc=20, ngram_range=(1, 3)):
    """
    WHY TF-IDF: domain-specific terms appear frequently in domain docs but
    rarely in general text. TF-IDF surfaces exactly these terms without
    needing a labeled training set.
    """
    vectorizer = TfidfVectorizer(
        ngram_range=ngram_range,
        max_df=0.85,   # too common across docs -> not domain-specific
        min_df=2,      # too rare -> likely noise / single-occurrence typo
    )
    tfidf_matrix = vectorizer.fit_transform(documents)
    feature_names = vectorizer.get_feature_names_out()
    candidates = Counter()
    for row in tfidf_matrix:
        top_indices = row.toarray()[0].argsort()[::-1][:top_k_per_doc]
        for idx in top_indices:
            candidates[feature_names[idx]] += 1
    return candidates
```

## §5 混合检索 —— 最强：RAGFlow / queryforge（双路并行 + 融合）

**能力**：词法（BM25 精确/模糊）与语义（向量）**双路并行**检索，融合成候选池——RAGFlow 用 `MatchTextExpr + MatchDenseExpr + FusionExpr`，queryforge 用 `_keyword_search + _dense + asyncio.gather`。

**解释**：两路各覆盖对方的失效模式：BM25 抓住精确术语（尤其领域缩写），向量抓住同义改写。**并行**让延迟 = max(两路) 而非 sum。queryforge 额外支持**多查询并发**（改写出的子问题一起 `asyncio.gather`）——这是 recall 的最后一招，不是地基（RAGFlow 经典路径用单查询 + 混合融合）。

**代码位置**：RAGFlow `rag/nlp/search.py:209-235`（DSL）；queryforge `app/core/rag/retriever.py:23/35/52/71/80`

**核心代码（RAGFlow DSL）**：

## §6 融合策略 —— 三方三种（weighted_sum vs RRF，别信口号，用评估数据选）

**能力**：把词法分（BM25，量级 0-30）和向量分（余弦，0-1）合成分数——RAGFlow 用 `weighted_sum`，RAG-BUILD-SKILLS 和 queryforge 用 `RRF`。

**解释**：两者都是真方案，取舍在：**RRF 只用排名**（`Σ 1/(k+rank)`），天然免疫量纲差异，稳健但丢掉"第一 vs 第二差多远"的强度信息；**weighted_sum 保留分数量级**，可调权但归一化本身引入偏差。落地用评估数据（§10 recall@K）决定，别照抄方法论口号。

**代码位置**：RAG-BUILD-SKILLS `hybrid_retriever.py:144-186`；queryforge `app/core/rag/retriever.py:35`

**核心代码（RRF）**：
```python
# RAG-BUILD-SKILLS/hybrid_retriever.py:144-186 —— RRF 融合（真实现）
def _fusion_rrf(lexical_results, dense_results, k, top_n):
    """
    Reciprocal Rank Fusion: sum of 1 / (k + rank) across paths.
    CORE: 唯一融合策略。RRF 只用排名，天然避免 BM25(0-30) 与余弦(0-1) 量纲不可比。
    """
    rrf_scores = {}
    def add_path(results, rank_label):
        for rank, r in enumerate(results, start=1):
            cid = r["chunk_id"]
            if cid not in rrf_scores:
                rrf_scores[cid] = {**r, "lexical_rank": 0, "dense_rank": 0, "rrf_score": 0.0}
            rrf_scores[cid][rank_label] = rank
            rrf_scores[cid]["rrf_score"] += 1.0 / (k + rank)   # ← RRF 公式，k 通常 60
    add_path(lexical_results, "lexical_rank")
    add_path(dense_results, "dense_rank")
    ranked = sorted(rrf_scores.values(), key=lambda x: x["rrf_score"], reverse=True)[:top_n]
    for i, item in enumerate(ranked):
        item["rank"] = i + 1
    return ranked
```

**面试怎么说**：> "融合词法和向量分我会先说清楚量纲问题：BM25 是 0-30 的 TF-IDF 分、向量是 0-1 的余弦，直接加权和不公平。我倾向 RRF——只用排名、加 1/(k+rank)，稳健还免调权；但 RAGFlow 生产上用的是带权融合 0.001:1，说明分数融合没有银弹，最终以评估数据为准。"

def keyword_completion(query, index):
    """WHY: BM25 benefits from both forms being present. Documents may use the
    full form while the user typed the abbreviation, or vice versa."""
    matches = _match_keyword(query, index["abbreviations"])
    rewritten = query
    applied = []
    for m in matches:
        abbr, full = m["abbr"], m["full"]
        # Only expand if the abbreviation appears WITHOUT its full form already.
        if abbr.lower() in rewritten.lower() and full.lower() not in rewritten.lower():
            rewritten = rewritten.replace(abbr, f"{abbr} ({full})")
            applied.append(f"{abbr}->{abbr} ({full})")
    if not applied:
        return {"type": "unchanged", "text": query, "source": "rule", "applied": []}
    return {"type": "keyword_completion", "text": rewritten, "source": "rule", "applied": applied}
```

def check_loop1_convergence(history, config):
    """# CORE: 2 consecutive iterations with Top-5 gain < loop1_convergence_pp
    -> fine-tuning has converged, redirect effort elsewhere."""
    threshold = config["eval"]["loop1_convergence_pp"] / 100.0
    window = 2
    if len(history) < window + 1:
        return False                       # 需要 window+1 轮才有 window 个增益
    recent = history[-(window + 1):]
    gains = [recent[i]["recall_at_5"] - recent[i-1]["recall_at_5"]
             for i in range(1, len(recent))]
    return all(g < threshold for g in gains)
```

**代码注释**：检索层用"GT 文档是否活到 reranker"（文档级 recall）而不是精确排名——排名是 reranker 的活，检索只管召回；决策树分支对应不同修复动作（改词典/微调/查融合）；收敛判据把"优化到什么时候该停"量化成连续 2 轮增益阈值。

## §11 增量知识管理 —— 最强：RAG-BUILD-SKILLS（三类分诊 + 双层元数据）

**能力**：上线后文档持续变更的管理方法论——**文档级三类分诊**（替换 / 并行 / legacy）+ **双层元数据**（文档级关系库 + chunk 级标量字段）+ **append-only 词典**。

**解释**：RAG 上线后最大的杀手不是检索，是**文档版本混乱**——旧版失效内容还在被召回。三类分诊是一次摄入一个决策：同型号升级→**替换**（删旧写新）、不同型号→**并行**（只写新不动旧）、同型号但旧版有参考价值→**legacy**（标记退役、默认过滤、要历史才放宽 + prompt 加版本警告）。双层元数据让"文档版本链"和"chunk 检索过滤"各归其位。

**核心决策逻辑（伪代码，纯方法论无现成代码）**：
```
对每份新文档 D（型号 m，版本 v）：
  if 已有 m 且 v 更新     → 替换：删旧版 chunk，写新版，标记 supersedes
  if m 是新型号          → 并行：只写新，旧不动
  if 同型号但旧版有参考价值 → legacy：旧块 status=legacy，检索默认过滤，
                                放宽过滤才召回 + prompt 加 ⚠️ 旧版警告
删文档 D 时：删除 D 的 chunks，但不删词典词条（query 可能还在用）
```

**面试怎么说**：> "RAG 上线后的长期胜负手是增量知识管理。我的原则是文档级三类分诊：升级就替换、新型号就并行、旧版有价值就标 legacy 默认过滤。元数据分两层——文档版本链放关系库，chunk 过滤标签放向量库标量字段。关键词词典 append-only，删文档不删词条，因为用户查询可能还在用。"

## §12 SQL/工具安全 —— 最强：queryforge（guard + 只读沙箱）

**能力**：**双层防线**——`guard.py` 用 sqlglot 把 LLM 输出解析成 AST，只放行单条 SELECT（含 CTE）、禁 DDL/DML/多语句、自动注入 LIMIT；`executor.py` 只读沙箱执行（sqlite `mode=ro` / postgres 只读事务 + `statement_timeout` + `asyncio.wait_for` 超时 + 行数上限）。

# app/sql/guard.py:51-81 —— 校验 + 加固：只放行单条 SELECT，注入 LIMIT
def validate_and_secure(sql, dialect=None, max_rows=None):
    """校验并加固 SQL，返回可安全执行的最终 SQL。"""
    raw = _strip_fences(sql)          # LLM 爱输出 ```sql``` 和结尾分号，先剥掉
    if not raw:
        raise SQLGuardError("空 SQL")
    statements = [s for s in sqlglot.parse(raw, dialect=dialect) if s is not None]
    if len(statements) != 1:
        raise SQLGuardError("只允许单条语句")
    stmt = statements[0]
    if isinstance(stmt, _FORBIDDEN) or stmt.find(*_FORBIDDEN):
        raise SQLGuardError(f"禁止的语句类型: {type(stmt).__name__}")
    if not isinstance(stmt, _READ_ONLY_ROOTS):
        raise SQLGuardError("仅允许 SELECT 查询")
    if not stmt.args.get("limit") and hasattr(stmt, "limit"):
        stmt = stmt.limit(max_rows)   # 自动注入 LIMIT 防全表扫描
    return stmt.sql(dialect=dialect)
```

async def _run_postgres(sql, max_rows, timeout):

## §13 生产韧性 —— 最强：queryforge（熔断 / 重试 / 优雅降级）

**能力**：外部依赖（LLM/Embedding/Rerank）统一走**命名熔断器**（连续失败达阈值短路、超时半开试探）+ **指数退避重试**；所有基础设施（Redis/Langfuse/语义缓存/检索后端）**未启用或出错一律降级为 no-op/miss，不阻断主链路**。

**代码位置**：`queryforge-test2sql/app/core/resilience.py:27-34/57-81/88-96`

# app/core/resilience.py:57-81 —— 熔断器核心：短路 + 半开试探
class CircuitBreaker:
    def _allow(self) -> bool:
        if self._opened_at is None:
            return True
        # 超过冷却时间 → 半开，允许一次试探
        if time.monotonic() - self._opened_at >= self.reset_timeout:
            return True
        return False

    async def call(self, fn, *args, **kwargs):
        if not self._allow():
            raise CircuitOpenError(f"熔断器 {self.name} 处于打开状态")
        try:
            result = await fn(*args, **kwargs)
        except Exception:
            self._failures += 1
            if self._failures >= self.fail_threshold:
                self._opened_at = time.monotonic()   # 达到阈值 → 打开熔断
            raise
        else:
            self._failures = 0
            self._opened_at = None                   # 成功 → 关闭熔断
            return result
```

## §14 缓存 —— 最强：queryforge（Redis 精确 + pgvector 语义近似 + 逐级短路）

**能力**：**两层缓存短路**——先 Redis 精确缓存（`(db_id, 归一化问题)` sha256 键），再 pgvector **语义近似缓存**（问题 embedding 近邻 + 相似度阈值命中同义问题），都未命中才进 LangGraph 图，成功结果回写两层；**语义命中会回填精确缓存**形成冷热互哺；带多轮历史的请求自动跳过缓存。

@staticmethod
def _similarity(a, b) -> float:
    """相似度 = max(Jaccard 词集合, difflib 字符序列)，零向量库也能算"""
    a_norm, b_norm = cls._normalize(a), cls._normalize(b)   # 小写 + 压缩空格
    ta, tb = cls._tokenize(a_norm), cls._tokenize(b_norm)   # 按空格分词
    jaccard = len(ta & tb) / len(ta | tb) if (ta | tb) else 1.0
    ratio = difflib.SequenceMatcher(None, a_norm, b_norm).ratio()
    return max(jaccard, ratio)

## §16 可观测 / 评测基建 —— 最强：queryforge（Prometheus + Langfuse + structlog）

**能力**：**三层可观测**——Prometheus `qf_*` 指标（请求量/时延/LLM/检索/SQL/缓存命中）挂 `/metrics`、Langfuse 链路追踪（通过图 config 注入 handler）、structlog 结构化日志（ContextVar 注入 user_id/session_id + correlation-id）；评测用**执行准确率按难度分桶 + ragas**。

**解释**：可观测是"改了有没有变好"的证据来源。指标回答"系统健康吗"（延迟/成功率/熔断触发），追踪回答"这一条请求经历了什么"（LLM/检索/缓存每段时延），日志回答"出错了上下文是什么"。评测分桶不看均值——均值会掩盖"简单全对、难题全错"。

**代码位置**：queryforge `app/core/metrics.py:16-44`、`app/core/observability.py:35-82`、`app/core/logging.py:187-213`

**核心代码**：

**面试怎么说**：> "我把可观测做成分层：Prometheus 指标看系统健康（时延、成功率、熔断、缓存命中率），Langfuse 看单条请求经历了什么，structlog 用 ContextVar 给每条日志注入 user_id 和 correlation-id 方便排查。评测我坚持按难度分桶看执行准确率，绝不看总均值——均值会掩盖'简单全对、难题全错'。"
