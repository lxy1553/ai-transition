# 四项目整合蓝图：RAGFlow × RAG-BUILD-SKILLS × queryforge × vanna

> 把四个项目按 **RAG 生产全生命周期** 拆开，各取其优点，互相补缺，合成一张"生产级领域 RAG + Agent + SQL"参考架构。
> 四个项目各有定位，不是互相替代，是**四层拼图**：
> - **RAGFlow** = 实现层（通用 RAG 引擎，能跑）
> - **RAG-BUILD-SKILLS** = 方法论层（怎么建、怎么评估、何时停，全是"判断标准"）
> - **queryforge** = 应用/编排层（Text-to-SQL，LangGraph + 生产韧性 + SQL 安全）
> - **vanna** = Agent 层（SQL Agent 循环 + 工具分派 + 钩子 + 记忆）
>
> 一句话：**RAGFlow 给你"引擎"，RAG-BUILD-SKILLS 给你"方向盘和仪表盘"，queryforge 给你"安全带和导航"，vanna 给你"驾驶员"**。

## 1. 各项目优点清单（整合"优点"）

### 1.1 RAGFlow —— 实现层：把文档变成可检索的知识

| # | 优点 | 出处 | 备注 |
|---|------|------|------|
| 1 | **文档解析全家桶**：DeepDoc 版面分析(LayoutRecognizer)、表格结构化(TableStructureRecognizer)、OCR、PDF/DOCX/MD | `ragflow/03_*` | 生产文档进系统的第一关，别家都没有 |
| 2 | **rag_tokenizer 定制分词**：datrie + huqite 词典，coarse/fine 两级 | `ragflow/05_01` | 中文领域分词的工程范本 |
| 3 | **混合检索 DSL**：MatchText + MatchDense + Fusion(weighted_sum) | `ragflow/07_` | 与 RAG-BUILD-SKILLS 的 RRF 形成对照 |
| 4 | **双重排**：rerank_with_knn（加权 TK/余弦）+ rerank_by_model（LLM/交叉编码） | `ragflow/07_` | 工程上两种重排都做了 |
| 5 | **全文检索 FulltextQueryer**：IDF×NER×词性 加权 query | `ragflow/05_` | 关键词检索不裸奔 |
| 6 | **ES 连接器 + 在线问答端到端**（SSE + 引用溯源 `[ID:i]`） | `ragflow/08_`/`09_01` | 全链路可落地 |
| 7 | **Go 并行 ingestion + 原生 PDF 解析** | `ragflow/13_*` | 高性能解析路径 |
| 8 | **GraphRAG 知识图谱** | `ragflow/11_02` | 进阶检索手段 |
| 9 | **Agent 画布 + TaskExecutor 调度 + 可观测重构** | `ragflow/12_*`/`11_01` | 把 RAG 流水线升级成可编排任务 |

### 1.2 RAG-BUILD-SKILLS —— 方法论层：RAGFlow 没讲透的"判断标准"

| # | 优点 | 出处 | 备注 |
|---|------|------|------|
| 1 | **三层评估漏斗**：离线管线 → Q-DOC 检索层 → Q-DOC-A 生成层 | `rag-build-skills/00` 九节 | 检索与生成**不可互减** |
| 2 | **坏例六分类 + 瓶颈决策树**（engineering 永远优先） | 同上 9.3 | 从"哪些坏"到"为什么坏、进哪个循环" |
| 3 | **收敛判据**：Loop1 微调 5pp / Loop2 prompt 0.5pp，连续 2 轮就停 | 同上 9.3 | "何时停"的数学化 |
| 4 | **deploy/revert 门槛**：≥5pp 部署 / ≤-2pp 回滚 | 同上 7.8 | 微调不是玄学 |
| 5 | **增量知识管理**：三类分诊（替换/并行/legacy）+ 双层元数据 + append-only 词典 | 同上 十节 | 上线后运营，全行业最缺 |
| 6 | **父子分块 + 分词器分离 + 重排优先 + RRF** | 同上 三、六节 | 四条核心原则 |
| 7 | **Q-DOC-Q 数据集自动生成**（1:1 + 1:N）+ schema 契约校验 | 同上 7.5/7.6 | 免人工标注造评估集 |
| 8 | **查询改写**：规则优先 LLM 兜底（缩写/拆分/口语）+ protected 防误匹配 | 同上 8.1 | 比 queryforge 的纯 LLM 改写便宜可审计 |
| 9 | **容错 JSON 解析三重防御** | 同上 8.3 | 工程故障不伪装成质量问题 |

### 1.3 queryforge —— 应用/编排层：把 RAG 变成生产服务

| # | 优点 | 出处 | 备注 |
|---|------|------|------|
| 1 | **LangGraph 编排**：12 节点 + 条件路由 + **自纠错环**（validate/execute 失败绕回 generate，最多 SQL_MAX_RETRY）+ HIL 人审断点 | `queryforge/主干1` + `langgraph/graph.py` | 非线性流的正确编排姿势 |
| 2 | **三层缓存**：Redis 精确缓存 + pgvector **语义近似缓存**，两层短路，成功回写 | `queryforge/主干4` | 没有缓存的生产 RAG 是不完整的 |
| 3 | **SQL 安全闸门**：sqlglot 解析只放行单 SELECT、禁 DDL/DML、自动注入 LIMIT + 只读沙箱执行 | `queryforge/主干3` + `sql/guard.py` | 工具调用安全的范本 |
| 4 | **生产韧性**：熔断 + 重试 + 优雅降级（Redis/Langfuse/rerank/ES 全 no-op 兜底）+ Prometheus/Langfuse/structlog 可观测 | `queryforge/主干5` | "外部依赖挂了自己不挂" |
| 5 | **RAG 三语料混合检索**：schema_doc / fewshot_example / rag_chunk + RRF + gte-rerank | `queryforge/主干2` | 多语料检索的设计 |
| 6 | **LLM 与 embedding 双 endpoint 分离**（OpenAI + DashScope） | `queryforge/主干2` | 解耦模型供应商 |
| 7 | **多轮会话 + JWT 鉴权**（DB 是历史唯一真相源，不依赖 checkpointer） | `queryforge/阶段A` | 多轮的工程正确性 |
| 8 | **评测实验方法论**：执行准确率按难度分桶 + ragas | `queryforge/阶段B` | 实验要分桶，不看均值 |
| 9 | **配置驱动**：模型/维度/检索后端/缓存阈值全在 pydantic-settings | `queryforge/CLAUDE.md` | 换组件不改代码 |

### 1.4 vanna —— Agent 层：把 RAG/SQL 变成会思考的 Agent

| # | 优点 | 出处 | 备注 |
|---|------|------|------|
| 1 | **Agent 循环**（ask → train → generate → execute 闭环） | `vanna/01_主干01` | 最简单的"会自己干活"范式 |
| 2 | **Tool 抽象 + Registry 分派** | `vanna/02_`/`03_` | 工具即函数，按名分派 |

## 2. 缺口互补矩阵（补充"没有的部分"）

### 2.1 按维度看：每个能力从哪家取

| 能力维度 | 谁最强 | 谁缺失 | 缺失的由谁补 |
|---------|--------|--------|-------------|
| 文档解析 | **RAGFlow** | queryforge、vanna、RAG-BUILD-SKILLS | ← RAGFlow 的 DeepDoc |
| 分块策略 | **RAG-BUILD-SKILLS**（父子） | queryforge、vanna | ← 父子分块 + boundary-aware |
| 分词/索引 | **RAGFlow**（rag_tokenizer） | vanna | ← datrie+huqite 定制词典 |
| 领域词典 | **RAG-BUILD-SKILLS**（TF-IDF+专家） | RAGFlow（有但未成方法论）、queryforge | ← 5 字段 schema + query 日志 |
| 混合检索 | **RAGFlow / queryforge** | vanna | ← 双路并行 + 融合 |
| 融合策略 | 三方三种（weighted_sum / RRF / RRF） | — | ⚠️ 见 2.3 批判 |
| 查询改写 | **RAG-BUILD-SKILLS**（规则+LLM） | vanna | ← 规则优先，别学纯 LLM |
| 编排 | **queryforge**（LangGraph） | RAG-BUILD-SKILLS（手写） | ← 有自纠错/分支才值得上图引擎 |
| Agent 能力 | **vanna**（循环+工具+钩子） | RAGFlow/queryforge/RAG-BUILD-SKILLS | ← Agent 循环 + Registry |
| 评估体系 | **RAG-BUILD-SKILLS** | vanna（弱）、RAGFlow（部分） | ← 三层漏斗 + 坏例决策树 + 收敛判据 |
| 增量知识管理 | **RAG-BUILD-SKILLS** | 全部三家 | ← 三类分诊 + 双层元数据 |
| SQL/工具安全 | **queryforge** | RAGFlow、vanna（弱） | ← guard + 只读沙箱 + 自动 LIMIT |
| 生产韧性 | **queryforge** | RAG-BUILD-SKILLS、vanna | ← 熔断/重试/优雅降级/可观测 |
| 缓存 | **queryforge**（语义近似缓存） | RAG-BUILD-SKILLS、vanna | ← pgvector 语义缓存 |
| 多轮/记忆/权限 | **vanna+queryforge** 合体 | RAGFlow（部分） | ← DB 历史 + JWT + Memory |
| 可观测/评测基建 | **queryforge** | vanna、RAG-BUILD-SKILLS | ← Prometheus/Langfuse + 分桶评测 |

### 2.2 每个项目的 gap → 它最缺什么

- **RAGFlow 缺**：① 评估循环（有 Benchmark 无坏例决策树/收敛判据/部署门槛）② 增量知识管理方法论（版本退役靠手工）③ 工具/SQL 安全 ④ 语义缓存。
- **RAG-BUILD-SKILLS 缺**：① **一切实际实现**（解析/检索/执行全是占位）② 编排引擎 ③ 生产韧性 ④ 多轮/记忆/权限。它是"最全的方法论 + 最少的可运行物"。
- **queryforge 缺**：① 文档解析/父子分块（ingest 太薄，文档 RAG 是短板）② 增量知识管理 ③ 坏例决策树 ④ 领域词典构建（pg_jieba 太裸）。
- **vanna 缺**：① 评估体系 ② 检索/重排（它不建 RAG）③ 方法论 ④ 生产韧性 ⑤ 缓存。它是"最能跑的壳，最没有引擎"。

### 2.3 批判点（整合时别照单全收）

| 冲突 | 各方主张 | 判断 |
|------|---------|------|
| 融合策略 | RAG-BUILD-SKILLS 说"RRF 永远、score-level 永不"；RAGFlow 生产用 `weighted_sum`(0.001,1)；queryforge 用 RRF | **都真**。RRF 稳健丢量纲，weighted_sum 可调分数量级。落地用评估数据选，别信口号 |
| 父子 vs mom 块 | RAG-BUILD-SKILLS 256/1024 父子；RAGFlow mom 块跨文件聚合 | 场景不同：单文档问答父子好，多文档聚合 mom 好 |
| 查询改写 | RAG-BUILD-SKILLS 规则优先；queryforge 的 rewrite 节点靠 LLM | **规则便宜可审计，LLM 灵活贵**。先规则后 LLM |
| 路由 | RAG-BUILD-SKILLS 警告"精度<50% 删路由"；queryforge 直接用确定性 filter | 一致性：两者其实都倾向"别用模型路由" |
| 词典格式 | 配置存 `.json`，jieba 读 `.txt` | 落地时统一格式 |

## 3. 整合蓝图：一套"生产级领域 RAG + Agent + SQL"参考架构

按 RAG 生产全生命周期逐段拼：**每段取最强的项目**。

```
①文档解析     ← RAGFlow DeepDoc（版面/表格/OCR/PDF/DOCX）
②领域词典     ← RAG-BUILD-SKILLS TF-IDF+专家 5 字段 schema + query 日志
③分块         ← RAG-BUILD-SKILLS 父子 256/1024 + boundary-aware + 双层元数据
④分词/索引    ← RAGFlow rag_tokenizer(datrie+huqite) 喂 BM25；embedding 走模型自带 BPE
⑤混合检索     ← queryforge 三语料并行 + RRF（schema/fewshot/doc 各自建语料）
⑥重排         ← queryforge gte-rerank + RAG-BUILD-SKILLS "子块打分→父块喂 LLM"
⑦查询改写     ← RAG-BUILD-SKILLS 规则优先（缩写/拆分/口语+protected）LLM 兜底
⑧编排         ← queryforge LangGraph：自纠错环 + HIL 断点 + 条件路由
⑨Agent 化     ← vanna Agent 循环 + Tool/Registry + LifecycleHook/WorkflowHandler
⑩生成         ← RAG-BUILD-SKILLS 六要素 prompt + 容错 JSON 三重防御 + ^引用溯源^
⑪评估        ← RAG-BUILD-SKILLS 三层漏斗 + 坏例六分类决策树 + 收敛判据 + Kappa 校准
⑫上线运营     ← RAG-BUILD-SKILLS 三类分诊 + append-only 词典 + queryforge 三层缓存
⑬生产底座     ← queryforge 熔断/重试/优雅降级 + Prometheus/Langfuse/structlog + SQL guard
⑭多轮/记忆    ← vanna Memory + queryforge DB 历史 + JWT 权限
```

**蓝图关键决策（带理由）**：
1. **重排优先、父子分块、RRF**：先上这"低成本高收益三件套"，再谈微调。
2. **评估驱动**：所有改动的唯一裁判是 Q-DOC/Q-DOC-A + 坏例决策树，不是感觉。
3. **工程问题永远先修**（RAG-BUILD-SKILLS 坏例树第一分支）：解析失败/JSON 解析失败会伪装成质量问题。
4. **编排别过度**：只有需要**自纠错环/分支/HIL 断点**这种非线性流才上 LangGraph；线性流水线用 RAGFlow 式 task 链。
5. **缓存是生产必需**：Redis 精确 + pgvector 语义近似，成功回写，降级 no-op。
6. **增量知识管理是长期胜负手**：上线后文档天天变，三类分诊 + 双层元数据决定系统多久开始"说错话"。

## 4. 落地到 ai_assistant（信贷风控助手）

> 四个项目都写了 `对标ai_assistant_改造建议.md`，这里只做**优先级总排序**。ai_assistant 是信贷风控 RAG 助手，建议按"能跑 → 会评估 → 不胡说 → 会运营"四期：

### 4.1 按"投入产出比"搬什么（分三期）

| 期 | 搬什么 | 从哪拿 | 理由 |
|----|--------|--------|------|
| **P0 能跑** | 父子分块 + RRF 混合检索 + rerank | RAG-BUILD-SKILLS 六节 + RAGFlow 检索 | 检索质量决定一切，先把它做对 |
| P0 | 六要素 prompt + 容错 JSON + ^引用溯源^ | RAG-BUILD-SKILLS 五/8.3 | 生成端不崩、能溯源 |
| P0 | 查询改写规则优先 | RAG-BUILD-SKILLS 8.1 | 风控术语多，规则词典见效快 |
| **P1 会评估** | Q-DOC/Q-DOC-A 双层 + 坏例六分类决策树 + 收敛判据 | RAG-BUILD-SKILLS 九节 | 没有评估，后面全是拍脑袋 |
| P1 | Q-DOC-Q 自动造评估集 + 契约校验 | RAG-BUILD-SKILLS 7.5/7.6 | 免人工标注 |
| P1 | 语义缓存 + Redis 精确缓存 | queryforge 主干4 | 信贷问答重复率高，省钱省延迟 |
| **P2 不胡说** | 容错 JSON + 自纠错环（如果接工具/SQL） | queryforge LangGraph | 有失败回退才敢让 Agent 干活 |
| P2 | SQL guard + 只读沙箱（如果接数仓） | queryforge sql/ | 风控最不能执行 DDL |
| P2 | 生产韧性：熔断/降级/可观测 | queryforge 主干5 | 信贷服务 7×24 |
| **P3 会运营** | 增量三类分诊 + 双层元数据 + append-only 词典 | RAG-BUILD-SKILLS 十节 | 风控政策文档经常更新，这是长期胜负手 |
| P3 | Agent 循环 + Hook（如果要对话代理） | vanna | 先不要，评估到位后再加 |

### 4.2 分期决策顺序（一次只改一个，评估背书）

```
阶段0 基线：父子分块 + 混合检索 + rerank + 六要素 prompt  → 跑通最小闭环
阶段1 评估：Q-DOC-Q 造集 → 三层漏斗跑分 → 记基线
阶段2 优化：坏例决策树定位 → 一次改一个 → 收敛判据喊停
         （词典 → 改写 → RRF k → top_n → prompt → 最后才微调）
阶段3 生产：缓存 + 韧性 + 可观测
阶段4 运营：增量知识管理 + 多轮记忆 + （可选）Agent/工具
```

### 4.3 三个"别学"的坑

1. **别学 RAG-BUILD-SKILLS 的"RRF 永远"**——你的场景可能 weighted_sum 更好，用评估数据选。
2. **别学 queryforge 的纯 LLM 改写**——信贷术语固定，规则词典又便宜又可审计。
3. **别学 RAGFlow 的"什么都能解析"**——先支持 PDF/MD 两类，够用再扩，解析是重投入。
