# 深挖：DOCX 与其他格式解析（deepdoc/parser/ + rag/app/naive.py + rag/flow/parser/parser.py）

> 深挖 03_01/03_03 都在讲 PDF 的视觉路线。本篇回答"**非 PDF 格式怎么解析、和 PDF 差在哪**"。
> 核心认知：**DOCX/Excel/PPT 有原生结构对象，直接读 XML 拿行列/段落/表格——根本不需要版面分析/OCR/TSR 那套视觉模型**。这是解析效率和准度的分水岭。
> 所有格式最终统一成 `[{text, image, doc_type_kwd}, ...]` 的 JSON 块列表，下游 chunk/索引只认这套结构。

- 源码位置：`github/project/ragflow/deepdoc/parser/{docx,excel,ppt,markdown,html,txt}_parser.py` + `rag/app/naive.py` + `rag/flow/parser/parser.py`
- 上游：深挖 02_01 的 Parser 组件按后缀分派
- 下游：统一 JSON 块 → Chunker（深挖 04_01）

---

## 三问

- **Q1 解决什么问题**：PDF 是"视觉"文档（字是画），Office 文档是"结构化"文档（字是 XML 节点）——不能共用同一套视觉解析。
- **Q2 数据流哪一环**：解析链路的入口分派——`Parser._invoke` 按后缀选 handler，各自解析后**统一输出 JSON 块列表**。
- **Q3 删掉会怎样**：DOCX/Excel/PPT 进不来知识库——现实中这类文档占比很大，缺了等于知识库缺半壁江山。

## 一、DOCX 两层解析

**底层 `RAGFlowDocxParser`**（deepdoc/parser/docx_parser.py:33）——python-docx 读段落/表格：

```python
def __call__(self, fnm, from_page=0, to_page=MAXIMUM_PAGE_NUMBER):
    self.doc = Document(fnm) if isinstance(fnm, str) else Document(BytesIO(fnm))
    pn = 0
    for p in self.doc.paragraphs:                        # 遍历段落
        for run in p.runs:
            if "lastRenderedPageBreak" in run._element.xml:   # 用 XML 分页符估算页码
                pn += 1
        secs.append(("".join(runs_within_single_paragraph), p.style.name or ""))
    tbls = [self.__extract_table_content(tb) for tb in self.doc.tables]   # 遍历表格
    return secs, tbls                                     # (段落, 表格) 两元组
```

**flow 实际用的子类 `naive.Docx`**（rag/app/naive.py:560-673）——沿 `doc._element.body` **按文档顺序**交错段落/图片/表格：

```python
for block in self.doc._element.body:
    if block.tag.endswith("p"):            # 段落
        p = Paragraph(block, self.doc)
        ...
    elif block.tag.endswith("tbl"):        # 表格
        tb = DocxTable(block, self.doc)
        html = "<table>"
        if title:
            html += f"<caption>Table Location: {title}</caption>"
        for r in tb.rows:                  # ★ 原生行列 → 直接转 HTML
            html += "<tr>"
            for j in range(col_idx + 1, len(r.cells)):
                if c.text == r.cells[j].text:   # ★ 相同文本视为跨列合并 → colspan
                    span += 1
            html += f"<td colspan='{span}'>{c.text}</td>"
        html += "</table>"
        lines.append({"text": "", "image": None, "table": html})
```

**图片提取**（docx_parser.py:34-71）——XPath 找 `pic:pic`/`a:blip/@r:embed`，从 `document.part.related_parts[embed].image.blob` 取二进制，包成 `LazyImage` 懒加载。

**作用**：`naive.Docx.__call__` 返回 `(text, image, table_html)` 三元组列表——**保留文档顺序**，表格零视觉模型直接出 HTML。底层 `RAGFlowDocxParser.__call__` 在 docx 路径上实际是"死代码"，真正常用的是子类覆盖版。

**DOCX 表格 vs PDF 表格**：
- **DOCX**：`tb.rows[i].cells[j].text` 原生行列 → 直接转 `<table>`。`__compose_table_content`（docx_parser.py:79-158）只做**语义分类**（blockType 正则标日期/数字/英文/文本，用于识别表头行），**不做结构识别**。
- **PDF**：`_table_transformer_job`（深挖 03_03）——布局检测框表格 → 裁图 → TSR 模型识别结构 → OCR 匹配绑定。**一条视觉重路**。

## 三、`Parser._invoke` 后缀分派 ★（rag/flow/parser/parser.py:1393-1434）

```python
async def _invoke(self, **kwargs):
    function_map = {
        "pdf": self._pdf, "markdown": self._markdown, "text&code": self._code,
        "html": self._html, "spreadsheet": self._spreadsheet, "slides": self._slides,
        "doc": self._doc, "docx": self._docx, "image": self._image,
        "audio": self._audio, "video": self._video, "email": self._email, "epub": self._epub,
    }
    for p_type, conf in self._param.setups.items():
        if from_upstream.name.split(".")[-1].lower() not in conf.get("suffix", []):
            continue                                    # ★ 纯后缀字符串匹配
        await thread_pool_exec(function_map[p_type], name, blob, **call_kwargs)
        done = True; break
```

```python
# setups 定义（parser.py:125-253）——每种类型的 suffix + 输出格式
"docx":        {"suffix": ["docx"], "output_format": "json", ...},
"spreadsheet": {"suffix": ["xls","xlsx","csv"], "output_format": "html", ...},
"slides":      {"suffix": ["pptx","ppt"], "output_format": "json", ...},
"markdown":    {"suffix": ["md","markdown","mdx"], ...},
"html":        {"suffix": ["htm","html"], ...},
"doc":         {"suffix": ["doc"], ...},   # 老格式 .doc 走 tika
```

**作用（关键）**：`.docx` → `_docx`、`.xlsx` → `_spreadsheet`……**后缀决定解析器**，`.doc`（老二进制格式）在 `_docx` 里特判走 tika（parser.py:913-945）。

## 四、统一输出 —— JSON 块列表 + `doc_type_kwd` ★

**DOCX 输出**（parser.py:961-977）——三元组归一化成 JSON 块：

```python
for text, image, html in main_sections:
    sections.append({
        "text": text, "image": image,
        "doc_type_kwd": "text" if flatten_media_to_text or image is None else "image",
    })
    if html:                                        # 表格 → 追加一个 table 块
        sections.append({
            "text": html, "image": None,            # ★ 表格体就是 HTML 字符串
            "doc_type_kwd": "text" if flatten_media_to_text else "table",
        })
self.set_output("json", sections)
```

**PDF 输出**（parser.py:747-770）——每个 bbox 归一化成同样结构，多 `page_number/positions` 定位字段：

```python
for b in bboxes:
    if flatten_media_to_text:  b["doc_type_kwd"] = "text"
    elif layout == "table":    b["doc_type_kwd"] = "table"
    elif layout in {"figure","image"}:
        b["layout_type"] = "figure"; b["doc_type_kwd"] = "image"
    elif not has_layout and b.get("image") is not None: b["doc_type_kwd"] = "image"
    else:                      b["doc_type_kwd"] = "text"
```

**作用（统一点）**：无论来源，最终都是 `[{text, image, doc_type_kwd, ...}]`，`doc_type_kwd ∈ {text, image, table, figure}`。下游 chunker/索引**只认这套结构**；DOCX/PPT/PDF 的图片都走同一个 `enhance_media_sections_with_vision`（VLM 描述，深挖 04_01）。

## 五、数据流转示意

```
.doc/.docx/.xlsx/.pptx/.md/.html 文件（二进制 blob）
   │
   ▼
Parser._invoke (parser.py:1425)
   │  name.split(".")[-1].lower() 命中 setups[...]["suffix"]
   ▼
对应 handler（_docx / _spreadsheet / _slides / ...）
   │  调用 naive.Docx / excel_parser / ppt_parser / ...
   ▼
三元组列表 / 文本列表 / 表格 HTML
   │
   ▼ 归一化 (parser.py:961-977)
[ {"text":"...", "image":LazyImage, "doc_type_kwd":"text"},
  {"text":"<table>...</table>", "image":None, "doc_type_kwd":"table"}, ... ]
   │
   ▼ 可选后处理：remove_toc / remove_header_footer / enhance_media_sections_with_vision(VLM)
   ▼
set_output("json", sections) → 与 PDF 相同的 JSON 块列表 → Chunker / 索引 / RAG
```

## 六、对照 ai_assistant

| RAGFlow | 你的 ai_assistant | 差距 |
|---------|------------------|------|
| 后缀分派（docx→_docx） | 可能只有 PDF/txt | ⚠️ 只支持少数格式 |
| DOCX 原生结构直接转表格 HTML | — | ❌ 表格进不来 |
| Excel 三通道（html/markdown/键值行） | — | ❌ 表格进不来 |
| 统一 `doc_type_kwd` 输出契约 | 无 | ⚠️ 格式间不一致 |
| `.doc` 老格式 tika 兜底 | 无 | ⚠️ 老文档读不了 |
| 表格跨列合并（colspan） | 无 | 概念参考 |

**落地优先级**：
- **P0**：**DOCX 解析 + Excel 解析**——Office 文档是企业知识库最常见的格式，python-docx/openpyxl 几十行就能接。
- **P1**：统一 `doc_type_kwd` 输出契约——text/image/table 三种类型对齐，下游只认一种结构。
- **P2**：`.doc` 老格式（tika）+ 图片 VLM 描述（deepdoc 04_01）。

## 七、总结

| 环节 | 代码 | 作用 |
|------|------|------|
| DOCX 底层 | `RAGFlowDocxParser`（docx_parser:33） | python-docx 段落/表格提取 |
| DOCX 顺序化 | `naive.Docx`（naive:560） | 段落/图片/表格按文档序交织 |
| DOCX 表格 | 原生 rows/cells → HTML + colspan | 零视觉模型 |
| Excel | excel_parser 三通道 | html/markdown/键值行 |
| PPT | ppt_parser 按位置排序 | 每页拼接文本 |
| 分派 | `Parser._invoke` function_map（parser:1393） | 后缀 → handler |
| 统一输出 | `doc_type_kwd` 归一化（parser:961） | text/image/table/figure |

**一句话心法**：**解析的核心不是"把文件变成文本"，而是"把文件变成统一的结构"**。有原生结构（Office）就走直读，没有（PDF）才上视觉模型；**全格式统一成 `{text, image, doc_type_kwd}` 的输出契约**，让下游完全不用关心文件来源——解析器的价值在"统一"，不在"单个格式读得多花哨"。
