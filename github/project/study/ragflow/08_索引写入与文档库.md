# 离线阶段 ⑤：索引写入与文档库

> 这是离线链路的**收尾**——把「chunk + 向量 + 关键词 + 元数据」批量写入文档库（ES / Infinity）。
> 对照你上一个问题「第七步：索引写入」，这里的实现就是生产级样板：**稳定 ID + 批量 upsert + 存储可插拔**。

## 三问

- **Q1 解决什么问题**：让 chunk 能被「向量检索 + 全文检索」同时命中——所以一个 chunk 要存**多个字段**（向量列 + 分词列 + 元数据列），而不是只存文本。
- **Q2 数据流哪一环**：离线链路最后一步——上游 Tokenizer 产出带 `q_{dim}_vec` 的 chunks，这里落库。
- **Q3 删掉会怎样**：向量在内存里、关键词在别处，检索时对不上——知识库形同虚设。

---

## 一、一个 chunk 存什么（写入文档库的字段结构）

从 `search.py` 的 `src` 字段列表（检索时取回的字段）+ `insert_chunks` 可以还原 chunk 结构：

```python
# 写入文档库的一条 chunk（ES/Infinity 的一条 document）
{
    "id": "xxhash64(内容)",            # ★ 稳定 ID（内容哈希，幂等/去重）
    "text": "上文+正文+下文",           # chunk 最终文本（含表格/图片上下文）
    "q_1024_vec": [0.12, -0.03, ...], # ★ 向量（维度写在字段名里）
    "content_ltks": "词 词 词",         # 正文分词（粗粒度，BM25 用）
    "content_sm_ltks": "...",          # 正文分词（细粒度）
    "title_tks": "文档名分词",          # 标题分词
    "important_kwd": ["关键词1", ...],  # 重要词
    "question_tks": "...",             # 问题分词（预生成的 Q&A）
    "doc_id": "...",                   # 来源文档 ID
    "docnm_kwd": "季度报告.pdf",        # 文档名（前端显示 + 聚合）
    "kb_id": "...",                    # 知识库 ID（租户隔离过滤）
    "page_num_int": 3,                 # ★ 页码（引用定位/高亮）
    "position_int": 12,                # ★ 位置（引用定位/高亮）
    "chunk_order_int": 5,              # 块序号（还原文档顺序）
    "create_timestamp_flt": 1723456789,# 时间戳
    "mom_id": "...",                   # 父级大块 ID（父子文档结构）
}
```

**作用（关键）**：
- **向量列 + 分词列并存** → 同一份 chunk 既支持向量检索又支持 BM25 全文检索（混合检索的基础）。
- **`page_num_int` / `position_int` / `docnm_kwd`** → 支撑前端「引用定位 + 原文高亮」（README 的 Grounded citations）。
- **`q_{dim}_vec` 维度写进字段名** → 换 embedding 模型维度变了，字段名也变，新旧向量不冲突。
- **`mom_id`** → 父子文档结构（小 chunk 检索、大 chunk 喂 LLM）的落库形态。

## 二、写入逻辑 insert_chunks（task_executor.py:1292）

```python
async def insert_chunks(task_id, task_tenant_id, task_dataset_id, chunks, progress_callback):
    """把 chunks 写入文档库（ES 或 Infinity）"""

    # ① 拆母块（mom）：每个 chunk 的 "mom" 字段 = 它的父级大块
    #    小 chunk 精准命中，母块提供完整上下文 —— 父子文档结构
    mothers = []
    mother_ids = set([])
    for ck in chunks:
        mom = ck.get("mom") or ck.get("mom_with_weight") or ""
        if not mom:
            continue
        id = xxhash.xxh64(mom.encode("utf-8")).hexdigest()   # ★ 内容哈希 → 稳定 ID
        ck["mom_id"] = id                                     # 子块记录父块 ID
        ...
        mom_ck = copy.deepcopy(ck)                            # 母块只保留关键字段
        mom_ck["id"] = id
        mom_ck["content_with_weight"] = mom
        mom_ck["available_int"] = 0                           # 母块默认不可用（不直接检索）
        mothers.append(mom_ck)

    # ② 批量写入母块（DOC_BULK_SIZE 一批，对应 bulk upsert）
    for b in range(0, len(mothers), settings.DOC_BULK_SIZE):
        await thread_pool_exec(
            settings.docStoreConn.insert,
            mothers[b : b + settings.DOC_BULK_SIZE],
            search.index_name(task_tenant_id),     # 索引名：ragflow_{tenant_id}
            task_dataset_id,
        )
        if has_canceled(task_id):                  # ★ 中途取消检查
            progress_callback(-1, msg="Task has been canceled.")
            return False

    # ③ 批量写入子块（真正的可检索 chunk）
    for b in range(0, len(chunks), settings.DOC_BULK_SIZE):
        await thread_pool_exec(
            settings.docStoreConn.insert,
            chunks[b : b + settings.DOC_BULK_SIZE], ...
        )
    ...
```

**作用（关键）**：
1. **父块（mom）+ 子块（chunk）双写**：这就是「父子文档」在落库层的实现——**检索时命中子块，但取回父块的完整上下文**（对应你之前说的"检索用小 chunk、喂 LLM 用大 chunk"）。
2. **`xxhash.xxh64(内容)` 稳定 ID**：同一内容重跑生成同一 ID → **幂等**，不会重复插入（对应你之前说的"稳定 ID 用内容哈希，别用自增"）。
3. **批量写 + 线程池**：`DOC_BULK_SIZE` 分批，`thread_pool_exec` 丢线程池，避免一次塞爆存储。
4. **中途取消检查**：每批之间查一次任务是否取消，随时可停。


```python
# task_executor / search 只认 settings.docStoreConn 接口
settings.docStoreConn.insert(chunks, index_name, kb_id)   # 写入
settings.docStoreConn.search(...)                          # 检索
```

**作用**：**存储后端可插拔**（ES / Infinity / GaussDB / OceanBase），上层 `Dealer` / `insert_chunks` 只认 `DocStoreConnection` 接口。换存储 = 改配置，不改主流程（对照主干⑥的可插拔思想）。

## 五、增量 / 全量（幂等 + 可重跑）

```python
# 全量：TaskExecutor 重新解析文档 → insert_chunks（稳定 ID 幂等）
# 增量：只处理 updated 的文档（TaskService 里按状态过滤）
# 更新：同一 doc_id 的旧 chunk 先删除，再插入新的
```

**作用**：因为 `id` 是内容哈希，**同一文档重跑 = 覆盖更新，不产生重复**。删除旧 chunk + 插入新 chunk 就是对已更新文档的标准处理（增量）。这对应你之前说的"增量复用向量 + 可重跑"。

## 六、总结

| 环节 | 代码 | 作用 |
|------|------|------|
| chunk 字段结构 | `search.py` src 列表 | 向量 + 分词 + 元数据并存 |
| 父块/子块双写 | `insert_chunks` | 父子文档结构落库 |
| 稳定 ID | `xxhash.xxh64` | 幂等 / 去重 |
| 批量写 | `DOC_BULK_SIZE` | bulk 分批 |
| 存储可插拔 | `DocStoreConnection` | ES/Infinity/GaussDB/OB |
| 动态建索引 | `init_kb` | 换模型重建索引 |

**核心心法**：索引写入不是"把文本塞进一个库"，而是**「向量列 + 分词列 + 元数据列」结构化落库 + 父子双写 + 稳定 ID 幂等 + 批量写 + 存储可插拔**。你的 ai_assistant 如果只是"存文本 + 存向量"两列，就缺了关键词列（BM25）和元数据列（引用/权限）。
