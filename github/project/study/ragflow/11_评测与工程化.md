## 三问

- **Q1 解决什么问题**：改了解析/分块/embedding 参数，效果变好还是变坏？上线会不会被打爆？
- **Q2 数据流哪一环**：质检 gate（上线前）+ 贯穿全程的护栏（运行时）。
- **Q3 删掉会怎样**：改参数靠感觉，上线靠运气，一打爆就挂。

## 一、检索评测 Benchmark（rag/benchmark.py）

### 核心流程（benchmark.py:40-80 + 209-259）

```python
from ranx import evaluate
from ranx import Qrels, Run

class Benchmark:
    def __init__(self, kb_id):
        # 加载知识库 + embedding 模型
        self.kb_id = kb_id
        e, self.kb = KnowledgebaseService.get_by_id(kb_id)
        self.similarity_threshold = self.kb.similarity_threshold
        self.vector_similarity_weight = self.kb.vector_similarity_weight
        embd_model_config = resolve_model_config(self.kb.tenant_id, LLMType.EMBEDDING, self.kb.embd_id)
        self.embd_mdl = LLMBundle(self.kb.tenant_id, embd_model_config, lang=self.kb.language)

    def _get_retrieval(self, qrels):
        """对每个 query 跑检索，得到 run（query → chunk_id → similarity）"""
        run = defaultdict(dict)
        for query in list(qrels.keys()):
            ranks = settings.retriever.retrieval(
                query, self.embd_mdl, self.tenant_id, [self.kb.id],
                1, 30, 0.0, self.vector_similarity_weight)
            for c in ranks["chunks"]:
                run[query][c["chunk_id"]] = c["similarity"]
        return run

    # ★ 用 ranx 算指标：
    # ndcg@10、map@5、mrr@10
    evaluate(Qrels(qrels), Run(run), ["ndcg@10", "map@5", "mrr@10"])
    # 逐 query 算 ndcg@10 并排序 → 找出最差的 query（bad case 归因）
    evaluate({key: qrels[key]}, {key: run[key]}, "ndcg@10")
```

**作用（关键）**：
1. **标准检索评测**：用 `ranx`（信息检索标准评测库）算 **ndcg@10 / map@5 / mrr@10**。
2. **qrels + run**：`Qrels`（query → 期望命中的 chunk）+ `Run`（query → 实际检索到的 chunk + 分数）——这是 IR 评测的标准输入格式。
3. **逐 query 归因**：对每个 query 单独算 ndcg@10 并排序 → **找出最差的 query**，看是"标注错了"还是"检索漏了"——这就是 bad case 归因。

## 二、限流器（rag/svr/task_executor_limiter.py）

```python
from common.asyncio_utils import LoopLocalSemaphore

MAX_CONCURRENT_TASKS = int(os.environ.get("MAX_CONCURRENT_TASKS", "5"))          # 任务并发
MAX_CONCURRENT_CHUNK_BUILDERS = int(os.environ.get("MAX_CONCURRENT_CHUNK_BUILDERS", "1"))  # 分块并发
MAX_CONCURRENT_MINIO = int(os.environ.get("MAX_CONCURRENT_MINIO", "10"))        # 存储 IO 并发

task_limiter = LoopLocalSemaphore(MAX_CONCURRENT_TASKS)     # 任务级
chunk_limiter = LoopLocalSemaphore(MAX_CONCURRENT_CHUNK_BUILDERS)  # 分块级
embed_limiter = LoopLocalSemaphore(MAX_CONCURRENT_CHUNK_BUILDERS)  # ★ embedding 限流
minio_limiter = LoopLocalSemaphore(MAX_CONCURRENT_MINIO)    # 对象存储限流
kg_limiter = LoopLocalSemaphore(2)                            # 知识图谱构建限流
```

**作用**：用 `LoopLocalSemaphore`（异步信号量）给每个环节设并发上限：
- `embed_limiter` 防止几十万 chunk 同时打 LLM embedding API（**背压**）。
- `minio_limiter` 防止存储 IO 打爆。
- 所有限流**可配置**（环境变量）——上线前按机器能力调。

```python
# 用法（在 embedding 循环里）：
async with embed_limiter:            # ★ 拿信号量，超过并发上限就等待
    vts, c = await thread_pool_exec(batch_encode, texts_batch)
```

## 三、重试 + 错误分类（LLM 抽象里的工程化）

从主干⑥已学，这里归纳成工程化要点：

```python
# ① 错误分类：把错误字符串 → 统一错误码
error_code = self._classify_error(error)   # QUOTA / RATE_LIMIT / AUTH / TIMEOUT / SERVER...

# ② 只对"可重试"错误重试
@property
def _retryable_errors(self) -> set[str]:
    return {
        LLMErrorCode.ERROR_RATE_LIMIT,   # 429 → 等退避重试
        LLMErrorCode.ERROR_SERVER,       # 5xx → 服务端暂时故障
    }
# QUOTA/AUTH 不重试（重试也没用），直接抛

# ③ 指数退避 + 抖动
delay = self.base_delay * random.uniform(10, 150)
```

**作用**：**区分可重试/不可重试错误**——rate_limit/server 等退避重试，quota/auth 直接抛。避免"拿一个错 key 疯狂重试"烧资源（对应你之前说的"坏数据/坏配置别反复重试"）。

**作用**：
- **每步记录**：耗时、输入输出、函数返回值——出问题能回溯到"卡在哪一步"。

- **Redis 日志 trace**：组件级别的 trace 日志，每步 elapsed_time。

## 五、对照 ai_assistant

| RAGFlow | 你的 ai_assistant | 差距 |
|---------|------------------|------|
| Benchmark（ndcg@10/map@5/mrr@10） | eval_qa.py（55 条端到端） | ⚠️ 补检索召回评测 |
| 限流器（embed/task/minio） | 无 | ❌ 该加 embedding 限流 |
| 错误分类 + 只重试可重试 | 重试不分类 | ⚠️ 该区分 |
| recording_context 可观测 | 日志不全 | ⚠️ 该补 trace |

**结论**：你有端到端评测（答案对不对），缺检索评测（召回准不准）；你有评测集但缺工程化护栏（限流/重试分类/观测）。两者结合 = 完整评测 + 完整工程化。

## 六、总结

| 工程能力 | 代码 | 作用 |
|---------|------|------|
| 检索评测 | `benchmark.py` + ranx | ndcg@10 / map@5 / mrr@10 + bad case |
| 限流 | `task_executor_limiter.py` | 背压（embed/task/minio） |
| 重试 | `_retryable_errors` | 只重试 rate_limit/server |
| 可观测 | `recording_context` + callback | 每步 trace + 进度 |

**核心心法**：**能上线 = 评测 gate + 限流背压 + 智能重试 + 全链路观测**。评测管"好不好"，工程化管"稳不稳"。你的 ai_assistant 该把这两块补齐——尤其 `embed_limiter` 和"只重试可重试错误"，是生产必踩的坑。
