# AI 数据问答项目实战（数仓 + LLM）

> 代码位置：`credit_risk_control_system/src/ai_assistant/`
> 运行：`python3 scripts/demo_qa.py` 和 `python3 scripts/eval_qa.py`

---

## 一、项目定位（grill-me 拷问后的结论）

最初想"重新生成一个数仓+AI 项目"，但 grill-me 挖出三个致命矛盾：

1. **"生产级"和"不跑通"互斥**——不能跑的生产级代码是空壳
2. **"重新生成"会废掉现有项目**——现有数仓已经很完整，真实生产是演进不是重写
3. **"注释给小白"和"生产级"冲突**——解法是两层注释（文件头大白话 + 行内讲 why）

**最终定位**：不重写，在现有数仓之上补一层 **AI 数据问答层**，主线是
"用户自然语言问数仓 → 意图识别 → Query改写 → RAG → NL2SQL → 校验 → 执行 → 解释 → 审计"。

**最关键的拷问结论**：最初这版是"学习骨架"（Mock LLM + 写死数据），拿出去面试会被当玩具刷掉。
必须补"三针"才能变成"能落地、能讲的作品"。

## 二、三针补齐（从玩具到作品）

### 第 1 针：真调 LLM（`llm_client.py`）

- `DeepSeekLLM`：真实调用 DeepSeek API（`chat` 和 `chat_json` 两个方法）
- `create_llm()` 工厂：设 `DEEPSEEK_API_KEY` 用真 DeepSeek，没 Key 自动降级 Mock
- 核心设计：所有模块依赖 `LLMClient` 接口，不依赖具体模型 → 换模型改一处

### 第 2 针：连真实数据库（`mock_warehouse.py`）

- 用 SQLite 落地 ADS 层简化版（`ads_delinquency_daily`、`ads_model_monitor_daily`）
- `QueryExecutor` 真的执行 SQL，返回真实查询结果（不再写死数据）
- SQL 生成器用 SQLite 方言 `strftime`（真实生产要针对目标数据库方言生成 SQL）

### 第 3 针：评测集 + bad case（`eval_qa.py` + `bad_cases.md`）

- 50 条评测集，6 个维度（意图识别/同义词/时间表达/权限/安全/边界），每类有正例反例
- 评测脚本按维度分组统计准确率
- `bad_cases.md` 记录 4 次迭代的完整归因过程

## 四、核心设计（面试能讲）

### 1. LLM 抽象层（面向接口编程）
所有模块依赖 `LLMClient` 接口，不依赖某家模型。换模型改一处，测试用 Mock。

### 2. Schema 注入
NL2SQL 生成前必须先拿准确表结构，否则模型会瞎编字段名。这就是 `schema_catalog.py` 的职责。

### 3. 安全门 + 降级
SQL 执行前过 5 道校验（禁危险操作、防全表扫描、行数限制、权限、JOIN 限制）；
意图识别置信度低时反问用户，不硬猜。

### 4. 解耦意图识别和指标解析（最有价值）
NLP 经典模型 **Intent + Slot**：
- **意图**：用户想干什么（查数/问概念/查来源/闲聊）—— 看动作信号
- **槽位**：对象是谁（指标名、时间）—— 看指标目录

耦合的危害：用"指标是否存在"判断"是否查询意图"，导致"查不存在的指标"被误判成闲聊。
解耦后：意图只看"动作信号"（多少/查/是多少），指标解析独立处理"查什么、存不存在"。

---

## 五、三条通用教训

1. **同义词是长尾，别硬编码**——用别名表/向量检索兜底
2. **精确匹配会漏**——简称、全称、口语变体都要处理，做双向包含匹配
3. **意图和指标解析要解耦**——意图判断"想不想查"，解析判断"查什么"
