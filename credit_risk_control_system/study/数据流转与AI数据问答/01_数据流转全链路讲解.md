# 数据流转全链路讲解

> 问题来源：用户问"帮我完整模拟一条数据在 credit_risk_control_system 中如何详细流转，比如用户进来一个问题——公司上个月环比逾期率变化是多少"。

先说一个关键认知：这个问题**不是实时决策场景，而是数据问答场景**。它不经过 `inference_pipeline`（那是用户来贷款时打分用的），它查的是数仓 ADS 层里一张叫 `ads_delinquency_daily`（逾期率日报）的表。

所以数据流转要讲**两条腿**：
- **第 1 条腿**：逾期率这个数字**是怎么被算出来的**（数据血缘，从源头到 ADS）
- **第 2 条腿**：你提问后，系统**怎么把这条数据找出来回答你**（Agent 问答链路）

---

## 一、全链路总览

```
你问："上个月环比逾期率变化是多少"
        │
        ▼
┌─────────────┐   ┌──────────────────────────┐
│  ① Agent 层  │   │   ② 数据从源头怎么来的      │
│  听懂你问什么   │   │   (数据血缘，一步步加工)    │
└──────┬──────┘   └───────────┬──────────────┘
       │                       │
       ▼                       ▼
┌───────────────────────────────────────────────┐
│  ③ 查 ADS 层 ads_delinquency_daily 表          │
│     上月逾期率 vs 上上月逾期率 → 算出环比         │
└───────────────────────────────────────────────┘
```

---

## 二、第 2 条腿先讲：逾期率这个数字是怎么来的？

这是**数据血缘**，是理解整个系统的关键。逾期率不是凭空冒出来的，它从每个用户的真实行为一点点加工出来。

### 源头：用户的行为事件（真实世界）

用户小张在 App 上操作，产生三类原始数据：

| 事件 | 落到哪张原始表 | 例子 |
|------|--------------|------|
| 小张填了贷款申请 | `ods_application`（申请表） | 申请金额、收入、设备号、城市 |
| 小张在 App 点来点去 | `ods_user_behavior`（行为埋点） | 页面浏览、输入、提交 |
| 小张的还款情况 | `ods_repayment`（还款记录） | 应还、实还、是否逾期 |

### 第 1 站：ODS 层 —— "原封不动的快递盒"

ODS（原始数据层）原则：**业务系统来什么，我就存什么，一个字都不改**。所以这里充满脏数据：

```python
apply_amount = [-1000, 0, None, 5000, ...]      # 有负数、有空值
product_type = ['cash_loan', 'UNKNOWN_TYPE', ...] # 有非法值
user_name    = '张三'        # ⚠️ 明文，还没脱敏
id_card      = '110101...'  # ⚠️ 明文身份证
```

> 类比：ODS 就像快递分拣站的收货区——包裹原样堆着，不拆不验，怕"我动了数据，回头说不清原始状态"。

### 第 2 站：DWD 层 —— "把脏东西洗干净"

DWD（明细数据层）开始加工，每张表对应 ODS 一张表：

| 加工动作 | 例子 |
|---------|------|
| **脱敏** | 张三 → 张*，身份证 → 1101**********34 |
| **修正脏数据** | apply_amount = -1000 → 0 |
| **标准化** | UNKNOWN_TYPE → 标准字典映射 |
| **打质量分** | 每条算 dq_score，低于 60 分标记"疑似脏数据" |

### 第 3 站：DWS 层 —— "把一个用户的所有信息捏成一张卡片"

DWS（汇总层）是数仓核心。它把三张 DWD 明细表，**按用户聚合**成"用户风险特征宽表"：

```
3 张 DWD 明细表（一个人几十条记录）
        │ groupby(user_id) + 时间窗口 + 三表 left join
        ▼
1 张宽表（一个人一行）：user_risk_feature_wide
  特征: apply_amount_avg, apply_cnt_7d, night_ops_ratio_30d,
        overdue_cnt_hist, on_time_rate, ... 共17维
```

**关键点**：`night_ops_ratio_30d`（近30天夜间操作占比）这类特征，是从行为埋点按**时间窗口**算出来的。

### 第 4 站：ADS 层 —— "直接给业务用的成品"

ADS（应用数据层）不做复杂加工，**预聚合、即查即用**。其中 `ads_delinquency_daily`（逾期率日报）就是你要查的。

**逾期率怎么算？**

```python
daily['delinquency_rate'] = bad_loans / total_loans   # 坏样本数 / 总样本数
```

而"坏样本"（label=1）是**30 天后**才定性的——这就是 **PIT 原则**：

> 用户 7 月 1 日申请贷款，**7 月 1 日的特征**去预测**8 月 1 日（T+30）是否逾期**。
> ⚠️ 如果拿 8 月 1 日的特征去判断 7 月 1 日的申请，就是**时间泄漏**——已经知道答案了还预测什么？

### 血缘全图

```
真实世界                            数仓
────────                            ────────
用户申请/行为/还款                     ODS层→DWD层→DWS层→ADS层
用户贷款申请 ──binlog/上报──► ods_application ──清洗脱敏──► dwd_application ──聚合──► 用户风险特征宽表 ──加标签──► ads_delinquency_daily
用户App行为 ──SDK埋点──► ods_behavior ──► dwd_behavior ──► (17维) ──► ★逾期率日报
用户还款    ──binlog──► ods_repayment ──► dwd_repayment ──►
```

## 三、第 1 条腿：你的问题怎么被系统"听懂"并"查出"数据

### 步骤①：意图识别

LLM 判断你的问题属于哪类：
- "上个月环比逾期率变化" → 命中"离线指标查询" → 走 NL2SQL

### 步骤②：NL2SQL（人话翻译成 SQL）

带着 Schema Catalog（表结构清单）让 LLM 生成 SQL，防止编造字段名。

### 步骤③：安全校验

执行前过 5 道检查（面试亮点）：危险操作、分区过滤、行数限制、权限、JOIN 限制。

### 步骤④：执行 → 拿到结果 → LLM 回答

```
执行结果:
  2026-06  逾期率 3.2%   （上月）
  2026-05  逾期率 2.8%   （上上月）
LLM 翻译:
  "6月逾期率 3.2%，比 5月的 2.8% 上升 0.4 个百分点，环比约 14%"
```

## 四、关键概念速查（小白必懂）

| 概念 | 一句话理解 |
|------|-----------|
| ODS/DWD/DWS/ADS | 数据加工 4 个车间：原样收→洗干净→揉成团→做成成品 |
| 血缘 (Lineage) | 每个数字都能追溯到它从哪个源头算出来的 |
| PIT 原则 | 只用"过去"的信息预测"未来"，防止偷看答案 |
| label / 标签 | 这笔贷款 30 天后有没有逾期（0=没逾期，1=逾期） |
| 环比 | 这个月跟上个月比（vs 同比：这个月跟去年同月比） |
| NL2SQL | 把自然语言翻译成 SQL |
