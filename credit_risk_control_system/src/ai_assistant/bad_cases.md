# Bad Case 归因分析

> 用 `scripts/eval_qa.py` 真实跑出来的结果，不是编的。
> 当前（修复后）：评测集 50 题，意图识别准确率 **98%**（49/50），指标解析准确率 **100%**（36/36）。

面试时，最打动面试官的不是"我的系统 100% 对"，而是"我知道它哪里会错、为什么错、怎么改"。
这份文档记录了我从 70% 迭代到 98% 的完整过程，每一步都是真实的 bad case 驱动。

---

## 一、迭代过程（四次真实修复）

### 第 1 版：意图 72%，指标 86%

**问题**：MockLLM 硬编码了"逾期率""通过率""额度"三个词，不认识同义词。

**修复**：让 MockLLM 接收指标目录（catalog），靠查别名表识别同义词，不再硬编码。

### 第 2 版：意图 82%，指标 92%

**问题**：暴露了三个新的真实缺陷——
1. "什么是坏账率"里"是什么"三个字不连续（是"什么是"），匹配不到"口径解释"
2. "数据来源是什么"被误判成"口径解释"（因为先判了"是什么"，没先判"来源"）
3. "额度""逾期"这类简称，Mock 只做了 `别名 in query`，没做 `query in 别名`

**修复**：加"什么是"语序、调整判断顺序、改双向包含匹配。

### 第 3 版：意图 94%，指标 100%

**问题**：还剩 3 个 bad case，全是"未知指标"边界——用户有查询动作，但指标不存在，被判成闲聊。

### 第 4 版（当前）：意图 98%，指标 100% —— 解耦

**问题本质**：意图识别靠"指标是否存在"来判断"是否指标查询"，把两个层次耦合了。

**修复**：解耦。意图识别改成"动作信号 OR 指标信号"——
- 动作信号："多少""查""查询""是多少"（用户想查数，不管指标存不存在）
- 指标信号：含指标同义词（陈述式查询，如"最近30天的逾期率"）

详见下面第二节。

---

## 二、核心修复：解耦意图识别和指标解析

这是整个迭代里最有价值的改动，也是最值得面试讲的。

### 为什么耦合是错的

NLP 经典模型 **Intent + Slot（意图 + 槽位）** 把一句话拆成两个独立问题：
- **意图**：用户想干什么（查数/问概念/查来源/闲聊）
- **槽位**：对象是谁（指标名、时间、维度）

判断"用户想订机票"（意图），不需要先知道"目的地是不是个真实城市"（槽位）。

### 耦合的危害

之前的代码用 `_find_indicator(query) is not None`（有没有已知指标）来判断"是不是查询意图"，
导致"指标不存在"反向污染了"意图判断"：

| 问题 | 用户真实意图 | 耦合时的判断 |
|------|------------|------------|
| 查一个不存在的指标xyzabc | 想查数（有"查"） | 闲聊 ❌ |
| 收入是多少 | 想查数（有"是多少"） | 闲聊 ❌ |

### 解耦后的方案

```python
# 意图识别：动作信号（想查数） OR 指标信号（陈述式查询）
if self._has_query_action(query) or self._find_indicator(query) is not None:
    return "指标查询"
```

`_has_query_action` 只看动作词，不碰指标目录：
- ✅ 用"多少""是多少""查""查询""有没有"（精准，闲聊里几乎不出现）
- ❌ 不用"怎么样""看看""帮我"（太宽，会误判"今天天气怎么样""帮我写首诗"）

这样，指标不存在时，意图依然正确（"指标查询"），只是走到"指标解析"那一步才反问"没找到这个指标"。

### 解耦带来的设计原则

**意图判断"想不想查"，解析判断"查什么"，两者是不同层次，必须解耦。**
真实系统里，意图识别用动作信号，指标解析用目录映射，两者独立演进、独立测试、独立失败。

## 三、最后一个 Bad Case（这是评测标注的争议，不是系统缺陷）

| 编号 | 问题 | 预期 | 实际 |
|------|------|------|------|
| 40 | 帮我看看上个月的表现 | 指标查询 | 闲聊 |

**为什么这个 case 不该算系统错**：

"表现"这个词太模糊，没有明确指标指向。用户说"看看上个月的表现"，没说要看哪个指标——
是逾期率？通过率？还是额度？系统无从判断，反问"您想了解哪个指标"是**正确的产品行为**。

如果把"看看"也加进动作信号，确实能把这个 case 判成"指标查询"，但代价是引入更多误判：
"今天天气怎么样"、"帮我看看新闻"都会被误判成"指标查询"。

**取舍**：宁可让模糊问题走"闲聊→反问"，也不要为了凑评测分数把动作信号放宽到误伤真正的问题。

## 四、三条通用教训（贯穿整个迭代）

1. **同义词是长尾，别硬编码**——用别名表/向量检索兜底，Mock 查别名表，真实 LLM 靠语义
2. **精确匹配会漏**——简称、全称、口语变体（"什么是 X" vs "X 是什么"）都要处理，做双向包含匹配
3. **意图和指标解析要解耦**——意图判断"想不想查"，解析判断"查什么"，两者是不同层次

这三条，每一条都是真实生产里会踩的坑。能主动讲出"我为什么从 70% 迭代到 98%，
每一步修了什么、为什么"，比"我的系统很准"有说服力一百倍。

## 四、怎么跑真 LLM 评测

当前评测是 Mock 模式（免费、可复现，但测的是"链路对不对"，不是"语义理解准不准"）。

要测真实水平，设置 DeepSeek API Key 后重跑：
```bash
export DEEPSEEK_API_KEY=sk-你的key
python3 scripts/eval_qa.py   # 会自动切到真 DeepSeek
```

真 LLM 模式下，同义词、语序、未知指标这三个短板会大幅改善——
因为真实 LLM 靠语义理解，不靠关键词匹配。但真 LLM 有随机性（temperature），
建议把 temperature 设 0 再评测，保证结果可复现。
