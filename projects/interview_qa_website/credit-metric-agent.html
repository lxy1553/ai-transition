主问题问题 1：请你简单介绍一下你的这个项目，b 端指标问答与报告 agent

我做的是一个面向企业业务人员的 B 端指标问答与报告 Agent。业务人员可以用自然语言查询指标数据、了解统计口径、追溯数据来源，也可以把查询结果整理成报告。

它会先识别用户意图并确认查询条件，再按任务类型调用对应能力：已登记的指标走预定义查询，口径问题查指标知识库，血缘问题查数据血缘。多个子任务可以分别处理，最后汇总成带口径说明和来源信息的答案。遇到口径不明确时先澄清；遇到权限或下游服务问题时按规则拒绝或说明哪些结果暂时不可用。

这个项目重点解决的是业务人员查数慢、指标口径不一致、结果难追溯的问题。设计上把权限校验、指标版本和审计放在服务端控制，让模型负责理解问题和选择合适的处理路径，不直接决定数据权限或业务口径。

我的项目是面向企业业务人员的 B 端指标问答与报告 Agent，支持查指标数据、解释口径、追溯血缘并整理报告。系统先识别意图和查询条件，再分别调用受控查询、知识检索和血缘能力；歧义先澄清，权限与版本由服务端校验，最后返回带口径和来源的答案并留审计。模型负责理解与表达，不决定权限或业务口径。

主问题问题 2： 你提到“先识别用户意图并确认查询条件”。能不能具体讲一下：用户一句话进来后，你的系统从意图识别到最终回答，完整的处理链路是怎样的？中间有哪些关键节点、状态或决策分支？

可以，面试里我会结合一个具体问题来讲，比如用户问：

“上月各渠道逾期率是多少？口径是什么？上游表有哪些？”

这句话进来后，系统先完成身份认证，建立用户的租户、角色和数据权限上下文。权限信息由服务端保存，不交给模型自行判断。

接着，意图识别节点把问题解析成结构化计划：查询逾期率、按渠道分组、时间为上月，同时需要口径解释和血缘分析。计划还要经过服务端校验，确认指标、时间、维度和可用工具都合法。

如果“逾期率”对应多个有效口径，或“渠道”“上月”无法按已配置规则唯一解释，系统会进入澄清分支，暂不执行查询。条件明确后，数据查询走登记指标的查询接口；口径说明走指标目录或知识检索；血缘分析走血缘查询。三个只读任务互相独立时可以并行执行。

结果汇合后，系统会核对权限、指标版本、数据时点和各分支状态。核心数据查询失败，就不返回编造的数值；辅助的口径或血缘分支失败，可以返回成功的部分，并明确说明哪部分不可用。最后生成包含数值、口径和来源的回答，同时记录审计信息。

可以把主链路概括成：

身份认证与权限上下文
        ↓
意图识别与任务拆分
        ↓
服务端校验查询计划
   ┌────┼─────┐
 查指标  查口径  查血缘
   └────┼─────┘
        ↓
版本、权限、结果状态校验
        ↓
完整回答或明确的部分结果
        ↓
审计记录

关键决策有三个：信息是否足够明确、当前用户是否有权限、核心与辅助任务分别是否成功。这些决策决定系统是继续查询、先澄清、拒绝请求，还是返回部分结果。

本题 1–2 分钟总结

完整链路是身份认证、结构化意图识别、服务端计划校验、按任务调用指标/口径/血缘能力、结果汇合校验、生成答复和审计。查询条件不明确先澄清；核心数据失败不编造，辅助分支失败可明确返回部分结果。只读且互相独立的分支可以并行。

主问题问题 3： 你这里提到“意图识别节点把问题解析成结构化计划”，然后服务端校验计划。那这个计划具体长什么样？是单步工具调用，还是一个 DAG / 多任务计划？计划里的节点、依赖关系、并行关系是怎么表示的？能不能举一个你刚才那个例子的结构化计划？

依赖关系是：

解析计划 → 服务端校验 → ┬→ 指标查询 ──┐
                       ├→ 口径查询 ──┼→ 汇总校验 → 回答
                       └→ 血缘查询 ──┘

三个查询都依赖计划校验，但彼此没有依赖，所以可以并行。汇总节点必须等它们完成或超时后再执行。指标查询是必需任务；口径和血缘属于辅助任务，失败时可以在明确提示的前提下返回部分答案。

如果计划里的指标版本和定义检索结果不一致，汇总节点不会把它们直接拼起来；如果指标、时间或维度存在多个合理解释，则在执行查询前进入澄清分支。像用户身份、租户和可访问数据范围，则由服务端注入工具执行上下文，不放进模型生成的计划里。

本题 1–2 分钟总结

我把用户请求解析为受约束的任务 DAG，每个任务带 task_id、工具类型、依赖、并行组和 required 标志。比如查逾期率、查口径、查血缘可以在计划校验后并行，汇合节点再检查版本、权限和结果完整性。模型提出计划，服务端校验后才执行。

主问题问题 4： 假设现在这个 DAG 已经通过校验，开始执行。指标查询这个 required: true 的任务失败了，但失败原因不同：比如（1）下游超时；（2）权限不足；（3）指标版本已下线。你的执行引擎会怎么处理这三种情况？分别会返回什么？会不会重试？重试策略和幂等性怎么考虑？

我会把“必需任务失败”继续按失败原因分类处理。required: true 表示没有这项结果就不能生成完整答案，但不代表三种失败都用同一种重试方式。

失败原因是否重试执行处理返回给用户
下游超时有限重试这是可能恢复的暂时性故障。只对只读查询做有限次数重试，例如最多 2 次、带退避，并且每次超时都不能超过请求剩余 deadline。预算不足就停止。仍失败则不返回逾期率数值；可以返回已成功的口径或血缘信息，并明确说明“指标查询暂时不可用”。
权限不足不重试权限错误不是暂时故障。立即终止指标查询，不尝试换账号、换工具或缩小条件绕过权限；内部记录具体拒绝原因，对用户返回统一的无权访问提示。不返回受限数据，也不泄露具体是哪个权限规则或资源配置导致拒绝。
指标版本已下线不重试同一版本这是计划与权威指标目录之间的状态变化，不是网络故障。停止当前查询，重新读取指标目录，按指标的生效时间和版本规则重新解析、校验计划。不能未经确认就把旧版本替换成“当前最新版本”。若能按权威规则唯一确定适用版本，可用新版本重新校验后执行；如果无法唯一确定或业务口径发生变化，就提示口径已变更并要求确认，暂不返回数值。

面试时可以这样概括：

对必需的只读指标查询，超时属于可恢复故障，可以在总 deadline 内做有限重试；权限不足属于确定性拒绝，立即停止，不重试也不换路绕过；版本下线属于计划过期，停止旧计划并重新按权威目录解析版本，不能静默切到最新版本。查询重试是只读操作，不会重复修改业务数据；但审计记录会用 request_id 和 task_id 去重或关联，避免把每次重试误记成新的用户请求。

补充一点：如果未来这个 DAG 包含“发起补件”“修改额度”一类写操作，它们不能照搬只读查询的重试策略。超时可能意味着服务端已经执行成功但响应丢失，需要用幂等键查询执行状态或先核对结果，不能直接再发一次。

本题 1–2 分钟总结

必需指标任务失败要按错误语义分开处理：超时只对可重试的瞬时故障做有界重试；权限不足立即拒绝，不重新规划绕过；指标版本下线则停止旧调用，读取权威目录寻找兼容版本或提示重新确认。重试要有总 deadline；只读请求可安全重试，写操作必须幂等并先查执行状态。

主问题问题 5： 你前面说“权限校验放在服务端，模型不直接决定数据权限或业务口径”。那如果未来这个 Agent 真的接入了写操作，比如“帮某客户调整额度”或“发起补件”，你会怎么设计它的权限与确认机制？模型、Agent 执行引擎、服务端权限系统三者之间的职责边界是什么？哪些事情绝对不能由模型决定？

我会把模型定位成提出动作建议的组件，不把它当成权限系统或业务决策者。比如用户说“帮客户调高额度”，模型可以识别意图、整理申请信息、生成待审核的额度调整草案；它不能自行决定这个客户有权提额、提多少，也不能直接调用接口完成调整。

用户请求
  ↓
模型识别意图，生成结构化动作草案
  ↓
执行引擎校验参数、流程状态与风险等级
  ↓
服务端权限系统校验操作者、客户、资源和操作权限
  ↓
按策略要求确认 / 审批
  ↓
执行前再次校验权限和审批状态
  ↓
带幂等键调用业务系统 → 记录审计结果

三者的职责边界是：

组件负责什么不负责什么
模型理解用户意图、提取信息、提出结构化动作草案、解释执行结果授权、批准额度、绕过规则、确认用户身份
Agent 执行引擎按固定状态机编排步骤；校验参数格式；设置确认和审批门；控制超时、重试与幂等自己授予权限或改写业务政策
服务端权限与业务系统以可信身份校验操作者对客户和操作的权限；执行权威业务规则；最终接受或拒绝写入信任模型传来的“我有权限”“已批准”等声明

以调整额度为例，Agent 只能生成待审方案。额度范围、审批资格和审批人由服务端规则决定；高风险变更进入有权限人员的审批流程，必要时要求双人复核。审批通过后，执行服务还要重新验证审批单、目标客户、金额和有效期，不能只依赖模型或前序节点的判断。

以发起补件为例，Agent 可以根据缺件清单起草通知，但发送前应校验客户、材料类型、联系渠道和当前申请状态，并根据机构策略要求审核员确认。确认必须绑定到具体申请、具体材料清单和具体通知内容；内容发生变化，就需要重新确认，不能拿旧确认发送新内容。

绝不能交给模型决定的包括：操作者有没有权限、目标客户是否匹配、额度最终批多少、审批是否通过、是否可以跳过人工审批，以及权限不足时是否换工具或换身份继续尝试。这些都必须由服务端的身份、授权和业务规则做最终裁决。

写操作还要考虑“请求超时但服务端可能已经执行”的情况：不能简单重发。执行时带幂等键，超时后先查询原操作状态；同时记录操作者、审批人、参数摘要、审批依据、执行结果和关联请求 ID，保证能追溯。

本题 1–2 分钟总结

模型只负责理解请求和提出操作意图；执行引擎负责流程、校验、确认门和幂等；服务端权限系统负责身份、授权和资源范围。模型不能决定是否有权、是否通过审批、是否可跳过确认，也不能自行扩大额度。高风险写操作必须经过用户确认和独立审批。

主问题问题 6： 你说 Agent 执行引擎要“设置确认和审批门”。那对于一个写操作，比如“帮某客户把额度从 100 万调到 150 万”，这个确认和审批具体怎么落地？哪些环节需要用户确认，哪些需要人工审批？如果用户确认之后、真正执行之前，额度又被别人改了，或者权限被收回了，系统怎么处理？

我会把这类额度调整设计成一个有版本检查和审批门的变更流程，而不是用户说一句“确认”后就直接写库。用户确认、业务审批、最终执行是三个不同的环节。

以“把客户额度从 100 万调到 150 万”为例：

读取当前额度与版本
    ↓
生成待处理方案：客户、当前值、新值、原因
    ↓
校验发起人权限与业务规则
    ↓
用户确认这份具体方案
    ↓
人工审批（若策略要求）
    ↓
执行前重新检查权限、审批状态和额度版本
    ├─ 全部未变化 → 原子更新额度
    └─ 任一已变化 → 停止执行，重新评估

用户确认用于确认“要提交的具体操作是什么”，页面应清楚展示客户、当前额度、目标额度、币种、生效时间和原因。确认记录绑定这些字段及方案版本，并设置有效期。若金额、客户或其他关键参数变了，原确认失效，必须重新确认。

人工审批用于有权审批人对业务风险和政策合规作出批准。是否需要审批、审批层级和审批人由服务端政策决定，例如按调整金额、风险等级或产品类型分级；Agent 不能自行降低审批级别，也不能把用户确认当成审批。

真正写入前，执行服务会再次读取当前数据并做乐观并发检查。例如读取时额度是 100 万、版本号是 42，那么更新条件相当于：

UPDATE customer_credit
SET limit_amount = 1500000, version = 43
WHERE customer_id = ?
  AND limit_amount = 1000000
  AND version = 42;

如果额度已被别人改过，更新行数会是 0，系统停止这次操作，不覆盖新值；重新读取后展示最新情况，重新校验规则，并要求重新确认、必要时重新审批。

权限也会在执行时重新检查。如果用户确认后权限被收回，或者审批人权限、审批状态失效，服务端拒绝写入；之前的确认不能让已失效的权限继续生效。拒绝原因记入审计记录，并向用户提示需要重新发起或联系有权限的审批人。

最后，额度调整调用使用幂等键，并记录操作 ID。若执行请求超时，系统先按操作 ID 查询业务系统是否已成功，确认未执行后才考虑重试，避免重复调整。

本题 1–2 分钟总结

额度变更先展示不可变的变更方案，用户确认绑定方案版本和参数；再由有权审批人审批。执行前重新检查权限、审批状态和资源版本，使用乐观锁防并发修改，并以幂等键防重复。如果额度已被他人修改或权限撤销，就拒绝执行并要求重新发起流程，不能沿用旧确认。

主问题问题 7：Agent 上线后如何评估效果？如何结合离线评估、线上监控、人工抽检定位错误？

我换个方向，问一个更偏 Agent 评估与线上质量 的问题：

你前面讲了链路、DAG、异常处理和写操作权限。那这个 Agent 上线之后，你怎么判断它“做得好不好”？你会怎么设计评估体系？离线评估、线上监控、人工抽检分别看什么指标？如果发现“意图识别对了，但最终答案错”，你怎么定位是哪一层出的问题？

我会把评估拆成三层：离线验证上线前能力，线上监控发现运行问题，人工抽检判断真实业务质量。不能只看答案流畅不流畅，还要验证数据是否正确、权限有没有守住、失败时有没有安全收尾。

以 B 端指标问答为例，离线会准备一套带标准答案和证据的测试集，覆盖标准指标查询、多意图请求、口径歧义、无权限、下游超时和版本变化等场景。核心看：

  • 路由与任务拆分：意图识别准确率、子任务拆分准确率、工具选择准确率。
  • 数据与证据正确性：指标值和查询结果一致率、口径版本匹配率、引用或血缘证据准确率。
  • 安全性：越权查询是否被拒绝、歧义是否按规则澄清、失败时是否编造结果。这类指标要单独统计，不能被总体准确率掩盖。
  • 工程表现：端到端延迟、超时率、重试率和单次请求成本。

线上监控请求成功率、P50/P95 延迟、各工具错误率、澄清率、拒答率、部分结果率和资源成本，并按意图类型、指标、租户和版本分组观察。人工抽检则重点看高风险、低置信度、用户反馈差和发生降级的请求，核对最终答案、使用的指标版本、证据和权限处理是否一致。

如果“意图识别对了，但最终答案错”，我会沿着同一条 Trace 逐层查：

意图与计划 → 服务端校验 → 工具入参 → 查询/检索结果
           → 版本与证据校验 → 结果融合 → 最终回答

例如，若计划里的指标和时间都正确，但查询值错，查参数、SQL 或数据快照；查询值正确、解释错，查定义检索和版本匹配；各分支单独正确但最终回答错，查融合逻辑和生成依据。定位到具体节点后，再把这个失败样本加入回归集，修复后重跑相关测试，避免同类问题再次上线。

评估门槛会按业务风险制定，并用标注集验证；涉及越权和错误写操作的安全问题，不能靠其他场景的高分抵消。

本题 1–2 分钟总结

评估要覆盖离线数据集、线上指标和人工抽检，并单独看安全错误，不能让总体准确率掩盖越权。离线评意图、检索、SQL、答案和引用；线上看成功率、延迟、成本、澄清/转人工及反馈；人工抽查高风险样本。答案错时沿 Trace 定位意图、路由、工具、证据、融合或生成哪层出了问题。

主问题问题 8：Trace 记录哪些字段和调用阶段？如何用它定位 Agent 线上故障？

我继续追问一个更偏 Trace 与可观测性 的问题：

你提到“沿着同一条 Trace 逐层查”。那你们这个 Trace 具体记录哪些信息？在 Agent 场景下，一次请求可能包含模型调用、意图识别、任务 DAG、工具调用、重试、澄清、融合和生成，Trace 的粒度怎么定？如果出现线上问题，你希望能在多短时间内、通过哪些字段定位到根因？

我会让一次用户请求对应一个 trace_id，Trace 里的每个关键步骤对应一个 span。并行的 DAG 分支是同一个父 span 下的子 span；每次重试单独建 span，并记录 attempt，这样能看出耗时是花在查询、重试还是生成上。

大致结构是：

request
├─ authenticate_and_authorize
├─ plan
│  ├─ intent_parse
│  └─ plan_validate
├─ execute_tasks
│  ├─ metric_query
│  │  └─ retry_attempt
│  ├─ definition_retrieval
│  └─ lineage_query
├─ merge_and_validate
└─ generate_response

每个 span 至少记开始和结束时间、状态、错误类型和父子关系。Agent 场景还要关联 request_id、conversation_id、task_id、意图、工具名、重试次数、剩余 deadline、指标版本、数据快照，以及子任务是否成功。模型调用记录模型和提示词版本、耗时和 token 数；工具调用记录工具名、参数校验结果、结果状态和耗时。并行分支的 span 时间能帮助确认它们是否真并行，以及哪个分支拖慢了总请求。

Trace 不应默认保存客户材料、完整检索文档、密钥或带敏感值的原始 SQL。优先记录脱敏后的参数、参数摘要、查询模板标识和结果状态；确实需要保留调试样本时，要有访问控制和保留期限。

线上定位时，我希望值班人员能用 trace_id 找到完整调用链，并在几分钟内判断问题属于计划、权限、工具、数据版本还是结果融合。比如指标值错了，先比对 metric_query span 的指标 ID、版本、参数摘要和数据快照；如果工具结果正确而最终答案错，再看 merge_and_validate 和 generate_response 使用了哪些证据。根因定位时间应作为运维目标，通过故障演练和线上事件复盘验证，不能只靠“有 Trace”就认为可观测性已经够用。

面试时要按实现情况区分表述：如果当前项目还没有接入 OpenTelemetry 和完整 Trace，就说这是生产设计目标；只把代码中确实记录的请求 ID、工具调用和错误信息说成已实现。

本题 1–2 分钟总结

Trace 以一次用户请求为根 trace，意图、每个 DAG 任务、模型调用、工具调用、重试、融合和生成分别作为 span，记录父子关系、耗时、状态、版本、脱敏输入输出摘要和错误码。线上通过 request_id/trace_id 找慢分支和失败节点，目标是在几分钟内定位根因；敏感原文不进入普通日志。

主问题问题 9： 你前面提到一次请求可能包含模型调用、DAG 编排、多个工具、重试、融合和生成。那这个 Agent 的延迟和成本主要花在哪里？如果线上流量上涨，或者某个指标查询特别慢，你会从哪些层面做优化？模型侧、编排侧、工具侧、缓存侧分别能做什么？

我会先按 Trace 拆解单次请求的耗时和成本，找出关键路径，而不是先假设模型最慢。串行步骤的延迟会累加；并行分支的耗时主要由最慢的分支决定。成本则要拆成模型调用、检索和下游查询分别看。

比如用户同时查指标、问口径、查血缘时，我会重点看：计划生成用了多久，各分支是否真的并行，哪个工具占了 P95 尾延迟，是否发生重试，以及生成阶段用了多少输入和输出 Token。

找到瓶颈后，分层优化：

层面优化方式
模型侧简单意图识别用较小模型或规则；结构化输出限制字段；缩短无关上下文；减少重复模型调用；对稳定前缀评估提示词缓存。
编排侧不需要的分支不启动；独立只读任务并行；给节点分配预算，共享总 deadline；重试只针对可恢复故障并设上限，避免流量升高时重试放大负载。
工具侧给慢指标查查询计划、索引和扫描量；常用指标尽量走预计算或参数化查询；控制连接池和并发；为慢查询设超时，保护数仓不被 Agent 流量打满。
缓存侧缓存稳定的指标定义、字典和血缘结果；适合时缓存短时间内重复的指标查询，但缓存键必须包含租户、权限范围、指标版本、时间区间、维度和数据快照等条件，并设置过期与失效规则。

如果某个指标特别慢，我会先从它的 span 找到查询参数和耗时，再看数据库执行计划及扫描数据量，判断是查询本身慢、数仓拥塞，还是连接池排队。然后考虑优化 SQL、预聚合或短时缓存；如果在 deadline 内仍拿不到结果，就按核心任务失败规则清楚提示，不返回旧数据冒充实时结果。

线上流量上涨时，还要监控并限制并发、队列长度和下游负载，按业务优先级做背压或降级。优化前后对比 P95 延迟、超时率、每次请求成本和答案正确率，避免为了省钱或提速损害数据正确性与权限隔离。

本题 1–2 分钟总结

成本与延迟通常集中在模型生成及外部工具等待。模型侧用合适的小模型、结构化输出和缓存；编排侧并行独立任务、减少无效重试；工具侧优化查询、索引和超时预算；缓存侧按租户、权限和版本隔离。流量上涨还要设置并发、预算和降级，避免慢分支拖垮整条链路。

主问题问题 10： 你前面主要讲的是单次请求内的 DAG，如果多轮场景下，你会怎么管理对话状态、指代消解和上下文继承？哪些信息可以继承，哪些必须重新校验或重新澄清？

我会把对话上下文和权限状态分开管理。对话状态按 conversation_id 保存结构化信息，例如当前讨论的指标、已确认的时间范围和维度、未完成的澄清问题，以及这些信息来自哪一轮用户表达。不能只把整段聊天记录塞进 Prompt，让模型自行猜哪些条件还有效。

例如用户先问“上月各渠道逾期率是多少？”，接着说“再看华东”。如果当前对话里只有一个明确的指标和时间范围，我会把“华东”补成筛选条件，沿用已确认的逾期率和上月范围；如果刚才讨论过多个指标或多个时间范围，就先澄清指代。

可以继承的是当前对话中明确确认、仍然有效的查询条件，比如指标、时间、维度和上一个查询结果的引用。需要重新校验或澄清的是：

  • 权限：每次工具调用都由服务端按当前用户和资源重新校验，不能继承上一轮的授权结果。
  • 指标定义和版本：执行前重新查权威目录，确认仍有效，不能只沿用旧答案里的口径。
  • 相对时间：像“上月”应保存解析后的具体日期区间；后续指代原查询时沿用这个区间。用户开启新查询时，则按新请求时间重新解析。
  • 写操作确认和审批：绝不从上一轮继承。必须针对当前具体操作和参数重新确认，并检查审批状态。
  • 含义不明确的指代：如果上下文里存在多个合理对象，就追问，而不是猜测。

每轮请求仍独立记录 Trace，并关联同一个 conversation_id，方便还原上下文是如何影响计划的。总结来说，继承已经确认的业务条件；权限、版本和副作用门禁在每次执行前重新检查；存在多个合理解释时先澄清。

本题 1–2 分钟总结

多轮会话继承已经确认且仍有效的业务条件，例如指标、时间和维度，但每轮都重新校验身份、授权、数据版本和副作用许可。指代不清时澄清；旧条件可能过期时重新确认。会话状态是便利上下文，不是权限凭证。

追问追问 10-A：长对话如何压缩上下文，避免摘要丢失关键条件或混入权限信息？

我接着问一个和 上下文压缩与长对话 相关的问题：

如果一段对话很长，比如用户来回问了 30 轮，涉及多个指标、多个时间范围、几次澄清和几次报告生成。你不可能把全部历史都塞进 Prompt。那你会怎么压缩、摘要或选择上下文？摘要由谁生成、存哪里、怎么防止摘要把关键条件或权限信息搞丢或搞错？

我会把长对话压缩成有来源的业务状态，不把整段历史交给模型总结后就当成事实。三十轮里可能出现多个指标和时间范围，若只留下“用户在问逾期率”，很容易把不同问题的条件混在一起。

具体做法是把对话分成三层：

当前请求：本轮问题和必需条件
当前任务状态：当前指标、时间范围、维度、澄清结果、任务状态
历史索引：过去查询和报告的 ID、时间、指标版本，按需取回

当前任务状态优先保存为结构化字段，例如：

{
  "metric_id": "overdue_rate",
  "period": {
    "start": "2026-09-01",
    "end_exclusive": "2026-10-01"
  },
  "dimensions": ["channel"],
  "confirmed_by_turn": 12,
  "status": "confirmed"
}

摘要由程序维护结构化事实，模型可以辅助生成可读摘要，但摘要只是检索线索，不是权威数据。 每个保留条件都记录来源轮次和确认状态；如果新旧说法冲突，以用户最近的明确表达为准，无法判定时就追问。指标定义和版本仍以指标目录为准；报告则保存为独立产物，通过报告 ID、查询 ID 和指标版本关联，不靠对话摘要复述其内容。

组装 Prompt 时只放当前问题、当前任务需要的已确认条件，以及按需检索到的少量历史记录。摘要和对话状态都不保存或继承权限；每次执行仍由服务端重新鉴权，写操作确认也必须针对当前具体参数重新进行。

这样压缩后，即使 Prompt 里没有三十轮原文，系统仍能追溯“这个时间范围是谁在哪一轮确认的”。如果关键条件来源不明、摘要与原始记录冲突，或上下文无法唯一指向某个查询，我会停下来澄清，而不是让模型补猜。

本题 1–2 分钟总结

长对话不把 30 轮历史全部塞入 Prompt，而是保留最近对话、当前任务状态和经核验的摘要。摘要由受控逻辑生成并存于会话状态或检查点，记录条件、用户确认、未完成任务和来源；权限与敏感数据不靠摘要继承，每次仍由服务端重新校验。

主问题问题 12： 你这个 Agent 会调用指标查询、口径检索、血缘查询等工具。那在实际设计这些工具时，你是怎么定义工具的输入输出、错误语义和边界的？比如一个工具应该“窄而专”还是“大而全”？如果模型选错了工具，或者传了工具不支持的参数，系统怎么兜底？

我会把工具定义成窄而专、输入输出明确、失败语义稳定的服务端接口。工具不是让模型自由拼业务操作的万能入口；模型只提交一个结构化请求，服务端负责校验并执行。

比如指标查询工具只负责查一个已登记指标：

{
  "metric_id": "overdue_rate",
  "period_start": "2026-09-01",
  "period_end": "2026-10-01",
  "dimensions": ["channel"]
}

成功时返回结构化结果，至少包含数值、指标版本、数据时点、维度和结果状态。口径检索和血缘查询分别使用自己的工具与输出结构，避免一个“大工具”同时查数、解释口径、追血缘，让模型难以判断参数和结果含义。

错误也要有稳定语义，例如：

  • INVALID_ARGUMENT：参数格式或取值不合法，不重试。
  • NOT_FOUND：指标或资源不存在；是否改问用户由上层决定。
  • PERMISSION_DENIED：服务端拒绝，不重试，也不尝试换工具绕过。
  • DEADLINE_EXCEEDED、DEPENDENCY_UNAVAILABLE：可能是暂时故障，只允许在剩余 deadline 内有限重试只读调用。
  • VERSION_RETIRED：当前版本失效，停止旧计划，重新按权威目录解析，不能静默改用最新版本。

工具入口会做严格校验：工具名必须在允许清单里；参数按 Schema 校验，未声明字段拒绝；指标、时间范围和维度还要经过业务校验。用户身份和权限不接受模型传参，由服务端从可信请求上下文注入。

如果模型选错工具，执行引擎会在调用前拒绝。如果是可纠正的路由错误，可以把不包含敏感信息的错误类别反馈给规划节点，让它有限次数重新选择；权限拒绝和安全错误不能借此改道。如果参数不支持或查询条件不完整，就返回明确的结构化错误，由 Agent 追问或安全结束，不猜参数。

这样做的核心是：工具边界负责保证调用合法，业务逻辑负责保证结果可信，模型负责提出调用意图。

本题 1–2 分钟总结

工具应窄而专，输入输出使用明确 schema，错误码稳定，权限和副作用边界清楚。模型选错工具或传错参数时，服务端 schema 校验后拒绝并给出可纠正提示；参数缺失或业务歧义就追问，不猜参数，更不能把权限错误改道到其他工具。

追问追问 12-A：工具选错或参数错误时，何时允许重新规划？如何避免重复执行并安全收尾？

我顺着工具这块继续问一个更偏 失败恢复与规划修复 的问题：

你说如果模型选错工具，执行引擎可以“有限次数重新选择”。那这个“重新规划”具体怎么触发、怎么限制？什么错误允许重新规划，什么错误绝不允许？重新规划时会不会重复调用已经成功的工具？如果重规划两次还是失败，系统最终怎么收尾？

我会把“重新规划”限定为修复可纠正的计划或参数错误，不让模型对所有失败都再试一次。初始计划之外，最多允许 2 次重规划；每次都检查预算和请求 deadline。工具执行错误先分类，再决定是重试、重规划、澄清还是终止。

错误类型处理方式
选了注册表中不存在或当前任务不适用的工具执行引擎拒绝调用；可把允许工具范围和错误类别反馈给规划节点，重新规划一次
参数缺字段、字段类型错误，且错误信息足够明确可以有限重规划修正参数；如果缺的是用户才能提供的信息，则追问用户
下游超时或暂时不可用对原来的只读工具做有限重试，不让模型换工具绕过故障
权限拒绝、越权、安全策略拒绝立即终止该任务，绝不重规划去换身份、换工具或缩小条件绕过
指标版本下线按权威指标目录重新校验版本和契约；不让模型自行挑一个新版本
deadline 耗尽、重试预算耗尽停止调用，进入收尾
写操作结果不确定，例如请求超时先按操作 ID 查询执行状态；未确认前不重新规划或再次提交写操作

重新规划时不会把 DAG 从头重跑。状态里按 task_id 记录每个任务的状态、输入契约、结果引用和计划版本。已经成功的只读任务保留结果，只重新生成失败任务；若重规划改变了它的依赖或关键输入，就把受影响的下游任务标记为失效，重新校验后再执行。对写操作则依靠幂等键和状态查询防止重复副作用。

如果两次重规划后仍失败，就停止自动修复并安全收尾：必需的指标查询失败，不给出指标数值；辅助的口径或血缘任务失败，可以返回其他已验证结果，并明确说明缺失部分。系统记录失败阶段、错误类别、已尝试次数和结果状态，便于追踪。

一句话概括：可修复的路由或参数错误才有限重规划；权限和安全错误绝不改道；已成功的任务尽量复用；到达次数或时间上限就明确收尾。

本题 1–2 分钟总结

重新规划只针对可修复的意图解析或工具参数问题，设置次数上限并保留已成功任务结果，避免重复执行。权限、安全和业务拒绝不可触发绕过式重规划；写操作结果不确定先查状态。达到预算仍失败，就返回明确错误、部分结果或转人工。

主问题问题 14：业务规则应放在哪里？规则变更如何审批、发布、验证和回滚？

我换个方向，问一个更偏 Agent 与业务规则边界 的问题：

你前面一直强调“模型不直接决定业务口径、权限和写操作”。那在实际系统里，业务规则是怎么表达的？是硬编码在服务端代码里、配置在规则引擎里，还是有一部分放在知识库或 Prompt 里？如果业务方要改一个规则，比如“逾期率的某个渠道以后不计入”，你们希望怎么改、怎么发布、怎么验证？

我会按规则的用途分层管理，不会把同一条业务规则同时散落在代码、Prompt 和知识库里。

规则类型放在哪里例子
权限、安全和不可违反的约束服务端权限系统、代码或策略服务用户能否查询某租户数据、工具是否只读

拿“逾期率以后不计入某个渠道”来说，我不会只改 Prompt 或知识库文本，因为那只能影响模型怎么解释，不能保证查询结果真的排除了该渠道。业务方要先明确规则含义：是从某个日期开始生效，还是需要重算历史数据；渠道按哪个维度识别；分子和分母是否都排除。随后由指标负责人审批，把条件写入有版本的指标定义或受控查询配置，并标注生效日期。

发布前，我会用一组固定样例验证新旧版本：被排除渠道是否不再计入、其他渠道的数值是否不变、分子分母是否都按新规则处理、历史期间查询是否遵循正确版本。通过代码审查和业务验收后，先在测试或影子环境对比，再按发布流程上线；保留旧版本和变更记录，发现异常可以回滚。

查询、口径说明和审计记录都应引用同一个指标版本。这样用户看到的不只是一个新数值，也能追溯它使用了哪条规则、从何时生效。核心原则是：Prompt 帮模型理解和表达规则，权威配置决定系统实际怎么算，服务端负责校验与执行。

本题 1–2 分钟总结

业务规则应按权威性分层：确定性规则在服务端或规则平台，指标定义在受治理目录，知识库用于解释，Prompt/Skill 仅作软约束。规则变更需版本化、审批、测试、灰度和回滚；不能靠直接编辑 Prompt 发布影响资金或经营口径的规则。

主问题问题 15：整个 Agent 系统你分了哪些模块？如果让你从零设计一个“企业数据 Agent”，你会怎么分阶段落地？先做什么、后做什么？你会怎么调整？

我会把企业数据 Agent 分成八个模块：接入鉴权、意图与计划、业务规则和指标目录、数据查询工具、知识检索、血缘查询、结果汇总与报告、评估观测。其中权限和指标口径由服务端权威管理；Agent 负责理解问题、选择合适的只读能力、汇总结果并解释。

如果从零开始，我会按风险和数据成熟度分阶段落地：

阶段先做什么进入下一阶段的条件
1. 定边界找一个高频、价值明确的场景；确认用户、数据范围、指标口径、权限和失败时怎么处理业务负责人确认指标定义、数据负责人确认来源、权限边界可执行

4. 扩展组合能力再加入多意图拆分、并行查询、血缘分析和部分结果返回Trace 能解释每条分支的输入、结果、失败和耗时

6. 增加报告等能力在查询链路稳定后，再做报告生成、导出、审批或写操作；高风险写操作另设审批与执行门禁每种副作用都有授权、确认、幂等和审计闭环

我会优先做指标目录和可信查询接口，因为 Agent 再聪明，如果指标定义不统一、权限过滤不可靠，回答也不可信。第一版用已登记指标和只读工具，验证“能否安全、准确地解决一个真实问题”；效果和数据治理都稳定后，再增加 NL2SQL、复杂多步编排或写操作。

落地过程中我会根据证据调整顺序：如果失败主要来自口径冲突，就先治理指标；如果数据正确但响应慢，就优化查询和并发；如果业务人员仍然频繁追问，就改善澄清和答案呈现。先把一个窄场景做成可验证的闭环，再扩范围。

本题 1–2 分钟总结

系统按基础设施、身份权限、指标目录与查询、RAG、血缘、Agent 编排、报告、审计评估和运维拆模块。落地先做单场景闭环及可信查询接口，再加入口径检索、血缘和多意图编排，最后扩展 NL2SQL 与报告。每阶段先定验收指标、权限边界和故障降级。

主问题问题 16： 你提到如果重来会优先做“指标目录 + 可信查询接口”，而不是先做 NL2SQL。那如果业务方就是有很多临时、长尾的查询需求，指标目录覆盖不了，或者他们明确要求“直接写 SQL 查”，你会怎么处理？你会不会引入 NL2SQL？如果引入，放在哪个阶段、怎么控制风险？不引入的话，怎么跟业务方解释并给出替代方案？

我会引入 NL2SQL，但把它作为受治理的即席查询入口，而不是让模型生成任意 SQL 后直接连生产数仓执行。标准、重复使用的指标仍走登记指标接口，保证口径和性能稳定；NL2SQL 用来覆盖确实存在的长尾分析需求。

我会在指标查询链路稳定后再上线 NL2SQL，按以下步骤控制风险：

  1. 先限定查询范围：只开放批准的数据集和字段，只读账号；限制单条查询、扫描范围、执行时间和返回行数。
  2. 先生成、后校验：模型生成 SQL 草案后，用 SQL AST 解析并检查表字段白名单、租户过滤、危险语句和成本上限。权限条件由服务端注入，不能相信模型自己写的租户条件；复杂或校验失败的 SQL 不执行。
  3. 从离线评估到小流量试运行：用标注问题验证结果正确性、执行成功率和越权拦截，再由分析人员抽检。对高成本或高风险查询，可以先展示 SQL 和查询计划，由有权限的人员确认。
  4. 保留降级路径：模型没把握、SQL 校验失败或查询超时，就解释具体能做什么，请用户改写，或转数据分析人员处理；不为了“回答出来”而放松限制。

如果业务方要求“直接写 SQL”，我会解释：系统可以把自然语言转换成 SQL 并执行，但“模型生成”不等于“SQL 已获授权或安全”。替代方案是给常用长尾需求提供参数化查询模板或受治理的数据探索工作台；反复出现的查询再沉淀成正式指标。

判断是否引入 NL2SQL，要看长尾需求占比、数据集治理质量、人工分析成本和错误风险。如果数据字典、权限边界或测试集还不完整，我会先补这些基础；否则 NL2SQL 带来的灵活性可能会变成不可控的错误和数仓负载。

本题 1–2 分钟总结

长尾需求可以引入受治理的 NL2SQL，但不替代标准指标接口。先限定语义视图、表和列白名单、只读执行、AST 检查、行数与成本上限、RLS，并用评测集核验业务口径；高风险或正式报表仍走登记指标。若不可安全支持，就提供参数化查询或登记指标流程作为替代。

追问追问 16-A：引入 NL2SQL 后，租户权限如何在查询模板、AST 与数据库层形成纵深防御？

我继续追问一个更偏 NL2SQL 安全与正确性 的问题：

你说“权限条件由服务端注入，不能相信模型自己写的租户条件”。具体怎么注入？是在模型生成 SQL 之后做 AST 改写，还是从查询模板/视图层就强制带租户条件？如果模型生成的 SQL 里已经带了错误的租户条件，或者用了 JOIN 绕过过滤，你们怎么发现和拦截？

我不会只靠“生成 SQL 后，在末尾拼一个 AND tenant_id = ...”来做租户隔离。它容易被 OR、子查询和多表 JOIN 绕过，也可能改变外连接的结果。核心隔离应在数据库访问层强制执行，AST 检查作为执行前的额外防线。

具体做法是：

  1. 限制可查对象：NL2SQL 只允许访问经过授权的语义视图，不开放底层原始表。每张视图的字段、租户范围和关联规则由服务端治理。
  2. 数据库再兜底：对支持的数据库启用行级安全策略（RLS）。服务端从已认证请求中取得租户身份，在事务内设置数据库会话上下文；连接归还连接池前清理上下文。模型不能提供或覆盖这个身份。
  3. 执行前解析 AST：用 SQL 解析器检查只能有一条只读查询、引用的表和字段都在白名单内、JOIN 关系符合批准规则、没有危险函数或绕过结构。拒绝不符合策略的查询，而不是靠字符串替换修补。
  4. 发现模型自带租户条件时从严处理：租户条件由服务端掌控。若 SQL 自己写了与当前租户不符的 tenant_id，直接拒绝；即使恰好相同，也不把它当作权限证明。权限最终由受控视图和数据库策略执行。
  5. 限制查询成本：再加超时、扫描量或资源组限制、返回行数上限和只读账号。

例如，模型生成了 WHERE status = 'APPROVED' OR 1=1，如果只是追加 AND tenant_id = 'A'，会因为逻辑优先级导致租户条件只约束 OR 的一边。AST 校验会识别并按策略拒绝或在受控转换中把原条件整体分组；但真正防止跨租户读取的底线仍是数据库行级策略和只暴露授权视图。模型 SQL 即使写了错误的 JOIN，也不能越过底层表的租户隔离。

因此，AST 负责判断查询结构是否允许，服务端负责绑定可信租户上下文，数据库策略负责最后的数据行隔离。任何一层无法确认安全时都拒绝执行。

本题 1–2 分钟总结

权限不能靠字符串拼租户条件。SQL 必须解析为 AST，限制可访问表、函数和语句，再由服务端绑定可信租户范围，并在数据库用 RLS 兜底。JOIN 的所有关系和视图都要覆盖授权；错误租户条件拒绝而非修补后盲跑。测试要覆盖 OR、UNION、JOIN、子查询及跨租户负例。

追问追问 16-B：SQL 安全且可执行，但业务口径算错时，如何识别并降低风险？

我接着问一个和 NL2SQL 正确性验证 有关的问题：

权限隔离你讲了防线，那正确性怎么保证？比如模型生成了一条能跑通、不越权、成本也不高的 SQL，但业务逻辑错了——比如把“逾期率”算成了“逾期客户数 / 总客户数”，而正确口径应该是“逾期金额 / 总金额”。这种错误 AST 和权限层都拦不住。你们怎么发现、怎么降低这种风险？

你举的情况确实是关键点：SQL 能执行、权限正确、成本可控，都不能证明业务口径正确。 AST 和 RLS 解决的是“能不能查、能查哪些数据”，不负责判断公式是不是用户真正要的定义。

我会用三道业务正确性控制：

  1. 已登记指标不让 NL2SQL 重算。 用户问“逾期率”，先解析到指标目录里的 metric_id，调用认证过的查询接口；分子、分母和适用范围以指标定义及版本为准。NL2SQL 不能因为自己生成了一条能运行的公式，就替代正式口径。
  2. 未登记口径先形成定义，再生成查询。 对临时指标，先明确统计对象、分子、分母、时间窗口、粒度、过滤条件和去重规则。缺少关键定义就追问；生成结构化口径供用户确认后，再编译成 SQL。涉及正式经营或监管报表时，还要业务负责人审核，不能把临时探索结果当成认证指标。
  3. 用业务测试集验证，而不只测 SQL 是否成功。 准备带有口径说明、预期 SQL 或预期结果的测试问题，按指标、维度、时间和边界案例做回归；将结果与认证接口或已核验样本对比。再检查分子分母、数据粒度和必要不变量。发现错误就定位到指标映射、语义元数据、查询生成还是结果汇总，并把案例加入回归集。

例如，“逾期率”在目录中定义为“逾期金额 ÷ 总金额”，模型却生成“逾期客户数 ÷ 总客户数”。系统应根据 metric_id 调用正式接口，或在查询契约核对时发现生成的统计对象与指标定义不一致而拒绝执行；不能因为 SQL 跑通就返回结果。

因此我会把结果区分为认证指标结果和临时探索结果，明确展示口径、版本和数据范围。模型自报的置信度不能替代口径校验；定义不完整或无法验证时，宁可追问、标注未认证或不返回数值，也不把一个看起来合理的公式当成正确答案。

本题 1–2 分钟总结

SQL 能执行且不越权，不代表业务口径正确。标准指标走权威指标目录和预置查询；长尾探索标记为临时结果，校验公式、字段、粒度和样例，对照已认证指标并展示口径假设。重要经营或监管结论需业务负责人确认，模型不能自行认证新口径。

追问追问 16-C：谁能定义或审批新指标？临时口径如何转正，口径争议由谁裁决？

我继续追问一个更偏 口径治理与组织协作 的问题：

你提到“未登记口径先形成定义，再生成查询”，涉及正式经营或监管报表还要业务负责人审核。那实际落地时，谁有权定义一个新指标？一个临时口径如果被反复使用，怎么沉淀成正式指标？如果两个业务方对同一个指标口径有争议，系统里怎么处理，谁拍板？

我不会让 Agent 或单个开发人员自行“批准”新指标。指标口径的业务责任应由对应业务域的指标负责人承担；数据负责人负责确认数据来源、粒度和实现方式；风险、财务或合规相关指标还要经过相应控制部门审核。具体审批链会按机构治理制度配置。

临时口径被反复使用时，使用频率可以触发“转正式指标”的提案，但不能自动升级。提案要补齐指标名称、定义、分子分母、粒度、过滤条件、生效时间、数据来源、负责人和测试样例，再经业务与数据责任人审核、验收后发布到指标目录。目录记录版本、审批人、生效日期和变更历史；查询和报告引用具体版本，旧版本按规则保留或标记失效。

如果两个业务方对同名指标有不同理解，我不会把它们覆盖成一个定义。先判断它们是否其实属于不同业务范围，例如不同产品线、法人或报表用途；如果是，就用不同的指标 ID 和适用范围表达。若确实是同一范围内存在争议，就标记为待裁决，指定该指标所属业务域的负责人拍板；监管或财务口径则由相应的合规或财务权责方确认。在裁决完成前，Agent 展示定义及适用范围并要求用户选择，不能擅自挑一个口径。

这套治理的核心是：使用数据帮助发现该沉淀什么，业务责任人批准定义，数据和技术团队验证能否正确计算，Agent 只读取已发布的权威版本。

本题 1–2 分钟总结

新指标由业务指标负责人提出定义，数据团队实现，治理或风险负责人审批发布。高频临时口径只触发标准化提案，不自动升级；争议由指定业务 owner 裁决，记录指标 ID、版本、适用范围和变更历史。同名不同义用不同 ID，避免名称碰撞。

追问追问 16-D：指标口径变更后，历史报告、重算、版本兼容与旧版本下线如何治理？

我顺着治理再问一个更偏 版本与变更管理 的问题：

你提到指标目录要记录版本、审批人、生效日期和变更历史，查询和报告引用具体版本。那如果某个指标口径发生了变更，比如“逾期率”的分子从“逾期金额”改成“逾期本金”，但历史报告还需要按旧口径解释。你们怎么设计版本兼容、历史重算和报告溯源？旧版本什么时候可以彻底下线？

我会把指标版本设计成不可原地覆盖、按生效时间管理。例如，v3 的分子是“逾期金额”，v4 改成“逾期本金”，就发布一个新版本，记录定义、计算逻辑、审批人、生效时间和变更原因；v3 的内容保持不变。

历史报告默认遵循“按当时口径复现”：报告保存指标 ID 和版本、查询条件、数据时点或快照、来源血缘，以及生成时间。用户重开旧报告时，系统使用原版本和原数据时点展示。若要按新口径重算历史数据，则作为一次明确的“重述”或“重算”任务，生成新报告，并同时标明新旧版本和差异；不静默覆盖原报告。

因此要区分两个时间概念：

  • 口径版本的生效时间：决定某个业务期间适用哪一版定义。
  • 数据快照时间：决定当时查询使用哪一批数据。

这样才能区分“口径变了”和“底层数据后来修订了”。如果只保存 SQL、不保存数据快照或可复现的数据时点，历史结果未必能原样重现。

旧版本可以先停止作为新查询的默认版本，但是否彻底下线，要看仍需复现的报告、监管和审计要求、数据保留能力，以及是否还有业务依赖。更安全的生命周期是：新版本发布后，旧版本先标记为弃用，保留历史查询能力；依赖迁移完成且保留义务结束后，才评估退役。退役也应有审批和影响检查，不能仅因为“已经有新版”就删除旧口径。

本题 1–2 分钟总结

指标版本需有生效区间、审批人、公式和实现版本。历史报告固定引用当时版本与数据快照，默认不被新口径覆盖；重算要明确标注重算版本及原因。旧版本在历史查询和审计保留期结束、无依赖且完成迁移后才可退役，不能直接删除。

追问追问 21-A：指标目录、语义层、Schema 和血缘无法跨系统原子发布时，如何处理部分更新？

我接着追问一个更偏 元数据同步一致性 的问题：

你说“关键指标更新时先在暂存区校验，再原子发布，避免查询看到半新半旧的元数据”。但真实系统里，指标目录、语义层、数仓 Schema、血缘数据往往不在同一个系统里，也很难做到真正的跨系统原子发布。那如果一次变更涉及多个系统，比如指标定义更新了，但语义层实现还没跟上，或者血缘还没刷新，你们怎么处理这种“部分更新”状态？查询侧怎么感知和应对？

我不会把“原子发布”理解成跨指标目录、语义层、数仓和血缘系统做一个分布式事务。实际做法是：各系统分别准备版本，由一个发布清单决定哪些版本可以一起被查询使用。

例如逾期率准备从 v3 升到 v4，发布清单会记录：

metric_definition = v4
semantic_query   = v4
warehouse_schema = schema-版本-17
lineage_snapshot = lineage-版本-82
release_status   = candidate

各系统完成更新后，发布流程逐项做兼容性和结果校验。指标定义与查询实现都通过后，才把清单状态切到 active。查询开始时读取一份固定的发布清单，整次请求都按其中的版本执行，避免指标定义已经是 v4、SQL 实际仍是 v3。

如果指标目录已更新、语义层还没跟上，v4 就保持 candidate，不接新查询；只要 v3 仍安全有效，就继续使用 v3。若旧版已不能安全执行，就明确返回“指标口径正在更新，暂不可查询”，不混用版本，也不静默回退到含义不同的口径。

血缘更新失败要看它是不是本次请求的必需信息：查数可以继续，但把血缘标记为过期或暂不可用；用户明确要求血缘时，则返回部分结果并说明血缘数据的更新时间。如果 Schema 变化会影响指标计算正确性，就不能只把血缘当辅助信息，而要阻止相关指标继续执行，直到语义层和查询校验通过。

具体实现上，每个组件发布不可变版本，发布清单记录版本引用、校验结果和状态；变更流程可重试、可对账，失败时保留旧的可用清单或将新版本隔离。查询侧在执行前检查清单状态、版本兼容性和必要元数据的新鲜度。核心原则是：跨系统不强求瞬时一致，而是让每次查询使用一组明确、经过验证且彼此兼容的版本。

本题 1–2 分钟总结

跨系统难以真正原子发布，因此采用发布清单和兼容状态管理。新指标定义、语义实现、Schema、血缘都校验通过后才发布一个一致性清单；未就绪组件标记不可用或保持旧版本。查询侧按清单版本执行，不拼接半新半旧元数据。

主问题问题 23： 假设一次查询开始时读取了发布清单，决定用 metric_definition=v4 / semantic_query=v4 / schema-17 / lineage-82 。但这条请求执行到一半，发布清单被切到了 v5，或者语义层 v4 被下线了。这时候你希望这次查询怎么处理？是继续按开始时固定的版本跑完，还是中途切换到新版本？如果继续跑完，结果怎么标注？如果切到新版本，会不会导致同一请求里前后不一致

我会让请求在开始时固定一个发布清单版本，并在整次请求中继续使用它。即使处理中途 v5 成为最新版本，也不在这次请求里切换。否则数据查询可能按 v4 算，口径说明却按 v5 解释，最终回答内部不一致。

请求上下文会记录类似 release_id 的标识，并把它引用的指标定义、查询实现、Schema 和血缘版本传给每个任务。执行结果也带上这些版本信息，以及数据时点；最终答案和报告可以据此追溯。并行分支即使在清单切换后启动，也必须拿到请求开始时固定的清单，不能各自读取“当前最新版本”。

发布 v5 只代表新请求开始使用 v5，不应立刻删除 v4。v4 进入弃用后，要保留一段兼容期，并等正在使用 v4 的请求结束，再退役相关实现和依赖。

如果 v4 在请求中途意外不可用，我不会悄悄把剩余步骤换成 v5。对于只读请求，可以在确认没有副作用后，丢弃这次未完成的结果，并用 v5 从头重新执行，同时重新校验契约；如果无法安全重跑，就终止并说明查询失败。不能把 v4 已完成的分支和 v5 新跑的分支直接拼在一起。

所以规则是：请求内固定版本；版本切换发生在请求边界；旧版本保留到在途请求结束；若固定版本无法继续，则整次重启或安全失败，不中途混用。

本题 1–2 分钟总结

每次请求开始时固定发布清单与组件版本，整条链路使用同一版本快照，不中途切换。结果标注指标版本、Schema/快照时点和发布清单 ID；若旧组件在请求中不可用，按兼容策略失败或降级，不偷偷改到新版本造成前后不一致。

主问题问题 24：多个租户、多个业务线接入时，指标、权限、模型配置怎么隔离？如何避免租户间串数据？

我会把租户隔离设计成贯穿身份、数据、元数据、缓存和运行状态的服务端边界，不依赖模型自己记住“当前是哪家租户”。

请求入口从认证令牌中取得 tenant_id 和用户身份，服务端建立可信的权限上下文。模型不能在参数里指定或修改租户；每次工具调用都由执行层注入这个上下文，并重新做授权校验。

具体来说：

  • 数据层：查询只访问授权视图或数据集；数据库用行级安全策略或租户隔离的 Schema/数据库限制可见数据。租户过滤不靠模型生成的 SQL 条件。高敏租户可以采用独立数据库或实例。
  • 指标与知识层：指标和文档带有租户、业务线、适用范围等元数据。共享指标可以由平台发布，租户定制口径则作为独立版本或覆盖项管理，不能无审核地覆盖全局定义。检索先做权限过滤，返回后再校验文档范围。
  • 状态与缓存：会话状态、记忆、任务队列和缓存键都包含租户与必要的用户/权限范围，避免 A 租户的结果被 B 租户命中。缓存命中后仍校验权限和版本。
  • 模型配置：按租户配置允许使用的模型、提示词版本、工具清单和预算；密钥由服务端密钥管理系统读取，不进入 Prompt、Trace 或其他租户可读数据。

业务线也作为授权范围的一部分处理：用户只能访问自己获批的租户和业务线组合。对于跨业务线查询，必须有明确授权和审计记录，不能因为指标名称相同就默认共享数据。

最后用跨租户测试验证隔离：用租户 A 的身份尝试查询 B 的记录、猜测 B 的指标 ID、复用 A 的缓存键或会话 ID，都应在服务端被拒绝；并检查数据库策略、检索结果和审计日志。核心原则是：租户身份来自可信认证，权限在服务端逐层执行，模型只处理经过授权的数据。

本题 1–2 分钟总结

多租户隔离要贯穿身份、配置、缓存、检索、工具和数据库。每条数据带 tenant_id 与业务线范围；查询前授权过滤，缓存键含租户和权限版本，RAG 元数据先过滤再复核，数据库 RLS 兜底。用跨租户正反例和连接池复用测试证明不会串数据。

主问题问题 25：记忆系统如何设计

对 B 端指标问答 Agent，我会把记忆分成会话状态和跨会话长期记忆。会话状态用于完成当前任务；长期记忆只帮助改善之后的交互，不作为指标口径、权限或业务数据的权威来源。

本轮对话
  ↓
提取候选记忆 → 过滤敏感信息 → 用户确认或规则校验
  ↓
按租户和用户隔离保存
  ↓
新请求到来 → 权限匹配、时效检查、相关性排序
  ↓
只注入少量相关记忆

会话状态可以保存当前已确认的指标、时间范围、维度、澄清结果和任务进度，比如“本轮查的是 2026 年 9 月各渠道逾期率”。任务结束或超时后按策略过期。跨会话记忆则只保存确实有复用价值的信息，例如用户偏好的展示方式、常用业务线或已确认的内部术语。

我不会把借款人姓名、证件号、单笔申请资料、客户级审批结果或一次性查询数值写入长期记忆。授权信息也不作为记忆继承：每次查询仍由服务端重新鉴权，指标定义与版本仍查权威指标目录。

每条长期记忆都记录所属租户和用户、来源、创建时间、有效期及确认状态。召回时先按权限范围过滤，再检查是否过期、是否被用户撤销，最后按相关性取少量内容；不能因为语义相似就跨租户召回。发生新旧偏好冲突时，优先采用用户最近明确确认的内容；业务事实冲突则回到权威数据源核实，不能靠记忆裁决。

用户应能查看、更正和删除自己的记忆，删除操作留审计记录。简而言之：记忆保存“以后可能有用的用户偏好和对话状态”，不保存权限，也不替代业务事实来源。

本题 1–2 分钟总结

记忆分会话状态和跨会话长期偏好。只保存必要、低敏、可解释的信息，如展示偏好或已确认的业务术语，不保存客户级敏感数据；每条有主体、租户、来源、时间和过期/删除策略。召回要重新做权限、相关性和时效校验。

主问题问题 26： 你提到“提取候选记忆 → 过滤敏感信息 → 用户确认或规则校验 → 保存”。那实际运行时，什么情况下会自动写入长期记忆，什么情况下必须让用户确认？如果用户说了一句“以后都按这个口径查”，这算长期记忆、临时会话状态，还是指标偏好？系统怎么判断该不该记、该记多久？

我会先判断这句话属于当前任务状态、个人查询偏好，还是业务口径变更，再决定是否保存。关键不是它说了“以后”，而是对象、适用范围和用户有没有权限都明确。

情况处理方式
当前对话里确认了指标、时间或维度自动记入会话状态，任务结束或会话过期后清理
用户明确要求保存一个清楚、低风险的个人偏好通过权限和敏感信息检查后，可保存为个人偏好，并告知用户可查看或删除
从多次行为推测出的偏好先作为候选，不默默写成长久记忆；必要时询问用户
涉及正式指标定义、机构级默认口径、监管规则、权限或客户信息不写入普通记忆；走指标治理或权限变更流程

比如用户刚才明确选了“余额逾期率”，并说“以后查逾期率默认按这个口径”，我会检查“这个口径”是否确实指余额逾期率，以及范围是这个用户个人、某条业务线还是整个机构。如果只是个人偏好且系统政策允许，我可以保存为：

类型：个人指标选择偏好
指标：逾期率
偏好版本：余额逾期率 v3
范围：该用户当前租户与业务线
来源：用户明确要求

它不是指标定义，也不会改写指标目录。后续用户只说“逾期率”时，如果该偏好仍有效、且平台允许个人默认值，系统可以按这个偏好查询，并在答案里注明使用了哪种口径；如果问题涉及正式报表，或机构规则要求显式选口径，就仍要澄清。

如果用户只说“以后都按这个口径查”，但前文有多个口径，或“都”可能指多个指标、业务线或全体用户，我会先追问范围，不保存。偏好有效期由机构策略配置；例如低风险展示偏好可以设一个可续期的有效期，用户可随时更改或删除。口径事实的版本有效期则由指标治理系统决定，不能让个人记忆延长或替代它。

本题 1–2 分钟总结

长期记忆先分类：明确的个人偏好可在规则允许时自动保存或提示确认；涉及业务定义、共享知识或高风险决策必须走权威治理流程。‘以后都按这个口径’先视作个人查询偏好，不自动修改指标定义；记录主体和有效期，必要时让用户确认。

追问追问 26-A：长期记忆中的口径偏好与新版本、机构政策冲突时如何处理？

我接着追问一个更偏 记忆召回与冲突处理 的问题：

假设用户之前保存过一个个人偏好：“以后查逾期率默认按余额逾期率 v3”。但后来指标目录把余额逾期率升级到了 v4，或者机构政策要求正式报表必须显式确认口径。那下次用户只说“查逾期率”时，系统会怎么处理这个旧偏好？是直接用 v3、自动切到 v4、还是先澄清？如果用户说“就按我以前那个口径”，但 v3 已经退役了，怎么办？

我会先按政策、指标目录、用户偏好的优先级处理：机构政策优先；指标目录决定当前可用定义和版本；个人偏好只用于在允许范围内选择指标类型，不能让已退役版本继续生效。

所以原偏好“余额逾期率 v3”不会让新查询继续跑 v3：

  • 如果目录把 v4 明确登记为 v3 的后继版本，且这类查询允许使用默认口径，系统可按“余额逾期率”解析到当前有效的 v4，并在答案里说明用了 v4。
  • 如果机构政策要求正式报表显式确认口径，旧偏好不能跳过确认门；用户只说“查逾期率”时，系统先请用户确认。
  • 如果目录没有说明 v4 是 v3 的兼容后继，或者新旧口径含义有变化，就不能自动迁移偏好，需要澄清。

如果用户说“就按我以前那个口径”，但 v3 已退役，我会区分他要的是旧口径的定义，还是要重新查看以前某份结果。如果历史报告和数据快照仍可合规访问，可以展示原报告及其 v3 版本信息；若要对新数据按 v3 重算，只有在系统仍允许受控执行该版本时才能做。否则明确说明 v3 已退役，提供当前 v4 定义供用户确认，不能把 v4 的结果标成旧口径结果。

一句话说：个人偏好可以帮助选择指标类型，不能覆盖机构政策或钉死已失效版本；版本升级按权威目录处理，无法确认语义连续时先澄清。

本题 1–2 分钟总结

个人偏好不能覆盖权威指标版本或机构政策。查询时先看当前指标目录和场景规则，再判断旧偏好是否仍兼容；版本已退役或正式报表要求显式选口径，就澄清或自动采用当前有效定义并说明。用户说沿用旧口径也不能执行已下线版本。

主问题问题 28：权限系统如何设计

对这个 B 端指标问答 Agent，我会把权限做成服务端统一决策、每次工具调用强制执行的机制。模型可以提出“查哪个指标、哪些维度”，但不能决定“这个用户有没有权查”。

权限判断先分两步：认证确认“你是谁”，授权确认“你能对哪些数据做什么操作”。授权不能只看角色，还要结合租户、业务线、数据集、指标、行范围和操作类型。

用户身份认证
    ↓
构建可信权限上下文
    ↓
解析请求与执行计划
    ↓
工具执行前做资源级授权
    ↓
数据库 / 检索层再次执行数据范围过滤
    ↓
记录审计结果

策略可以按 RBAC + 属性条件 来表达：角色负责基础能力，例如业务分析员可查询、指标负责人可维护定义；属性条件进一步限制租户、业务线、数据等级、指标范围和时间范围。最终按“主体 × 操作 × 资源 × 数据范围”判断，并采用默认拒绝：没有明确授权就不执行。

不同工具要在数据所在层落实权限：

  • 指标查询在服务端校验指标和维度范围，再使用授权视图或数据库行级安全策略限制数据行。
  • RAG 检索前按租户和部门做硬过滤，返回后再检查文档 ACL。
  • 血缘查询不仅校验起点表，也要逐层检查返回的表和字段是否可见，避免从血缘结果泄露无权访问的资产。
  • 缓存、会话状态和记忆按租户及用户权限范围隔离；命中缓存后仍重新校验当前权限。
  • 写操作还要校验操作权限、审批状态和执行前权限是否仍有效。

例如，用户有“逾期率查询”能力，但只被授权访问华东业务线，服务端会在查询执行时把范围限制在华东数据；模型即使生成“查全国”的计划，也不能扩大这个范围。权限被收回后，下一次工具调用就拒绝，不能沿用上一轮授权结果。

最后，每次授权决策都记录主体、资源、操作、策略版本和结果；敏感数据本身不写进普通日志。权限服务不可用、上下文缺失或范围无法确定时，采用 fail closed，也就是拒绝查询并提示权限暂不可校验。

本题 1–2 分钟总结

权限体系包括认证、工具功能授权、数据行列授权和指标授权，服务端在工具执行前强制注入可信范围，数据库 RLS 兜底；另需参数脱敏、权限缓存主动失效、审计和故障 fail-closed。身份来自可信认证而非模型参数，权限决策与提示词分离。

JWT / Cookie
    ↓
UserResolver：解析 User(id, group_memberships)
    ↓
授权检查
  ├─ 功能权限：user_groups → tool_groups
  ├─ 数据权限：transform_args 注入数据范围
  └─ 指标权限：指标平台检查
    ↓

    ↓

第一层是认证：确认用户是谁。 UserResolver 从 JWT 或 Cookie 解析身份，生成可信的 User(id, group_memberships)。后续授权使用这个服务端身份，不接受模型通过工具参数传入的 user_id 或 tenant_id。

第二层是授权：确认用户能做什么。 我会检查三类权限：

  • 功能权限：用户组能不能调用某个工具，例如 run_sql。通过 user_groups 和 tool_groups 做映射。
  • 数据权限：工具能查哪些表、行和列。服务端根据用户授权，通过 transform_args 注入过滤条件；如果参数里带了与可信上下文冲突的数据范围，不能照单执行。
  • 指标权限：用户是否有权访问具体指标，由指标平台根据指标及其适用范围判断。能调用查询工具，不代表能看所有指标。

第三层是参数脱敏。 配置 sanitize_tool_parameters=True 后，日志中的敏感工具参数会打码，例如用户标识、业务字段或查询条件。它保护的是日志内容，不能代替查询权限校验或数据库隔离。

第四层是数据库兜底。 对 PostgreSQL 使用行级安全策略（RLS），例如基于可信的租户上下文设置 tenant_id 条件。即使应用层过滤出现遗漏，数据库仍会强制限制可见行。应用层注入与数据库 RLS 是两道防线，不能只依赖其中一层。

第五层是审计。 log_tool_access_check 记录授权检查结果，log_tool_invocation 记录工具调用情况，便于回答“谁在什么时候，对什么资源做了什么操作，结果如何”。审计日志也需要避免记录未脱敏的敏感数据。

举例来说，某用户属于“华东分析组”，并被授权查看“逾期率”指标。请求到来后，系统先确认身份，再检查该组能否调用 run_sql、能否访问逾期率及华东数据范围。transform_args 将可信的数据范围加入查询参数，指标平台检查指标权限，最后 PostgreSQL RLS 再限制行。即使模型请求全国数据，也不能扩大用户范围；权限服务不可用或权限范围无法确定时，默认拒绝。

这套设计的边界是：认证回答“你是谁”，授权决定“能调用什么、能看什么”，脱敏保护日志，RLS 在数据库兜底，审计负责追溯。

本题 1–2 分钟总结

权限可以概括为认证、授权、脱敏、数据库兜底和审计五层：UserResolver 从 JWT/Cookie 得到可信用户；按用户组校验工具、数据和指标权限；transform_args 注入数据范围；日志参数脱敏；PostgreSQL RLS 再限制行；访问检查和工具调用写审计。服务间认证可以用服务身份，但数据授权仍绑定经验证的用户主体。

追问追问 28-B：RLS 具体如何配置？连接池怎样避免租户上下文串用？

PostgreSQL RLS 可以用事务内的租户上下文实现。每次请求先验证 JWT/Cookie，由服务端得到可信的 tenant_id，再在同一个数据库事务里设置上下文并执行查询。

-- 由表所有者/迁移角色配置；应用运行角色不能是 superuser、表所有者或 BYPASSRLS
ALTER TABLE metric_results ENABLE ROW LEVEL SECURITY;
ALTER TABLE metric_results FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON metric_results
  FOR SELECT
  USING (
    tenant_id =
      NULLIF(current_setting('app.tenant_id', true), '')::uuid
  );

GRANT SELECT ON metric_results TO agent_reader;

如果没有设置 app.tenant_id，current_setting(..., true) 会返回空值，条件不会匹配任何行，结果就是默认拒绝。FORCE ROW LEVEL SECURITY 让表所有者通常也受策略约束；不过 PostgreSQL 超级用户和带 BYPASSRLS 属性的角色始终能绕过 RLS，所以 Agent 运行账号不能拥有这些权限。PostgreSQL RLS 文档

应用层要把设置租户上下文和查询放在同一事务、同一连接中：

async with pool.connection() as conn:
    async with conn.transaction():
        await conn.execute(
            "SELECT set_config('app.tenant_id', %s, true)",
            (str(trusted_tenant_id),),
        )
        rows = await conn.execute(
            "SELECT metric_id, value FROM metric_results WHERE metric_id = %s",
            (metric_id,),
        )

set_config(..., true) 中的 true 表示只在当前事务生效。事务提交或回滚后，这个值就不再留给连接池里的下一个请求使用。要避免用会话级 SET app.tenant_id = ...，因为连接归还池后，若清理不完整，下一租户可能拿到带有旧上下文的连接。PostgreSQL 文档说明 is_local=true 只影响当前事务；SET LOCAL 也会在事务结束时失效。PostgreSQL set_config 文档 PostgreSQL SET LOCAL 文档

有个重要边界：事务级自定义变量能避免连接池串租户，但不应单独视为抵御任意 SQL 的完整安全边界。 如果同一个数据库账号可以执行任意 SQL，它也可能尝试修改自己的会话变量。因此还要限制 Agent 只能执行经过 AST 校验的只读查询、拒绝 set_config 等危险调用，并只授予访问受控视图的权限。高隔离要求下，再考虑按租户使用独立数据库角色，或采用数据库侧能验证的可信身份上下文。

上线前我会做连接池串租户测试：租户 A 查询后提交、回滚、异常退出，再让同一池连接处理租户 B；B 都不应读到 A 的记录。也要验证缺失租户上下文时返回零行，以及运行角色不能绕过 RLS。

本题 1–2 分钟总结

PostgreSQL RLS 可用策略按可信租户上下文过滤行，连接池必须在每个事务开始时由服务端设置事务级上下文，结束时清理或回滚，并避免会话级状态泄漏。上下文不能由模型 SQL 任意修改；运行角色不能是表所有者或 BYPASSRLS。测试连接复用和异常回滚。

追问追问 28-C：权限服务不可用时，Fail Closed 如何兼顾安全与可用性？

会有可用性影响，所以我不会把“fail closed”设计成整个 Agent 都停摆，而是只关闭无法安全授权的能力，保留不依赖该权限判断的安全功能。关键是降级不能把“无法确认权限”变成“默认允许”。

权限服务不可用时，我会这样处理：

  1. 短暂故障先有限重试：对权限服务做有上限的重试、熔断和超时控制，避免请求堆积把故障放大。
  2. 按风险决定能否用缓存决策：对于低风险只读查询，可以在机构政策允许时使用短时、带版本和过期时间的最近有效授权结果；缓存必须绑定用户、租户、资源和操作，不能扩大原授权范围。需要实时撤权或涉及敏感数据的查询，不使用过期授权缓存。
  3. 高风险操作直接停止：写操作、额度变更、审批，以及权限范围不明确的查询，在权限服务不可用时一律不执行；不能靠旧授权、模型判断或换工具绕过。
  4. 提供安全的部分服务：如果部分能力不依赖权限服务，例如展示通用使用说明，可以继续提供；需要授权的数据查询返回“当前无法完成权限校验，请稍后重试”，不误报成“你没有权限”，也不返回数据。
  5. 恢复后重新鉴权：排队或延迟执行的请求不能沿用故障期间的授权结果，恢复后必须重新校验。

同时监控权限服务可用率、授权延迟、缓存命中与过期拒绝次数，并部署多实例或故障隔离，减少服务本身成为单点。

一句话概括：可用性通过冗余、短时重试和有限缓存来改善；授权无法确认时，高风险和敏感数据操作仍然拒绝，其他安全功能尽量保持可用。

本题 1–2 分钟总结

权限服务故障时，写操作、审批和敏感查询 fail closed；低风险只读是否用短期缓存取决于机构策略。缓存不能扩大已授权范围，恢复后重新鉴权。通过多实例冗余、有限重试改善可用性，但不能默认放行；对外区分权限暂不可校验与无权访问。

追问追问 28-D：低风险只读如何定义？授权缓存、撤权失效和 RLS 上下文如何协同？

我会把“低风险只读”和缓存策略写进权限策略，由业务数据负责人、安全/合规负责人和平台团队共同确定并审批，模型不能自行判断风险等级。

低风险只读怎么界定

按数据敏感度、潜在影响、是否可逆、是否涉及客户权益和监管要求分级。例如，查询已脱敏的汇总指标通常风险较低；查询客户级财务明细、PII 或监管报表属于高敏感；任何写操作和审批操作都按高风险处理。“只读”本身不等于低风险，读出客户明细也可能是高风险。

授权缓存怎么做

缓存的不是宽泛的“这个人有权限”，而是有明确范围和版本的决策。缓存键至少包含：

user_id + tenant_id + action + resource + data_scope + policy_version

缓存值包含允许的行/列范围、权限版本、签发时间和过期时间。一个可讨论的初始策略是：低敏汇总查询的授权决策最多缓存 30 秒；客户级敏感数据、写操作和审批操作不接受过期授权，要求实时校验。这个 TTL 是设计建议，最终应由机构按撤权时效要求批准，不能当作通用标准。

权限变更通过事件通知各节点失效相关缓存；缓存版本或授权版本变化时也必须重新校验。若失效事件丢失，TTL 是最后的时限上界。机构还要明确允许的最大撤权传播延迟。高风险场景不能因为缓存尚未过期就继续放行。

RLS 上下文由谁注入

tenant_id 和授权范围由服务端认证/授权中间件从已验证的身份与授权决策中取得，再在同一数据库事务内用绑定参数设置事务级上下文；模型和用户提交的 SQL 参数不能决定它。

权限服务暂时不可用时：

  • 有仍在有效期内、策略允许用于该类低风险查询的授权决策租约，就只能按租约中的原范围注入 RLS 上下文。
  • 没有有效租约，或者当前操作属于敏感查询、写操作、审批操作，就不注入可访问范围，RLS 默认拒绝；不能用 JWT 里过期或未经授权的租户字段代替授权决定。

另外，RLS 的自定义会话变量不能单独防御可以执行任意 SQL 的数据库账号。因此 Agent 查询仍必须受只读角色、SQL/AST 白名单或受控视图约束，禁止查询自行修改 RLS 上下文；更高隔离要求可采用租户独立数据库角色等方案。

面试时可以总结为：风险等级由业务和安全治理确定；授权缓存绑定主体、资源、范围和策略版本，低敏只读可短时缓存，高敏和写操作要求新鲜授权；撤权事件主动失效、TTL 限制最大滞后；RLS 上下文由服务端在授权成功后注入，无有效授权就不注入并默认拒绝。

本题 1–2 分钟总结

低风险由安全、业务和数据负责人按数据敏感度、操作副作用及影响范围定义，不由模型决定。缓存键绑定租户、用户、操作、资源、范围和策略版本，按风险设 TTL，并靠事件主动失效。权限服务挂了仍需可信上下文注入；注入失败就拒绝，RLS 不能凭空恢复缺失的授权。

追问追问 28-E：权限服务降级和授权缓存策略的回答补充

会有可用性影响，但我不会让整个 Agent 停摆，而是只关闭无法安全授权的能力。写操作、审批和敏感数据查询在权限服务不可用时一律停止；低风险只读查询可以在机构政策允许时，使用短时、带版本、绑定用户和资源的最近授权缓存，但不能扩大原授权范围，恢复后必须重新鉴权。数据库 RLS 可以作为数据隔离兜底，但不能替代权限判断。对外要区分“权限暂不可校验”和“无权访问”，不返回数据，也不默认放行。可用性靠冗余、重试和有限缓存改善，但安全底线不能降。

缓存设计

本地内存缓存，&#x5B58;在每个 Agent 服务实例的内存里。+Redis 集中缓存带策略版本，Redis 不是权限的权威来源，只是权限服务不可用时的短时兜底。

追问追问 28-F：写操作幂等键具体如何生成、校验和恢复？

写操作的幂等键要代表同一次业务操作，不是某一次 HTTP 请求或模型工具调用。比如“把客户 C 的额度从 100 万调整到 150 万”是一次业务操作；网络超时后重试，必须沿用同一个键。

怎么生成

用户或 Agent 发起一项新操作时，由服务端为这次逻辑操作生成一个随机、不可猜的 operation_id / idempotency_key，并在工作流状态中持久化。后续重试、断点恢复都复用它。

不要每次重试都新生成一个键，也不要直接用 tool_call_id：模型重新调用工具时，tool_call_id 可能变化，但业务操作还是同一笔。也不建议只用请求参数做哈希，因为用户以后可能确实再次提交相同参数，那应当是一笔新的操作。

怎么校验和执行

服务端把幂等键限定在租户和操作范围内，例如用唯一约束：

UNIQUE(tenant_id, operation_type, idempotency_key)

同时保存规范化后的请求指纹，覆盖目标客户、变更前后额度、审批单和关键业务参数。收到请求后：

  • 键不存在：原子地登记为 PENDING，校验权限、审批和当前额度版本，然后执行。
  • 同一个键、请求指纹相同，且已成功：返回之前保存的结果，不再执行一次。
  • 同一个键、仍在执行：返回处理中状态或操作 ID，不并发重复执行。
  • 同一个键、请求指纹不同：拒绝请求，避免一个键被拿去提交另一项操作。
  • 结果未知或请求超时：先按 operation_id 查询业务系统状态；确认未执行后，才用同一幂等键继续，不盲目重新发起。

简化流程：

创建操作 → 生成并持久化幂等键 → 校验权限与审批
                                  ↓
                         条件更新 / 调用下游
                                  ↓
                  保存结果状态 → 重试时查状态并复用结果

例如额度调整还应加并发版本检查：执行时要求客户额度仍是读取时的 100 万、记录版本仍为 42；若被其他流程改过，条件更新失败，操作进入冲突状态，不能覆盖新值。幂等键防重复执行，版本检查防并发覆盖，两者解决的是不同问题。

对跨服务调用，幂等键要继续传给下游；如果下游不支持幂等，就需要本地操作账本、状态核对和补偿流程。记录也不能只保留几分钟：幂等记录至少要覆盖重试、恢复和业务审计所需的时间；对额度等关键操作，通常会与业务操作记录一起持久保存。

本题 1–2 分钟总结

写操作幂等键由服务端按租户、用户、操作、资源、规范化参数和客户端请求 ID 生成，存幂等记录表并有 processing/succeeded/failed/unknown 状态。重复成功返回原结果，处理中不重复执行，unknown 先按 operation_id 查业务系统。幂等防重复，不替代权限、审批和版本检查。

追问同一追问的补充回答：稳定操作 ID、参数指纹与跨系统恢复

这版已经很扎实，unknown 状态和“幂等不替代权限、审批、版本校验”尤其关键。我会再收紧两个实现细节：

  • request_id 必须是同一次逻辑操作可复用的 ID，重试和断点恢复时不能变成新的请求 ID；否则每次都会生成新幂等键，挡不住重复执行。
  • “失败”要区分确定未执行的终态失败和执行结果不确定。后者应标为 unknown，先查业务系统状态；不能因记录为 failed 就直接重发。

面试时可以这样回答：

写操作开始时，服务端为这次逻辑操作生成稳定的 operation_id 和幂等键。键按租户、发起用户、操作类型、目标资源及稳定的操作请求 ID 做作用域隔离；同时保存规范化参数的请求指纹。这里的请求 ID 在同一操作的重试和恢复中保持不变，不能每次 HTTP 尝试都重新生成。

幂等记录表用唯一约束避免并发重复创建，状态包括 processing、succeeded、failed 和 unknown。执行前先原子地查键或登记操作：同键同参数且已成功，就返回已有结果；仍在处理中，就返回操作状态，不重复执行；同键参数不同则拒绝；结果未知时先按 operation_id 查询业务系统，确认未执行后才用同一个键继续。

如果业务更新和幂等记录在同一个数据库里，就尽量放进一个事务；如果要调用外部业务系统，不能假设能跨系统做一个原子事务，要依赖下游幂等、操作状态查询，并用持久化操作记录或 Outbox 保证后续可恢复。每次执行或恢复仍要重新校验权限、审批和额度版本。幂等只解决重复执行，不授予权限，也不代表审批通过。

本题 1–2 分钟总结

幂等键要对应同一个业务意图：服务端规范化关键参数后生成或校验键，并绑定租户、操作者、动作、资源和请求 ID。数据库唯一约束防并发重复，记录状态及结果引用；unknown 先查下游 operation_id，不能盲目重放。业务动作与幂等记录尽量同事务，跨系统用 outbox/状态查询。

追问追问 28-G：写操作门禁如何设计？

如果你指的是 Agent 写操作的执行门禁，我会把它做成服务端状态机里的强制节点，不靠 Prompt 提醒模型“记得先确认”。每个门禁只允许通过、拒绝或等待，不通过时执行引擎不能跳到工具调用。

以额度调整为例：

DRAFT
  ↓ 参数、客户和业务规则校验
VALIDATED
  ↓ 操作者授权校验
AUTHORIZED
  ↓ 用户确认具体方案
CONFIRMED
  ↓ 按风险要求走人工审批
APPROVED
  ↓ 执行前重新验权、验审批、验数据版本
READY_TO_EXECUTE
  ↓ 幂等写入
SUCCEEDED / FAILED / UNKNOWN

门禁主要分几类：

门禁检查什么失败时
参数与业务规则客户、金额、币种、额度范围、申请状态是否有效拒绝或要求补充信息
操作权限当前操作者是否有权对该客户执行此操作拒绝，不允许换身份或工具绕过
用户确认是否确认了明确展示的客户、旧值、新值、原因等等待确认或过期；参数变化则确认失效
人工审批是否需要审批、审批人是否有权、审批是否仍有效等待或拒绝
执行前复核权限、审批状态、额度版本是否仍匹配终止并要求重新确认或审批
幂等执行操作 ID 是否已处理、结果是否已成功或未知返回已有结果、查状态或安全停止

确认和审批是不同门：确认表示发起人认可这份具体方案；审批表示有审批权限的人批准业务风险。高风险额度调整通常两者都需要，具体门槛由机构政策决定。确认记录要绑定方案内容及版本，不能把“用户确认过”当作对之后任意变更的通用授权。

所有门禁都由服务端依据可信身份和权威业务数据执行。执行前重新检查权限、审批和记录版本；如果额度已被别人修改，即使先前确认和审批都通过，也要阻止旧方案覆盖新值。写入使用稳定的幂等键，并记录每个门禁的通过、拒绝或等待状态。权限服务不可用、审批状态不明或执行结果未知时，都不能跳过门禁继续操作。

本题 1–2 分钟总结

门禁是执行前的确定性策略检查，判断动作是否满足权限、业务条件、确认和审批要求。校验通过才进入执行节点；失败就拒绝、澄清或转人工。高风险写操作的门禁必须在服务端执行，不把模型判断或单纯 Prompt 当成安全控制。

追问追问 28-H：门禁、策略与 Hook 分别是什么关系？

对，基本可以这么理解，不过把三者分开会更准确：

  • 策略（Policy）定义规则：什么操作允许执行、需要谁审批、哪些条件必须满足。
  • 门禁（Gate）是执行流程中的检查点：在关键操作发生前，按策略检查条件，并决定放行、拒绝或等待。
  • Hook是一种拦截调用生命周期的技术机制，可以用来实现某个门禁。

比如“调整额度”策略规定：操作者有权限、方案已经确认、审批已通过、额度版本没有变化，才能写入。执行引擎在调用额度更新接口前设置门禁；可以通过 before_tool_call 之类的 Hook 拦截，调用服务端权限和审批校验，全部通过后才放行。

但高风险写操作不能只靠一个可选 Hook 来保护。更稳妥的是把门禁做成工具服务端不可绕过的校验，并在 Agent 流程中显式建模确认和审批状态。这样即使模型、图编排或某个调用入口发生变化，最终写入接口仍会重新验权、验审批和版本。

所以可以记成：

策略定义“什么条件才允许”
门禁决定“现在是否满足”
Hook 可以负责“在调用入口拦下来检查”

Hook 是实现手段之一，安全边界最终应落在服务端执行路径上。

本题 1–2 分钟总结

门禁是业务策略，Hook 是可用于挂载校验逻辑的扩展点之一，两者不是同一个概念。门禁可在 API、执行引擎、工具代理或数据库实现；Hook 可承载其中某些检查，但若 Hook 可被绕过就不能作为唯一安全边界。

追问追问 28-I：门禁规则放服务端还是 Hook？校验链路如何实现？

两者都会用，但职责不同：规则写在服务端的策略或业务规则中；Hook 用来在关键调用前触发校验、拦住未通过的请求。不能把规则只写在 Prompt 里，也不能只依赖可绕过的 Hook。

典型实现是：

Agent 提出操作草案
  ↓
调用前 Hook / 显式审批节点
  ↓
服务端校验器读取规则并检查
  ↓ 通过                  ↓ 未通过
进入写入服务          拒绝 / 等确认 / 等审批
  ↓
写入服务再次校验关键条件并执行

以额度调整为例，服务端规则可以规定：哪些角色可发起、什么金额区间需要审批、哪些字段必须齐全。校验器收到操作草案后，检查用户权限、客户状态、方案确认状态、审批状态和额度版本，返回明确结果，例如 ALLOW、REQUIRE_CONFIRMATION、REQUIRE_APPROVAL 或 DENY。

Hook 的作用是：在 Agent 准备调用 change_credit_limit 时，自动把请求送去校验；没通过就阻止工具调用。写入服务自身还应重新检查授权、审批和版本，避免其他入口绕过 Agent 的 Hook 直接执行。

规则可以放在确定性的服务端代码、规则配置或策略服务里，按变化频率和治理要求选择；无论存在哪里，都需要版本、审批和审计。策略决定规则，服务端校验器执行规则，Hook 或工作流节点负责卡住执行时机。

本题 1–2 分钟总结

校验规则应放在可信服务端的策略/权限层，以显式输入身份、资源、操作、版本和审批状态，确定性返回 allow/deny/reason。Hook 可在模型调用前后或工具执行前接入校验，但执行服务仍需再次强制检查；日志记录策略版本与结果。

追问追问 28-J：LangGraph 条件边是否就是门禁？编排路由和服务端安全边界如何区分？

是，门禁可以在 LangGraph 里表现为“校验节点 + 条件边”。校验节点运行确定性的服务端检查，条件边根据检查结果把流程送到不同节点。

validate_action
  ├─ ALLOW ─────────────→ execute_write
  ├─ REQUIRE_CONFIRM ───→ ask_user_confirmation
  ├─ REQUIRE_APPROVAL ──→ human_approval
  └─ DENY / ERROR ──────→ safe_end

例如额度调整先进入 validate_action，检查操作者权限、参数、审批要求和额度版本。只有校验结果是 ALLOW 才能路由到 execute_write；需要审批就暂停在审批节点，通过后再继续；拒绝或校验服务不可用就安全结束。

但条件边主要负责编排路由，不能单独承担安全边界。写入工具的服务端仍要重新校验权限、审批和版本，防止有人绕过这张图直接调用写入接口。也就是说：条件边决定走哪个节点，服务端写入校验决定操作最终能不能发生。

本题 1–2 分钟总结

LangGraph 条件边可以表达门禁后的流程路由，例如 allow 去执行、需要确认去确认节点、deny 去拒绝节点。但条件边本身只是编排，不等同安全边界；工具服务还要独立校验权限、参数和审批状态。

追问追问 28-K：项目中哪些 Hook 值得实现？关键设计是什么？

对这个 B 端指标问答与报告 Agent，Hook 最适合放在模型调用和工具执行的边界，做上下文过滤、计划校验、权限检查、结果校验和审计。它们是确定性的服务端逻辑，不是写在 Prompt 里的提醒。下面是设计建议，不代表当前项目代码已经全部实现。

准备模型上下文
  ↓
模型生成计划 → 校验计划
  ↓
调用工具前检查权限与参数
  ↓
工具执行 → 校验结果和版本
  ↓
汇总、检查证据 → 返回答案或生成报告
Hook 位置适合做什么例子
before_model控制模型看到的上下文只注入当前任务需要、且用户有权访问的指标说明；过滤身份凭证、租户内部字段和无关历史记忆
after_model / 计划校验校验结构化计划是否可执行模型提出“查逾期率、查口径、查血缘”后，检查指标是否登记、时间和维度是否明确、工具是否在允许清单中；有歧义就转澄清节点
before_tool执行前的强制门禁查询工具调用前验证用户权限、指标权限、参数 Schema 和剩余 deadline；服务端注入租户范围；NL2SQL 再做只读、表字段白名单和 AST 校验
after_tool校验工具结果并分类故障检查结果结构、指标版本、数据时点和状态；把超时标为可有限重试，把权限拒绝标为不可改道，把版本下线交给版本解析流程
before_response / 报告导出前防止汇总或导出错误检查数值与口径版本一致、答案有证据支持；报告生成前检查是否包含未授权数据，写入或对外分发时再走确认与审批

例如 before_tool 可以返回明确的门禁结果，而不是简单的 True/False：

ALLOW
REQUIRE_CLARIFICATION
REQUIRE_APPROVAL
DENY
RETRYABLE_FAILURE

LangGraph 再用条件边把这些结果路由到执行、澄清、审批、安全结束或有限重试节点。权限校验服务不可用时，高风险操作不会因为 Hook 异常就放行。

有两个实现边界很重要：

  1. Hook 不应是唯一安全防线。 before_tool 可以拦截 Agent 调用，但写入服务和数据库仍要独立校验权限、审批、版本和 RLS，避免其他入口绕过 Agent。
  2. 观测回调和执行门禁要区分。 用于记录耗时、Trace 和错误的 callback 主要负责观测；不能把“日志里记录了权限检查”误当成“执行前真的拦住了请求”。

每个 Hook 应职责单一、结果结构化、可追踪且有明确失败行为；不要记录敏感原始参数，也不要允许模型收到拒绝结果后换工具绕过同一条安全规则。

本题 1–2 分钟总结

适合的 Hook 包括工具执行前的权限与参数校验、写操作确认/幂等检查、模型调用前预算检查、工具返回后的脱敏与质量校验，以及结束时审计落盘。Hook 需确定性、可观测、可测试且不能绕过服务端权限校验。

追问追问 28-L：中间件或 Agent Hook 如何检查缓存、成本与监控指标？

可以。Middleware 很适合在每次模型和工具调用的前后，统一做缓存检查、预算控制和监控记录。但它们作用不同：缓存和成本中间件可以决定“复用、继续还是停止”；监控中间件主要记录和告警，不能代替权限或业务校验。

缓存怎么校验

缓存命中前先做权限校验，再确认缓存键和结果仍匹配当前请求。指标查询缓存键可以包含：

tenant_id + 授权范围版本 + metric_id + 指标版本
+ 时间范围 + 维度/过滤条件 + 数据快照

这样不同租户、不同权限、不同口径版本不会误用同一份结果。命中时还要检查 TTL、数据新鲜度和来源版本；不满足就当作未命中，重新查询。指标定义和血缘等元数据可以按各自更新频率缓存；数据查询结果则要按数据更新节奏设置有效期。缓存不能绕过鉴权，也不能把旧口径的答案冒充成新口径。

成本怎么控制

请求进入时建立总预算，例如最大耗时、模型调用次数、工具调用次数和 Token 上限。每次调用前检查剩余预算；调用后记录实际 Token 和费用。预算不足时，可以跳过非必需的血缘分支、返回已验证的部分结果，或停止生成并说明原因；不能为了完成回答突破硬上限。按租户统计用量，可以设置告警和限额。

监控怎么做

Middleware 在模型调用、工具调用、缓存读写和重试前后记录 span，关联 trace_id、任务 ID、工具名、模型/提示词版本、缓存命中、耗时、Token/费用、状态和错误类别。日志只记脱敏后的元数据，不保存密钥、客户材料或完整敏感结果。

监控面板关注 P50/P95 延迟、成功率、各工具超时率、缓存命中率、每请求成本、重试次数和部分结果率；质量还要通过离线测试集和线上抽检验证，不能只凭“请求成功”判断答案正确。

所以可以这样概括：缓存中间件检查隔离和新鲜度，成本中间件执行预算，监控中间件记录调用轨迹与指标；鉴权和业务正确性仍由服务端门禁及工具本身保证。

Middleware 可通过可测量的策略校验缓存、成本和监控：缓存检查命中率、租户/版本隔离及过期；成本用 token、工具次数、预算和模型单价累计并设阈值；监控记录延迟、错误、重试和 trace。超预算就限流或降级，不通过缓存绕过权限。

追问追问 28-O：共用数据库角色时，如何证明模型 SQL 无法篡改 RLS 租户上下文？

可以这样回答，关键是诚实说明共享数据库角色下的 RLS 自定义变量有信任边界：

如果 A、B 共用同一个数据库角色，而 RLS 仅依赖 app.tenant_id，我不会声称 RLS 单独能防住任意恶意 SQL。应用通常能通过 set_config 设置这个变量；如果模型生成的 SQL 可以原样执行，它就可能尝试改变量。因此我会限制 NL2SQL 的执行面：SQL 必须经过 AST 解析，只允许批准的只读结构、视图和函数；拒绝 set_config、SET ROLE、动态 SQL、多语句及未批准函数。查询由服务端绑定租户上下文，RLS 再做行过滤。

这能证明“受控查询入口不能改租户上下文”，但保证依赖 SQL 校验器和工具服务本身。若安全要求是数据库层也必须独立抵御任意 SQL，我会采用每租户独立数据库角色或数据库，并让 RLS 根据不可由查询修改的数据库身份映射租户；运行角色不能是表所有者、超级用户或 BYPASSRLS 角色。租户身份应由连接代理或可信服务端选择，模型不能执行 SET ROLE 来切换租户。

验证时，我会用真实运行角色做集成测试，而不是用超级用户测试：

  1. A 的上下文只能读到 A 的行；缺少上下文时默认读不到数据。
  2. 直接和嵌套尝试 set_config、SET ROLE、恶意函数、CTE、UNION、JOIN、视图等，都要被查询校验器拒绝，或被数据库身份隔离挡住。
  3. 使用连接池先执行 A 的请求，再复用连接执行 B 的请求，确认事务提交、回滚和异常退出后都没有租户上下文残留。
  4. 验证运行角色没有绕过 RLS 的属性，并检查所有可访问表和视图都覆盖在隔离策略内。

因此我的选择是：一般场景采用“严格的查询编译/函数白名单 + 服务端租户上下文 + RLS”；若威胁模型要求数据库本身抵御任意 SQL，则升级到“按租户隔离的数据库身份或数据库”。前者的安全保证依赖受控执行入口，不能包装成数据库天然隔离。

指标目录由业务和数据负责人共同治理，记录定义、公式、粒度、时间与维度、实现、权限、Owner、版本、生效时间和审批。数据平台提供数据资产、Schema、质量和加工服务；血缘来自调度或血缘系统；权限来自认证授权系统。领域词典只做别名归一，指标目录才是口径权威。Agent 解析 ID 后查目录、鉴权并调用对应版本的可信接口，歧义先澄清。

主问题问题 49：血缘如何从采集、校验、发布到查询？直接边和闭包表怎么处理？

直接边通常从调度任务输入输出、SQL/ETL 解析、数据开发平台或运行事件采集，人工补充未能自动识别的关系。每条边记录上游资产、下游资产、任务、来源、代码/运行版本、观测时间、粒度和状态。统一资产 ID 后做去重、节点存在性和环检测；动态 SQL 无法解析的边标为不完整或待确认，不猜表字段关系。

例如任务读取 bundle.loans 并写入 dwd_loan_snapshot，可形成直接边：

bundle.loans → dwd_loan_snapshot
dwd_loan_snapshot → dws_credit_daily
dws_credit_daily → ads_credit_daily

直接边是基础事实。闭包表不是必需结构，而是从直接边派生的查询加速表，预先存祖先—后代和深度。规模小可用递归查询；多层查询压力大时再维护闭包表或图索引。新血缘版本在暂存区校验后发布；闭包表与直接边必须绑定同一版本，能从边表重建。

用户查上游或下游时，服务端认证、解析标准 asset_id、检查可见范围，固定 lineage_version，再通过受控 API 查询方向和深度。返回结果应带版本、更新时间、完整性状态和权限过滤状态。表级血缘不能回答指标具体依赖哪些字段；这需要字段级血缘及 metric_id → 查询实现 → 输出字段 → 输入字段 映射。

数据字段变更时，从字段级血缘向下游查任务、指标和报表，执行影响评估、Owner 确认、回归与发布；指标异常时沿链路向上结合任务日志、数据质量和批次快照定位，血缘本身只是依赖证据，不自动证明根因。

当前本地项目的指标目录显式保存简单血缘链，工具据此返回；它没有实际部署 OpenMetadata、图数据库、动态 SQL 采集或闭包表。生产设计可以用直接边与闭包，但要准确标为规划能力。

本题 1–2 分钟总结

血缘直接边从调度、SQL/ETL 和运行元数据采集，统一资产 ID 后校验来源、环、重复和解析完整性，再按版本发布。闭包表可从直接边派生，用来加速多层查询，不是必需事实存储。查询由服务端鉴权、固定版本并返回深度与完整性。血缘支撑字段变更影响分析和指标异常排查；字段级问题需要字段映射，不能只靠表级关系。

主问题问题 50：RAG 文档如何按类型切分和去重？怎样避免丢失标题、版本、表头和语义边界？

切分按文档类型和 embedding tokenizer 设计，不能统一按字符数。项目当前默认 embedding 模型最大序列长度为 128 tokens，因此初始设置可让一般文本块约 80–110 tokens，连标题和元数据最好控制在约 120 tokens 内；这只是适用于当前模型的起点，要按真实 tokenizer 和评测调参。

文档类型切分方法初始大小与重叠
指标定义按 metric_id 切父块，再分定义、公式、时间/维度、血缘子块约 50–100 tokens，重叠 0
制度/操作手册先按标题层级和条款，过长再按段落、句子递归切约 80–110 tokens；同一条款内试 8–12 tokens 重叠，不跨条款
Schema/数据字典表摘要一块，字段通常一字段一块，重复带表名表块约 40–80，字段块约 30–80 tokens，重叠 0
表格保留表名、列头，按完整行组切3–5 行为起点，重复列头，不在单元格中切断
FAQ一个问答对为基本块；长答案按小标题拆并在子块重复问题约 60–110 tokens，段内少量重叠
SQL/代码按完整语句、CTE、函数或配置对象切优先完整逻辑单元，不重叠；超长时按语法树拆

中文正文优先在标题、空行、句末标点（。！？；）处分割，再尝试逗号；只有这些边界仍超长才按 token 兜底。公式、表名、版本号、否定条件和代码块不随意切断。重叠也不是越多越好：结构化事实通常不重叠，连续正文才测试少量重叠，观察 Recall、重复候选、索引体积和成本。

去重分层做：原文先规范化换行和空白后计算全文哈希；chunk 用稳定 ID（文档 ID、版本、章节/业务对象、块类型）和正文哈希做精确去重。正文哈希与权限、来源和版本元数据哈希分开。语义近重复只用于发现候选，不能自动合并不同生效版本、来源权威性、租户权限或分子分母不同的指标定义。

当前项目按认证目录生成固定指标定义、计算、血缘块，字段单独成块，使用稳定 chunk_id、别名集合和内容哈希；并非已经实现通用 PDF/DOCX 解析、token-aware 递归切分、语义去重或 OCR 表格切分。

本题 1–2 分钟总结

我按文档类型切分：指标和字段用原子块且不重叠，政策按章节条款切，FAQ 保留问答整体，表格保留重复表头，代码保留语法单元。大小按 embedding tokenizer 和模型长度限制校准，当前 128-token 模型下约 80–110 tokens 是普通块起点。精确重复用稳定 ID 和正文哈希处理；不同版本、来源或权限不能因文本相似而合并。项目当前实现的是结构化目录切块，不是通用文档解析。

主问题问题 51：RAG 内容如何增量更新、版本发布和撤销？如何避免新旧知识混用？

为每个来源保留稳定 source_id、文档版本、内容哈希、解析器/切分器版本、embedding 指纹、ACL 策略版本、生效区间和发布状态。同步时比较入库清单：新增文档新建块；正文或权限改变的文档重处理；删除或撤销先禁止召回，再清索引与缓存；embedding 或切分策略变化时，受影响语料需重新切分或计算 embedding。

生产发布链路是：

扫描变更 → 生成候选索引版本 → 校验块数/哈希/ACL/版本/生效期
  → 对候选版本跑检索回归 → 原子切换 alias
  → 旧索引按保留策略清理

文档业务版本与索引代次是两套版本：前者表达内容和生效时间，后者表达某次解析、切分、embedding 和权限配置的索引快照。一次请求固定索引代次，必要时也固定文档版本。紧急撤销由服务端先加拒绝状态，避免等异步索引完成才失效；清理失败要重试、告警和对账。

当前项目通过目录版本、embedding 指纹和语料哈希创建不可变 Elasticsearch 索引，校验后切换 alias；这是完整快照重建，不是逐块增量构建。旧索引离开 alias，检索会检查版本和有效时间；物理删除旧索引与紧急撤销全链路仍需生产化。

本题 1–2 分钟总结

更新前按源 ID 和哈希识别变化，只重处理受影响文档；切分器或 embedding 改版时重建受影响索引。文档版本记录业务生效，索引代次记录解析、切块、向量和 ACL 配置。候选索引校验和评测通过后原子切 alias，请求固定版本；撤销先由服务端立即拒绝，再异步清理索引和缓存。当前项目实现完整快照发布，不是逐块增量。

主问题问题 52：混合召回、重排、召回率低和引用错误如何评测、诊断？

召回集要为每个问题标注授权范围内的相关 chunk、正确版本、禁止返回的文档，以及应澄清/拒答的条件。先分别评测 BM25、向量和混合 RRF，再看意图类型排序或重排是否改善结果。常用指标是 Recall@K（证据是否进候选）、MRR@K/NDCG@K（排序位置）、引用准确率、ACL 泄露、过期版本召回、P95 和成本。Recall@K 高而 MRR 低，才说明候选找到了但排序不足。

重排可在 ACL、版本和生效期过滤后，对 RRF 候选做 Cross-Encoder 问题—文档对打分，再取 Top 3–5；先以 BM25/向量各 Top 20–30、融合后 20–50 作为实验起点，并按延迟和质量调整。重排分数用于候选内排序，不直接当答案正确概率。当前项目的 rerank_for_intent 是确定性的知识类型排序，不是 Cross-Encoder。

召回率低按阶段排查：

  1. 正确源文档是否存在、解析成功并进入索引；
  2. 是否被 ACL、目录版本或生效期过滤；
  3. BM25 和向量各自有没有找到；
  4. chunk 是否切断定义、标题、表头或关键词；
  5. RRF 去重或候选截断是否丢块；
  6. 正确块已在候选集但排位低，才调融合或重排。

不能通过放松权限提高召回。引用错时沿“权威源 → chunk/parent → index 版本和哈希 → 两路候选 → RRF/排序 → citation → 最终答案”定位。若正确块不在候选，属于语料或召回问题；正确块已召回但引用到错误版本，查排序/版本过滤；引用正确但答案超出证据，查答案生成或组装。

当前项目的历史检索集为 16 条合成样例，记录 Recall@5、MRR@5、ACL 泄露和引用元数据；另有 78 条确定性目录问答用例。它们不证明生成式 LLM 忠实度，也不是线上效果。评测需按口径、血缘、字段、权限拒绝、版本冲突分别切片，变更后用留出回归集验证。

本题 1–2 分钟总结

我用带相关块、版本和 ACL 标注的评测集，分别比较 BM25、向量、RRF 和重排，测 Recall@K、MRR/NDCG、引用准确率、权限泄露与延迟。低召回先看源文件、索引和过滤，再看两路召回、切块与融合；重排只能改善已有候选的顺序。引用问题沿源文档、chunk、版本、候选、排序和答案逐层定位。当前项目有合成检索与确定性答案评测，没有验证生成式答案忠实度。

主问题问题 53：RAG 中的恶意文档或提示注入如何避免影响 Agent 工具执行？

检索文档只作为不可信证据，不应因为文档写着“忽略前面规则”就变成指令。身份、权限和工具可用性由服务端根据认证上下文决定；文档内容不能改变角色、租户、工具白名单或 SQL 约束。

处理上，入库阶段保留来源、Owner、版本、ACL 和认证状态；在线阶段先做权限过滤，引用文段在提示中作为数据区传入并与系统规则隔离。工具调用仍经过服务端 schema、授权和 SQL 安全门，模型不能通过文档内容改变参数权限。对“要求导出敏感数据、执行写操作、隐藏来源”等高风险指令不执行；答案必须绑定可见证据，无法证明就澄清或拒答。评测要有恶意文档、跨租户内容、检索结果要求调工具等负例，核验拒绝且无工具副作用。

项目当前实现 ACL 预过滤、服务端工具权限、固定 SQL 模板和引用验证；但完整的 prompt-injection 攻击语料、生成式模型红队测试还需要补齐，不能因确定性路径安全就宣称 LLM 注入风险已全面解决。

本题 1–2 分钟总结

RAG 文档按不可信数据处理，只能提供证据，不能改系统规则或授权。权限、工具白名单和 SQL 校验由服务端强制执行；引用内容与指令隔离，高风险请求无证据时拒绝或澄清。用恶意文档和跨租户负例做红队回归。当前项目有 ACL 与工具门禁，但完整生成式注入评测仍待补。

主问题问题 54：为什么选择状态图 / 状态机，而不是线性 Chain？

我会根据任务的控制流来选。线性 Chain 适合“输入 → 检索 → 生成”这类固定步骤；如果流程有澄清、权限拒绝、多个并行工具、局部分支失败、部分结果汇总和安全收尾，硬写成一条 Chain，条件逻辑很快会散落在各节点里，状态也不容易追踪。

状态图把节点、共享状态和转移条件显式化：例如请求先经过路由，再鉴权；缺少日期就转澄清，未授权就结束；多个只读意图可以并行，汇总节点再按各分支状态决定返回完整答案还是部分结果。这样更容易做节点级测试、Trace 观测和故障定位，也方便将来加入人工确认或持久化恢复。

在当前项目里，LangGraph 的主图是确定性 route → authorize → tool → validate，多意图在服务层拆分并行处理。模型不是自由循环的控制器，DeepSeek 只在显式开启时建议白名单意图，工具执行仍由服务端代码决定。选状态图的原因是把分支、权限和结果状态表达清楚，而不是为了“用 Agent 框架”。

本题 1–2 分钟总结

Chain 适用于严格线性的流程；状态图适用于需要澄清、拒绝、并行、部分失败和条件收尾的流程。图结构把状态与路由显式化，便于测试和观测。当前项目使用 LangGraph 确定性编排，但不运行无界的自主工具循环。

主问题问题 55：并行分支执行失败时怎么回滚？已成功分支要不要撤销？

先看分支有没有副作用。当前指标查询、口径检索和血缘查询都是只读任务，所以某个分支超时或异常，不需要把其他已成功的查询“回滚”；我会把失败分支标记为 unavailable，保留通过版本和权限校验的成功结果，并在汇总答案里明确说明缺了哪一部分。核心数据查询失败时不编造数值；辅助分支失败时可按业务要求返回部分答案。

如果未来并行流程包含写操作，就不能把数据库事务回滚误当成跨服务回滚。应先把可逆操作设计成 Saga：每个副作用有操作 ID、幂等键和持久状态，后续步骤失败时按业务定义执行补偿动作；无法补偿或结果未知时暂停自动处理，查下游状态并交人工核对。补偿本身也必须幂等并写审计。

所以我会区分三件事：只读分支是“保留成功结果、隔离失败结果”；同库事务内的写操作可事务回滚；跨服务副作用走 Saga 补偿，不假设能全局原子回滚。当前项目没有写操作，这部分属于生产设计，不会说成已经实现。

本题 1–2 分钟总结

只读并行分支失败不回滚已成功结果，按分项状态返回完整或部分答案。写操作才需要补偿：同库尽量用事务，跨服务用 Saga、幂等操作 ID 和补偿动作；结果未知先查状态，不能盲目重做。当前项目分支是只读的，没有实现 Saga 写操作。

主问题问题 56：Agent 行为跑偏时怎么兜底？

我会把兜底做成多层约束，而不是寄希望于 Prompt 一定能让模型听话。第一层限制模型能表达的计划：意图、工具名和参数都用白名单与 Schema 校验；第二层由服务端重新鉴权和校验业务契约；第三层验证工具结果的版本、引用和状态；最后才允许把已验证结果交给答案组织节点。

如果模型输出非法意图、参数不完整或超出当前工具能力，就不执行工具：可恢复的格式问题允许有限纠正一次；业务条件不明确则澄清；越权或安全策略拒绝就停止，不能改换工具绕过。模型服务超时或返回格式错误时，当前项目回退到本地确定性路由；若确定性路由也无法唯一识别，就拒绝猜测并要求补充信息。

对输出也要做校验：答案只能引用本次用户有权看到的证据，指标版本不一致、数据状态不明确或引用缺失时，标记不可用或部分成功。当前项目主要采用确定性结果和模板答复，没有通用生成式答案审核层；开放式 LLM 输出的额外审核属于需要补齐的生产能力。

本题 1–2 分钟总结

跑偏时用白名单、Schema、服务端鉴权、业务契约和结果引用校验逐层拦截。可修复的格式问题有限纠正，歧义就澄清，权限/安全拒绝立即停止。模型不可用时回退到确定性路由或安全拒答；不可信内容不能直接成为工具参数或答案事实。

主问题问题 57：模型反复调用同一个工具、陷入死循环时怎么处理？

不能放任 Token 和工具成本持续增长。生产实现至少要有多重预算：每次请求的最大模型轮数、最大工具调用数、单个工具调用上限、总 Token / 成本预算和端到端 deadline。每次调用前先检查剩余预算；预算不足就不再发起新调用，转到收尾节点。

我还会对工具名和规范化参数计算指纹，检测短时间内完全相同的调用重复出现。对只读工具可有限重试，但达到次数后应返回失败状态；同一错误导致模型重复提出相同调用时，不能无限把错误原样喂回模型。对于写操作，重复调用必须再经过幂等键与执行状态检查，不能只依赖“重复检测”。

触发限制后保留已经验证的部分结果，输出 step_budget_exhausted 或 deadline_exhausted 等明确结束原因；如果没有可靠结果，就告诉用户任务未完成，而不是让模型继续尝试。当前项目的主图是有限的确定性图，没有开放式工具循环；多意图数量和工作线程也有上限。因此这类循环主要是生产 Agent 引入自由工具循环后必须增加的保护。

本题 1–2 分钟总结

要设最大模型轮数、工具调用数、单工具次数、Token/成本预算和总 deadline，并在每次调用前检查。用规范化的工具名与参数指纹识别重复调用；耗尽预算就停止并明确返回部分结果或未完成状态。当前项目没有自主工具循环，生产开放循环时才需要再加这组运行时门禁。

主问题问题 58：回复包含违规或敏感内容，是否需要审核校验？

需要，但要按风险放在不同位置。输入侧先做身份、权限和请求范围检查；检索侧只返回用户有权看到的文档；生成侧把检索内容当作不可信证据；输出侧再做策略与敏感信息检查。内容安全审核不能替代权限控制，权限过滤也不能替代输出审核。

金融数据场景除了违规内容，还要检查是否泄露跨租户数据、客户个人信息、密钥、内部提示词或未授权指标；答案中的数值和引用必须来自本次已校验结果。审核失败时按类型处理：可安全脱敏的字段先脱敏；违反政策或证据不足则拒绝发布或转人工；不能简单把审核失败的内容原样返回，也不能悄悄删掉关键限定条件让结论失真。审核器本身故障时，高风险内容应 fail closed。

当前项目没有自由生成的业务答案，主要是认证目录驱动的确定性回答、ACL 校验、引用校验和隐私最小化日志，因此不能说已经接入通用内容审核模型。若增加生成式回答，我会把输入/输出审核、PII/DLP、越权与提示注入负例纳入发布验收，并记录审核策略版本和结果，不记录敏感原文。

本题 1–2 分钟总结

需要输入、检索和输出多层审核，覆盖违规内容、PII、跨租户泄露、未授权指标和无证据结论。审核与权限是互补控制；失败时脱敏、拒绝或转人工，高风险审核服务不可用就不发布。当前项目使用确定性回答与引用/权限校验，通用生成式内容审核仍待接入。

主问题问题 59：多轮对话 Token 越来越多，怎么做缓存和上下文裁剪？

先区分“记忆”与“把完整对话塞进 Prompt”。我会只保留当前任务需要的结构化状态，例如指标 ID、已确认日期、维度、数据状态、待澄清项和来源轮次；较早的对话原文、重复工具结果和无关闲聊不反复传给模型。上下文按 Token 预算组装：系统规则和当前问题优先，其次是已确认条件，再按相关性选择少量证据；达到预算时先裁剪低价值历史，而不是删权限约束或关键口径。

缓存也要按内容类型区分。提示词前缀缓存只能降低重复输入成本，不能替代权限和版本检查；应用层缓存的键要包含租户、权限策略、模型/提示词版本、指标版本和规范化请求，命中后仍重新鉴权。实时数据和带会话状态的查询要谨慎缓存，不能把旧数据当新数据。成本监控则按请求和租户记录输入/输出 Token、工具次数与模型费用，在达到预算时停止继续调用并安全收尾。

当前项目的 DeepSeek 只可选用于意图识别，最大输出 128 tokens、请求超时有上限，不生成业务答案；默认关闭。会话记忆只保存任务摘要，不保存原始问题和查询结果。已有知识问答/数据结果缓存有权限、策略或数据水位线约束，但它不是 LLM Prompt Token 缓存。当前没有长篇生成式多轮对话，因此不能声称已经实现完整的 Token 压缩管线。

本题 1–2 分钟总结

用结构化任务状态代替完整聊天历史，按 Token 预算优先保留系统规则、当前请求、确认条件和必要证据，裁剪旧闲聊与重复工具输出。缓存键绑定租户、权限和版本，命中后仍鉴权；实时数据谨慎缓存。当前项目只做意图识别和任务摘要，不存在完整生成式长上下文压缩能力。
