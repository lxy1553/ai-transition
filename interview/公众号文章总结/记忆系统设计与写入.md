# Agent 记忆系统与 Agent 进化

---

## 第一部分：Agent 记忆系统设计

### 一、一句话总览

Agent 的记忆系统是**分层架构**，不能一概而论：

| 层级 | 作用 | 时效 | 容量 |
|------|------|------|------|
| **工作记忆** | 当前上下文窗口内容，模型直接可用 | 即时 | 最小 |
| **短期记忆** | 整个会话的对话历史，维持单次任务连贯性 | 会话内 | 中等 |
| **长期记忆** | 跨会话持久化，存用户偏好、历史决策、经验教训 | 永久 | 最大 |

**核心观点**：真正的难点不在"存"，而在"**管**"——长期记忆怎么检索才准？什么记忆该淘汰？新旧记忆冲突听谁的？怎么控制 Token 成本？这些问题没想清楚，记忆系统最后只会变成**噪声源**，帮倒忙。

---

### 二、为什么需要分层记忆？

很多人第一次接触 Agent 记忆，会觉得"不就是存聊天记录吗"，然后把所有历史全塞回上下文。这样做有**三个致命问题**：

1. **装不下** — 上下文窗口再大也有限。之前大模型上下文 128k，目前 GPT-5.6、Claude Opus 4.8 都是 1m，聊久了肯定溢出；更高的上下文成本，延迟翻倍。
2. **噪声大** — 上下文越长，模型越容易忽略中间位置的信息，学术上叫 **"Lost in the Middle"**。十天前的闲聊跟今天的任务有什么关系？全塞进去只会干扰判断，降低准确率。
3. **成本高** — 工作记忆里的每一个 Token 都是要花钱的，不能什么都往里塞。

所以记忆必须**分层**——不同时效、不同重要性的信息，放在不同的地方，用不同的策略管理。就像人脑也分瞬时记忆、短期记忆、长期记忆。

---

### 三、三层记忆架构详解

#### 第一层：工作记忆

工作记忆就是大模型的**上下文窗口本身**，每一轮推理都能直接看到。

- **特点**：最快、最准，但最贵、容量最小。
- **类比**：CPU 的寄存器——离计算单元最近，读写零延迟，但只有几十个字节。
- **放什么**：
  1. System Prompt — 角色设定、安全规则、输出格式（固定，每轮都要有）
  2. 最近几轮对话 — 保证当前对话的连贯性
  3. 当前任务状态

> 💡 工作记忆满了怎么办？把不重要的内容移到短期记忆或者压缩掉，给新内容腾空间——这就是记忆管理的核心动作。

---

#### 第二层：短期记忆（会话内的上下文缓冲）

短期记忆是**会话级别**的，一次对话从头到尾的完整记录都存在这里。存储介质一般用 **Redis** 或内存数据库，按 `session_id` 存，会话结束后按 TTL 自动过期（比如用户关了页面，24 小时后自动清掉）。

短期记忆的实现方案有三种，从简单到复杂：

| 方案 | 做法 | 优点 | 缺点 | 适合场景 |
|------|------|------|------|----------|
| **滑动窗口** | 只保留最近 N 轮对话，超出的直接丢弃 | 零实现成本，信息完整无损 | 窗口外的信息彻底丢失（"金鱼脑"） | 客服机器人、单轮任务型 Agent |
| **滚动摘要** | 对话长到一定程度，把前面的内容用 LLM 摘要压缩 | 能保留更长时间的信息，Token 成本可控 | 摘要不是无损的，会有**事实漂移** | 中等长度对话、对精确性要求不极高的场景 |
| **关键帧机制**（推荐） | 重要节点完整保存，中间过程只存摘要 | 兼顾成本和准确性 | 实现相对复杂 | 工业界生产环境 |

**关键帧机制补充说明**：
- **什么是关键帧？** 用户明确表达偏好、任务目标变更、重要工具调用结果——这些不能丢
- **怎么判断关键帧？** 简单用规则触发，复杂用轻量分类模型打分（比每轮调大模型便宜得多）

---

#### 第三层：长期记忆（跨会话的知识沉淀）

长期记忆是**持久化**的——用户上周说过的话、上个月做过的决策、半年前提过的偏好，都能存下来。下次用户再来，系统能"认出"他。

按内容分三类（源自认知心理学）：

| 类型 | 存什么 | 特点 | 用途 |
|------|--------|------|------|
| **情景记忆** (Episodic) | "发生过什么事"：对话片段、任务执行记录 | 时间属性强，有具体场景 | 回溯历史对话、复盘决策 |
| **语义记忆** (Semantic) | "事实性知识"：对花生过敏、常用 Python、市场部 | 结构化、事实性、更新频率低 | 个性化服务、偏好预判（"Agent 懂我"的关键） |
| **程序记忆** (Procedural) | "怎么做事情"：先看摘要再看详情、按周维度汇总 | 经验和方法论 | 优化工作流、减少重复沟通 |

**长期记忆怎么用？→ 检索式召回**

不可能把所有长期记忆都塞回上下文（几万条早就爆了）。正确做法是**按需检索**：用户问一个问题，先去长期记忆库搜相关内容，只把最相关的 Top-K 条捞出来拼到上下文。这本质上就是 **RAG**，只不过知识库不是产品文档，而是用户的历史记忆。

**长期记忆检索的三重评分**（面试加分点）

只看相似度是初级做法。斯坦福 Generative Agents 论文提出**三重评分框架**：

1. **相关性 (Relevance)** — 语义相似度，这条记忆跟当前问题有没有关系。用 Embedding 余弦相似度计算。
2. **重要性 (Importance)** — 这条记忆本身有多重要？"用户对花生过敏"比"用户今天喝了杯咖啡"重要得多。用 LLM 打 1-10 分，或训练轻量模型分类。
3. **时效性 (Recency)** — 越新的记忆权重越高，符合人脑遗忘曲线。用指数衰减函数：时间越久分数越低。

> 最终分数 = 相关性 × α + 重要性 × β + 时效性 × γ，三个权重按业务场景调。

### 四、生产级记忆写入流程（完整四阶流水线）

> **核心原则**：先提纯，再存储。不是存得越多越好，而是存的每一条都得有价值。写入环节做好了，检索准确率能提升 30% 以上，存储成本反而能降一半。

#### 为什么"直接存"是错的？

真实对话中，有效信息可能只占 30%-40%。如果全量存储，三个问题会引爆：

1. **噪声过载**：大量"好的""收到"、工具调用的完整 JSON 日志、用户改口前的错误信息等，会成为检索时的巨大噪声。
2. **粒度过粗**：用户在一轮对话中可能说了职业、提了需求、补了偏好、吐槽了竞品。将整段话压成一个向量，语义重心会非常模糊。
3. **无差别存储**：致命信息（如"我对花生过敏"）和一次性闲聊（如"今天天气不错"）被同等对待。

---

#### 第一关：降噪清洗——把垃圾先挑出来

用规则把明显没用的内容过滤掉，不进入后续处理。

**过滤对象**：
- 无意义寒暄（"你好""谢谢"）
- 工具调用的完整返回日志（只保留核心结论）
- 用户修正前的内容（"用Python……不对，用Go"）
- 系统的固定话术

**价值**：实现成本极低，但能有效过滤掉 **30%-50%** 的无效内容。

---

#### 第二关：语义切分——拆成独立的"记忆原子"

清洗完的对话不能整段存储，需要拆分成一个个**独立的、只包含一个核心信息点**的"记忆原子"。

**做法**：
- **方案一（推荐）**：用轻量级小模型（如 Qwen3-14B）做信息抽取，提取结构化的"事实列表"
- **方案二**：规则（正则）处理简单模式，复杂场景再调用大模型

**价值**：拆分后，每条记忆的语义重心清晰，检索精度显著提升。实测数据显示，**Top-5 召回准确率平均能提升 22%**。

---

#### 第三关：分级筛选——不是所有记忆都配进长期库

拆好的记忆原子，需要根据其价值进行打分，并决定其"命运"。

**打分维度**：
- **事实性**：是明确事实（"对花生过敏"），还是情绪碎片（"今天心情不错"）？
- **持续性**：有效期多久？是"今天赶时间"（短期），还是"我是做运营的"（长期）？
- **影响力**：对后续服务影响大吗？（过敏信息影响安全，权重高；"喜欢美式"影响小）

**分级处理**：
- **高分（核心记忆）** → 进长期库，永久留存
- **中分（短期有效）** → 进短期缓存（如 7-30 天），到期清除
- **低分（噪声）** → 直接丢弃

**价值**：此步骤能将长期库的日均新增量大幅削减（如从 1800 条降至 350 条），**检索准确率反而会提升**。

---

#### 第四关：元数据标注——给记忆贴上"身份证"

为每条合格记忆打上标准化的标签（元数据），用于检索时进行**前置过滤**。

**必带标签**：
- **基础属性**：`user_id`、创建/访问时间
- **类型标签**：情景记忆（事件）/ 语义记忆（事实）/ 程序记忆（流程）
- **场景标签**：客服/创作/编程等
- **置信度**：直接提取的为"高置信"，推理生成的为"低置信"

**价值**：检索时先用元数据"粗筛"（如只搜"编程场景+高置信"），再用向量"精排"，**既快又准**，避免了跨场景记忆干扰。

### 五、记忆管理的核心挑战与解法

#### 挑战一：记忆越存越多，检索变慢、噪声变大

- **现象**：系统跑了三个月，向量库膨胀十几倍，检索从 200ms 变成 2s
- **解法**：必须有**遗忘机制**——不重要的、太久没访问的、已经过时的，该删就删。重要性低于阈值的，30 天后自动归档；半年没被检索过的，直接清理

#### 挑战二：新旧记忆冲突，听谁的？

- **现象**：用户上个月说"我用 React"，这个月说"我转 Go 了"，两条记忆都在，模型就懵了
- **解法**：**时间戳优先 + 冲突检测**。每条记忆带创建时间，冲突时默认采信新的；复杂场景用小模型判断是"更新"还是"补充"
- **进阶做法**：把事实做成有时间范围的版本，保存`valid_to`字段。北京记录的失效时间落在搬家那天；默认查询只读取当前有效版本；审计时仍能看到历史变化。
- **并发控制**：多个 Agent 同时更新时，用**版本号**防止静默覆盖——只有你读到的版本仍是最新版，写入才成功；否则重新读取并处理冲突。

#### 挑战三：摘要压缩导致事实漂移

- **现象**：滚动摘要滚了几轮之后，信息慢慢失真
- **解法**：**关键事实结构化存储，不参与摘要压缩**。核心偏好、过敏信息、重要参数，单独存在结构化槽位里，永远是原始值

#### 挑战四：记忆注入破坏 Prompt Cache

- **现象**：大模型有 Prompt Cache 功能，System Prompt 固定能省 30% 成本还提速；但记忆系统每轮往 System 里塞东西，缓存直接失效
- **解法**：记忆**不要放 System Prompt**，放 User Message 部分；或不要每轮更新，攒几轮再统一更新

#### 挑战五：同步写入拖慢响应

- **现象**：对话结束后同步进行提取、向量化、写入，增加了 300ms 延迟
- **解法**：改为**异步写入**。对话结果正常返回，写入流程丢到后台消息队列执行。仅核心偏好（如过敏信息）走同步链路。

#### 挑战六：小模型提取出"虚假记忆"

- **现象**：小模型（如 7B）有约 8% 的错误率，可能将"我朋友喜欢 VS Code"误提取为"用户喜欢 VS Code"
- **解法**：为记忆打**置信度分数**。"高置信"记忆参与决策，"低置信"记忆仅作参考。并建立**人工抽检审计**机制。

#### 挑战七：重复记忆挤爆 Top-K

- **现象**：用户反复提及同一偏好（如"喜欢简洁表格"），库里产生十几条重复记忆，挤占了 Top-K 中其他有效记忆的位置
- **解法**：写入前做**相似度去重**。当新记忆与已有记忆的余弦相似度超过阈值（如 0.92），则**更新旧记忆的最后访问时间和访问次数**，不新增条目。访问次数高的记忆在检索时会获得更高权重。

### 六、记忆系统的本质

很多人觉得记忆系统就是个存储模块，其实不是。**记忆系统的本质是认知管理**——它决定了 Agent 在每一个时刻"脑子里装着哪些信息"。

存什么、忘什么、什么时候想起、以什么形式呈现——这些决策直接决定了 Agent 的表现。就像人一样，真正聪明的人不是过目不忘，而是**在需要的时候，能准确想起该想的事情**。

---

### 七、面试回答框架（60 秒版）

> 我不会把 Agent 记忆系统只设计成向量库，而会拆成写入、管理和读取三段。

**写入时**：先判断信息是否值得长期保存、来源是否可信、是否敏感，再决定新增、更新、替代还是不写，并把任务状态、长期事实、历史经历和做事规则分层保存。

**管理时**：每条记忆都带用户范围、来源、有效期和版本号。新旧事实冲突时不直接覆盖，而是让旧版本失效、保留证据链；并发更新用版本检查避免静默覆盖。

**读取时**：先按租户、用户、权限和有效期硬过滤，再做语义召回和精排，最后按模型一次能带入的信息额度——也就是上下文预算——组装。

**最后测试**：跨用户隔离、偏好更新和重启后的持久化。这样才能证明它**记得对、改得动、取得准**。
