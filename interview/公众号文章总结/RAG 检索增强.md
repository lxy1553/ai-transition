## 一、RAG 基础概念

### 1. 什么是 RAG？完整工作流程

> ID: `X046`

**💡 简要回答**

RAG 全称 Retrieval-Augmented Generation，即检索增强生成。核心是在生成答案之前先去外部知识库检索相关内容，
把检索结果和用户问题一起交给 LLM，让它基于这些上下文来回答。本质上是给 LLM 开了一个开卷考试的口子，不靠死记硬背。

**📝 完整流程（离线 + 在线）**

**离线阶段（只做一次）：**

```
文档加载 → 文档切割（Chunking）→ Embedding 向量化 → 入库（向量数据库）
```

1. **第一步：数据接入与文档解析 (Ingestion & Parsing)**
多源数据接入：系统需要从文件系统(PDF/Word/Excel)、数据库、Web API等各种来源采集数据。

文档格式解析：用专用解析器将非结构化文档（如PDF、扫描件等）转换为程序可读的纯文本。对于扫描版PDF等图像类文档，需要集成 OCR 进行文字识别。

关键原则：“垃圾进，垃圾出”。数据加载质量直接影响后续所有环节。

2. **🧹 第二步：数据清洗与预处理 (Cleaning & Preprocessing)**
清洗与标准化：去除HTML标签、特殊字符等噪声，统一文本编码格式。

元数据提取与扩充：提取并附加文件名、章节标题、时间戳等信息。丰富的元数据对后续按来源、时间等条件过滤检索至关重要。
3. ✂️ **第三步：文本分块 (Chunking) 最重要的也是最难的**
这是离线链路中最核心的难点。由于模型输入有长度限制，且整篇文档生成的向量太“粗糙”，难以检索到具体信息，因此必须将清洗后的长文档切割成语义完整的小块。
你的判断非常准确。在实际生产中，**Chunk（文本块）的切分策略必须根据不同业务场景“量身定制”**，没有一种放之四海而皆准的“最优解”。

这背后的逻辑很简单：**切分方式决定了检索的最小单元，而检索单元的质量直接影响最终答案的准确性。** 如果切分不合理，后续再好的召回和重排都难以完全弥补。

下面我为你拆解，在生产环境中如何针对不同业务场景设计切分策略。

---

### 🎯 Chunk核心原则：先看“内容结构”，再看“业务目标”

在选择切分策略前，先问自己两个问题：
1.  **我的文档是什么类型的？**（纯文本、Markdown、代码、表格？）
2.  **用户通常怎么提问？**（是问一个具体数值，还是问一个完整流程？）

这两个问题的答案，基本决定了你该采用哪种策略。

---

### 📄 场景一：长文档、书籍、政策文件——用“语义完整性”优先

**适用场景**：员工手册、法律合同、技术白皮书、学术论文。

**特点**：
- 内容连贯，逻辑性强。
- 用户问题通常是“完整流程”、“整体概念”或“某一段落的细节”。

**切分策略**：**基于文档结构的递归切分**
- **做法**：优先利用文档的自然结构（标题、段落、章节）作为切分边界。
- **工具**：`RecursiveCharacterTextSplitter`（LangChain 提供），设置分隔符优先级：`["\n\n", "\n", "。", "！", "？", "；", "，", " "]`。
- **块大小**：通常 **512-1024 tokens**。
- **重叠（Overlap）**：**10%-20%**，防止切断了完整段落。

**示例**：
- 员工手册中“年假政策”章节 → 作为一个独立的 chunk，而不是与其他章节混在一起。

---

### 🗣️ 场景二：客服对话、FAQ、多轮交互——用“原子信息”优先

**适用场景**：客服历史记录、产品常见问题、多轮对话记录。

**特点**：
- 每轮对话包含多个信息点（用户身份、具体问题、解决方案）。
- 用户后续提问通常是“回忆某个细节”或“问一个具体事实”。

**切分策略**：**按句子或按“问答对”切分**
- **做法**：
  1.  优先将每轮对话拆成独立的“用户问题-客服回答”对。
  2.  再将每个“问答对”作为一个完整的 chunk。
  3.  避免将多个问答对合并，防止语义混淆。
- **块大小**：通常 **200-500 tokens**，以保留完整的一句话或一个简短回答。
- **重叠**：**0% 或 5%**，尽量避免引入无关上下文。
文本对话：首选 RecursiveCharacterTextSplitter，追求更精细的切分效果则可引入基于BERT的语义分割模型或大模型驱动的切分工具。
音频对话：采用 Qwen3-ASR 或 Qwen3-ForcedAligner 等专用语音工具。
**示例**：
- 用户：“我密码忘了怎么办？” → 客服：“请点击登录页面的‘忘记密码’，按提示重置。” → 这条问答作为一个独立 chunk。

---

### 🗂️ 场景三：结构化文档、表格、API文档——用“键值对”或“表头”优先

**适用场景**：产品规格表、数据库 Schema、API 接口文档、Excel 表格。

**特点**：
- 信息高度结构化，很多是“字段名-值”形式。
- 用户问题通常是查询具体数值或配置。

**切分策略**：**按“逻辑单元”切分**
- **做法**：
  1.  对于表格：将每一行（或每一列）作为一个独立的 chunk，并带上表头信息。
  2.  对于API文档：将每个接口的“路径 + 参数 + 返回值”作为一个 chunk。
- **工具**：可借助 `Unstructured` 等库提取表格内容，再按行切分。
- **块大小**：**100-300 tokens**，避免引入无关字段。
- **重叠**：**0%**，结构化内容通常不需要重叠。

**示例**：
- 表格中某一行：`产品编号：P10086 | 价格：299元 | 颜色：黑色` → 这条记录作为一个 chunk。

---

### 💻 场景四：代码仓库、技术文档——用“代码块”或“函数”优先

**适用场景**：GitHub 仓库、技术博客、代码示例。

**特点**：
- 包含大量代码片段、函数定义、类声明。
- 用户提问通常是“某个函数怎么用”或“这段代码的作用”。

**切分策略**：**按“语义边界”切分**
- **做法**：
  1.  利用代码的结构（函数、类、import 语句）作为切分边界。
  2.  每个函数或类的完整定义作为一个 chunk。
- **工具**：可使用 `langchain.text_splitter.Language` 识别代码语言，自动按语法切分。
- **块大小**：**512-1024 tokens**。
- **重叠**：**10%**，避免切断依赖关系。

**示例**：
- Python 文件中的一个完整函数 `def calculate_discount(price, rate):` → 作为一个独立 chunk。

---

### ⚙️ 通用工程实践（无论哪种场景都适用）

1.  **多做 A/B 测试**：在实际业务中，用一组有代表性的测试集，对比不同切分策略下的 **召回率（Recall）** 和 **MRR（Mean Reciprocal Rank）**，用数据说话。
2.  **保留元数据**：在切分时，把文档的 **文件名、章节标题、页码、时间戳** 等信息作为元数据一并存储，用于后续的 **按条件过滤检索**（比如只搜某个文件夹下的文档）。
3.  **定期评估与迭代**：随着业务发展，用户提问方式会变化。建议定期（如每季度）重新评估切分策略是否依然有效。

### 🎤 面试话术参考

如果在面试中被问到这个问题，你可以这样回答：

> “在实际生产中，切分策略必须根据业务场景来定制。对于长文档，我会优先用递归切分，保证段落和句子的完整性；对于客服对话，
> 我会按‘问答对’来切分，确保每个 chunk 包含一个完整的信息单元；而对于表格或API文档，我会按行或按字段切分。同时，
> 我会通过 A/B 测试来验证哪种策略在当前业务场景下召回效果最好，并定期复盘优化。”

4. **第四步：向量化 (Embedding) 与索引存储 (Indexing & Storage)**
这是将文本转化为机器语言并入库的环节。

向量化 (Embedding)：调用Embedding模型，将每个文本块转换成固定长度的向量（一组数字）。这一般使用 Bi-Encoder 模型，它处理速度快，适合离线批量编码。
构建索引与存储：将生成的向量、对应的原始文本块和元数据一起存入向量数据库。
索引：数据库会为向量建立专门的索引（如FAISS的IndexFlatL2、HNSW等），以实现毫秒级的近似最近邻（ANN）搜索。

存储：方案选择多样，从轻量级的 Chroma、高性能的 FAISS到企业级的 Milvus。| 入库 | 存进向量数据库（Chroma/Milvus/Qdrant） | 专门优化高维向量的相似度搜索 |
POC/开发测试（<10万向量）	Chroma	pip install 即用，零配置，与 LangChain 无缝集成
小规模生产（10万-1000万）	Qdrant	Rust 编写性能优异，支持复杂过滤，Docker 部署成熟
大规模生产（千万级以上）	Milvus	分布式架构，支持存算分离、高可用，生态完整
已有 PostgreSQL 基础设施	PGVector	不引入新组件，复用现有运维体系


**⚙️ 进阶优化实践**
一个生产级的RAG系统，在基础流程上还会有以下优化：
混合检索 (Hybrid Retrieval)：同时建立稠密向量索引（语义）和稀疏向量/关键词索引（如BM25，精确匹配），在查询时融合两种结果，兼顾语义理解和关键词命中。
父子块索引 (Parent Document Retriever)：索引时存“小块”（如一句话）保证检索精度，但返回给大模型时，连带其所属的“大块”（如整个段落）一起提供，确保上下文完整。
增量更新与生命周期管理：设计定期全量重建 + 实时增量插入机制，并淘汰过时文档，保持知识库新鲜。
索引压缩与优化：使用乘积量化（PQ） 等技术，可将存储空间降低 60%-80%，在精度和资源间取得平衡。
质量验证：建立自动化的文档质量评估机制，过滤低质量或无效文档。
 

**在线阶段（每次用户提问执行）：**

```
Query 处理 → 向量检索（粗排）→ Rerank（精排）→ 拼 Prompt → LLM 生成
```

| 步骤 | 做什么 | 为什么 |
|------|--------|--------|
| Query 处理 | 改写口语化问题、补全指代 | 用户提问往往模糊，直接检索效果差 |
| 向量检索 | 问题转向量，ANN 搜索 Top-K | 快速粗筛，毫秒级 |
| Rerank | Cross-Encoder 深度打分，重新排序 | 粗排结果里混有噪声，精排过滤 |
| 拼 Prompt | 精排后的 chunk + 用户问题 | 约束 LLM 只根据资料回答 |
| 生成 | LLM 基于参考资料生成答案 + 溯源 | 答案可追溯，可信度高 |

**核心价值：** 知识可热更新（加文档就行，不用重新训练）；答案可溯源（每句话可追溯到具体 chunk）。
RAG的在线链路，就是在用户提问的那一刻，系统实时完成“理解问题 -> 检索知识 -> 生成答案”的完整过程。
它的目标是从已经建好的“书架”（离线索引）上，快速、准确地找到相关书籍，并整理成一份条理清晰的回答。
如果说离线链路决定了RAG系统的质量上限，那么在线链路就决定了用户体验的优劣——它必须做到快（毫秒级响应）和准（答案相关且有用）。
下面我把在线链路的完整流程，从用户输入到答案输出，一步步拆解给你看。

🧭 第一步：查询理解与意图改写 (Query Understanding)
用户的问题往往不够精确，直接拿去检索效果会很差。这一步就是先把用户问题“翻译”成计算机更容易理解的形式。

核心任务：
意图识别：判断问题是事实查询、对比分析、操作步骤还是闲聊？
实体提取与消歧：识别问题中的关键实体（人名、地名、产品名等）。比如“苹果”是指水果还是公司？需要结合上下文消除歧义。
查询改写：将口语化的问题改写成更规范的表达。例如，将“年假咋算的？”改写为“公司年假计算规则”。
子问题分解：对于复杂问题，将其拆解成多个子问题。例如“今年的年假政策是什么？和去年有什么不同？”可拆解为“今年年假政策”、“去年年假政策”、“对比两者差异”。

常用技术：
使用 小参数的大语言模型（如7B-14B模型）进行快速改写和意图识别，兼顾效果和速度。
维护一份同义词词典或实体库，辅助精准的实体识别。

🔎 第二步：多路召回 (Multi-path Retrieval)
查询理解完成后，系统会并行使用多种检索策略，从向量数据库中快速找到最相关的候选文档块。

核心任务：

向量检索：将用户问题（及改写后的多个查询）转换成向量，在稠密向量索引中寻找语义最相近的Top-K个文档块。这能理解“意思”，但可能漏掉精确关键词。

关键词检索：利用BM25等算法，在倒排索引中匹配精确关键词。这能确保“模型编号”等专有名词不被漏掉。

混合检索：将上述两路结果合并。这一步的目标是高召回率，宁可多捞一些，也不要漏掉真正相关的。

常用技术与策略：

多查询检索：将改写后的多个子问题并行检索，扩大召回范围。

HyDE：先让大模型生成一个“假设性答案”，再用这个答案去检索，有时能取得更好的语义匹配效果。

向量数据库：使用Milvus、Qdrant等专业向量数据库，它们支持海量数据下的毫秒级检索，配合 HNSW、IVF 等索引算法实现高性能搜索。

🎯 第三步：重排序与精排 (Reranking)
第一轮召回可能有几十上百个候选块，但大模型的输入长度有限，不能全塞进去。这一步就是对候选块进行精细打分，重新排序，只留下最可能有用的一小部分。

核心任务：

精排模型：使用 Cross-Encoder 模型，将“用户问题”和“每个候选文档块”拼接在一起，进行深度语义分析，计算它们之间的相关性分数。

多维度打分：除了相关性，还可以考虑文档的时效性（更新时间）、权威性（来源可信度）、多样性（避免多个块内容重复）等因素，调整最终排序。

过滤与截断：通常只保留重排后的 Top-3 到 Top-10 个文档块，用于后续的答案生成。

为什么需要重排？
因为向量检索是“大致相似”，而精排是“精确匹配”，它能有效提升最终结果的准确率（Precision）。

💬 第四步：上下文组装与增强 (Context Assembly)
将筛选出的高质量文档块，与用户的原始问题，按照一定的模板和格式组装成一个 “增强提示”（Augmented Prompt）。

核心任务：

模板构造：设计Prompt模板，明确告诉大模型它的角色（如“你是一个智能客服”）、任务（“基于以下参考资料回答问题”）、和约束（“如果资料中没有答案，请直接说不知道”）。

格式化与截断：确保所有内容符合模型输入格式要求，如果总长度超限，按重要性截断最不相关的部分。

注入元数据：在Prompt中附上每个参考块的来源信息（如文档名称、页码），以便模型在回答中引用。

🤖 第五步：大模型生成答案 (LLM Generation)
这是最后一步，也是“生成”环节的核心，将增强提示输入到大语言模型，生成最终的自然语言答案。

核心任务：

答案生成：大模型依据Prompt中的参考资料，生成一个连贯、准确、有帮助的回答。

引用标注：要求模型在回答中标注信息来源（如【来源：员工手册-2024版】），增加可信度。

流式输出（Streaming）：采用SSE（Server-Sent Events）等技术逐字输出，提升用户体验。

关键约束：

忠实度约束：要求模型严格基于参考材料，禁止“自由发挥”。

安全合规：添加安全过滤器，防止生成有害或违规内容。

📊 在线链路与离线链路的完整对照
为了让你更清晰地理解它们的分工，我将离线与在线链路进行了对比：

环节	离线链路（建库阶段）	在线链路（查询阶段）
输入	海量、静态的文档库	一个用户的实时问题
核心操作	解析、清洗、切块、向量化、建索引	理解、召回、重排、组装、生成

### 2. RAG 主要用来解决什么问题？

> ID: `X057`

**💡 简要回答**

RAG 主要解决三个问题，根源都是同一件事：**知识被固化在了模型参数里**。

1. **知识时效性**：LLM 训练完知识就固定了，训练截止日期之后的事一概不知
2. **私有知识缺失**：公司内部文档、行业专有数据没进过训练集，LLM 是空白的
3. **幻觉问题**：没有知识依据时，LLM 会「自己发挥」编造答案

**核心逻辑：**
- 知识过期 → LLM 用历史规律「推测」→ 可能出错
- 知识缺失 → LLM 硬着头皮编 → 幻觉产生
- 幻觉是知识缺失的**副产品**，不是独立的 bug

**RAG 的解法：** 把知识从参数里搬到外部知识库，用的时候实时检索注入——**不动模型本身，只动输入**。


### 3. RAG vs 微调（Fine-tuning）

> ID: `X059`

| 维度 | 微调 | RAG |
|------|------|-----|
| 本质 | 改模型参数，把知识「烧」进去 | 不改参数，推理时注入知识 |
| 知识更新 | 重新训练，成本高 | 更新知识库即可，实时生效 |
| 推理延迟 | 低 | 多一次检索，几百毫秒到一秒 |
| 实现成本 | 高（GPU + 标注数据） | 低（向量库 + Embedding API） |
| 答案可溯源 | 不支持 | 支持，可追溯到具体 chunk |

**组合使用：** 微调解决「怎么说」（输出格式、语气、术语），RAG 解决「说什么」（具体知识内容）。先微调再套 RAG，各司其职。


## 二、存储层：文档切割 + Embedding + 向量数据库

### 4. 文档切割（Chunking）策略

> ID: `X060`

**💡 核心问题**

文档不能整篇存进向量库：一是 Embedding 模型有输入长度限制；二是整篇压缩成一个向量会丢失细节信息。

**每条 chunk 存三部分：**

| 部分 | 作用 | 谁用 |
|------|------|------|
| 向量 | 相似度检索 | 检索系统 |
| 原文 | 塞给 LLM 读 | LLM |
| Metadata | 过滤 + 溯源 | 两者 |

**切割策略对比：**

| 策略 | 做法 | 适用场景 | 优缺点 |
|------|------|----------|--------|
| 固定大小 + 重叠 | 按 token 数切，前后重叠 | 纯文本、无明显结构 | 简单可控，但可能在语义中间截断 |
| 语义边界切割 | 在句子/段落边界处切 | 段落分明的文章 | 语义完整，但 chunk 大小不均 |
| 标题层级切割 | 按 Markdown/HTML 标题切 | 有清晰标题结构的文档 | 天然语义独立，带结构 metadata |
| 代码按函数切割 | 用 AST 识别函数/类边界 | 代码文件 | 保留代码逻辑完整性 |
| 父子切割 | 小块检索 + 大块返回 | 追求高质量 | 检索精准 + 上下文完整，存储翻倍 |

**粒度建议：** 通常 500~1000 token 是起点，关键是根据文档类型选策略。


### 5. 规避语义被切割

> ID: `X061`

**问题本质：** chunk 被单独拿出来后失去语境，语义被拆散导致检索召回不到。

**六种方案：**

| 方案 | 核心思路 | 代价 |
|------|----------|------|
| **重叠切割** | 相邻 chunk 有内容重叠 | 存储轻微增加 |
| **语义边界切割** | 在句子/段落边界切 | 需要 NLP 工具 |
| **句子窗口检索** | 命中单句，返回前后 N 句 | 存储量大 |
| **父子切割** | 小块检索、大块返回 | 存储翻倍 |
| **命题化切割** | LLM 拆成独立命题 | LLM 调用成本高 |
| **Contextual Retrieval** | 向量化前补全背景上下文 | LLM 调用（可 Prompt Caching 降 80-90%） |

**Contextual Retrieval（Anthropic 2024）亮点：**
- 每个 chunk 向量化前，LLM 先生成一段背景说明，拼在 chunk 前面再向量化
- 配合 Prompt Caching，成本降低 80-90%
- Top-20 检索失败率降低约 49%

**实际组合：** 重叠切割做兜底 + 语义边界切割保证质量 + 高质量场景加父子切割或 Contextual Retrieval。


### 6. Embedding 是什么？怎么选模型？

> ID: `X062`

**💡 简要回答**

Embedding 是把文本转成高维向量的过程。**关键性质：语义相近的文本，向量距离也近。** RAG 的语义检索就是靠这个实现的——不是匹配关键词，而是比较「意思相不相近」。

**选模型三要素：**

| 维度 | 说明 |
|------|------|
| 中文支持 | 中文场景选 BGE/Qwen3-Embedding，效果优于 OpenAI |
| 向量维度 | 越高精度越好，但存储成本也越大 |
| 最大输入长度 | 决定能处理多长的 chunk |

**常见模型对比：**

| 模型 | 维度 | 中文效果 | 开源 | 适用场景 |
|------|------|----------|------|----------|
| text-embedding-3-small | 1536 | 一般 | ❌ API | 英文为主、快速上手 |
| bge-large-zh-v1.5 | 1024 | 很好 | ✅ | 中文经典 |
| bge-m3 | 1024 | 好 | ✅ | 中英混合、多语言 |
| Qwen3-Embedding | 多种 | 很好 | ✅ | 中文新一代 |
| Voyage-3-large | 1024 | 一般 | ❌ API | 英文高精度 |

**评估方法：** 不要只看 MTEB 排行榜，要在**自己的业务数据**上跑 Hit@K 测试。Hit@5 < 0.7 就要考虑换模型或优化 Chunking。


### 7. Embedding 算法三代演进

> ID: `X063`

| 世代 | 代表模型 | 核心特点 | 主要局限 | RAG 适用性 |
|------|----------|----------|----------|------------|
| **第一代** | Word2Vec、GloVe、FastText | 词级静态向量 | 无法处理多义词 | 不适用 |
| **第二代** | ELMo、BERT | 上下文动态向量 | 检索需两两拼接，速度极慢 | 不适用 |
| **第三代** | SBERT、SimCSE、BGE、E5 | 句子级 bi-encoder，对比学习 | 精度略低于 cross-encoder | 标配 |

**关键演进逻辑：**
- 第一代：每个词一个固定向量，多义词处理不了（「苹果手机」和「吃苹果」的「苹果」一样）
- 第二代：BERT 解决了多义词，但检索时要把 query 和每个候选拼在一起跑，百万级知识库跑百万次，根本没法用
- 第三代：独立编码每个句子，提前算好存库，查询只算一次余弦相似度，毫秒级返回


### 8. 什么是向量数据库？

> ID: `X064`

**💡 简要回答**

向量数据库是专门存储和检索高维向量的数据库，核心能力是 **ANN（近似最近邻搜索）**。普通关系型数据库的 B-tree 索引对高维向量基本失效，向量数据库用专门的索引结构（HNSW/IVF）把检索加速到毫秒级。

**核心索引算法：**

| 算法 | 原理 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| HNSW | 多层图导航 | 召回率高（95%+），查询快 | 内存消耗大 | Qdrant/Milvus/Chroma 默认 |
| IVF | 聚类分桶 | 内存小，适合超大规模 | 精度略低，需调参 | 亿级规模 |

**选型对比：**

| 数据库 | 部署 | 适合规模 | 特点 |
|--------|------|----------|------|
| Chroma | 本地/云 | 中小 | 零配置上手快，适合原型 |
| Qdrant | 自托管/云 | 中大规模 | 性能好，Rust 实现 |
| Milvus | 分布式 | 大规模（亿级） | 可水平扩展，大厂在用 |
| Pinecone | 全托管云 | 中大规模 | 无需运维，费用高 |
| pgvector | PostgreSQL 插件 | 中小 | 无需新组件，可 JOIN |

## 三、检索层：Query + 召回 + Rerank

### 10. 在线工作流程

> ID: `X047`

**完整六步：**

| 步骤 | 做什么 | 为什么 |
|------|--------|--------|
| **1. Query 预处理** | 改写口语化、补全指代、HyDE、多角度扩写 | 用户提问质量决定检索天花板 |
| **2. Query Embedding** | 问题转向量 | 必须用和建库时**完全相同**的模型 |

| **5. Prompt 拼装** | 精排结果 + 问题 + 约束指令 | 抑制幻觉 |
| **6. 生成 + 溯源** | LLM 生成答案，标注来源 | 可信度提升 |

**耗时分：** Query 改写几十 ms，向量检索几十 ms，Rerank 几百 ms，LLM 生成 1~10 秒。


### 11. 向量检索 vs 关键词检索

> ID: `X048`

| 维度 | 关键词检索（BM25） | 向量检索 |
|------|---------------------|----------|
| 匹配方式 | 词汇重叠统计 | 语义空间距离 |
| 同义词处理 | ❌ 无法处理 | ✅ 天然支持 |
| 精确词命中 | ✅ 极好 | ❌ 容易漏 |
| 适合场景 | 专有名词、代码、精确查询 | 语义问答、模糊表达 |

**两者盲区互补，工程做法是混合检索 + RRF 融合：**

```
向量检索召回 + BM25 召回 → RRF 融合排序 → 送 Rerank
```

**RRF 公式：** `score(doc) = Σ 1 / (k + rank)`，k=60，只看排名不看原始分数。


### 12. Query Rewrite

> ID: `X049`

**四种方法：**

| 方法 | 解决的核心问题 | 额外开销 | 适合场景 |
|------|---------------|----------|----------|

### 16. 图数据库增强向量检索

> ID: `X053`

**向量检索的局限：** 只能做「单跳」检索，找不到多个实体之间的关联关系。

**图数据库的价值：** 沿关系边做多跳遍历，把向量检索够不到的关联信息收集回来。

**组合方式：** 向量检索做入口定位实体 → 图数据库接力做关系遍历 → 合并上下文给 LLM

**适合场景：** 企业关系分析、医疗知识图谱、代码依赖查询、供应链溯源

**判断标准：** 问题里是否同时出现多个具体实体名，并且在问「有什么关系」或「通过关系能到什么」。如果是，值得考虑图增强；如果只是查某段描述性内容，向量检索就够了。

### 17. 规避幻觉

> ID: `X054`

**两类幻觉来源：**

| 类型 | 根源 | 解法 |
|------|------|------|
| **检索层幻觉** | 检索没找到相关内容，LLM 靠猜 | 检索质量门控 + 多路召回优化 |

| 方案 | 机制 | 成本 |
|------|------|------|

### 19. 知识库动态更新

> ID: `X056`

**核心原则：** 文档内容一变，Chunking 边界就变了，不能做「局部更新」。正确做法是 **「先删后增」**。

**变更检测：**
- **内容 hash**（MD5/SHA256）：文档入库时存 hash，下次对比
- **最后修改时间 + hash**：先用时间粗筛，再对变更的算 hash

**变更感知方式：**

| 方式 | 延迟 | 复杂度 | 适用 |
|------|------|--------|------|
| 定时轮询 | 分钟~小时级 | 低 | 更新频率低 |
| Webhook | 秒级 | 中 | 数据源支持 |
| 消息队列 | 秒级 | 中高 | 大规模生产 |

**chunk ID 设计：** 带上文档 ID 前缀（如 `doc_001_chunk_001`），方便批量删除。

| **文档预处理** | PDF 表格、扫描件、双栏排版解析乱码；代码块切割破坏逻辑 |
| **检索质量调优** | Chunking、Embedding、Query 改写，任何一个出问题都影响结果，排查极费劲 |
| **效果评估** | 没有量化指标体系就不知道优化方向，优化变瞎猜 |

**核心感受：** 原型 Demo 一两天能跑起来，但调到生产可用往往要几周甚至几个月。每个环节都可能成为瓶颈，且环环相扣。


## 核心要点速记

### 一句话回答清单

| 问题 | 一句话回答 |
|------|-----------|
| RAG 是什么？ | 检索增强生成，给 LLM 开卷考试 |
| RAG 解决什么问题？ | 知识时效性 + 私有知识缺失 + 幻觉 |
| RAG vs 微调？ | RAG 不改参数，微调改参数；组合用最好 |
| Chunking 怎么切？ | 500~1000 token，按文档类型选策略 |
| Embedding 是什么？ | 文本转向量，语义相近向量距离近 |
| 向量数据库是什么？ | 专门做 ANN 高维相似度搜索 |
| 向量检索 vs BM25？ | 向量管语义，BM25 管精确词，混合用 |
| 怎么防幻觉？ | Prompt 约束 + 检索门控 + 引用核查 |
| 怎么评估 RAG？ | 检索层 Hit@K/MRR + 生成层 RAGAs |
| 最难的是什么？ | 文档预处理 + 检索调优 + 效果评估 |


### 核心认知

1. **RAG 不训练模型**，只是在推理时把知识塞进 prompt。微调是改参数，RAG 是改输入，两者完全不同。
2. **检索是 RAG 的天花板**。LLM 只能基于检索到的内容回答，检索不到就答不对。
3. **混合检索是标配**：向量检索（语义）+ BM25（精确词）+ RRF 融合。
4. **幻觉的根因是知识缺失**，不是 LLM 故意撒谎。治幻觉先治检索。
5. **原型易跑，生产难调**。文档预处理 + 检索调优 + 效果评估是三大硬骨头。
