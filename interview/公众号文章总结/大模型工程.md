

> 涵盖：LLM原理、训练流程、微调方案、推理优化、部署选型、评测方法


## 一、核心概念

### 1. 什么是大语言模型？和传统 NLP 模型有什么区别？

**💡 简要回答**

大语言模型是用海量语料预训练、参数到百亿千亿规模、自回归生成的统一模型。

**与传统 NLP 的三个本质区别：**

| 维度 | 传统 NLP | LLM |
|------|----------|-----|
| 任务方式 | 一任务一模型，pipeline 串联 | 一个模型干所有事，Prompt 统一接口 |
| 输出范式 | 判别式（输出标签/概率） | 生成式（输出文本） |
| 能力来源 | 显式监督训练 | 大规模预训练 + 涌现 |

**关键概念：**

- **自回归生成**：每次只生成一个 token，拼到序列末尾继续
- **涌现能力**：规模超过临界点（50B-100B）后，出现训练目标没教过的能力（多步推理、上下文学习、跨语言迁移）

### 2. Transformer 架构基本原理

**核心创新：Self-Attention**

Self-Attention 让每个 token 直接关注序列中任意位置，一次性并行计算，解决了 RNN 的两个致命缺陷：

- **顺序计算无法并行** → 训练慢
- **长距离梯度消失** → 看不到远处的信息

**Q/K/V 机制：**

```text
Q = X @ W_Q  # Query：我想找什么
K = X @ W_K  # Key：我有什么标签
V = X @ W_V  # Value：我的实际内容

Attention(Q,K,V) = softmax(Q·K^T / √d_k) · V
```

**为什么除以 √d_k：** 防止 d_k 很大时点积值过大，softmax 变成 one-hot 导致梯度消失。

**三种架构对比：**

| 架构 | 代表模型 | 注意力方式 | 预训练目标 | 适合场景 |
|------|----------|-----------|-----------|----------|
| Encoder-only | BERT | 双向（无遮蔽） | MLM | 理解任务 |
| Decoder-only | GPT/Claude/Qwen | 单向（因果遮蔽） | CLM（预测下一个 token） | 生成任务 |
| Encoder-Decoder | T5/BART | 双向 + 单向 | 多种 | 翻译/摘要 |

**为什么 Decoder-only 赢了：**
- 目标统一：所有 NLP 任务都能用「预测下一个 token」表达
- 数据规模大：互联网文本天然可做自监督训练
- 涌现能力强：规模越大，能力越强


## 二、训练流程

### 3. 大模型是怎么训练出来的？三个阶段

| 阶段 | 做什么 | 训练目标 | 类比 |
|------|--------|----------|------|
| **预训练** | 用海量公开文本训练 | 预测下一个 token | 读万卷书 |
| **SFT** | 用(指令,回答)对训练 | 学会按指令格式回答 | 面试培训 |
| **对齐** | 用偏好数据训练 | 学会「好好说话」 | 职业素养培训 |

**三阶段缺一不可：**
- 预训练定能力天花板
- SFT 给格式
- 对齐给价值观

### 4. Scaling Law 与 Chinchilla 配比

**Scaling Law（OpenAI 2020）：** loss 随参数 N、数据 D、算力 C 按幂律下降，且没有看到饱和点。

**Chinchilla 配比（DeepMind 2022）：** 固定训练算力下，参数和数据按 **1:20** 配更优。

| 模型 | 参数 | 数据 | 比例 | 效果 |
|------|------|------|------|------|
| GPT-3 | 175B | 300B | 1:1.7 | 基线 |
| Chinchilla | 70B | 1.4T | 1:20 | 超过 GPT-3 |

**Llama 3 的突破：** 8B + 15T tokens（1:1875）超过 GPT-3 175B，说明 Chinchilla 是「固定算力下的最优配比」，不是数据上限。

### 5. Post-Training：RLHF、DPO、GRPO、拒绝采样

| 方法 | 是否用 RL | 维护模型数 | 训练稳定性 | 典型应用 |
|------|-----------|-----------|-----------|----------|
| **RLHF（PPO）** | 是 | 4（policy/ref/RM/value） | 较差 | ChatGPT 早期 |
| **DPO** | 否 | 2（policy/ref） | 好 | Zephyr、Mistral 派生 |
| **GRPO** | 是 | 3（policy/ref/RM） | 好 | DeepSeek R1、Qwen-Math |
| **拒绝采样** | 否 | 2（policy/RM） | 极好 | Llama 2 热身 |

**GRPO（DeepSeek 2024）核心创新：** 砍掉 PPO 的 Value Model，用「同一问题采样 G 个回答，组内归一化」估计优势函数，显存减半、训练更稳。

### 6. 微调方案

**两个正交维度：**

**维度一：改哪些参数**
- 全量微调：改全部参数，效果最好但显存需求极大（80GB+）
- LoRA：只改旁路小矩阵（参数量降到 0.1%-1%），推理可合并零开销
- QLoRA：量化基础模型（NF4）+ LoRA，消费级 GPU 可微调 7B-13B

**维度二：学什么目标**
- SFT：学「按指令回答」
- DPO：学「哪种回答更受欢迎」（偏好对齐）

**组合使用：** 可用 LoRA 做 SFT，也可用 LoRA 做 DPO。两者正交。

**LoRA 五个优点：**
1. 参数量减少 100 倍以上
2. 推理零开销（可合并回原权重）
3. 部署灵活（一基底 + 多套 LoRA，热切换）
4. 灾难性遗忘风险更低
5. 训练更稳定，超参不敏感
6. （进阶）多个 LoRA 可加权混合（LoRA Merging）


## 三、推理优化

### 7. KV Cache 与 Prompt Caching

**KV Cache（单次推理内优化）：** 缓存所有 token 的 K/V 矩阵，每步只算新 token，总计算量从 O(N³) 降到 O(N²)。

**KV Cache 显存公式：**
```text
KV Cache = 2 × B × N × L × H × d_k × 2 字节（FP16）
```
7B 模型 32K 上下文：约 17GB，是推理显存的第一大开销。

**Prompt Caching（跨请求优化）：** 不同请求间复用相同前缀的 KV Cache，读取 token 费用可降到正常价的 10%。

**工程要点：** 固定内容在前，动态内容在后，前缀差一个字符就 cache miss。

### 8. MHA 的局限与优化方案

**MHA 三个痛点：**
1. 显存爆炸：KV Cache 随头数和序列线性增长
2. 访存慢：Attention 反复读写 HBM 大矩阵，瓶颈在带宽
3. N² 复杂度：序列翻倍计算量翻 4 倍

**三种优化：**

| 方案 | 改什么 | 效果 | 代价 |
|------|--------|------|------|
| **MQA** | 所有头共享 K/V | 显存压到 1/H | 表达力损失 2-5% |
| **GQA** | 分组共享 K/V（H→G 组） | 显存压到 G/H | 几乎无损失（<0.5%） |
| **Flash Attention** | 分块 + 在线 softmax | 显存 O(N²)→O(N)，速度 2-4 倍 | 数学等价，无精度损失 |

**关键认知：** MQA/GQA 是「结构层」优化，Flash Attention 是「实现层」优化，**两者叠加使用**（主流模型都是 GQA + Flash Attention）。

### 9. 位置编码：sin/cos、RoPE、ALiBi

| 方案 | 编码类型 | 长上下文外推 | 主流采用 |
|------|----------|-------------|----------|
| **sin/cos** | 绝对位置 | 差（断崖下跌） | 原始 Transformer |
| **RoPE** | 相对位置（旋转 Q/K） | 很强（配合 NTK/YaRN） | Llama/Qwen/DeepSeek 全系 |
| **ALiBi** | 相对位置（距离惩罚） | 好 | MPT、BLOOM |

**RoPE 赢的三个原因：**
1. 天然相对位置编码，不用模型自己学
2. 配合 NTK/YaRN 可扩展到极长上下文
3. 零参数，兼容 KV Cache、Flash Attention、MQA/GQA

### 10. Tokenizer 与分词

**为什么需要 Tokenizer：** 模型只能处理整数，Tokenizer 是文字到数字 ID 的桥梁。

**BPE 原理：**
1. 初始化：拆成最小单元（字符/字节）
2. 反复合并：找最高频的相邻 pair 合并成新 token
3. 重复直到词汇表达到预设大小

**工程影响：**
- API 按 token 计费：1000 汉字 ≈ 1000-1500 tokens
- 上下文窗口管理：不能只看字数
- 避免截断重要信息

### 11. 量化：INT8/INT4/AWQ/GPTQ

**量化本质：** 将高精度浮点数（FP16）映射到低精度整数（INT8/INT4），用 scale + zero_point 做线性映射。

**量化收益：**
- 7B 模型：FP16 14GB → INT4 3.5GB（1/4）
- 推理速度提升 2-4 倍

**精度边界（经验值，具体看任务）：**
- INT8：<0.5% 损失
- INT4：1-3% 损失（甜蜜点）
- INT3：5-10% 损失
- INT2：20%+ 损失

**主流算法：**

| 算法 | 核心思路 | 特点 |
|------|----------|------|
| **GPTQ** | 逐层量化 + 误差补偿 | 数学严谨，支持极端低位 |
| **AWQ** | 激活感知 + 保护重要权重 | 推理速度快，效果稳 |
| **QLoRA NF4** | 非均匀量化 + LoRA | 消费级 GPU 微调 |

**选型：**
- 生产部署：AWQ/GPTQ（看框架支持）
- 个人微调：QLoRA NF4
- 边缘设备：GGUF Q4_K_M

### 12. 解码策略：贪心、Beam Search、采样

| 策略 | 类型 | 特点 | 适合场景 |
|------|------|------|----------|
| **贪心** | 确定性 | 每步选最高概率，简单但易复读 | 代码、SQL、JSON 生成 |
| **Beam Search** | 确定性 | 保留 B 条候选路径，找全局最优 | 翻译（已失宠） |
| **Temperature 采样** | 随机性 | 缩放概率分布锐度 | 通用（最常用） |
| **Top-K** | 随机性 | 固定截断前 K 个词 | 较少单独用 |
| **Top-P（Nucleus）** | 随机性 | 自适应截断到累加概率 P | 通用（比 Top-K 更智能） |

**为什么 LLM 时代 Beam Search 失宠：**
- 生成式任务没有「单一最优答案」，Beam Search 找概率最高反而等价于「最 boring 的回答」
- 与 KV Cache、Flash Attention 不兼容

**Temperature 设置经验：**
- 代码/SQL：0~0.2
- 日常对话：0.5~0.7
- 创意写作：0.8~1.2

**最佳实践：** 一次只调一个参数，先调 temperature，top_p 保持 0.9 左右，top_k 不设置。


## 四、部署选型

### 13. 部署框架对比

| 框架 | 核心创新 | 最佳场景 | 性能 |
|------|----------|----------|------|
| **vLLM** | PagedAttention + Continuous Batching | 高吞吐 LLM API | 极高 |
| **SGLang** | RadixAttention（共享前缀树） | Agent/多轮/Few-shot | 极高（特定场景） |
| **TGI** | HF 生态集成 | 企业级 + HF 生态 | 高 |
| **llama.cpp** | C++ 重写 + GGUF | CPU/Mac/边缘 | CPU 上极强 |

**选型决策：**
- 生产高吞吐 API → vLLM（默认）
- Agent/多轮对话 → SGLang（前缀共享场景更优）
- HuggingFace 生态深用户 → TGI
- 本地/Mac/边缘 → llama.cpp
- NVIDIA 集群追求极致 → TensorRT-LLM

**PagedAttention：** 模仿操作系统虚拟内存，把 KV Cache 切成固定 Block，显存利用率从 30-40% 拉到 90%+。

**RadixAttention：** 把 KV Cache 组织成 Radix Tree，多个请求共享相同前缀，显存省 50-80%。

### 14. 评测指标

**学术 Benchmark：**

| Benchmark | 测什么 |
|-----------|--------|
| MMLU/MMLU-Pro | 综合知识广度和推理 |
| HumanEval/MBPP/SWE-bench | 代码能力 |
| GSM8K/MATH/GPQA | 数学和科学推理 |
| MT-Bench/Arena/τ-bench | 对话/偏好/工具调用 |
| HELM/LiveBench | 综合、防数据污染 |

**关键问题：数据污染** → Benchmark 题目在互联网公开，可能被模型预训练时见过。

**工程评估方案：**
1. 业务测试集：从真实请求采样 50-200 条，人工标注期望输出
2. LLM-as-Judge：用强模型（如 GPT-4o）代评分
3. 离线评估 + 线上指标闭环
