Agent 进化——从 Prompt 到 Graph

### 一、概念演进时间线

```
2023 年       Prompt Engineering     —— 怎么"说"
2024 年       Context Engineering    —— 喂什么"材料"
2026 年 2 月  Harness Engineering    —— 干活的"驾驶舱"
2026 年 6 月  Loop Engineering       —— 不按回车"松手"
2026 年 7 月  Graph Engineering      —— 多 agent 并行编排
```

**核心规律**：每个新词的出现，都是上一瓶颈被解决、新瓶颈暴露。模型每变强一截，瓶颈就往外移一层：

- 从你说的那句话（prompt）
- → 到你给的那堆材料（context）
- → 到它干活的环境（harness）
- → 落到你本人身上（loop）
- → 再到多任务协作（graph）

> Agent = 模型 + harness。同一个模型，驾驶舱不一样，能力可以差出几倍。

### 二、Loop Engineering 详解

#### 1. 起因

- **Peter Steinberger**（OpenClaw 作者，6 月 7 日）：「每月例行提醒：你不该再给 coding agent 打 prompt 了。你该去设计那个给 agent 打 prompt 的 loop。」
- **Addy Osmani**（Google Cloud AI 总监）给出定义并写长文
- **Boris Cherny**（Claude Code 创始人）：「我已经不 prompt Claude 了。是 loop 在运行着 prompt Claude、决定做什么。我的工作是写 loop。」

一个造工具的、一个定方法论的、一个每天泡在一线的创始人，同一周说了同一件事。

#### 2. 什么是 Loop Engineering？

> Loop engineering 就是把"亲自给 agent 写 prompt 的那个你"替换掉，转而设计那个代替你做这件事的系统。

- **过去**：回合制协作。你写一条 prompt → 读输出 → 再写一条。agent 是工具，你全程握着它。
- **现在**：把"发现任务、布置任务、检查结果、决定下一步"设计成一个能自己运转的循环，让循环去握着 agent。

**打个比方**：以前你是客服热线的接线员，每个电话亲自接；现在你升级成设计工单系统的人——电话怎么分流、哪类问题转给谁、办结标准是什么、办不了的怎么升级。你没有离开公司，但岗位变了。

> 一句话：你不再是 prompt 的作者，你是 **prompt 生产系统的设计师**。

注意：工作没有变容易，是杠杆的支点移动了。以前写一条好 prompt，收益是"这一次回答变好"；现在设计一个好 loop，收益是"之后每一次循环都变好"。投入从消耗品变成了资产。

#### 3. 一个 Loop 由什么组成？（六大核心构件）

Addy Osmani 在其定义长文中，将一个完整的 Loop 系统拆解为六大核心构建块：

| 部件 | 职责 | 在 Codex 中 | 在 Claude Code 中 |
|------|------|-------------|-------------------|
| **自动化** | loop 的心跳——定时或事件触发，自动启动任务并进行初步分诊 | Automations 面板 + 分诊收件箱 | 计划任务、/loop、hooks |
| **worktree** | 让并行不变成打架——给每个 agent 独立工作目录和分支，物理互不干扰 | 每个线程内置 worktree | git worktree、隔离配置 |
| **skill** | 治好 agent 的"金鱼记忆"——将项目知识、开发规范"外化"为可复用文件 | Agent Skills | Agent Skills |
| **connector** | 让 loop 摸到真实世界——基于 MCP 协议连接 GitHub、Slack 等工具 | 基于 MCP 的 Connectors | MCP servers |
| **sub-agent** | 写查分离——让 A 出方案，让干净上下文的 B 来挑刺 | 配置文件定义子 agent | 子 agent、agent teams |
| **记忆** | loop 的命根子——放在磁盘上而不是上下文里（markdown 文件或任务看板） | markdown 或接工单系统 | markdown 或接工单系统 |

**两个关键点**：
- 两家都有 `/goal` 类能力——跑到你写的条件为真才停（"所有测试通过且 lint 干净"），每轮结束由独立模型判断条件。这就是"写的人和查的人分开"，用在停止条件上。
- **loop 的设计正在变得工具无关**——部件是同样的部件，差的只是商标。值得积累的是图纸，不是对某家工具的肌肉记忆。

#### 4. 三个值得警惕的风险

Addy Osmani 在定义这一概念的同时，也发出了清醒的警告，指出了 Loop Engineering 可能带来的三个副作用：

**第一盆：验证仍然归你（Validation）**
- 无人值守运行的 loop，也是无人值守犯错的 loop
- 检查 agent 嘴里的 "done" 只是一个声明，不是一个证明——它说没问题，和真的没问题，中间还隔着你的眼睛。系统越自动，出错的成本可能越高。

**第二盆：知识断层，理解债（Comprehension Debt）越顺滑涨得越快，**
- loop 交付你没写过的代码越快，"仓库里实际存在的东西"和"你脑子里真正理解的东西"之间的鸿沟就越大
- 技术债是代码烂；理解债是代码可能不烂，但你不知道它为什么是对的。系统自动生成的代码越多，工程师对系统真实运行逻辑的理解就越少，形成知识断层。

**第三盆：认知投降（Cognitive Surrender），最舒服的姿势最危险**
- 不再对产出有自己的观点，它给什么就收什么。当系统运行顺畅时，人很容易停止独立思考，无条件接受系统产出的一切。
- Osmani 的博客里有一段关于它的原话，非常锋利：
- > "带着判断力去设计 loop，它是解药；为了逃避思考去设计 loop，它是助燃剂。同一个动作，相反的结果。"

最后还有一笔很现实的账：token 成本。loop 是按循环烧 token 的，sub-agent 每多一个，就多一份模型和工具的开销。
比较务实的花法，是把 sub-agent 用在「值得买第二意见」的地方，而不是处处双保险。token 富裕和精打细算这两种人，
会设计出两种完全不同的 loop。

Osmani 文章的结尾有一段话，我觉得是整场讨论里最值得带走的：
「两个人可以搭一模一样的 loop，得到完全相反的结果。一个用它在自己深刻理解的工作上加速，另一个用它彻底逃避理解工作。
loop 分不出区别，你分得出。」
#### 5. 一个真实的 Loop 长什么样？

> 任务：每天早上自动把项目里值得修的问题找出来、修好、提交审核。

1. 每天早晨，自动化准时触发，调用负责**分诊**的 skill
2. skill 读昨天的 CI 失败记录、未关闭的 issue、最近提交，把"哪些问题值得处理"写进状态文件
3. 对每个值得处理的问题，开隔离的 worktree，派 sub-agent 起草修复
4. 第二个 sub-agent 对照项目 skill 规范和现有测试，审草稿
5. 审过了，connector 自动开 PR、更新工单
6. loop 搞不定的问题不硬来，丢进待办收件箱，等真人来看
7. 所有经过写回状态文件，明天从今天停下的地方继续

> 整个过程你只设计了一次，中间任何一步都没写 prompt。你的活从"每一步都出现"变成"只在两个地方出现"：**设计循环的时候** + **收件箱里有东西的时候**。

#### 6. 实操：30 秒搭出第一个 Loop

```bash
/loop 10m 检查当前分支 PR 的 CI 状态：
  有失败的检查就读日志、修复、推送；
  全部变绿后停下来，给我一句话总结改了什么
```

- `10m` 是心跳：每 10 分钟自动醒来跑一轮
- 中间是任务：每一轮干什么
- 最后是停止条件加汇报

**使用边界**：
1. `/loop` 活在当前会话里，适合"今天盯着这件事"的轮询，关电脑就停；想睡觉时也跑的，要用计划任务或云端 routines
2. 最小 loop 只有心跳、任务和停止条件，没有 worktree、没有写查分离的 sub-agent。**这不是缺陷，是起点**——部件是一件一件长出来的

> **浓缩成 3 句话：**
> 1. 从 prompt 到 context 到 harness 再到 loop，四个词是一场瓶颈迁移：模型越强，瓶颈越往外移，最后移到"亲自按回车的你"身上。
> 2. 一个 loop = 六大件 + 一份磁盘记忆：自动化是心跳，worktree 防打架，skill 治金鱼记忆，connector 摸到真实世界，sub-agent 写查分离，状态文件让明天接得上今天。
> 3. loop 把你的杠杆变长了，但验证、理解债、认知投降这三笔账也同时变大了。工具分不出你是在加速还是在逃避，你自己分得出。



# Harness Engineering 完全指南：从概念到大厂实践，一次讲透

> 从 Prompt Engineering 到 Context Engineering 再到 Harness Engineering，AI 工程的重心三次迁移。这篇文章把 Harness 的来龙去脉、六层骨架、五个大厂难题全讲清楚了。


## 开篇：这个新词到底从哪儿冒出来的？

不知道你最近是不是和我一样有这种感觉：AI 圈造新词的速度是真的快。Prompt Engineering 这个词大家刚整明白，Context Engineering 又火了一年，资料还在到处转。最近圈子里又冒出来一个新词，叫「Harness Engineering」，翻译过来叫「驾驭工程」。

三天一概念，五天一炸裂，一周一个新名词。甚至每次 AI 圈新诞生一个很火的概念，面试就大概率会被问到。

你是不是已经麻了？但麻归麻，我还是去把这个新词的来龙去脉认认真真扒了一遍。扒完之后我发现，这次还真不是又一个换皮的概念，它确实是在解决一个之前那两个词都解决不了的问题。

### Harness 这个词最早是谁喊出来的？

很多人跟风聊 Harness Engineering 的时候，压根没搞清楚这个词最早是谁提出来的。等你知道了它是谁先喊出来的，你就会明白为啥它这次真的能火，而不是又一个换皮概念。

Harness Engineering 这个词最早被正式叫响，是在 **2026 年 2 月 5 号**一篇博客里。作者叫 **Mitchell Hashimoto**——基础设施圈的老法师，HashiCorp 联合创始人，写过 Vagrant、Packer、Terraform、Vault 这些业界知名的工具。

标题叫《My AI Adoption Journey》，中文大概是「我接纳 AI 的历程」。讲的就是他作为一个老派工程师，是怎么一步一步从「不信 AI」到「每天让 Agent 替我干活」的心路历程。

他把整个过程拆成了 6 个 Step：

- **第一步，直接扔掉对话框。** 一上来别用 ChatGPT 那种聊天界面，要用就用能自主执行任务的 Agent。聊天界面会给你一种「我在和 AI 讨论」的幻觉，但实际上你啥也没干。Agent 才是真正让 AI 动起来的形态。只有把 Agent 放开让它自己执行，你才能真正感知到它的能力边界在哪儿。
- **第二步，用 Agent 去重做自己已经手写过的代码。** 明明自己两下就能写完的活，非要等 Agent 慢慢磨。他原话说这个过程「painful」，折磨人。但目的很明确：只有你亲自用 AI 去重做你已经熟得不能再熟的任务，你才能精准校准「它到底哪里行、哪里不行」。
- **第五步，他给自己这套做法起了个名字，就叫 Engineer the Harness，打磨这套马具。**

他给的定义特别简洁：

> **每次当你发现 Agent 犯了一个错误，就花点时间去工程化一个解决方案，让它永远不会再犯同样的错误。**

你品品这个思路。绝大多数人遇到 Agent 犯错是怎么办的？骂两句，手动改掉，祈祷下次它别再犯。但 Mitchell 不是这么干的，他每次 Agent 犯错，都会停下来问自己：**我能不能把这个错误永久性地修到环境里，让它下次在结构上就不可能再犯？** 可能是给 AGENTS.md 加一条规则，可能是加一个 linter，可能是补一个自动化测试，也可能是搞一个 Git Hook。关键是：**这个修补必须沉淀到环境里，而不是留在人脑子里。**

这套做法的威力在于它是「**复利**」的。每一次 Agent 犯错，环境就会变强一点；环境变强一点，Agent 下一次就更少犯错；犯错变少，你改进的速度就更快。时间一长，你的 Harness 会越来越坚固，Agent 在你这个项目里会越跑越稳。

博客发出来一周后，**OpenAI** 紧接着也发布了一篇官方博客，标题就叫《Harness engineering: leveraging Codex in an agent-first world》。这篇博客讲的是他们内部一个从 3 人起步的小团队，从一个空仓库出发，用 5 个月时间，靠 Agent 写出了 100 万行代码、合并了 1500 个 PR，全程没人手动写过一行代码。

这篇博客一出，Harness Engineering 这个概念直接被推上了 AI 圈的风口浪尖。

所以你能看明白这个词的路径了吧：一个基础设施圈的老法师先喊出来 → OpenAI 几天后发文背书 → 一周内整个 AI 圈开始刷屏。这种出身决定了它不会像很多 AI 新词一样「炒一波就凉」，它更像是一个在真实工程土壤里长出来的东西。


## 第一部分：从提示词到 Harness——AI 工程的三次迁移

要真正讲清楚 Harness Engineering 在解决啥问题，咱们不能一上来就讲它。因为它不是凭空冒出来的新概念，而是 AI 工程这几年一步一步「被逼出来」的结果。

你去复盘一下过去两年 AI 圈的变化就会发现一件特别有意思的事：**AI 工程的重心，其实已经悄悄换过三次了。**

| 阶段 | 核心问题 | 关注点 |
|------|----------|--------|
| **Prompt Engineering** | 怎么让模型「听懂」你想干啥 | 优化意图表达 |
| **Context Engineering** | 怎么让模型「知道」该用什么信息 | 优化信息供给 |
| **Harness Engineering** | 怎么让模型在真实执行里「持续做对」 | 优化整个运行系统 |

这三个阶段不是谁取代谁，而是每一步都在上一步撞到天花板之后，继续往前啃出来的。

### 第一阶段：Prompt Engineering，先让模型「听懂」你

大模型本质上是一个**对上下文极度敏感的概率生成器**。你给它的输入越模糊，它猜的范围就越大；你给它的输入越具体，它猜的范围就越收敛。正因为这种敏感性，大家慢慢摸索出了一套「提示词配方」：

- **角色设定**：你是谁？比如「你是一个有十年经验的后端工程师」
- **背景信息**：当前在干啥？比如「我正在用 Go 写一个订单系统」
- **参考资料**：相关的文档、历史对话、代码片段
- **明确任务**：具体要你干啥
- **约束条件**：哪些不能做，比如「不要修改其他文件」
- **输出格式**：希望以什么形式返回

有意识地去设计和调整提示词、让模型稳定输出你想要的内容，就叫 **Prompt Engineering**。

它解决的核心问题：**模型不是不会，而是你没把问题说明白。** 提示词工程在短链路任务（聊天、问答、翻译）上效果很好，但很快大家想做的事情变复杂了：让模型分析财报、写代码、组合 API 调用。这个时候你会发现：**提示词写得再漂亮，也替代不了「事实」本身。**

### 第二阶段：Context Engineering，让模型「知道」该用什么信息

为什么 Context Engineering 会突然火起来？因为 Agent 火了，模型不再只是「回答问题」，而是要进到真实环境里去「干活」：多轮对话、调用工具、写代码、查数据库、在多个步骤之间传递中间结果。

这个时候问题完全变了。系统面对的已经不是「这一次回答对不对」，而是「整条链路能不能跑通」。

**什么叫上下文？每一次发给大模型的所有信息加在一起，就叫上下文。** 提示词只是上下文里很小的一部分。一个完整的上下文还包括：用户输入、历史对话、检索到的资料、工具返回的结果、当前的任务状态、中间产物、系统规则、安全约束。

Context Engineering 的核心思想：**模型未必知道，所以系统必须在合适的时机，把正确的信息送进去。**

但有一个让人头疼的现实：**大模型一次能处理的上下文是有上限的。** 这个上限叫「上下文窗口」。就算窗口够大，当上下文塞得太满的时候，模型会出现「**上下文腐化**」：记不住前面的内容，前后矛盾，忽略最初定下的规则。

实践下来，Context Engineering 可以拆成三步：

1. **召回**：从一大堆资料里找出跟当前任务最相关的那部分（RAG）
2. **压缩**：对每段做摘要，对历史对话压缩成一句话总结
3. **组装**：按一定顺序、格式组装起来（大模型对「靠后的信息」更敏感）

**Agent Skills** 提出的思路叫「**渐进式披露**」：一开始只给模型看每个能力的「目录」，等模型真的判断「我现在需要用某个工具」的时候，再把那个工具的详细说明动态加载进来。上下文优化的本质不是「给得更多」，而是「按需给、分层给、在正确的时机给」。

### 第三阶段：Harness Engineering，让模型「做对」一连串的事

后来大家又发现了一个更麻烦的问题。你把提示词写得再漂亮，把上下文管理得再完美，模型在「单步」上的表现确实越来越好了。但只要任务的链路一长，模型就会出问题：

- 计划做得很好，但执行的时候突然跑偏了
- 调用工具调对了，但理解错了工具返回的结果
- 在一个很长的任务链里，已经悄悄偏离初衷了，但系统完全没察觉
- 跑着跑着突然忘了自己最初要干啥

提示词工程优化的是「意图的表达」，上下文工程优化的是「信息的供给」，但这两个都还停留在「**输入侧**」。当模型真正开始「连续行动」的时候，会出现一个全新的问题：**谁来监督它？谁来约束它？谁来在它跑偏的时候把它拉回来？**

Harness 这个英文词，直译过来叫「马具」或「缰绳」。放在 AI 系统里，这个比喻特别贴切：当模型从「回答问题」走向「执行任务」，系统就不能只负责喂信息，还要能「驾驭」整个执行过程。

**Prompt ⊂ Context ⊂ Harness**。三层边界一层比一层大，后者天然包含前者。

圈子里流传着一个特别简洁的等式：

> **Agent = Model + Harness**


## 第二部分：Harness 拆开看——六层骨架

如果你去看 OpenAI、Anthropic、LangChain 这些做 Agent 的顶级团队，会发现一个有意思的事：产品形态不一样、技术栈不一样，但把 Harness 掀开看内部结构，里面的组件居然惊人地相似。这不是巧合，而是「让一个 Agent 在真实世界里稳定工作」这个命题，天然就会推着所有人往同一个方向收敛。

一个成熟的 Harness 可以拆成六块核心组件：

| 层 | 这一层在解决的一句话问题 |
|---|------------------------|
| 上下文精细化管理 | 模型这一轮该看到什么？ |
| 工具系统 | 模型用什么动手？ |
| 执行编排 | 模型下一步该干啥？ |
| 记忆与状态 | 模型跨轮该记住什么？ |
| 评估与观测 | 模型做得好不好有没有尺子？ |
| 约束与恢复 | 模型出错了能不能爬起来？ |

这六层可以分成三组：

- **输入侧**（让模型看到正确的东西）：上下文管理 + 记忆与状态
- **动作侧**（让模型做出正确的事）：工具系统 + 执行编排
- **校验侧**（让模型知道做没做对 + 出错能爬起来）：评估观测 + 约束恢复

为了不让这六层变成抽象的概念堆，我们用同一个例子贯穿整章：**每天定时扫 GitHub 上你关注仓库的新 PR，挑出值得关注的，生成摘要和点评，发到 Slack。**

### 第一层：上下文的精细化管理

模型每次被调用的时候，到底该看到什么？关键修饰词是「每次被调用的时候」——这一层管的是「空间」（这一轮发给模型的那一坨上下文长啥样），而第四层管的是「时间」（上一轮发生的事情怎么流动到下一轮）。

PR Review Agent 真正需要的是一组精挑细选的信息：
- PR 的标题和描述
- diff 里真正被改动的那几个文件
- 这些文件在仓库里对应的模块说明
- 作者最近几次提交的风格偏好
- 仓库的 code review 惯例

塞越多无关信息，注意力越散。Anthropic 把这个现象叫「**上下文腐化**」，解法是「**just-in-time retrieval**」——边干活边按需抓信息，而不是一上来就把所有可能有用的东西一股脑塞进去。

这一层核心三件事：
1. **把角色和目标钉死**：模型得知道自己是一个「PR 审查助手」
2. **动态筛选而不是一次塞满**：只把当前这个 PR 相关的那几块信息拉进来
3. **结构化组织**：固定规则放一处，动态证据放一处，中间结论放一处，三者要分开

### 第二层：工具系统的可控调用

没有工具的大模型本质上还是一个文本预测器。它能告诉你一个 PR 应该怎么审，但它没法真的去 GitHub 上读那个 PR。接上工具之后，PR Review Agent 才真正活过来。但工具不是接得越多越好——OpenAI 在 Codex 早期踩过这个坑，后来砍掉一大半，效果反而上去了。

这一层要回答三个问题：

1. **给它哪些工具？** PR Review Agent 至少需要：gh 命令行工具（拉 PR 列表、看 diff）、读文件工具、代码搜索工具、Slack 发送工具。别的工具先别加。
2. **什么时候用哪个工具？** 该查的时候要查，不该查的时候别瞎查。已经在上下文里的东西别再去重新拉。
3. **工具结果怎么喂回模型？** 调用代码搜索拿到 30 条匹配，不是把 30 条原文原样塞回去，而是先做一层提炼，只留核心模块的那几条再喂回去。

**MCP（Model Context Protocol）** 本质上就是在做工具层的标准化。

### 第三层：任务执行的全局编排

能动手不等于能做成事。Agent 的本质是一个 **for 循环**：思考一步 → 行动一步 → 观察结果 → 再思考下一步。这个结构叫 **ReAct（Reasoning + Acting）**。

PR Review Agent 的工作轨道：
1. 拉取仓库当前所有开放的 PR 列表
2. 对每一个 PR：读 diff 和描述 → 判断涉及的是核心模块还是边缘模块 → 核心模块的 PR 做深度分析 → 给出重要性打分（1-5）
3. 按重要性排序，选前 3 个
4. 为每一个生成摘要和点评
5. 汇总发到 Slack
6. 检查发送是否成功，失败则重试

有了这条轨道，Agent 就知道「我现在在哪一步，下一步该干啥」。

业界常见的编排模式：**Plan-and-Execute**（先规划完整计划再执行，适合长链路）、**Reflexion**（每次失败让 Agent 反思再重试）、**Tree of Thoughts**（同时探索多条思路再选最好的）。

### 第四层：记忆与状态的分层管理

没有状态管理的 Agent，每一轮调用之间都是失忆的。PR Review Agent 今天跑了一遍，明天再跑完全不记得「这个 PR 昨天已经审过了」，于是又审一遍再发一次消息。

**Agent 的状态不应该放在上下文窗口里，而应该外化到文件系统。** Anthropic 的具体做法是让 Agent 维护一个日志文件、一个启动脚本、加上完整的 git history，作为「长期记忆介质」。下一轮换一个全新的、干净的上下文窗口接手时，从这些文件里一读，立刻就知道「现在到哪一步了」。

三类状态要分层存：

- **任务状态**：今天已经处理到哪个 PR 了？写在一个 `today-progress.json` 里，当天任务跑完就归档
- **会话中间结果**：当前这一轮里对某个 PR 的初步判断，随会话结束就可以丢
- **长期记忆和用户偏好**：你喜欢关注什么类型的 PR？写在 `user-preferences.md` 里，每次调用都注入

**Claude Code、Cursor、Trae 里的规则文件（CLAUDE.md / .cursorrules）**，就是「长期记忆」这一类的典型实现。

### 第五层：独立的评估与观测体系

这一层最容易被跳过，但跳过之后就进退两难。很多团队做出 Agent 之后高高兴兴上线，跑了两周才发现实际成功率只有 50%。不是它不出结果，而是它每次都出结果，但一半时候是错的。问题在于这两周里没人发现，因为根本没有机制能告诉团队「它这次到底做得对不对」。

**Eval 集（evaluation set）** 是做 Agent 开发的业界标准做法，也是这一层的灵魂。手写一批典型任务，每一个都标注好「正确答案长啥样」，然后每次你对 Harness 做了任何改动，都让 Agent 把这批任务再跑一遍，对比成功率。

对 PR Review Agent 来说：从过去三个月挑 20 个真实 PR，每一个都标注「是不是重要」「摘要应该怎么写」，每次改完 Agent 就跑一遍这 20 个，看它挑对了几个、写对了几个。

**没有 Eval 集，你对 Agent 好不好的判断永远停留在「我感觉这次变好了」的玄学阶段。**

LangChain 把 Terminal Bench 成绩从 52.8 推到 66.5，靠的就是基于 Eval 集做 trace 回放和迭代。Anthropic 和 OpenAI 内部同样有大量的 Eval 基础设施——**这不是锦上添花，是工程级 Agent 的必需品。**

你还得看到 Agent 每一次的真实足迹：每一步做了什么决策、调了哪个工具、拿到什么返回、花了多少 token。这就是 **LangSmith、Langfuse** 这类 trace 系统存在的意义。

### 第六层：约束校验与失败恢复机制

在真实环境里，失败不是例外，是常态。PR Review Agent 真跑起来之后，一定会遇到各种奇形怪状的失败：GitHub API 限流、diff 太大把上下文冲爆、Slack webhook 过期、token 耗光一半预算。

这一层要做三件事：

1. **约束**：定义「什么事 Agent 不能做」——「一次最多分析 20 个 PR」「不能对已 closed 的 PR 再评论」「token 用量超过 10 万就立刻停下」。这些约束最好硬编码到代码或 linter 规则里，而不是写在提示词里靠 Agent 自己遵守。
2. **校验**：在每一步输出前后都做自动检查——摘要是不是 Markdown？Slack 频道名是不是在白名单里？校验不是审美品味，是硬规则。
3. **恢复**：失败之后有预案——GitHub 限流就等一段时间重试；Slack 发送失败就先落到本地队列；token 快耗光就立即停下并保存进度。

### 六层与 Mitchell Hashimoto「复利效应」的对应

Mitchell 说 Harness 的核心是「每次 Agent 犯错，都把修复沉到环境里」。那个修复到底沉到哪儿？答案就是这六层的其中某一层：

- 发现 Agent 总是漏掉某个上下文信息 → 改第一层
- 发现它总是用错工具 → 改第二层
- 发现它步骤乱 → 改第三层
- 发现它跨天记不住进度 → 改第四层
- 发现你没法判断它做得好不好 → 搭第五层
- 发现它一失败就崩溃 → 强化第六层

这六层不是一张「必须一次搭完」的任务清单。它是一张路标，告诉你下一次 Agent 犯错时，你的修复应该落到哪里。


## 第三部分：五个大厂难题与 Harness 解法

讲完六层能力的骨架，你可能会觉得这套东西好像挺有体系的。但真要动手做，各大公司都会告诉你一个共同的感受：**概念清晰是一回事，落地是另一回事。** 下面挑 5 个大厂在真实项目里踩过的典型坑。

### 难题一：Agent 跑久了为啥会越走越偏？

几乎所有做长链路 Agent 的团队都会遇到。一开始 Agent 表现挺好，目标清晰，步骤明确。但跑着跑着，它开始「忘」：忘了最初定的目标，忘了之前已经做过的决定，开始重复劳动，开始偏离主线。

Cognition（做 Devin 那家公司）在用 Claude Sonnet 4.5 重做 Devin 的时候，观察到一个现象，叫「**上下文焦虑**」：模型自己好像也能感觉到「我快撑不住了」。当它觉得上下文窗口快用完的时候，不仅开始丢细节，还会出现一种奇怪的行为——**开始着急地想收尾**，突然简化方案、跳过验证步骤、急匆匆地宣布「任务完成」。更神奇的是，模型对自己「还剩多少上下文」的估计非常不准。

**很多团队第一反应是做「上下文压缩」（Context Compaction）。** 但 Anthropic 挑明了一个更扎心的观察：**光压缩根本不够。** 一旦「上下文焦虑」这种状态上来了，只压缩历史、不把整个上下文窗口彻底换掉，那种「已经累了」的负担感模型还是带着。

**真正解开这个结的关键动作叫 Context Reset：直接把旧的上下文窗口整个丢掉，换一个干净的接手。**

具体怎么做？整个系统只有一个 Agent，系统提示词、工具集、整套 harness 全都一样。真正在变的只是每一轮的初始 user prompt：
- 第一轮用一个「初始化」prompt，让 Agent 把环境信息、项目状态、约束条件整理好，写到 `claude-progress.txt` 日志、`init.sh` 启动脚本、一个初始 git commit 里
- 后续每一轮用一个「增量推进」prompt，让它做一点进展，然后把新状态再写回这几份文件

**每一轮开始的时候，Agent 都面对一个完全干净的上下文窗口，它根本不记得上一轮的对话历史，它靠的完全是读取文件系统里这几份「交接文档」来恢复「我现在在哪一步」。**

核心不在「压缩上下文」，而在**把状态外化到文件系统**。文件系统变成了真正的长期记忆，上下文窗口本身只负责处理当前这一轮，处理完就可以整个丢掉。

> **原则一：重启胜过修补，状态沉到文件里，Agent 随时可以在一个干净的上下文窗口里接力继续。**

### 难题二：让 Agent 自己给自己打分，为啥总偏乐观？

很多人做 Agent 的时候让 Agent 干活，干完之后再让它自己评估「做得怎么样」。实际效果？**Agent 永远觉得自己干得不错。** 特别是在那些没有标准答案的任务上，自评的偏差特别明显。

Anthropic 想明白了一件事：**让干活的和验收的，必须是不同的人。** 他们搞出了一个三角分工：

- **Planner（规划者）**：把模糊的需求扩展成完整的规格说明
- **Generator（生成者）**：一步一步去实现
- **Evaluator（验收者）**：像 QA 一样真实地测试——不是看一眼代码就完事，而是真的去操作页面、看具体的交互、检查实际的运行结果

只要这三个角色足够独立，系统就能形成一个真正有效的循环：规划 → 生成 → 验收 → 修复 → 再验收。

> **原则二：生产和验收必须分离，而且验收方必须能摸到真实世界。**

### 难题三：Agent 总是失败，工程师到底该干啥？

当 Agent 反复失败的时候，一般人的本能反应只有两个：要么再调调提示词，要么换个更强的模型。但 OpenAI 在做 Codex 项目的时候，实践告诉他们：**这两招其实都是错的方向。**

在 Codex 那个百万行代码的项目里，人类工程师几乎不写一行代码，全部由 Agent 来写。那人类工程师到底在干啥？

1. **把产品目标拆解成 Agent 能力边界内的小任务**，确保每一件事都是 Agent 接得住的
2. **当 Agent 反复失败时，不是去催它「再努力一点」，而是去看它「环境里缺了什么能力」**，然后把那个能力补进环境里
3. **建立反馈链路**，让 Agent 真正能看到自己工作的结果

传统做法是加一句提示词「请仔细检查代码不要有 bug」，然后祈祷模型这次听话。Codex 团队的做法是：给 Agent 接上 lint、单测、运行环境，让它自己写完自己跑，看见 bug 自己改。

> **原则三：Agent 反复失败的时候，别问模型能不能更努力，要问环境还缺什么。**

### 难题四：规范文件越写越长，为啥 Agent 反而更糊涂？

OpenAI 早期做 Codex 的时候，搞了一个特别大的 AGENTS.md 文件，把所有的规范、所有的约定全部塞进去。结果 Agent 更糊涂了。因为上下文窗口是稀缺资源，这个文件被当作系统提示词每次都注入进去，当它变得越来越长的时候，模型的注意力被严重稀释。

OpenAI 后来把 AGENTS.md 从一本「百科全书」改成了一个「目录页」：

- **主文件只保留 100 行左右的核心索引**，不告诉 Agent 每条细节规则，只告诉 Agent「你想看什么，去哪儿看」
- **详细的内容拆到具体的子文档里**：架构文档、设计原则、产品规格、执行计划、质量评分，每份都有清晰的主题
- Agent 平时只看目录，只有真的需要某一部分的时候，才钻进对应的子文档

这套做法就是「**渐进式披露**」——和软件设计里的「按需加载」「懒加载」一脉相承。

> **原则四：规则文件宁缺毋滥，给模型看的东西少即是多。**

### 难题五：Agent 写的代码越堆越烂，技术债怎么还？

当 Agent 负责写绝大多数代码之后，会发生一件很自然但也很糟糕的事：Agent 会疯狂模仿仓库里已有的代码模式。好的模式会被复制，坏的模式也会被复制。一旦早期某段代码写歪了，Agent 会把那个歪的写法当成「惯例」，越堆越多，越堆越歪。OpenAI 团队给它起了一个名字，叫 **AI slop，AI 代码泔水。**

OpenAI 一开始用最朴素的办法：每周拿出整个周五让人类工程师去手工清扫。然后呢？**这个方案失败了。** Agent 产出代码的速度太快，人类工程师清理的速度根本跟不上，周五清一天，周一一早又堆满了新的。

OpenAI 最后用一个非常 Harness 的思路解决了这个问题：

1. 把人类工程师关于「什么是好代码」的经验，写成一套「**Golden Principles**」沉进仓库——「优先用共享工具包而不是手写 helper」「不要瞎猜数据格式，必须校验边界或用带类型的 SDK」
2. 让一批后台 Agent 按固定节奏自动跑，定期去扫描仓库，对比 Golden Principles，找出偏离的地方，然后自动开修复 PR。大部分修复 PR 可以在 1 分钟内被人类审完，直接 auto merge。

> **原则五：技术债不是攒一堆集中还，而是每天让后台 Agent 自动偿还一点。**

### 一个反直觉的发现：Agent 用「老技术」反而更稳

OpenAI 在实践中发现，Agent 对那些被人类称为「boring」的老技术反而掌握得最好。AI 训练数据里，一个出现了十几二十年的老库，相关的代码示例、StackOverflow 问答、博客文章多如牛毛，AI 对它的各种用法了如指掌。而一个昨天才出的新框架，AI 只看过零星几篇文档，很容易张冠李戴。

**越老、文档越齐全、在开源社区里沉淀了越久的技术，Agent 反而越容易帮你做对。**


## 第四部分：写在最后

AI 工程的重心，过去两年换过三次：
- **Prompt Engineering** 解决「怎么把任务讲清楚」
- **Context Engineering** 解决「怎么把信息送对」
- **Harness Engineering** 解决「怎么让模型在真实执行中持续做对」

这三个不是替代关系，而是**层层包含**：Prompt ⊂ Context ⊂ Harness。

> **Agent = Model + Harness**
>
> 模型决定了一个 Agent 的天花板，但 Harness 决定了它能不能落地、能不能稳定交付、能不能真正跑在生产环境里。

如果你最近也在做 Agent 相关的事情，别再把所有精力都花在调模型、调提示词上了。回过头来看看你的 Harness 长啥样：有没有规则文件？有没有校验闭环？有没有任务编排？有没有评估机制？有没有失败恢复？这些东西，每一项都能让你的 Agent 上一个台阶。

一个值得深思的趋势：如果你真的把 Harness 这件事认真做几个月，你会发现一个很微妙的变化——**你花在「亲手写代码」上的时间越来越少，花在「写规则、写流程、设计环境」上的时间越来越多。** OpenAI Codex 团队那几个工程师能撬动百万行代码，靠的就不是键盘敲得快，而是把 Agent 的运行环境设计到位。

**写代码这件事本身会越来越多地交给 Agent，但设计一个能让 Agent 高质量产出的环境，这件事在很长一段时间里都得是人来做。这可能就是未来程序员真正的主战场。**

五个原则打包成一个小口诀：

> **重启胜过修补，生产验收分家，与其催模型不如改环境，规则宁缺毋滥，技术债天天还。**

### 三、Graph Engineering 详解

#### 1. 起因

- 距 loop engineering 才 40 天，OpenClaw 创始人说"我们还在聊 loop，还是已经切到 graph 了？"
- 大佬跟帖："loop engineering 已死，graph engineering 永生！"

#### 2. 什么是 Graph Engineering？

graph = 数据结构里的"节点加连线"。节点叫 **Node**，连线叫**边（Edge）**。

**它干什么**：按照任务之间的依赖关系，用 graph 编排整个流程——该串行的串行，该并行的并行，每一块交给职责明确的节点完成。

**和 loop 的关系**：不冲突。
- **loop engineering** 解决单个 agent 如何反复思考、调用工具、修正结果（管**节点内部**）
- **graph engineering** 解决多个执行单元如何拆分、并行、汇合、返工（管**节点之间**）

> 一个 loop 就是一张最小的 graph：只有一个节点、一条边，且这条边指回自己。

**为什么不能一个 agent 串行走到底？**

1. **慢** — 后端、前端、测试能三路一起跑，串行只能排着队
2. **中断灾难** — 执行到第 40 步突然中断，要么从头重跑，要么钻进上下文翻
3. **暂停麻烦** — 很难中途停下来等人工审批，隔天再从断点接着干
4. **无法表达复杂分工** — 想要"一个规划的、三个干活的、一个挑刺的"，串行流程开始吃力

#### 3. 工作原理：节点 + 边 + 状态

**第一样：节点（Node）—— 干活的那个**
- 可以是完整思考循环的 agent、固定规则的普通代码、数据库查询、甚至**人**（审批节点）
- 好节点的标准：只干一件事，单独就能测，想换掉它别的节点不受牵连

**第二样：边（Edge）—— 决定下一步执行哪个节点**

设计一条边，是在回答两个问题：

1. 下一个节点由什么决定？
   - **确定性边**（Deterministic Edge）：固定规则，如"测试全过就部署"，不用模型掺和
   - **模型决策边**（Model-decided Edge）：交给模型判断，如"工单派给退款还是投诉节点"

2. 流程是否固定？
   - **条件边**（Conditional Edge）：根据上一步结果分叉，"测试通过进下一节点，失败返回返工"

> 设计的功夫就在分清哪条边该写死、哪条该交给模型。能写死的尽量写死，把模型的判断留给少数需要理解语义的分支。

**第三样：状态（State）—— 字段结构固定的对象**

```json
{
  "backend": {"status": "done", "artifact": "api/export.js"},
  "frontend": {"status": "running"},
  "tests": {"status": "pending"},
  "tokens_used": 12000
}
```

- 执行到哪、每步产出什么、消耗多少 token，都存这里
- 谁要看进度，读这个对象就行，不用钻聊天记录
- 每个节点完成后保存状态 = 存一次档。中断不再是"白跑了"，而是"读档，重试那一个节点"

**三样凑齐，问题各有解法：**
- 想并行？`fan-out` 一个节点分出三条边，干完 `fan-in` 汇合
- 想暂停等审批？增加一个等待人工确认的节点
- 想中断后接着跑？读上一个存档点

#### 4. 实操：什么样的任务适合用 Graph？

**先泼冷水**：大部分任务按顺序执行就够了，犯不着专门用 graph 编排。

**适合用 graph 的特征：**
- 任务能拆成互相独立的子任务，需要缩短总耗时，不能全串行
- 不同环节需要不同模型、工具、权限（干活的节点可写、审查的节点只读）
- 流程中间有必须人工确认的环节
- 任务执行时间长、分支多，需要随时查看每个分支的进度、产物和 token 消耗

> 前提：先确保每个节点都能稳定完成一件事，再谈编排，顺序不能反。

**开发需求例子**（给系统加数据导出功能）：
1. **规划节点**：拆成后端/前端/测试三份任务，定 API 契约，写进状态对象
2. **并行分支**：三个开发节点同时启动，各自在独立 git worktree 干活
3. **集成节点**：合并三个分支，跑全量测试
4. **条件边**：测试全过→继续；失败→把对应任务标记返工，只重做那一路（其他两路保留结果）
5. **人工确认节点**：暂停流程，等你确认 diff，才合入主干

#### 5. 用 LangGraph 怎么写？

```python
from langgraph.graph import StateGraph, START, END

g = StateGraph(DevState)

# 注册节点
g.add_node("plan", plan_task)
g.add_node("backend", backend_dev)
g.add_node("frontend", frontend_dev)
g.add_node("tests", test_dev)
g.add_node("integrate", integrate_code)
g.add_node("rework", rework_code)
g.add_node("approval", human_approval)

# 从规划节点开始
g.add_edge(START, "plan")

# 规划完成后，三个节点并行执行
g.add_edge("plan", "backend")
g.add_edge("plan", "frontend")
g.add_edge("plan", "tests")

# 三个节点都完成后，再进入集成节点
g.add_edge(["backend", "frontend", "tests"], "integrate")

# 根据测试结果决定下一步
g.add_conditional_edges(
    "integrate",
    check_tests,
    {"pass": "approval", "fail": "rework"}
)

# 返工完成后重新集成
g.add_edge("rework", "integrate")

# 人工确认后结束
g.add_edge("approval", END)

app = g.compile()
```

关键解读：
- `StateGraph(DevState)`：DevState 就是状态对象，每个节点都能读写
- `add_edge(["backend","frontend","tests"], "integrate")`：必须等三个节点都完成才进集成
- `add_conditional_edges`：读测试结果，通过进人工确认，失败进返工
- `compile()`：把节点和边组装成可执行的 graph

#### 6. 用 Claude Code 怎么玩？

- **subagent** 充当节点：`.claude/agents/` 下一个 md 定义一个专职 agent（职责、工具、模型），干活的给写权限，审查的只给只读
- **hook** 强制固定检查：agent 结束任务前自动跑测试，没通过就继续改
- **workflow** 编排：一段负责拆任务、派 agent、等结果、处理分支的调度脚本。你只要讲清目标：

```
用 workflow 帮我开发一个记账网站，拆成后端接口、前端页面、测试用例三块并行开发，
做完合并跑全量测试，测试全部通过后叫我确认
```

- 运行中随时输 `/workflows` 看进度树：三路 agent 各跑到哪、消耗多少 token
- `/deep-research` 本身就是一个 graph 工作流：拆解 → 并行搜索 → 抓原文 → 交叉验证 → 合成报告

> 共同点：主会话只负责拆解任务、启动 subagent、等待结果、最终汇总，不再亲自完成中间每一步。这也把**调度过程**和**具体执行过程**分开了。

#### 7. Graph Engineering 和 LangGraph 有什么区别？

- **graph engineering 是一种设计方法**：关注任务怎么拆、哪些并行、下一步由什么决定、状态怎么记录、失败怎么返工
- **LangGraph 是实现这套方法的框架**：提供现成的节点、边、状态、流程控制
- 做 graph engineering 不一定要 LangGraph：AutoGen、Google ADK、Claude Code 的 workflow，甚至自己写调度代码都行

> 更准确的关系：**graph engineering 告诉你应该怎么设计，LangGraph 帮你把设计实现出来。**

这套技术并不新，新的是这个名字，以及大家把注意力从"单个 agent 怎么完成一步"转向"多个 agent 怎么共同完成一条复杂流程"。

#### 8. 最后总结

- graph engineering = 把一个复杂任务拆成多个职责明确的节点，按依赖关系安排串行、并行、条件分支、失败返工
- **节点**负责完成任务，**边**负责决定下一个执行哪个节点，**状态**负责记录流程进度和结果
- 不是所有任务都值得用 graph：任务小、顺序执行能完成的，直接交给一个 agent 跑完就行
- 真正值得关注的不是新名字，而是它背后的**问题**：我们要解决的已经不只是"这一步怎么做对"，而是"几十个步骤怎么稳定地协作起来"

> 名字是新的，问题不是新的。就算过几个月 graph engineering 又被下一个新词替代，**节点、边、状态和任务调度这些东西，依然不会消失**。

## 整体核心总结

1. **记忆系统**的核心是"先提纯，再存储"——写入侧的降噪、切分、分级、标注四步做好的话，检索侧工作量减半，效果反而更好。

2. **从 Prompt 到 Graph** 的演进是一场瓶颈迁移：模型越强，瓶颈越往外移，最后移到"亲自按回车的你"身上。

3. **Loop Engineering** = 五大件 + 磁盘记忆，把你的杠杆变长了，但验证、理解债、认知投降这三笔账也同时变大了。

4. **Graph Engineering** = 节点 + 边 + 状态，解决的是多个 agent 如何稳定协作完成复杂流程的问题。名字是新的，但节点、边、状态和任务调度这些东西不会消失。
