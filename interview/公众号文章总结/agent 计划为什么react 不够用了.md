# Agent 规划三条路：从 ReAct 到 ToT、LATS，一次讲透

> 核心观点：ReAct 很强，但它只解决了"能不能动起来"，不擅长回答"整件事应该怎么做"。当任务从单步执行变成复杂规划时，我们需要在 ReAct 上面加规划层。


## 一、为什么 ReAct 不够了？

### 1.1 ReAct 的核心机制

ReAct 的核心循环：**Thought → Action → Observation → Thought → Action → Observation**

它厉害的地方在于：
- 模型不再只是"想"，而是可以**执行动作**
- 可以接收**环境反馈**，再根据反馈**继续修正**

所以 ReAct 是 Agent 从"文本生成器"走向"行动体"的第一步。但它本质上是一个 **"边看边走"的局部决策框架**，不是全局规划框架。

### 1.2 ReAct 的 6 个核心局限

| # | 局限 | 具体表现 |
|---|------|----------|
| 1 | **短视，容易做局部最优** | 看到一个相关网页就深入，追着追着主线丢了。ReAct 擅长"下一步做什么"，不擅长"为了最终目标，这一步值不值得做" |
| 2 | **没有显式全局计划** | 任务一长就漂移。缺乏主目标、子目标、依赖关系、中间验收点这些"任务骨架"，模型容易中途改目标、重复做事、跳过关键步骤 |
| 3 | **缺少真正的回溯能力** | 纯 ReAct 是单路径前进。错了只能在错误轨迹上继续补，而不是回到岔路口重新选分支 |
| 4 | **轨迹越长，上下文越脏** | 历史 observation 太多，关键信息被淹没；中间错误思路残留，后续决策被污染；Token 成本升高，模型越来越难抓住主线 |
| 5 | **对"高分支决策"不友好** | 当任务需要"选择"而非"执行"时（如 bug 根因判断、研究切入点选择），ReAct 天然吃亏 |
| 6 | **容易形成"假忙碌"** | Agent 一直思考、调工具，看起来勤奋，但最后效果一般。因为它陷入了"行动很密，策略很弱"的状态 |

### 1.3 问题的本质

> **纯 ReAct 是局部贪心式闭环。它能让模型行动，但不能稳定解决长周期、高分支、强不确定性的复杂任务。**

所以工业界开始在 ReAct 外面加规划层。

### 1.4 ReAct 不是过时了，而是需要分层

> ReAct 解决的是**行动闭环问题**，而 ToT/LATS 解决的是**搜索与规划问题**。它们不是替代关系，而是**分层关系**。

更强的系统通常是：
- **外层**：搜索/规划（决定探索哪些候选路径）
- **内层**：局部节点仍然用 ReAct 执行（完成动作-反馈闭环）


## 二、三种规划范式总览

它们回答的是同一个问题：**Agent 的规划，到底应该在什么时候发生、规划到什么粒度、允许探索多少分支？**

| 范式 | 一句话定义 | 规划位置 | 默认路径数 | 是否回溯 |
|------|-----------|----------|-----------|---------|
| **Plan-Then-Act** | 先画施工图，再开工 | 执行前 | 1 条 | 弱 |
| **ReAct + 轻规划** | 边走边看 checklist | 执行中持续存在 | 1 条主路径 | 有限 |
| **Tree/Graph Planning** | 探索多张地图，再选路 | 搜索过程中反复发生 | 多条候选路径 | 强 |

### 核心区别

- **Plan-Then-Act**：先有地图，再走
- **ReAct + 轻规划**：边走边看地图
- **Tree/Graph Planning**：先探索多张地图，再决定走哪条


## 三、范式一：Plan-Then-Act —— 先想清楚，再动手

### 核心流程

```
Goal → Plan → Execute Step 1 → Execute Step 2 → ... → Finalize
```

与纯 ReAct 最大的区别：ReAct 把"思考"嵌在每一步里，而 Plan-Then-Act 把"全局思考"**前置**了。

### 适合场景

目标清晰、路径相对稳定、步骤依赖明确的长任务：
- 写结构化报告
- 固定流程的数据分析
- 有明确步骤的代码迁移
- 企业标准化工作流

### 优点

| 优点 | 说明 |
|------|------|
| 全局一致性更强 | 有了前置计划，任务不容易中途漂 |
| 更省工具调用 | 先想过路线，不东试西试 |
| 更好做权限/风控 | 计划可事前审批，标注敏感步骤 |
| 日志和复盘更清晰 | 能区分是"计划错了"还是"执行错了" |

### 缺点

| 缺点 | 说明 |
|------|------|
| 计划一旦错了，全局完蛋 | 前置规划偏了，执行再稳也没用 |
| 环境一变就过期 | 动态环境下计划很快失效 |
| 规划成本前置 | 简单任务上反而比直接做更慢 |
| 对不确定性任务不灵活 | 需要边探索边定义的问题会显得僵 |

> **一句话**：适合"路线大体可知"的任务，拿全局性换灵活性。


## 四、范式二：ReAct + 轻规划 —— 不是推翻，是加骨架

### 什么叫"轻规划"？

不是搞一个特别重的 Planner，而是加一些足够有用但不太贵的结构：

- 任务分解列表
- 当前子目标
- 剩余待办
- 成功标准
- 阶段性检查点
- 每 N 步重规划一次
- 执行前先选策略，再进 ReAct

### 和纯 ReAct 的核心区别

> **纯 ReAct 主要靠"轨迹"推动，ReAct + 轻规划主要靠"轨迹 + 小地图"共同推动。**

### 适合场景

中等复杂度、环境有变化、但又不值得上重搜索的任务：
- 多轮资料搜集与整理
- 中等复杂度的代码修改
- 多工具配合的工作流
- 有阶段目标的研究和分析

### 优点

| 优点 | 说明 |
|------|------|
| 比纯 ReAct 稳很多 | 有骨架牵引 |
| 比 Plan-Then-Act 灵活 | 可随环境调整 |
| 实现门槛相对低 | 不需要重搜索架构 |
| 工程性很好 | 容易迭代和调试 |

### 缺点

| 缺点 | 说明 |
|------|------|
| 本质还是"单主路径" | 不会同时探索多条路 |
| 规划层太弱 → 沦为装饰 | 需要设计得当 |
| 规划与执行容易互相污染 | 上下文管理要小心 |
| 极复杂任务依然不够 | 有天花板 |

> **一句话**：适合绝大多数真实 Agent 任务，拿一点复杂度换明显更稳的执行。


## 五、范式三：Tree / Graph Planning —— 真正把"搜索"引入 Agent

### ToT（Tree of Thoughts）的核心思想

> 把多个中间思路当成搜索节点，**展开 → 评估 → 选择**。

不是单轮长思维，而是**多路径探索**。

### LATS（Language Agent Tree Search）的核心思想

> 把树搜索与 Agent 执行闭环**真正结合**。

每个节点不只是"想法"，还包含：状态、动作、观测、价值评估、rollout 结果、未来潜力估计。

### 为什么还提 Graph Planning？

真实任务不一定是天然树：
- 很多路径会回到相同状态
- 有些中间结果可以复用
- 节点之间存在交叉依赖

此时用图比用树更自然。

### 适合场景

高不确定性、高分支、高价值的复杂任务：
- 复杂 bug 修复
- 深度研究与证据链构建
- 数学/逻辑推理
- 多路径网页交互
- 需要显式探索备选方案的 Agent

### 优点

| 优点 | 说明 |
|------|------|
| 真的能探索多个候选路径 | 不是只走一条 |
| 具备回溯能力 | 能回到岔路口重来 |
| 更有机会拿全局更优解 | 不是局部贪心 |
| 天然适配 value model/critic/reward | 评估驱动搜索 |

### 缺点

| 缺点 | 说明 |
|------|------|
| 贵，非常贵 | Token 成本高 |
| 分支爆炸是真问题 | 搜索空间指数增长 |
| 评估器不靠谱 → 整个搜索偏掉 | 评估器质量是关键 |
| 工程复杂度高很多 | 实现和维护成本大 |

> **一句话**：适合"路径选择本身就是难点"的任务，拿高成本换更强的探索与回溯能力。


## 六、真实工程里怎么选？

### 判断标准（三个问题）

| 你要判断的事 | 如果答案是"是" | 更适合 |
|-------------|---------------|--------|
| 路线是否大体已知？ | 是 | Plan-Then-Act |
| 执行时是否需要频繁根据反馈调整？ | 是 | ReAct + 轻规划 |
| 是否必须同时探索多个候选路径？ | 是 | Tree/Graph Planning |

### 最接地气的一句话

- 任务越像**走流程** → 越适合**先计划**
- 任务越像**边做边修** → 越适合**轻规划 ReAct**
- 任务越像**走迷宫** → 越需要**树和图搜索**

### 不是"哪个更高级"，而是"哪个更匹配任务结构"

| 场景 | 推荐范式 |
|------|----------|
| 固定步骤的数据处理、结构化报告、企业审批链 | Plan-Then-Act |
| 网页检索+汇总、多工具协作、中等复杂代码任务 | ReAct + 轻规划 |
| 复杂 bug 修复、高价值 research、长链条复杂决策 | Tree/Graph Planning |


## 七、核心要点速记

### 三种范式的本质区别

| 维度 | Plan-Then-Act | ReAct + 轻规划 | Tree/Graph Planning |
|------|---------------|----------------|---------------------|
| 规划位置 | 执行前 | 执行中持续存在 | 搜索中反复发生 |
| 默认路径数 | 1 条 | 1 条主路径 | 多条候选路径 |
| 是否允许回溯 | 弱 | 有限 | 强 |
| 适合任务 | 稳定长流程 | 动态中复杂任务 | 高分支复杂任务 |
| 核心优势 | 全局一致 | 平衡稳定与灵活 | 探索与全局最优 |
| 核心风险 | 计划僵化 | 仍偏单路径 | 成本和复杂度爆炸 |

### 面试回答框架

> 纯 ReAct 本质上是局部贪心式闭环。它能让模型行动，但不能稳定解决长周期、高分支、强不确定性的复杂任务。
>
> 所以工业界开始在 ReAct 外面加规划层：
> - 任务路径稳定 → Plan-Then-Act
> - 任务动态但复杂度中等 → ReAct + 轻规划
> - 任务需要探索多个候选解并支持回溯 → Tree/Graph Planning（ToT、LATS）
>
> 本质区别在于**规划发生的时机、搜索空间的宽度，以及是否支持显式回溯**。


## 八、最后的思考

真正成熟的工程思维，不是先选"最喜欢的范式"。

而是**先看任务结构，再选控制结构**。

你要学会问自己：

- 这个任务是**流程问题**，还是**探索问题**？
- 它需要**全局计划**，还是**局部反馈**？
- 它是一条路走到黑，还是要**保留多条候选路径**？
- 错误是能**局部修**，还是必须**回到岔路口重来**？

当你开始这样想问题时，你才真正开始进入 Agent 系统设计。

> **ReAct 很重要，但它不万能。Plan-Then-Act 很稳，但它不通吃。ToT、LATS 很强，但也不是每个系统都值得上重搜索。**
