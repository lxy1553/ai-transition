# Agent 记忆系统与 Agent 进化

---

## 一、Agent 的记忆系统怎么设计？

### 1.1 一句话总览

Agent 的记忆系统是**分层架构**，不能一概而论：

| 层级 | 作用 | 时效 | 容量 |
|------|------|------|------|
| **工作记忆** | 当前上下文窗口内容，模型直接可用 | 即时 | 最小 |
| **短期记忆** | 整个会话的对话历史，维持单次任务连贯性 | 会话内 | 中等 |
| **长期记忆** | 跨会话持久化，存用户偏好、历史决策、经验教训 | 永久 | 最大 |

真正的难点不在"存"，而在"**管**"：长期记忆怎么检索才准？什么记忆该淘汰？新旧记忆冲突听谁的？怎么控制 Token 成本？这些问题没想清楚，记忆系统
最后只会变成**噪声源**，帮倒忙。

### 1.2 为什么需要分层记忆？

很多人第一次接触 Agent 记忆，会觉得"不就是存聊天记录吗"，然后把所有历史全塞回上下文。这样做有**三个致命问题**：

1. **装不下** — 上下文窗口再大也有限。之前大模型上下文 128k，目前 GPT-5.6、Claude Opus 4.8 都是 1m，聊久了肯定溢出；更高的上下文成本， 延迟翻倍。
2. **噪声大** — 上下文越长，模型越容易忽略中间位置的信息，学术上叫 **"Lost in the Middle"**。十天前的闲聊跟今天的任务有什么关系？全塞进去只会干扰判断，降低准确率。
3. 所以记忆必须**分层** — 不同时效、不同重要性的信息，放在不同的地方，用不同的策略管理。就像人脑也分瞬时记忆、短期记忆、长期记忆。

### 1.3 第一层：工作记忆

工作记忆就是大模型的**上下文窗口本身**，每一轮推理都能直接看到。

- **特点**：最快、最准，但最贵、容量最小。
- **类比**：CPU 的寄存器 —— 离计算单元最近，读写零延迟，但只有几十个字节。
- **注意**：工作记忆里的每一个 Token 都是要花钱的，不能什么都往里塞。

工作记忆里通常放三类东西：

1. **System Prompt** — 角色设定、安全规则、输出格式（固定，每轮都要有）
2. **最近几轮对话** — 保证当前对话的连贯性
3. **当前任务状态**

> 💡 工作记忆满了怎么办？把不重要的内容移到短期记忆或者压缩掉，给新内容腾空间 —— 这就是记忆管理的核心动作。

### 1.4 第二层：短期记忆（会话内的上下文缓冲）

短期记忆是**会话级别**的，一次对话从头到尾的完整记录都存在这里。存储介质一般用 **Redis** 或内存数据库，按 `session_id` 存，
会话结束后按 TTL 自动过期（比如用户关了页面，24 小时后自动清掉）。

短期记忆的实现方案有三种，从简单到复杂：

**方案一：滑动窗口**
- 只保留最近 N 轮对话，超出的直接丢弃
- ✅ 零实现成本，信息完整无损
- ❌ 窗口外的信息彻底丢失（"金鱼脑"）
- 🎯 适合：客服机器人、单轮任务型 Agent

**方案二：滚动摘要**
- 对话长到一定程度，把前面的内容用 LLM 摘要压缩，腾出空间
- ✅ 能保留更长时间的信息，Token 成本可控
- ❌ 摘要不是无损的，会有**事实漂移**——用户说"不喜欢红色"，摘要两轮后可能变成"用户偏好红色"
- 🎯 适合：中等长度对话、对精确性要求不极高的场景

**方案三：关键帧机制**（工业界推荐）
- 借鉴视频编码思路：**重要节点完整保存，中间过程只存摘要**
- 什么是关键帧？用户明确表达偏好、任务目标变更、重要工具调用结果——这些不能丢
- 怎么判断关键帧？简单用规则触发，复杂用轻量分类模型打分（比每轮调大模型便宜得多）
- ✅ 兼顾成本和准确性

### 1.5 第三层：长期记忆（跨会话的知识沉淀）

长期记忆是**持久化**的——用户上周说过的话、上个月做过的决策、半年前提过的偏好，都能存下来。下次用户再来，系统能"认出"他。按内容分三类
（源自认知心理学，面试说出来很加分）：

| 类型 | 存什么 | 特点 | 用途 |
|------|--------|------|------|
| **情景记忆** (Episodic) | "发生过什么事"：对话片段、任务执行记录 | 时间属性强，有具体场景 | 回溯历史对话、复盘决策 |
| **语义记忆** (Semantic) | "事实性知识"：对花生过敏、常用 Python、市场部 | 结构化、事实性、更新频率低 | 个性化服务、偏好预判<br/>（"Agent 懂我"的关键） |
| **程序记忆** (Procedural) | "怎么做事情"：先看摘要再看详情、按周维度汇总 | 经验和方法论 | 优化工作流、减少重复沟通 |

**长期记忆怎么用？→ 检索式召回**

不可能把所有长期记忆都塞回上下文（几万条早就爆了）。正确做法是**按需检索**：用户问一个问题，先去长期记忆库搜相关内容，只把最相关的 
Top-K 条捞出来拼到上下文。这本质上就是 **RAG**，只不过知识库不是产品文档，而是用户的历史记忆。

**长期记忆检索的三重评分**（面试加分点）

只看相似度是初级做法。斯坦福 Generative Agents 论文提出**三重评分框架**：

1. **相关性 (Relevance)** — 语义相似度，这条记忆跟当前问题有没有关系。用 Embedding 余弦相似度计算。
2. **重要性 (Importance)** — 这条记忆本身有多重要？"用户对花生过敏"比"用户今天喝了杯咖啡"重要得多。用 LLM 打 1-10 分，或训练轻量模型分类。
3. **时效性 (Recency)** — 越新的记忆权重越高，符合人脑遗忘曲线。用指数衰减函数：时间越久分数越低。

> 最终分数 = 相关性 × α + 重要性 × β + 时效性 × γ，三个权重按业务场景调。
>
> 面试时能讲出这三重评分，说明你真的深入思考过，不是只会调向量库。

### 1.6 工程踩坑：记忆系统的几个真实问题

**坑一：记忆越存越多，检索变慢、噪声变大**
- 现象：系统跑了三个月，向量库膨胀十几倍，检索从 200ms 变成 2s
- 解法：必须有**遗忘机制**——不重要的、太久没访问的、已经过时的，该删就删。重要性低于阈值的，30 天后自动归档；半年没被检索过的，直接清理

**坑二：新旧记忆冲突，听谁的？**
- 现象：用户上个月说"我用 React"，这个月说"我转 Go 了"，两条记忆都在，模型就懵了
- 解法：**时间戳优先 + 冲突检测**。每条记忆带创建时间，冲突时默认采信新的；复杂场景用小模型判断是"更新"还是"补充"

**坑三：摘要压缩导致事实漂移**
- 现象：滚动摘要滚了几轮之后，信息慢慢失真
- 解法：**关键事实结构化存储，不参与摘要压缩**。核心偏好、过敏信息、重要参数，单独存在结构化槽位里，永远是原始值

**坑四：记忆注入破坏 Prompt Cache**
- 现象：大模型有 Prompt Cache 功能，System Prompt 固定能省 30% 成本还提速；但记忆系统每轮往 System 里塞东西，缓存直接失效
- 解法：记忆**不要放 System Prompt**，放 User Message 部分；或不要每轮更新，攒几轮再统一更新

### 1.7 记忆系统的本质

很多人觉得记忆系统就是个存储模块，其实不是。**记忆系统的本质是认知管理**——它决定了 Agent 在每一个时刻"脑子里装着哪些信息"。

存什么、忘什么、什么时候想起、以什么形式呈现——这些决策直接决定了 Agent 的表现。就像人一样，真正聪明的人不是过目不忘，而是**在需要的时候，能准确想起该想的事情**。

## 二、Agent 进化：从 Prompt 到 Graph

### 2.1 概念演进时间线

```
2023 年       Prompt Engineering     —— 怎么"说"
2024 年       Context Engineering    —— 喂什么"材料"
2026 年 2 月  Harness Engineering   —— 干活的"驾驶舱"
2026 年 6 月  Loop Engineering      —— 不按回车"松手"
2026 年 6 月  Graph Engineering     —— 多 agent 并行编排
```

**核心规律**：每个新词的出现，都是上一瓶颈被解决、新瓶颈暴露。模型每变强一截，瓶颈就往外移一层：

- 从你说的那句话（prompt）
- → 到你给的那堆材料（context）
- → 到它干活的环境（harness）
- → 落到你本人身上（loop）
- → 再到多任务协作（graph）

> Agent = 模型 + harness。同一个模型，驾驶舱不一样，能力可以差出几倍。

## 三、Loop Engineering 详解

### 3.1 起因

- **Peter Steinberger**（OpenClaw 作者，6 月 7 日）：「每月例行提醒：你不该再给 coding agent 打 prompt 了。你该去设计那个给 agent 打 prompt 的 loop。」
- **Addy Osmani**（Google Cloud AI 总监）给出定义并写长文
- **Boris Cherny**（Claude Code 创始人）：「我已经不 prompt Claude 了。是 loop 在运行着 prompt Claude、决定做什么。我的工作是写 loop。」

一个造工具的、一个定方法论的、一个每天泡在一线的创始人，同一周说了同一件事。

### 3.2 什么是 Loop Engineering？

> Loop engineering 就是把"亲自给 agent 写 prompt 的那个你"替换掉，转而设计那个代替你做这件事的系统。

- **过去**：回合制协作。你写一条 prompt → 读输出 → 再写一条。agent 是工具，你全程握着它。
- **现在**：把"发现任务、布置任务、检查结果、决定下一步"设计成一个能自己运转的循环，让循环去握着 agent。

**打个比方**：以前你是客服热线的接线员，每个电话亲自接；现在你升级成设计工单系统的人——电话怎么分流、哪类问题转给谁、办结标准是什么、办不了的怎么升级。你没有离开公司，但岗位变了。

> 一句话：你不再是 prompt 的作者，你是 **prompt 生产系统的设计师**。
>
> 注意：工作没有变容易，是杠杆的支点移动了。以前写一条好 prompt，收益是"这一次回答变好"；现在设计一个好 loop，收益是"之后每一次循环都变好"。投入从消耗品变成了资产。

### 3.3 一个 loop 由什么组成？（五大件 + 记忆）

**第一件：自动化 —— loop 的心跳**
- 定时或事件触发：每天早上自动扫 CI 失败、每次 PR 合并自动跑检查
- 没有自动化，loop 只是你跑过一次的任务

**第二件：worktree —— 让并行不变成打架**
- 多个 agent 同时改同一个文件的解法
- 给每个 agent 独立工作目录和独立分支，共享仓库历史，物理互不干扰，最后各开各的 PR

**第三件：skill —— 治好 agent 的"金鱼记忆"**
- agent 每个会话都是冷启动，项目规范一概不知
- 把项目知识写成文件放仓库里，让 agent 该用时自己读
- 对 loop 的意义：没有 skill，loop 每个周期从零重推；有了 skill，知识是**复利**的

**第四件：connector —— 让 loop 摸到真实世界**
- 基于 MCP 协议的连接器：读 issue、查监控、发消息、开 PR
- 完整 loop 会自己开好 PR、关联工单，CI 变绿后自己去频道通知人

**第五件：sub-agent —— 写的人和查的人必须分开**
- 让 A 出方案，让干净上下文的 B 来挑刺
- 写代码的模型给自己的作业打分时"实在太手下留情了"

**第六件：记忆 —— loop 的命根子**
- 模型两次运行之间会忘掉一切
- 解法朴素：把记忆放在**磁盘上**，而不是上下文里——一个 markdown 文件、一个任务看板
- > "agent 会忘，但 repo 不会。"

### 3.4 一个真实的 loop 长什么样？

> 任务：每天早上自动把项目里值得修的问题找出来、修好、提交审核。

1. 每天早晨，自动化准时触发，调用负责**分诊**的 skill
2. skill 读昨天的 CI 失败记录、未关闭的 issue、最近提交，把"哪些问题值得处理"写进状态文件
3. 对每个值得处理的问题，开隔离的 worktree，派 sub-agent 起草修复
4. 第二个 sub-agent 对照项目 skill 规范和现有测试，审草稿
5. 审过了，connector 自动开 PR、更新工单
6. loop 搞不定的问题不硬来，丢进待办收件箱，等真人来看
7. 所有经过写回状态文件，明天从今天停下的地方继续

> 整个过程你只设计了一次，中间任何一步都没写 prompt。你的活从"每一步都出现"变成"只在两个地方出现"：**设计循环的时候** + **收件箱里有东西的时候**。

### 3.5 工具支持对照表

| 部件 | 在 loop 里的职责 | Codex | Claude Code |
|------|----------------|-------|-------------|
| 自动化 | 定时发现和分诊 | Automations 面板 + 分诊收件箱 | 计划任务、/loop、hooks |
| worktree | 隔离并行任务 | 每个线程内置 worktree | git worktree、隔离配置 |
| skill | 固化项目知识 | Agent Skills | Agent Skills |
| connector | 连接外部工具 | 基于 MCP 的 Connectors | MCP servers |
| sub-agent | 分头干活、写查分离 | 配置文件定义子 agent | 子 agent、agent teams |
| 记忆 | 追踪进度 | markdown 或接工单系统 | markdown 或接工单系统 |

**两个细节：**
- 两家都有 `/goal` 类能力——跑到你写的条件为真才停（"所有测试通过且 lint 干净"），每轮结束由独立模型判断条件。这就是"写的人和查的人分开"，用在停止条件上。
- **loop 的设计正在变得工具无关**——部件是同样的部件，差的只是商标。值得积累的是图纸，不是对某家工具的肌肉记忆。

**实操：30 秒搭出第一个 loop**

```bash
/loop 10m 检查当前分支 PR 的 CI 状态：
  有失败的检查就读日志、修复、推送；
  全部变绿后停下来，给我一句话总结改了什么
```

- `10m` 是心跳：每 10 分钟自动醒来跑一轮
- 中间是任务：每一轮干什么
- 最后是停止条件加汇报

**使用边界：**
1. `/loop` 活在当前会话里，适合"今天盯着这件事"的轮询，关电脑就停；想睡觉时也跑的，要用计划任务或云端 routines
2. 最小 loop 只有心跳、任务和停止条件，没有 worktree、没有写查分离的 sub-agent。**这不是缺陷，是起点**——部件是一件一件长出来的

### 3.6 三盆冷水（Loop 的三个尖锐问题）

**第一盆：验证仍然归你**
- 无人值守运行的 loop，也是无人值守犯错的 loop
- 检查 agent 嘴里的 "done" 只是一个声明，不是一个证明——它说没问题，和真的没问题，中间还隔着你的眼睛

**第二盆：理解债（Comprehension Debt）越顺滑涨得越快**
- loop 交付你没写过的代码越快，"仓库里实际存在的东西"和"你脑子里真正理解的东西"之间的鸿沟就越大
- 技术债是代码烂；理解债是代码可能不烂，但你不知道它为什么是对的

**第三盆：认知投降（Cognitive Surrender），最舒服的姿势最危险**
- 不再对产出有自己的观点，它给什么就收什么
- > "带着判断力去设计 loop，它是解药；为了逃避思考去设计 loop，它是助燃剂。同一个动作，相反的结果。"

**还有一笔现实的账**：token 成本。loop 按循环烧 token，sub-agent 每多一个就多一份开销。务实的花法是把 sub-agent 用在"值得买第二意见"的地方，而不是处处双保险。

> **浓缩成 3 句话：**
> 1. 从 prompt 到 context 到 harness 再到 loop，四个词是一场瓶颈迁移：模型越强，瓶颈越往外移，最后移到"亲自按回车的你"身上。
> 2. 一个 loop = 五大件 + 一份磁盘记忆：自动化是心跳，worktree 防打架，skill 治金鱼记忆，connector 摸到真实世界，sub-agent 写查分离，状态文件让明天接得上今天。
> 3. loop 把你的杠杆变长了，但验证、理解债、认知投降这三笔账也同时变大了。工具分不出你是在加速还是在逃避，你自己分得出。

## 四、Graph Engineering 详解

### 4.1 起因

- 距 loop engineering 才 40 天，OpenClaw 创始人说"我们还在聊 loop，还是已经切到 graph 了？"
- 大佬跟帖："loop engineering 已死，graph engineering 永生！"

### 4.2 什么是 Graph Engineering？

graph = 数据结构里的"节点加连线"。节点叫 **Node**，连线叫**边（Edge）**。

**它干什么**：按照任务之间的依赖关系，用 graph 编排整个流程——该串行的串行，该并行的并行，每一块交给职责明确的节点完成。

**和 loop 的关系**：不冲突。
- **loop engineering** 解决单个 agent 如何反复思考、调用工具、修正结果（管**节点内部**）
- **graph engineering** 解决多个执行单元如何拆分、并行、汇合、返工（管**节点之间**）

> 一个 loop 就是一张最小的 graph：只有一个节点、一条边，且这条边指回自己。

**为什么不能一个 agent 串行走到底？**

1. **慢** — 后端、前端、测试能三路一起跑，串行只能排着队
2. **中断灾难** — 执行到第 40 步突然中断，要么从头重跑，要么钻进上下文翻
3. **暂停麻烦** — 很难中途停下来等人工审批，隔天再从断点接着干
4. **无法表达复杂分工** — 想要"一个规划的、三个干活的、一个挑刺的"，串行流程开始吃力

### 4.3 工作原理：节点 + 边 + 状态

**第一样：节点（Node）—— 干活的那个**
- 可以是完整思考循环的 agent、固定规则的普通代码、数据库查询、甚至**人**（审批节点）
- 好节点的标准：只干一件事，单独就能测，想换掉它别的节点不受牵连

**第二样：边（Edge）—— 决定下一步执行哪个节点**
- 设计一条边，是在回答两个问题：
  1. 下一个节点由什么决定？
     - **确定性边**（Deterministic Edge）：固定规则，如"测试全过就部署"，不用模型掺和
     - **模型决策边**（Model-decided Edge）：交给模型判断，如"工单派给退款还是投诉节点"
  2. 流程是否固定？
     - **条件边**（Conditional Edge）：根据上一步结果分叉，"测试通过进下一节点，失败返回返工"

> 设计的功夫就在分清哪条边该写死、哪条该交给模型。能写死的尽量写死，把模型的判断留给少数需要理解语义的分支。

**第三样：状态（State）—— 字段结构固定的对象**

```json
{
  "backend": {"status": "done", "artifact": "api/export.js"},
  "frontend": {"status": "running"},
  "tests": {"status": "pending"},
  "tokens_used": 12000
}
```

- 执行到哪、每步产出什么、消耗多少 token，都存这里
- 谁要看进度，读这个对象就行，不用钻聊天记录
- 每个节点完成后保存状态 = 存一次档。中断不再是"白跑了"，而是"读档，重试那一个节点"

**三样凑齐，问题各有解法：**
- 想并行？`fan-out` 一个节点分出三条边，干完 `fan-in` 汇合
- 想暂停等审批？增加一个等待人工确认的节点
- 想中断后接着跑？读上一个存档点

### 4.4 实操：什么样的任务适合用 graph？

**先泼冷水**：大部分任务按顺序执行就够了，犯不着专门用 graph 编排。

**适合用 graph 的特征：**
- 任务能拆成互相独立的子任务，需要缩短总耗时，不能全串行
- 不同环节需要不同模型、工具、权限（干活的节点可写、审查的节点只读）
- 流程中间有必须人工确认的环节
- 任务执行时间长、分支多，需要随时查看每个分支的进度、产物和 token 消耗

> 前提：先确保每个节点都能稳定完成一件事，再谈编排，顺序不能反。

**开发需求例子**（给系统加数据导出功能）：
1. **规划节点**：拆成后端/前端/测试三份任务，定 API 契约，写进状态对象
2. **并行分支**：三个开发节点同时启动，各自在独立 git worktree 干活
3. **集成节点**：合并三个分支，跑全量测试
4. **条件边**：测试全过→继续；失败→把对应任务标记返工，只重做那一路（其他两路保留结果）
5. **人工确认节点**：暂停流程，等你确认 diff，才合入主干

### 4.5 用 LangGraph 怎么写？

```python
from langgraph.graph import StateGraph, START, END

g = StateGraph(DevState)

# 注册节点
g.add_node("plan", plan_task)
g.add_node("backend", backend_dev)
g.add_node("frontend", frontend_dev)
g.add_node("tests", test_dev)
g.add_node("integrate", integrate_code)
g.add_node("rework", rework_code)
g.add_node("approval", human_approval)

# 从规划节点开始
g.add_edge(START, "plan")

# 规划完成后，三个节点并行执行
g.add_edge("plan", "backend")
g.add_edge("plan", "frontend")
g.add_edge("plan", "tests")

# 三个节点都完成后，再进入集成节点
g.add_edge(["backend", "frontend", "tests"], "integrate")

# 根据测试结果决定下一步
g.add_conditional_edges(
    "integrate",
    check_tests,
    {"pass": "approval", "fail": "rework"}
)

# 返工完成后重新集成
g.add_edge("rework", "integrate")

# 人工确认后结束
g.add_edge("approval", END)

app = g.compile()
```

关键解读：
- `StateGraph(DevState)`：DevState 就是状态对象，每个节点都能读写
- `add_edge(["backend","frontend","tests"], "integrate")`：必须等三个节点都完成才进集成
- `add_conditional_edges`：读测试结果，通过进人工确认，失败进返工
- `compile()`：把节点和边组装成可执行的 graph

### 4.6 用 Claude Code 怎么玩？

- **subagent** 充当节点：`.claude/agents/` 下一个 md 定义一个专职 agent（职责、工具、模型），干活的给写权限，审查的只给只读
- **hook** 强制固定检查：agent 结束任务前自动跑测试，没通过就继续改
- **workflow** 编排：一段负责拆任务、派 agent、等结果、处理分支的调度脚本。你只要讲清目标：

```
用 workflow 帮我开发一个记账网站，拆成后端接口、前端页面、测试用例三块并行开发，
做完合并跑全量测试，测试全部通过后叫我确认
```

- 运行中随时输 `/workflows` 看进度树：三路 agent 各跑到哪、消耗多少 token
- `/deep-research` 本身就是一个 graph 工作流：拆解 → 并行搜索 → 抓原文 → 交叉验证 → 合成报告

> 共同点：主会话只负责拆解任务、启动 subagent、等待结果、最终汇总，不再亲自完成中间每一步。这也把**调度过程**和**具体执行过程**分开了。

### 4.7 Graph Engineering 和 LangGraph 有什么区别？

- **graph engineering 是一种设计方法**：关注任务怎么拆、哪些并行、下一步由什么决定、状态怎么记录、失败怎么返工
- **LangGraph 是实现这套方法的框架**：提供现成的节点、边、状态、流程控制
- 做 graph engineering 不一定要 LangGraph：AutoGen、Google ADK、Claude Code 的 workflow，甚至自己写调度代码都行

> 更准确的关系：**graph engineering 告诉你应该怎么设计，LangGraph 帮你把设计实现出来。**
>
> 这套技术并不新，新的是这个名字，以及大家把注意力从"单个 agent 怎么完成一步"转向"多个 agent 怎么共同完成一条复杂流程"。

### 4.8 最后总结

- graph engineering = 把一个复杂任务拆成多个职责明确的节点，按依赖关系安排串行、并行、条件分支、失败返工
- **节点**负责完成任务，**边**负责决定下一个执行哪个节点，**状态**负责记录流程进度和结果
- 不是所有任务都值得用 graph：任务小、顺序执行能完成的，直接交给一个 agent 跑完就行
- 真正值得关注的不是新名字，而是它背后的**问题**：我们要解决的已经不只是"这一步怎么做对"，而是"几十个步骤怎么稳定地协作起来"

> 名字是新的，问题不是新的。就算过几个月 graph engineering 又被下一个新词替代，**节点、边、状态和任务调度这些东西，依然不会消失**。

**“你们 Agent 的记忆写入流程，具体怎么做的？”**

这个问题，大多数人的第一反应可能和我早期一样：觉得这是个简单的存储问题。但面试官真正想考察的，是当你面对海量、嘈杂的真实对话数据时，如何设计一套**高信噪比的记忆系统**。

一个常见的错误回答是：“每轮对话结束后，把用户和模型的回复存下来，转成向量塞进向量库就行了。” 这个方案在Demo里能跑，但在生产环境会立刻暴露三个致命问题：

1.  **噪声过载**：真实对话中，有效信息可能只占30%-40%。大量“好的”、“收到”、工具调用的完整JSON日志、用户改口前的错误信息等，如果全量存储，会成为检索时的巨大噪声，直接带偏模型。
2.  **粒度过粗**：用户在一轮对话中可能说了职业、提了需求、补了偏好、吐槽了竞品。将整段话压成一个向量，语义重心会非常模糊，导致该召回的召回不了。
3.  **无差别存储**：致命信息（如“我对花生过敏”）和一次性闲聊（如“今天天气不错”）被同等对待，浪费了存储和计算资源，也降低了关键信息的权重。

因此，**“先提纯，再存储”** 是核心原则。完整的生产级写入流程是一个**四阶流水线**：

---

### 📝 深度拆解：写入流水线的四道关卡

#### 第一关：降噪清洗 —— 把垃圾先挑出来
这是性价比最高的一关。通过规则（如正则表达式）过滤掉明显无用的内容，不进入后续处理。

*   **过滤对象**：无意义寒暄（“你好”、“谢谢”）、工具调用的完整返回日志（只保留核心结论）、用户修正前的内容（“用Python……不对，用Go”）、系统的固定话术。
*   **价值**：实现成本极低，但能有效过滤掉 **30%-50%** 的无效内容，让后续流程专注于有效信息。

#### 第二关：语义切分 —— 拆成独立的“记忆原子”
清洗完的对话不能整段存储，需要拆分成一个个**独立的、只包含一个核心信息点**的“记忆原子”。

*   **做法**：
    *   **方案一（推荐）**：用轻量级小模型（如Qwen3-14B）做信息抽取，提取结构化的“事实列表”。
    *   **方案二**：规则（正则）处理简单模式，复杂场景再调用大模型，以平衡成本和效果。
*   **价值**：拆分后，每条记忆的语义重心清晰，检索精度显著提升。实测数据显示，**Top-5召回准确率平均能提升22%**。

#### 第三关：分级筛选 —— 不是所有记忆都配进长期库
拆好的记忆原子，需要根据其价值进行打分，并决定其“命运”。

*   **打分维度**：
    *   **事实性**：是明确事实（“对花生过敏”），还是情绪碎片（“今天心情不错”）？
    *   **持续性**：有效期多久？是“今天赶时间”（短期），还是“我是做运营的”（长期）？
    *   **影响力**：对后续服务影响大吗？（过敏信息影响安全，权重高；“喜欢美式”影响小）。
*   **分级处理**：
    *   **高分（核心记忆）**：进长期库，永久留存。
    *   **中分（短期有效）**：进短期缓存（如7-30天），到期清除。
    *   **低分（噪声）**：直接丢弃。
*   **价值**：此步骤能将长期库的日均新增量大幅削减（如从1800条降至350条），同时因为过滤了噪声，**检索准确率反而会提升**。

#### 第四关：元数据标注 —— 给记忆贴上“身份证”
为每条合格记忆打上标准化的标签（元数据），用于检索时进行**前置过滤**，避免向量检索只看语义、不分场景的缺陷。

*   **必带标签**：
    *   **基础属性**：`user_id`、创建/访问时间。
    *   **类型标签**：情景记忆（事件）/ 语义记忆（事实）/ 程序记忆（流程）。
    *   **场景标签**：客服/创作/编程等。
    *   **置信度**：直接提取的为“高置信”，推理生成的为“低置信”。
*   **价值**：检索时先用元数据“粗筛”（如只搜“编程场景+高置信”），再用向量“精排”，**既快又准**，避免了跨场景记忆干扰。

---

### ⚠️ 三个真实的生产踩坑经验

1.  **同步写入拖慢响应**
    *   **问题**：对话结束后同步进行提取、向量化、写入，增加了300ms延迟，影响用户体验。
    *   **解法**：改为**异步写入**。对话结果正常返回，写入流程丢到后台消息队列执行。仅核心偏好（如过敏信息）走同步链路。

2.  **小模型提取出“虚假记忆”**
    *   **问题**：小模型（如7B）有约8%的错误率，可能将“我朋友喜欢VS Code”误提取为“用户喜欢VS Code”。
    *   **解法**：为记忆打**置信度分数**。“高置信”记忆参与决策，“低置信”记忆仅作参考。并建立**人工抽检审计**机制。

3.  **重复记忆挤爆Top-K**
    *   **问题**：用户反复提及同一偏好（如“喜欢简洁表格”），库里产生十几条重复记忆，挤占了Top-K中其他有效记忆的位置。
    *   **解法**：写入前做**相似度去重**。当新记忆与已有记忆的余弦相似度超过阈值（如0.92），则**更新旧记忆的最后访问时间和访问次数**，不新增条目。访问次数高的记忆在检索时会获得更高权重。

### 💡 收尾总结

**记忆系统的优化，应先看写入，再看检索。**

很多团队在检索侧花费大量精力（换模型、加Rerank），但如果写入环节是“整段对话直接存”，库里60%都将是垃圾。**在垃圾堆里翻宝贝，换再好的铲子也没用。**

## ◆💡 一句话回答

原始对话绝对不能直接写进记忆库，完整的生产级写入流程是一条四阶流水线：**降噪清洗 → 语义切分 → 分级筛选 → 元数据标注**。

核心逻辑就一句话：**先提纯，再存储**。不是存得越多越好，而是存的每一条都得有价值。写入环节做好了，检索准确率能提升 30% 以上，存储成本反而能降一半。

## ◆📝 深度拆解

### 先说为什么「直接存」是错的

很多学员对记忆写入的理解就是「对话结束→存起来→转向量」。这在 Demo 里能跑，但到了生产环境，三个问题会像地雷一样引爆：

**1. 噪声过载。** 你去翻翻真实的产品对话记录，会发现有效信息可能只占 30%-40%。剩下的是什么？「好的」「收到」「嗯嗯」这种无意义确认，工具返回的完整 JSON 日志（几百行），用户改口前说的错误答案，还有各种「哈哈」「笑死」的情绪垃圾。这些东西全塞进向量库，检索的时候分分钟被当成「相关结果」召回，直接把模型带偏。

**2. 粒度过粗。** 一轮对话里，用户可能同时说了自己的职业、提了一个需求、补了一个偏好、吐槽了一句竞品。你把这整段话压成一条向量，语义重心在哪？是职业？是需求？还是吐槽？向量表示会被这些杂七杂八的信息「稀释」，导致该召回的召回不了，不该召回的一大堆。

**3. 无差别存储。** 用户说「我对花生过敏」和用户说「今天天气不错」，在你的记忆库里权重一模一样，占一样的存储空间，都参与全库检索。前者可能决定推荐结果甚至用户安全，后者是一次性废话。把它们平等对待，就是在浪费算力和存储。

所以写入流程的核心目标，是把一堆原始对话加工成干净的、结构化的、有层级的记忆单元。

就像你去菜市场买了一堆乱七八糟的食材回来 —— 你不能把菜叶子、塑料袋、泥土一起扔锅里，得先洗菜、摘菜、分类，好的进冰箱，烂的扔掉，才能做出一顿像样的饭。

---

### 写入流水线的四道关卡

#### 第一关：降噪清洗 —— 把垃圾先挑出来

这是最基础但性价比最高的一关。干的事情很简单：用规则把明显没用的内容过滤掉，不进入后续处理。

**具体过滤什么？**

*   **无意义寒暄**：「你好」「在吗」「谢谢」「好的收到」—— 这些是礼貌用语，不含任何用户信息，直接丢。
*   **工具冗余**：Agent 调用工具返回的完整 JSON，少则几十行，多则上百行。你只需要保留工具执行的核心结论（比如「查询成功，返回 3 条结果」），具体的 JSON 结构、字段名、调试日志全部扔掉。
*   **修正前内容**：用户说「我想用 Python……不对，还是用 Go 吧」—— Python 那个就是口误，不应该被记住。
*   **系统固定话术**：Agent 每次回复前输出的格式化提示、安全声明、角色设定，这些是系统层面的固定输出，跟用户无关。

这一步用正则和规则就能搞定，实现成本极低，但能过滤掉 30%-50% 的无效内容。你说值不值？

举个真实例子：我们之前有一个客服 Agent，每天处理 2000 轮对话，不做清洗直接写入的话，每天新增 4000 条记忆（用户+模型各一条）。加了清洗之后，日均写入降到 1800 条 —— 砍掉了一半还多，检索信噪比直接提升了一个档次。

---

#### 第二关：语义切分 —— 把一段话拆成一个个「记忆原子」

清洗完的对话，不能整段存成一条。要拆成独立的「记忆原子」，每个原子只包含一个核心信息。

比如用户说了这么一句话：

> 「我是做运营的，平时主要用 Excel 做数据透视，但最近发现 Power BI 更适合做可视化，你们产品能对接 Power BI 吗？另外我之前用过你们竞品 XX，界面太难用了。」

这句话里至少有四个信息点：

*   用户职业：运营
*   核心工具：Excel（数据透视）+ Power BI（可视化）
*   潜在需求：产品能否对接 Power BI
*   竞品评价：竞品 XX 界面难用

如果你把这整段话压成一条向量，检索的时候用户问「这个用户用什么工具」，向量匹配可能会被「竞品界面难用」这个噪声信息干扰，导致召回不准。

拆成四条独立记忆，每条的语义重心都很清晰，检索精度自然就上去了。

**怎么拆？主流方案有两种：**

*   **方案一：轻量模型抽取。** 用 7B/14B 级别的小模型（Qwen3-14B 推荐）做信息抽取，输入是原始对话片段，输出是结构化的事实列表。成本只有大模型的几十分之一，适合大批量处理。
*   **方案二：规则 + 大模型混合。** 简单的模式（比如「我是做 XX 的」「我用 XX 工具」）用正则和模板直接匹配，复杂的多轮对话、隐含偏好才调用大模型提取。这样既能控制成本，又能保证复杂场景的提取质量。

> **注意：** 这个一定要灵活根据场景判断，实际生产环境中规则硬门判断往往出问题最多。

实测数据：拆分后的记忆，在检索时的 Top-5 召回准确率比不拆分平均高出 22%。这个提升不需要换 Embedding 模型、不需要加 Rerank，纯粹靠写入侧的粒度优化就能拿到。

---

#### 第三关：分级筛选 —— 不是所有记忆都配进长期库

拆好的记忆原子，不是全部都要存进长期记忆库。要先打分，决定它的命运。

**打分维度我用三个：**

*   **事实性（Factuality）：** 这是明确的事实还是随口的情绪？「我对花生过敏」是硬事实，「今天心情不错」是情绪碎片。前者必须进长期库，后者聊完就该扔。
*   **持续性（Persistence）：** 这个信息的有效期有多久？「我今天赶时间」只在今天有效，明天就是废话；「我是做运营的」可能半年内都有效；「我对花生过敏」是永久有效的。有效期越长，越值得进长期库。
*   **影响力（Impact）：** 这个信息对后续服务的影响有多大？过敏信息可能导致推荐事故，必须记住；「我喜欢喝美式」锦上添花，记不记影响不大。

三个维度综合打分后，分三档处理：

*   **高分（核心记忆）** 进长期库，永久留存。比如用户的职业、硬偏好、过敏信息、关键决策。
*   **中分（短期有效）** 只进短期缓存，会话结束后保留 7-30 天，到期自动清除。比如用户当次的任务上下文、临时提到的工具名。
*   **低分（噪声）** 直接丢弃，不做任何存储。比如寒暄、情绪碎片、一次性闲聊。

这一步的效果有多明显？我们有个 aigc 的项目上线分级筛选后，长期库的日均新增量从 1800 条降到了 350 条 —— 砍掉了 80%。而检索准确率反而提升了，因为库里全是高价值记忆，噪声少了，信噪比自然就上去了。

---

#### 第四关：元数据标注 —— 给记忆贴上「身份证」

最后一步，给每条合格的记忆打上标准化的元数据标签，再写入存储。

**为什么要打标签？**

因为纯向量检索有一个天然缺陷：它只看语义相似度，不看场景和类型。用户问编程问题的时候，如果你的记忆库里混着客服场景、创作场景、编程场景的各种记忆，向量检索可能会把不相关场景的记忆也召回来。元数据就是用来做前置过滤的。

**必带的标签包括：**

*   **基础属性**：user_id、创建时间、最后访问时间（用于时效性衰减计算）
*   **类型标签**：情景记忆（发生过什么事）/ 语义记忆（什么事实）/ 程序记忆（怎么做）
*   **场景标签**：客服场景 / 创作场景 / 编程场景 / 数据分析场景
*   **置信度**：原始对话直接提取的标记为「高置信」，从摘要或推理生成的标记为「低置信」

检索的时候，先用元数据做粗筛（比如只搜「编程场景 + 高置信」的记忆），再用向量相似度做精排。这样既快又准，还避免了跨场景的记忆干扰。

打个生活中的比方：你去图书馆找一本 Python 编程书。如果没有分类标签，你得把整个图书馆翻一遍；如果有「计算机→编程→Python」的分类路径，你直接去对应书架就行。元数据就是记忆库的分类标签系统。

---

### 写入之后：异步离线加工

除了实时写入流程，成熟的记忆系统还会配一套异步的离线加工任务，不用占实时响应的时间：

*   **记忆去重：** 用户每次提相同的偏好，都会新增一条记忆。不去重的话，库里会有十几条「用户喜欢简洁表格」的重复记忆，检索的时候全挤在 Top-K 里，挤占了其他有效记忆的位置。解法：写入前做相似度比对，超过阈值的只更新访问时间，不新增条目。
*   **反思聚合：** 零散的记忆可以聚合成更高层的洞察。比如从「用户三次都要求先给大纲」「用户每次都跳过细节直接看结论」这两条记忆，可以聚合出一条新记忆：「用户的认知偏好是先看框架再看细节」。这种高层洞察比原始碎片更有价值。
*   **过期清理：** 临时记忆到期后自动清理，长期未被访问的冷记忆定期归档。避免记忆库无限膨胀。

这三个任务定时跑就行，比如每天凌晨跑一轮，完全不影响用户对话的延迟。

---

### 三个真实的生产踩坑经验

讲完标准流程，再补三个我实际踩过的坑 —— 面试里说出来，直接拉开和「背八股」候选人的差距：

**坑一：同步写入把对话拖慢了 300ms。**

一开始我们每轮对话结束都同步做提取、转向量、写库，整个流程多出 300ms 延迟。用户体感很明显 —— 本来秒回的机器人突然变卡了。

后来改成异步写入：对话结果正常返回用户，写入流程丢到后台消息队列里跑。只有核心偏好（比如过敏信息）的更新走同步链路，确保即时生效。延迟问题直接消失。

**坑二：小模型提取出了「虚假记忆」。**

我们用 7B 模型做信息抽取，准确率大概 92%。看着挺高？但一天处理 2000 轮对话，8% 的错误率意味着每天产生 160 条虚假记忆。比如模型把用户说的「我朋友喜欢用 VS Code」错误提取成「用户喜欢用 VS Code」。后面检索出来，Agent 就会信以为真，给用户推荐 VS Code 插件 —— 用户一脸懵。

解法：给每条记忆打置信度分数。高置信（直接从对话提取）的记忆可以参与决策，低置信（推理或摘要生成的）只做辅助参考，不能作为核心判断依据。同时加了人工抽检机制，每周随机抽 100 条记忆做准确率审计。

**坑三：重复记忆把 Top-K 挤爆了。**

用户每提一次偏好，就新增一条。一个月下来，「用户喜欢简洁表格」这个事在库里有 15 条几乎一样的记忆。检索 Top-5 的时候，这 15 条里有 4 条挤进去了，真正有价值的其他记忆反而被挤出去了。

解法：写入前做相似度去重。新记忆和已有记忆的余弦相似度超过 0.92，就只更新「最后访问时间」和「访问次数」，不新增条目。这样库里永远只有一条「用户喜欢简洁表格」，但它的权重会随着访问次数增加而提升 —— 越经常被提到的偏好，越容易被召回。

---

### 收尾

有人问我：记忆系统的优化应该从哪里入手？

我的回答是：**先看写入，再看检索。**

很多人一上来就折腾检索 —— 换 Embedding 模型、加 Rerank、调相似度阈值、搞混合检索。这些当然有用，但如果你的写入环节是「整段对话直接存」，那你的记忆库里 60% 都是垃圾。在垃圾堆里翻宝贝，换再好的铲子也没用。

写入环节做好降噪、切分、分级、标注这四步，检索侧的工作量直接减半，效果反而更好。

就像做菜一样 —— 食材新鲜、处理得当，随便炒炒都好吃；食材是烂的，米其林大厨来了也救不了。

--------Agent 记忆系统设计

# Agent 记忆系统：向量库为什么不是答案？

先想象一个差旅 Agent。

用户第一次说：“我住北京，出发机场优先首都机场。”

一个月后他搬到杭州，又说：“以后从杭州出发，优先萧山机场。”

今天他临时在上海出差，让 Agent 订明早的机票。

如果我们把三句话原样扔进向量库，搜索“出发机场”时，北京、杭州、上海都可能被召回。它们在语义上都很相似，可业务含义完全不同：

- “住杭州”是当前仍然有效的长期事实；
- “在上海出差”只属于眼前这次任务；
- “住北京”是已经失效、但仍需保留来源的历史版本。

三句话都很相似，但只有**时间、范围和来源**能决定当前该用哪条。

向量检索只能回答“哪句话和当前问题像”，回答不了“哪条事实现在有效”“属于谁”“能不能被当前任务使用”。

---

## 01 记忆系统的本质

先说用途：这套系统负责决定旧信息该不该留下、过期后怎么退场，以及任务需要时怎样找回来；工程里叫**记忆系统（Memory）**。

所以我不会先用某个数据库来定义它。我更愿意把它理解成 **Agent 的旧信息使用系统**：

> 先决定什么能记，再维护它的生命周期，最后按任务把合适的信息送回模型。

这三个动词分别是 **Write、Manage、Read**。存储介质只是其中一个零件。

真正的记忆系统是一条 **Write—Manage—Read 闭环**。

CoALA 论文说明记忆与行动、决策共同构成 Agent 架构。

---

## 02 什么该记？先过一道写入门

真实系统里，最危险的往往不是“忘了”，而是“什么都记”。

一句寒暄、一次模型猜测、一条工具报错，甚至用户的敏感信息，如果全部进入长期记忆，数据库会越来越大，召回也会越来越脏。

所以写入之前，我会先设一道门：

- 这条信息对未来任务有没有复用价值？
- 它是用户明确表达的事实，还是模型自己推出来的？
- 有没有敏感信息，是否得到允许？
- 已经存在相同或冲突的记录吗？
- 它应该活多久，什么时候失效？

先讲作用：这道门负责拦掉不该长期保存的内容，并决定新信息是新增、更新、替代旧版本，还是干脆不写。工程里常叫它 **Write Gate，写入门**。

还是刚才的例子：

- “以后从杭州出发”是用户明确给出的稳定偏好，可以成为长期事实；
- “今天在上海出差”只该放在当前任务状态里；
- Agent 猜测“他以后都住上海”，既没证据，也不该写。

真正落库时，我不会只保存一段文字，至少还要带上：

- 用户范围
- 记忆类型
- 来源事件
- 生效时间
- 失效时间
- 置信度
- 版本号
- 删除标记

这样系统之后才有机会解释：这条记忆从哪来，为什么被使用，又为什么被替换。

---

### 记忆分层

记忆也不能都塞进同一个盒子。

- **当前线程正在做什么**，像摊在桌面上的便签，只在这次任务里使用；研究里通常叫**工作记忆（Working Memory）**。
- **“用户现在住杭州”** 是可以跨会话使用的事实，像通讯录里的资料；通常叫**语义记忆（Semantic Memory）**。
- **“上次订票时，用户把中转航班改成直飞”** 是一段带结果的经历，像错题本；通常叫**情景记忆（Episodic Memory）**。
- **“订票前先确认出发城市，再检查时间和预算”** 是一套做事方法，像操作手册；通常叫**程序性记忆（Procedural Memory）**。

这几类信息用途不同，生命周期也不同。分层不是为了显得架构复杂，而是为了让每类记忆有自己的写入规则。

Mem0 论文首页；其更新流程也把新增、修改、删除与不变分开处理。

---

## 03 新旧信息打架，谁算数？

用户从北京搬到杭州时，最省事的做法是直接覆盖旧记录。

但我不建议这么干。

因为覆盖以后，系统只知道“现在住杭州”，却不知道这个结论什么时候改变、依据是什么。出了问题，也没法还原当时为什么推荐了某个机场。

更稳的做法，是**把事实做成有时间范围的版本**。

为了让系统知道一条事实从哪天起不再使用，会专门保存一个 **“失效时间”**；字段常写作 `valid_to`。

- 北京记录的失效时间落在搬家那天；
- 新建杭州版本，并关联用户这次明确表达；
- 默认查询只读取当前有效版本；
- 审计或复盘时，仍能看到历史变化。

如果新信息只是模型推断，而旧信息来自用户明确确认，就不能因为“更新得更晚”自动获胜。**时间、来源和置信度要一起参与裁决**。

多个 Agent 同时更新同一条记忆时，还要防止后写入的人把先写入的结果悄悄覆盖。我会给每次更新带**版本号**：

> 只有你读到的版本仍是最新版，写入才成功；否则重新读取并处理冲突。

这就像两个人同时改同一份表格，不能谁最后按保存，谁就天然正确。

---

## 04 需要时，怎么取对而且不串人？

写得对，不代表读得对。

很多实现上来就按相似度取前 5 条。可对企业 Agent 来说，第一步不应该是“哪条更像”，而是 **“哪些记录有资格进入候选集”**。

我会先做几层硬过滤：

> 这里先解释一个词：给不同企业或团队分别划出的独立数据空间，工程里叫**租户（tenant）**。

- 只允许当前**租户、当前用户或当前项目**的数据；
- 只取仍在**有效期内、没有被删除**的版本；
- 根据任务选择**记忆类型**，不让一次性任务状态污染长期偏好；
- 再做**关键词与语义混合召回**；
- 最后按**相关性、时效性、重要度和来源可信度**重新排序。

先解释用途：把初步找回的候选再排一次，决定谁更该进入模型上下文，这一步叫**精排（Rerank）**。

---

### 为什么用户隔离必须放在相似度搜索前？

因为“用户 A 喜欢拿铁”和“用户 B 喜欢拿铁”几乎完全相似。等它们都被召回，再让模型判断属于谁，边界已经太晚了。

> 正确顺序是：先按用户空间隔离，再在这个空间里找相似内容。

---

## 05 如何证明你真正做过系统？（面试必讲）

面试里如果想证明方案不是纸上谈兵，我会补一个很小的测试：

1.  **隔离测试**：为了先确认“这条数据到底属于谁”，每个用户都要有唯一编号；工程字段常写作 `user_id`。建两个不同的用户编号，分别写入相反偏好，验证**零串记忆**；
2.  **更新测试**：给同一用户先写“喜欢拿铁”，再写“现在改喝美式”，检查是更新、保留版本，还是产生冲突；
3.  **持久化测试**：重启服务后再问一次，确认长期记忆真的持久化；
4.  **可观测性测试**：保存每次写入和召回的原始结果，不只看模型最后那句自然语言。

这四步比“我用了某某数据库”更能说明你真正做过系统。

---

## 06 面试时，用 60 秒这样回答（四句话复述：写入、管理、读取、验收）

如果让我现场回答，我会这样说：

> 我不会把 Agent 记忆系统只设计成向量库，而会拆成写入、管理和读取三段。

**写入时**：先判断信息是否值得长期保存、来源是否可信、是否敏感，再决定新增、更新、替代还是不写，并把任务状态、长期事实、历史经历和做事规则分层保存。

**管理时**：每条记忆都带用户范围、来源、有效期和版本号。新旧事实冲突时不直接覆盖，而是让旧版本失效、保留证据链；并发更新用版本检查避免静默覆盖。

**读取时**：先按租户、用户、权限和有效期硬过滤，再做语义召回和精排，最后按模型一次能带入的信息额度——也就是上下文预算——组装。

**最后测试**：跨用户隔离、偏好更新和重启后的持久化。

这样才能证明它**记得对、改得动、取得准**。

> 什么该记，旧信息怎么退场，需要时又凭什么取到正确的那一条。
